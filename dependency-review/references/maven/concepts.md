# Управление зависимостями в Maven - понятия, без которых нельзя проверять правила

Прочитай этот файл один раз сверху вниз. Здесь определён каждый термин, который
используют файлы правил Maven. Во время проверки правил возвращайся к нужным разделам.

## 1. Анатомия POM - части, важные для этого ревью

```xml
<project>
  <parent>                          <!-- наследование: этот POM наследует другой POM -->
    <groupId>com.acme</groupId>
    <artifactId>acme-parent</artifactId>
    <version>1.4.0</version>
    <relativePath>../pom.xml</relativePath>  <!-- где искать родителя на диске -->
  </parent>

  <artifactId>orders-service</artifactId>
  <packaging>jar</packaging>        <!-- jar | war | pom | ... ; у агрегаторов ОБЯЗАН быть "pom" -->

  <properties>                      <!-- здесь живут свойства версий -->
    <jackson.version>2.17.1</jackson.version>
  </properties>

  <modules>                         <!-- агрегация: какие подпроекты собирать -->
    <module>orders-api</module>
  </modules>

  <dependencyManagement>            <!-- пиннит версии; НЕ добавляет зависимости -->
    <dependencies> ... </dependencies>
  </dependencyManagement>

  <dependencies> ... </dependencies>       <!-- РЕАЛЬНЫЕ зависимости этого модуля -->

  <build>
    <pluginManagement> ... </pluginManagement>  <!-- пиннит версии плагинов -->
    <plugins> ... </plugins>
  </build>
</project>
```

## 2. Наследование и агрегация - две разные вещи, которые обычно совпадают

- **Наследование** (`<parent>`): дочерний POM получает от родителя свойства,
  dependencyManagement, pluginManagement и обычные dependencies. Работает даже между
  репозиториями - у многих компаний есть корпоративный parent POM, живущий отдельно.
- **Агрегация** (`<modules>`): реактор собирает перечисленные каталоги вместе.

В типичном мультимодульном репозитории корневой POM - одновременно агрегатор и родитель.
Но они могут расходиться: модуль может указывать другой `<parent>`, чем его агрегатор.
При ревью всегда проверяй ОБА: кто агрегирует модуль и от кого он наследует.

**Критичное следствие наследования:** обычная запись в `<dependencies>` родителя
**навязывается каждому ребёнку**, хочет он того или нет. `<dependencyManagement>` лишь
пиннит версию, а подключение - добровольное. Перепутать эти две вещи - самая частая
ошибка с родительскими POM.

## 3. `dependencyManagement` против `dependencies` - различие, на котором держится всё ревью

| | `<dependencyManagement>` | `<dependencies>` |
|---|---|---|
| Добавляет библиотеку в classpath? | **Нет** | Да |
| Пиннит версию для детей/себя? | Да | н/п |
| Правильное место в родительском POM | версии всего, что модули могут использовать | почти ничего (только истинно универсальные зависимости, и то дважды подумай) |
| Правильное место в дочернем POM | редко нужно (импорт дополнительных BOM) | реальные зависимости модуля, **без** тегов `<version>` |

Здоровый паттерн: родитель пиннит все версии в `dependencyManagement`; дети объявляют
только `groupId` + `artifactId`, версии наследуются.

## 4. Scope-ы

| Scope | Значение | Типичные ошибки |
|---|---|---|
| `compile` (по умолчанию) | компиляция + рантайм, транзитивен | это умолчание; классика - забытые здесь тестовые библиотеки |
| `provided` | компиляция; в рантайме поставляет контейнер (servlet-api, Lombok) | использование для того, что рантайм НЕ поставляет → `NoClassDefFoundError` |
| `runtime` | только рантайм (JDBC-драйверы, реализации логирования) | драйверы в `compile` - терпимо, но загрязняет compile classpath |
| `test` | компиляция и запуск только тестов | JUnit/Mockito/AssertJ в `compile` протекают в прод |
| `system` + `<systemPath>` | jar с фиксированного пути на диске | **всегда неправильно** - deprecated, непереносимо, без транзитивности |
| `import` | ТОЛЬКО внутри `dependencyManagement`, с `<type>pom</type>` - импортирует BOM | использование вне dependencyManagement (не делает ничего) |

`<optional>true</optional>`: зависимость не распространяется транзитивно на потребителей -
правильно для библиотек с необязательными интеграциями.

## 5. Механика импорта BOM

```xml
<dependencyManagement>
  <dependencies>
    <dependency>
      <groupId>org.springframework.boot</groupId>
      <artifactId>spring-boot-dependencies</artifactId>
      <version>3.3.2</version>
      <type>pom</type>
      <scope>import</scope>
    </dependency>
  </dependencies>
</dependencyManagement>
```

После этого все библиотеки, которыми управляет BOM, можно объявлять без версий.
Spring Boot-проекты часто вместо этого наследуют `spring-boot-starter-parent` - это тоже
нормально, но тогда корпоративный parent не может быть `<parent>` одновременно; команды
выбирают путь импорта BOM, чтобы сохранить своего родителя. Приемлемо и то и другое;
неприемлемо смешивать версии членов семейства.

Частые BOM в **проектах автотестов**: `org.junit:junit-bom` (JUnit 5),
`io.qameta.allure:allure-bom` (Allure), `org.testcontainers:testcontainers-bom`,
`org.seleniumhq.selenium:selenium-bom`. Их наличие для соответствующих семейств - плюс.

## 6. Как Maven разрешает конфликты версий (отличается от Gradle!)

Maven использует принцип **nearest-wins** («ближайший побеждает»): выигрывает версия,
ближайшая к корню дерева зависимостей; при равной глубине - **объявленная первой**. Maven
НЕ выбирает самую высокую версию (а Gradle выбирает). Следствия, которые надо усвоить:
- Добавление прямой зависимости молча **даунгрейдит** транзитивные (прямое объявление
  «ближе», чем что угодно транзитивное).
- Перестановка элементов `<dependencies>` может изменить разрезолвленные версии. Поэтому
  порядок объявления в Maven - не косметика.
- Защита - **maven-enforcer-plugin** с `<dependencyConvergence/>` или
  `<requireUpperBoundDeps/>`; правила на него ссылаются; его присутствие считай сильным
  плюсом.

`mvn dependency:tree -Dverbose` показывает конфликты пометкой
`(version omitted for conflict with X)`.

## 7. Свойства версий и CI-friendly-версии

Версии должны жить в `<properties>` (`<jackson.version>2.17.1</jackson.version>`,
используется как `${jackson.version}`) или в `dependencyManagement` - но не литералами,
рассыпанными по `<dependencies>`.

**CI-friendly-версии:** современные мультимодульные проекты часто используют
`<version>${revision}</version>` со свойством `<revision>` в корневых properties. Это
хорошо - но **требует** `flatten-maven-plugin`, иначе артефакты публикуются с буквальной
строкой `${revision}` в POM и не резолвятся. Видишь `${revision}` - проверь, настроен ли
flatten.

## 8. Где прячутся зависимости

1. **Цепочка родительских POM** - возможно, вне этого репозитория (корпоративный parent).
   Что он менеджит, отсюда не видно; отметь в отчёте, что для полной картины нужен
   `mvn help:effective-pom` (запусти, если разрешено; он печатает полностью слитый POM).
2. **Профили** (`<profiles>`) - зависимости внутри профилей действуют только при их
   активации; проверь, что добавляет каждый профиль.
3. **Зависимости плагинов** (`<plugin><dependencies>`) - влияют на сборку, не на приложение.
4. **Импорты BOM** - версии приходят из артефактов, которых может не быть локально.

## 9. Полезные команды (запускай, только если разрешено; статики хватает для большинства правил)

| Команда | Что показывает |
|---|---|
| `mvn -q help:effective-pom` | полностью слитый POM (наследование + импорты разрешены) |
| `mvn -q dependency:tree -Dverbose` | полное дерево, конфликтные пропуски помечены |
| `mvn -q dependency:analyze` | зависимости used-but-undeclared и declared-but-unused |
| `mvn -q versions:display-dependency-updates` | доступные обновления |

Никогда не запускай произвольный код проекта; эти goal-ы только читают, но скачивают
артефакты.

## 10. Проект автотестов - что меняется

Иногда проверяемый проект - не приложение, а отдельный проект автотестов: JUnit 5/TestNG,
Selenide/Selenium, RestAssured, Allure, Cucumber, Testcontainers, WireMock. Все правила
применяются БЕЗ изменений; отличаются только типичные примеры и одна деталь со scope-ами.

Универсальный принцип для scope - важно, ОТКУДА код использует библиотеку: код в
`src/main` (степы, клиенты, утилиты) → `compile`; библиотека нужна только коду в
`src/test` → `test`. В проекте автотестов степы часто лежат в `src/main`, поэтому junit или
selenide в `compile` - НЕ нарушение. В обычном приложении та же строка - нарушение.
Определи назначение проекта на Шаге 2 SKILL.md и суди по нему.

Ловушки автотестов: члены `org.junit.*` выравнивай через `junit-bom`; JUnit 4
(`junit:junit`) и JUnit 5 вместе - только через `junit-vintage-engine`; все `allure-*`
одной версии, а агент `org.aspectj:aspectjweaver` подключается как javaagent (не обычный
compile) и его версия должна подходить к версии Allure; Selenide уже тянет Selenium
транзитивно - свои версии Selenium рядом с ним дают конфликт.

## 11. Дерево зависимостей и транзитивные конфликты (частая причина «проект не собрать»)

Многие реальные проблемы не видны в самих POM: их создают **транзитивные** зависимости -
то, что притянуто не напрямую, а через другие библиотеки. Из-за медиации nearest-wins
(§6) одна транзитивная библиотека может молча даунгрейднуться до версии, несовместимой с
кодом, - и проект падает в рантайме или вообще не собирается, хотя в `<dependencies>` всё
выглядит нормально.

Поэтому построить дерево - **обязательный шаг**, если Maven доступен и его запуск не
запрещён (см. Шаг 5 SKILL.md). Для мультимодуля идёшь сначала по каждому модулю, потом
полностью:
```
mvn -q -pl <модуль> dependency:tree -Dverbose   # по каждому модулю отдельно
mvn -q dependency:tree -Dverbose                # полный прогон (из корня обходит весь реактор)
```
На что смотреть в выводе:
- пометки `(version omitted for conflict with X)` / `(version managed from Y)` - здесь
  сработала медиация; убедись, что победившая версия совместима;
- один и тот же `groupId:artifactId` разных версий в разных ветках дерева - транзитивный
  конфликт версий;
- члены одного семейства (jackson-*, spring-*, junit-*, selenium-*) с разъехавшимися
  транзитивными версиями - кандидат на BOM.
Найденное здесь записывай под тем же правилом, что и по смыслу (обычно G-C-07/M-C-06 -
выравнивание семейств, или конфликт версий), с пометкой «транзитивно, из dependency:tree».

Если запуск Maven НЕ разрешён - отметь в отчёте (в разделе «Требует внимания человека»),
что полную картину даёт `mvn dependency:tree -Dverbose` / `mvn help:effective-pom`, и что
статический обзор POM транзитивные конфликты пропускает.

## 12. Мини-глоссарий

- **Реактор (reactor)** - оркестратор мультимодульной сборки Maven; упорядочивает модули по зависимостям.
- **BOM (Bill of Materials)** - артефакт с packaging `pom`, чей dependencyManagement пиннит версии семейства.
- **Effective POM** - результат слияния POM со всей цепочкой родителей и импортами.
- **Медиация зависимостей** - разрешение конфликтов Maven по принципу nearest-wins.
- **Расхождение версий (version drift)** - одна библиотека, разные версии в разных модулях.
- **Корпоративный parent** - общекорпоративный родительский POM вне репозитория.
