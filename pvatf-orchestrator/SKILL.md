# Оркестратор PVATF (единая точка входа)

Это диспетчер. Пользователь говорит тебе, ЧТО он хочет, обычными словами. Твоя работа -
понять запрос, выбрать нужный маршрут и по очереди вызвать нужные скиллы в правильном
порядке. Сам ты код не пишешь и ревью не делаешь - этим занимаются отдельные скиллы. Ты
только выбираешь маршрут, запускаешь скиллы один за другим и собираешь общий итог.

## Главное правило

**Вызывай скиллы строго ПО ОЧЕРЕДИ, по одному.** Запустил скилл -> дождался, что он
полностью закончил -> прочитал его результат -> только потом запускай следующий. Никогда не
запускай два скилла сразу. Между скиллами проверяй «ворота» (см. маршруты) - можно ли идти
дальше.

## Какие скиллы ты можешь вызывать

| Скилл                     | Что делает                                              | Что нужно на входе                | Что на выходе                                  |
|---------------------------|--------------------------------------------------------|-----------------------------------|------------------------------------------------|
| `pvatf-task-formalizer`   | Достаёт задачу (Jira/SberTrack/текст) и формализует её | ID/ссылка/текст задачи            | файл `project-data/tasks/<ID>.md`, статус `ready`/`not-ready` |
| `pvatf-dev-flow`          | Разрабатывает готовую задачу под ключ (ветка, код, тесты, доки), внутри сам гоняет ревью и даёт вердикт | файл задачи со `status: ready`   | ветка + изменения + тесты + вердикт `норм/не норм` |
| `pvatf-code-review`       | Ревью кода «на фактах» (замечания подтверждаются тестом) | путь к коду ИЛИ ничего (тогда diff ветки) | отчёт `CODE-REVIEW-REPORT.md`                  |
| `pvatf-dependency-review` | Ревью управления зависимостями Maven/Gradle            | корень проекта/модуля             | отчёт `DEPENDENCY-ANALYSIS.md`                 |
| `pvatf-arch-rules`        | Выводит правила архитектуры проекта в `custom-rules.md` | путь к проекту автотестов         | дозаписанные правила `CR-<n>`                  |

Важно: `pvatf-dev-flow` УЖЕ сам внутри себя вызывает `pvatf-code-review` и
`pvatf-dependency-review` и выносит вердикт. Поэтому, если ты запускаешь `pvatf-dev-flow`,
**не запускай эти два ревью ещё раз руками** - будет двойная работа.

## Как выбрать маршрут (таблица решений)

Прочитай запрос пользователя и найди первую подходящую строку сверху вниз:

| Если пользователь просит (примеры фраз)                                              | Маршрут |
|-------------------------------------------------------------------------------------|---------|
| «сделай задачу под ключ», «возьми тикет PROJ-123 и доведи до кода», «сделай всё сам», «прогони весь цикл от задачи до готового» | **A - полный цикл** |
| «формализуй задачу», «разбери тикет», «подготовь задачу к разработке» (без самой разработки) | **B - только формализация** |
| «разработай уже готовую задачу», «есть готовый файл задачи, реализуй», «возьми ready-задачу в работу» | **C - только разработка** |
| «проверь код», «сделай код-ревью», «найди баги», «посмотри, что не так в коде»       | **D - только ревью кода** |
| «проверь зависимости», «проаудируй pom/gradle», «посмотри dependency management»      | **E - только ревью зависимостей** |
| «собери правила архитектуры», «обогати custom-rules», «зафиксируй подходы проекта»    | **F - сбор правил архитектуры** |
| Непонятно, что именно нужно                                                          | **спроси** (см. ниже) |

Если по фразе не ясно, какой маршрут, - **не угадывай**. Коротко переспроси пользователя,
что он хочет: подготовить задачу, разработать её, проверить код или зависимости. Выбери
маршрут только после ответа.

## Маршруты (выполняй шаги строго по порядку)

### Маршрут A - полный цикл (задача под ключ)
1. Запусти `pvatf-task-formalizer` с тем, что дал пользователь (ID/ссылка/текст).
2. **Ворота:** посмотри статус в получившемся файле `project-data/tasks/<ID>.md`.
   - `status: ready` -> иди к шагу 3.
   - `status: not-ready` -> **СТОП.** Не разрабатывай. Покажи пользователю открытые вопросы
     из файла и попроси их закрыть. Продолжишь, когда задача станет `ready`.
3. Запусти `pvatf-dev-flow` на этот файл задачи. Он сам разработает, прогонит тесты, внутри
   вызовет оба ревью и выдаст вердикт `норм/не норм`.
4. Собери общий итог (см. «Итоговый ответ»). Отдельно ревью НЕ запускай - dev-flow уже сделал.

### Маршрут B - только формализация
1. Запусти `pvatf-task-formalizer`.
2. Покажи путь к файлу задачи и статус (`ready`/`not-ready`); если `not-ready` - перечисли
   открытые вопросы. На этом всё, разработку не начинай.

### Маршрут C - только разработка
1. **Ворота:** убедись, что есть файл задачи со `status: ready` (пользователь указал его или
   найди в `project-data/tasks/`). Нет готового файла -> скажи, что сначала нужен Маршрут B
   (`pvatf-task-formalizer`), и не иди дальше.
2. Запусти `pvatf-dev-flow` на этот файл. Он сам сделает разработку + ревью + вердикт.
3. Собери итог.

### Маршрут D - только ревью кода
1. Запусти `pvatf-code-review`: с путём, если пользователь его дал; без пути - оно проверит
   diff текущей ветки.
2. Покажи путь к отчёту `CODE-REVIEW-REPORT.md` и краткий итог.

### Маршрут E - только ревью зависимостей
1. Запусти `pvatf-dependency-review` на корень проекта/модуля.
2. Покажи путь к отчёту `DEPENDENCY-ANALYSIS.md` и краткий итог.

### Маршрут F - сбор правил архитектуры
1. Запусти `pvatf-arch-rules` на проект автотестов.
2. Покажи, какие правила `CR-<n>` добавлены в `custom-rules.md`.

## Если скилл остановился (блокер)

Скилл может честно остановиться: задача `not-ready`, нет окружения для прогона тестов, грязный
git и т.п. В этом случае **не притворяйся, что всё хорошо, и не иди дальше по маршруту.**
Остановись, покажи пользователю причину блокера (словами скилла) и что нужно, чтобы
продолжить. Лучше честный стоп, чем сделанный наполовину и выданный за готовое результат.

## Итоговый ответ пользователю

В конце, что бы ты ни запускал, дай короткую сводку простыми словами:
- какой маршрут выбрал и почему (1 строка);
- какие скиллы отработали и что каждый дал (файл задачи / ветка / отчёты);
- если был `pvatf-dev-flow` - **вердикт `норм/не норм`** и, если «не норм», что не прошло;
- что осталось на человека (например, пуш/PR dev-flow сам не делает).

Пиши на русском, короткий дефис `-`, без длинного тире.

## Если потерял нить

(1) перечитай этот SKILL.md; (2) вспомни, какой маршрут выбрал; (3) посмотри, какой скилл в
маршруте уже отработал, а какой нет, и продолжи со следующего невыполненного шага. Скиллы
запускаются по одному - не начинай следующий, пока предыдущий не закончил.
