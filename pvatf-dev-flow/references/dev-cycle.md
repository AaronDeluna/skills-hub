# Цикл разработки и обязательный прогон тестов

Прочитай перед Шагом 4. Здесь - как крутить цикл и как реально прогонять тесты. Команды даны
через плейсхолдер `<RUN>` - подставь раннер, определённый на Шаге 2 (wrapper проекта
`./mvnw`/`./gradlew` или системный `mvn`/`gradle`).

## Под-цикл (повторяй, пока не зелено)

1. **Анализ** - что и где менять; сверься с критериями приёмки из файла задачи.
2. **Реализация** - минимальные изменения по задаче, по кодстайлу/Javadoc проекта.
3. **Юнит-тесты** - на новую/изменённую логику, в тест-фреймворке проекта, по его конвенциям
   (расположение, именование, статик-импорты ассертов). Покрой основной путь и границы/ошибки.
4. **Прогон** - запусти тесты РЕАЛЬНО (см. ниже). Не прошли -> чини код (или тест, если ошибка
   в нём) и запускай снова. Прошли -> дальше.

Ключевое правило: **тест без реального прогона не считается**. В заметках фиксируй факт
прогона: команду и итог (сколько прошло/упало).

## Как прогнать тесты

Точечно (только свои тесты - быстрее в цикле):
```
<RUN> -q -pl <модуль> -Dtest='<ИмяКласса>*' -DfailIfNoTests=false test   # Maven
<RUN> :<модуль>:test --tests '<пакет>.<ИмяКласса>*'                       # Gradle
```
Перед финалом - прогон всех тестов затронутого модуля, чтобы не сломать соседнее:
```
<RUN> -q -pl <модуль> test        # Maven
<RUN> :<модуль>:test              # Gradle
```

Компиляция и checkstyle (изменения не должны их ломать):
```
<RUN> -q -DskipTests compile test-compile   # Maven
<RUN> compileJava compileTestJava           # Gradle (Kotlin: compileKotlin compileTestKotlin)
<RUN> -q checkstyle:check                    # Maven (если checkstyle настроен)
<RUN> checkstyleMain checkstyleTest          # Gradle (если настроен)
```

Если раннер/сборка недоступны (нет окружения/сети) - это **блокер** для требования «тесты
обязаны прогоняться». Тесты всё равно напиши, но честно отметь в сводке, что прогон не
выполнен и задача не может считаться закрытой, с точной командой для ручного прогона.

## Актуализация документации (Шаг 5) - что и как

По правилам проекта (формат - как в существующих файлах):
- **CHANGELOG** - добавь запись под текущую/новую версию, в принятой секции (Added/Fixed/
  Changed…). ID задачи указывай в записи только если так оформлены существующие записи
  CHANGELOG; повторяй их формат, а не навязывай свой.
- **RELEASE NOTES** - если ведутся, добавь строку про изменение.
- **Документация** (`docs/`, README) - обнови, если поменялось поведение или публичный контракт.
- **Версия проекта** - подними по semver в зависимости от характера изменения:
  - **major** - несовместимое изменение публичного API/поведения;
  - **minor** - новая обратимо-совместимая функциональность;
  - **patch** - багфикс/внутренние правки без изменения контракта.
  Точную оценку major/minor для обновлений библиотек и версии можно доверить
  `pvatf-dependency-review` на Шаге 6.

## Коммиты

Коммить по конвенции проекта (стиль сообщений - как в `git log`). Коммить логическими
порциями в свою ветку фичи. Пуш и PR - только с явного разрешения пользователя (см. базовые
правила).
