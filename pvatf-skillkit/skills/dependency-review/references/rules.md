# Правила проверки зависимостей

Часть скилла `dependency-review`. Открывай, когда `deps.py next` выдал строку и написал
«КАК ПРОВЕРИТЬ: references/rules.md, раздел D-...».

## Как читать строку от скрипта

- `CANDIDATE` - скрипт нашёл места-кандидаты (строка «ДАННЫЕ»). Подтверди или отбрось каждое.
- `TODO` - кандидатов скрипт не ищет. Проверь по разделу правила ниже.
- Строки `VIOLATION`, `PASS`, `N/A` от скрипта не пересматривай. Исключение одно - D-P2, раздел ниже.
- Найденное поиском - только кандидат. Прежде чем записать `VIOLATION`, открой файл и прочитай
  10 строк вокруг места.
- Одно правило, 2 и более мест: первое место - `mark <N-n> VIOLATION --where ...`, каждое
  следующее - `add <D-id> --where ... --note ...`.
- Не уверен, нарушение это или нет - `NEEDS-HUMAN`, в `--note` твой вопрос человеку. Не угадывай.
- `--note` - одно-два предложения: что и где увидел. Нельзя: «проверено». Нужно: «junit-jupiter
  в compile, классы шагов в src/main/java/ru/demo/steps импортируют org.junit.jupiter - для
  проекта автотестов это норма».

## Тип проекта

Тип пишет скрипт (строка «ТИП ПРОЕКТА»): `автотесты` или `приложение или библиотека`. Правила
одни и те же. Тип меняет только D-20: в проекте автотестов тестовые библиотеки - рабочие
зависимости кода `src/main` (шаги, клиенты, классы страниц).

## D-20 - Scope по месту использования

Уровень WARNING. Принцип: библиотеку использует код `src/main` -> `compile` / `implementation`;
только код `src/test` -> `test` / `testImplementation`.

1. По каждому кандидату из «ДАННЫЕ» скрипт уже написал, импортирует ли библиотеку `src/main`.
2. «используется в src/main» -> `PASS` с пояснением «проект автотестов, шаги в src/main».
   Исключение: тип `приложение или библиотека` -> `VIOLATION`: тестовая библиотека уходит
   в боевой код.
3. «в src/main не используется» -> `VIOLATION`, нужный scope - `test` / `testImplementation`.
4. Кандидатов нет (`TODO`) - просмотри ещё эти случаи в файлах сборки:

   | Библиотека | Правильный scope | Нарушение |
   |------------|------------------|-----------|
   | lombok | `provided` / `compileOnly` + `annotationProcessor` | `compile` / `implementation` |
   | aspectjweaver (агент Allure) | подключение как javaagent в плагине тестов | обычная зависимость `compile` |
   | JDBC-драйвер, logback-classic | `runtime` / `runtimeOnly` | `compile` - `--level INFO` |

   Нет ни одного случая -> `mark <N-n> PASS --note "<что просмотрел>"`.

Нельзя -> нужно:
- нельзя: `VIOLATION` для `junit-jupiter` в `compile`, когда классы шагов в `src/main`
  импортируют `org.junit.jupiter`;
- нужно: `PASS` «проект автотестов, junit используют шаги в src/main».

## D-21 - Exclusion без обоснования

Уровень INFO; одинаковый exclusion в 3 и более файлах сборки - `--level WARNING`, в `--note`
причина «один exclusion в <n> файлах».

1. По каждому exclusion из «ДАННЫЕ» открой место. Над зависимостью или внутри блока есть
   комментарий с причиной -> это место в порядке.
2. Привычные exclusion-ы без комментария - тоже в порядке: `commons-logging`, старый
   транзитивный `junit:junit` или `hamcrest-core` при JUnit 5.
3. Остальное без причины -> `VIOLATION`. Как исправить: перенести исключение к управляемой
   версии в `dependencyManagement` корня или заменить зависимость, которая тянет лишнее.

## D-22 - Необъявленные транзитивные и мёртвые зависимости

Уровень: «используются без объявления» - `--level WARNING`, «объявлены и не используются» - INFO.

1. Есть `dependency:analyze` (Maven): строки D-22 скрипт `tree` ставит сам, по строке на модуль,
   проверять их не нужно:
   - «используются без объявления» -> `VIOLATION`, исправить - объявить явно;
   - «объявлены и не импортируются» -> `NEEDS-HUMAN` с вопросом «удалить?». Что грузится по
     имени (фрейм PVATF, драйверы БД, реализации логов, Allure, aspectjweaver, движки и
     плагины JUnit), скрипт в вопрос не берёт и пишет в той же строке «Не считаются».
   Строки D-22 со статусом `TODO` или `CANDIDATE` после `tree` бывают только без анализа - п. 2.
2. Анализа нет (`TODO`, в том числе Gradle): возьми 30 импортов кода
   `grep -rhn "^import " --include=*.java src | awk '{print $2}' | sort -u | head -30`;
   для каждого пакета найди библиотеку в файлах сборки модуля. Пакета нет ни в одной
   объявленной библиотеке и это не JDK и не фрейм -> `NEEDS-HUMAN`. Всё нашлось -> `PASS`.

## D-23 - Две библиотеки делают одно и то же

Уровень WARNING; `logback-classic` вместе с `log4j-core` или `slf4j-simple` - `--level CRITICAL`
(они спорят за привязку slf4j, логи пропадают молча).

1. По каждой паре из «ДАННЫЕ» посчитай импорты:
   `grep -rln "import <пакет библиотеки>" --include=*.java . | wc -l`
   (Jackson - `com.fasterxml.jackson`, Gson - `com.google.gson`, OkHttp - `okhttp3`,
   Apache HttpClient - `org.apache.http` и `org.apache.hc`, JUnit 4 - `org.junit.Test`,
   JUnit 5 - `org.junit.jupiter`, TestNG - `org.testng`).
2. Код использует обе -> `VIOLATION`. Одну использует только фрейм или другая библиотека
   транзитивно, а код - нет -> `PASS` с пояснением.
3. JUnit 4 рядом с JUnit 5: `junit-vintage-engine` в сборке и старые тесты на JUnit 4 -
   осознанный переход, `NEEDS-HUMAN` с вопросом «переводить старые тесты на JUnit 5?».

## D-24 - Направление зависимостей между модулями

Уровень WARNING. Только для мультимодуля; связи модулей - в «ДАННЫЕ».

1. Определи роль каждого модуля по имени и содержимому: общий (core, common, steps, clients,
   config) или тестовый (tests, *-tests, e2e, smoke).
2. Нарушение - общий модуль зависит от тестового, или тестовые модули зависят друг от друга
   ради общего кода. Как исправить: общий код - в общий модуль, тестовые модули зависят от него.
3. Цикл скрипт уже записал правилом D-09 - здесь его не повторяй.

## D-P2 - Как подключать фрейм

Строку D-P2 скрипт пишет сам (`CANDIDATE`: `next` выдаёт её как задание), в «Как исправить» нужен способ из документации
фрейма, а не из памяти.

1. Задай вопрос агенту `pvatf-docs` по `references/autotest-rules.md`, правила 2-3, метка `env`:
   «Как подключать артефакты фрейма PVATF в <Maven | Gradle>, чтобы версия была указана в
   одном месте: BOM, parent или свойство? Точные groupId и artifactId.»
2. Ответ есть -> `mark <N-n> VIOLATION --note "<что в сборке>; по документации (D-env-<n>): <способ с координатами>"`.
3. `MCP НЕДОСТУПЕН` или в документации нет -> `mark <N-n> VIOLATION --note "<что в сборке>; способ подключения в документации не найден - уточнить у команды фрейма"`.

## Уровни

- **CRITICAL** - ломает воспроизводимость или корректность сборки.
- **WARNING** - сегодня работает, но это известная ловушка: конфликты, боль при обновлении.
- **INFO** - порядок и единообразие.

Уровень по умолчанию стоит у правила. Другой уровень (`--level` в `mark` и `add`) - только там,
где раздел правила это прямо разрешает, с причиной в `--note`.
