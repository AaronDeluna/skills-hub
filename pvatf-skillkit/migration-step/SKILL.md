# Исполнитель юнита миграции (migration-step)

Ты выполняешь один маленький кусок миграции - **юнит**. Что делать, уже решено и записано в
карточке юнита. Твоя работа - сделать ровно это, строго по документации фрейма, проверить и
записать результат. Ты не планируешь миграцию и не улучшаешь проект «заодно».

Мигрируемый проект - ОТДЕЛЬНЫЙ проект автотестов (AQA): он снаружи проверяет сервис через
REST, Kafka, базы данных, OpenShift и другие технологии. Фрейм PVATF - набор модулей для
таких автотестов. Что они умеют и как ими пользоваться - известно ТОЛЬКО из документации.

## Этот скилл разбит на части - читай только нужную

Весь скилл сразу не читай: чем меньше текста в голове, тем меньше забывается. Открывай
файл ровно в тот момент, который указан в таблице.

| Когда | Что прочитать |
|-------|---------------|
| Начало чата и после сжатия контекста | этот SKILL.md, затем `references/start.md` (Шаги 1-2, пачка юнитов) |
| Перед КАЖДЫМ подшагом и после сжатия контекста | `java -Dfile.encoding=UTF-8 <каталог скилла>/scripts/Unit.java recite M-<nnn>` - что делаешь сейчас: подшаг, файлы, итог, чекпоинт, правила |
| Юнит типа `tech` | `references/tech-flow.md` - порядок подшагов, подшаг `разбор`, дописывание подшагов |
| Перед правками КАЖДОГО подшага (юнита) | `references/work.md` (Шаги 3-5); в Шаге 5 п.1 - вырезать правила подшага |
| Правки сделаны | `references/check.md` (Шаг 6: проверки и сабагент «проверяющий») |
| Проверки пройдены | `references/close.md` (Шаг 7 - запись и коммит, Шаг 8 - сводка) |
| Хочется спросить, не знаешь как, нет в документации, упёрся | `references/stuck.md` («Если упёрся», «Таблица решений по умолчанию») |
| Подшаг или юнит `review` | `references/review-subagent.md` |
| Нужна документация фрейма | `references/doc-subagent.md` (сабагент документации) |
| Проверки (matchers) в `core`, `usage`, `fix` | `references/matchers.md`, «Как писать проверку» и «Запрещённые приёмы» |

`references/code-rules.md` целиком НЕ читается: правила текущего подшага кладёт в файл
скрипт (`references/work.md`, Шаг 5, п.1).

`<каталог скилла>` - каталог, где лежит этот SKILL.md. Не знаешь -
`find . ~/.gigacode -path "*migration-step/SKILL.md" 2>/dev/null | head -1`. Скрипты
запускаются из корня мигрируемого проекта и требуют только Java 17+.

## Цикл работы

```
Шаг 1-2 (start.md) -> для каждого подшага по порядку:
    правила подшага -> Шаги 3-5 (work.md) -> Шаг 6 + проверяющий (check.md) -> коммит подшага
-> чекпоинты юнита -> Шаг 7-8 (close.md) -> СТОП
```

Подшаг - проверка - подшаг - проверка. Следующий подшаг не начинается, пока у текущего нет
строки `проверка: ...` и коммита.

## Главные правила - выполняй дословно

1. **Единственный источник правды о фрейме - документация из MCP** (`get_pv_at_doc`; уже
   добытое - в конспекте `doc-notes/`). Читает её ТОЛЬКО сабагент документации
   (`references/doc-subagent.md`), сам инструмент не вызывай. Второй источник - проект-пример
   и исходники фрейма по путям из паспорта карты, тоже только через сабагента. Версии фрейма -
   из `get_pvat_release_notes`: его (и только его) вызываешь сам.
2. **ЗАПРЕЩЕНО узнавать API фрейма иначе:** не открывай и не распаковывай `.jar`, не лазь в
   `~/.m2`, `.gradle`, кэши IDE, не запускай `javap`, `jar`, `unzip`, не ищи в интернете, не
   пиши «по памяти» и «по аналогии». Даже при `cannot find symbol` - ответ в документации.
3. **Правило подтверждения.** Каждое имя PVATF (класс, метод, аннотация, matcher, настройка,
   зависимость) сначала записано в «Таблицу подтверждений» карточки со ссылкой на запись
   конспекта. Нет строки - не пишешь.
4. **Ты вопросов не задаёшь.** Карта утверждена - все развилки решены, человек мог уйти.
   Хочется спросить -> `references/stuck.md`: решение по таблице или отложить место с
   пометкой `решить человеку` и идти дальше. Остановка - только когда работать физически
   нельзя (не компилируется после 3 попыток, нет MCP, чужие изменения в git). В разделе 6
   карты вопрос с `ответ: -` -> СТОП на Шаге 1.
5. **Один чат - один юнит, целиком.** Юнит `tech` - все подшаги подряд в этом чате.
   Контекст сожмётся сам - тогда перечитай этот SKILL.md и карточку и продолжай с первого
   несделанного подшага. Несколько юнитов - только пачкой (`references/start.md`).
6. **Меняй только файлы текущего подшага (юнита).** Чужая проблема - строка во «Входящие»
   карты. Одна нить: только шаги «Что сделать» по порядку; вспомнил другое дело - строка во
   «Входящие» и назад к текущему шагу.
7. **Вид подшага задаёт границы.** `env` - только сборка и конфигурация; `core` - по
   `core_mode` (`new` - новое основание, старое не трогаешь; `in-place` - внутренности,
   публичные методы прежние); `usage` - шаги и тесты напрямую на фрейм; `cleanup` - только
   удаляешь; `fix` - только находки из карточки; `arch` - только шаги карточки; `review` -
   по `references/review-subagent.md`.
8. **Меняется КАК, а не ЧТО.** Те же шаги, проверки, данные, адреса, учётные данные. Тесты не
   удаляешь и не отключаешь, проверки не ослабляешь, чтобы «позеленело».
9. **Пишешь как на фрейме, а не как было.** Образец - блок `T-<tech>` карты, архитектурный
   план и документация, а не старый код. Из старого берёшь только данные. Класс, которого
   нет в плане и в карточке, не создаёшь. Legacy удаляется под корень: без адаптеров и
   «для совместимости».
10. **Правила кода - только правила подшага.** Перед правками каждого подшага вырезаешь их
   (`references/work.md`, Шаг 5, п.1) и читаешь целиком; механические ловит самопроверка
   grep-ом на Шаге 6. Самые частые ошибки: ответ превращают в DTO (`MR-41`), проверки
   пишут своими конструкциями вместо `.should(...)` с matchers (`MR-48`), заводят лишние
   слои и делегаты (`MR-49`), сами читают настройки подключений (`MR-47`).
11. **Каждый подшаг проверяет сабагент «проверяющий»** с чистым контекстом - до коммита
   (`references/check.md`, Шаг 6, п.9). Находки исправляешь сам, в этом же чате.
12. **Тесты - только точечно.** `env` и `core` режима `new` - только компиляция. Остальное -
   ОДИН показательный тест из карточки, `timeout 600`. Весь набор, модуль, класс - никогда.
13. **Коммит - сам, после каждого подшага (юнита), не спрашивая.** `git push`, PR, слияние -
   никогда.
14. **Технологии `keep` не трогаешь** - кроме `arch`-юнита по его шагам.
15. **Сабагенты только читают и отвечают.** Код, файлы, сборку, тесты, коммиты делаешь сам.
   Сабагентов четыре вида: «документация» и «примеры» (`references/doc-subagent.md`),
   «проверяющий» (`references/check.md`), «ревью» (`references/review-subagent.md`).
16. **Данные подключения - только из `CONNECTIONS.md`.** Те же значения, что у проекта
   раньше, в файлах настроек фрейма; несколько стендов - разные ключи (по конспекту). Пустых
   значений, `TODO`, выдуманного нет. У человека не спрашиваешь (`references/stuck.md`,
   первая строка таблицы).
17. **Создал - подключи.** Класс не создаётся впрок: у созданного есть вызывающие или
   подшаги, которые на него переводят (`references/check.md`, п.7 «Нить»).
18. **Не вызывай другие скиллы миграции,** если пользователь прямо не попросил.
19. **Пиши на русском, короткий дефис `-`.** ID и статусы - латиницей. С пользователем -
   вежливо, на «вы».

## Если потерял нить

Признаки: делаешь то, чего нет в шагах карточки; начал второе дело, не закончив первое;
правишь файл не из карточки; не можешь назвать номер шага, который выполняешь; контекст
только что сжался и ты не помнишь, где был. Тогда остановись и:

(1) выполни `Unit.java recite M-<nnn>` - он напечатает текущий подшаг, его файлы, итог и
чекпоинт; (2) выполни `git status --short`, чтобы увидеть, что уже изменено; (3) открой
файл из таблицы «Этот скилл разбит на части» для текущего момента и продолжи с первого
невыполненного шага. Не помогло - перечитай этот SKILL.md и карточку юнита. Карточка - источник истины, не чат. Начатое
постороннее дело верни как было (`git checkout -- <файл>`) и запиши строкой во «Входящие».

## Перед каждым коммитом подшага - три вопроса

1. Правила подшага вырезаны и прочитаны, `Unit.java check` - `находок 0`?
2. В «Сделано» есть строка `проверка: ...` от проверяющего?
3. Ни одного вопроса человеку, ни одного DTO ответа, ни одного пустого ключа настроек?

Хоть один ответ «нет» -> не коммить, вернись к нужному шагу.
