# Начало работы: Шаги 1-2 и пачка юнитов

Часть скилла `migration-step`. Главные правила и порядок чтения - в `SKILL.md`.
«Если упёрся» и «Таблица решений по умолчанию» - `references/stuck.md`.

## Шаг 1 - Открой карту и возьми один юнит

1. Прочитай из `.gigacode/data/migration/MIGRATION-MAP.md` ТОЛЬКО: шапку, «1. Паспорт
   проекта» (команды, правила, таблица технологий), «4. Юниты работ» и «6. Открытые вопросы
   к человеку».
2. Ворота:
   - `map_status` не `approved` -> **СТОП**: карта не одобрена, нужен `migration-map`.
   - Файла карты нет -> **СТОП**: сначала `migration-map`.
   - В разделе 6 есть вопрос без ответа (`ответ: -`) -> **СТОП**: выведи эти вопросы и
     скажи, что миграция не продолжается, пока человек на них не ответит. Ничего не меняй.
3. Выбери юнит: передана пачка («пачка: M-001, M-002, ...») -> см. «Пачка юнитов» ниже;
   назван пользователем/оркестратором -> его; есть `in-progress` -> его; иначе
   первый сверху `todo`, у которого все «Зависит от» в статусе `done` (юнит, которого нет в
   таблице, но он есть в строке «В архиве» над ней, считается `done`). При `scope: core` в
   шапке карты бери только юниты типа `env`, а в юнитах `tech` - только подшаги `разбор`,
   `env` и `core`; остальное не трогай, даже если просят «продолжи». Подходящего нет ->
   **СТОП**, скажи почему (всё сделано / всё ждёт `blocked`).

## Шаг 2 - Прочитай карточку и проверь вход

1. Прочитай `.gigacode/data/migration/units/M-<nnn>.md` целиком (юнит `tech` - не целиком,
   а так, как сказано в разделе «Юнит технологии», п.1).
   Затем в карте, в разделе 2, прочитай блок целевой картины `T-<tech>` этой технологии
   (поле «Целевая картина» карточки) - это то, как код должен выглядеть в конце.
   Затем прочитай архитектурный план `.gigacode/data/migration/ARCHITECTURE.md`: разделы 1,
   2, 4 целиком, а из разделов 3 и 5 - строки своей технологии
   (`grep -n "| <tech> |" .gigacode/data/migration/ARCHITECTURE.md`). Файла нет (карта
   построена без плана) - работай по блоку `T` и запиши это в журнал карты.
   Затем в карте, в разделе «8. Что уже изменилось», прочитай строки с технологией этого
   юнита (поле `tech` карточки). Это то, что уже переведено до тебя: что на что заменено и
   как это теперь вызывать. Делай так же, как там, - не изобретай второй способ.
   Юнит `tech` (перед подшагом `env`) и юнит `env`: прочитай в
   `.gigacode/data/migration/CONNECTIONS.md` раздел своей технологии и разделы «Стенды»,
   «Переменные окружения и системные свойства», «Сертификаты и хранилища ключей». Файла нет
   (карта построена до реестра) - собери раздел своей технологии сам по шагу 1а Этапа 2
   скилла `migration-map` (команды поиска там) и запиши файл по его шаблону.
2. Проверь git:
   ```
   git status --short
   git branch --show-current
   ```
   - Ветка миграции в паспорте `-` (это первый юнит): перейди на основную ветку из паспорта,
     создай ветку миграции (`git checkout -b <имя>`) и впиши имя в паспорт карты. Имя - по
     конвенции веток проекта из паспорта; конвенции нет - `pvatf-migration`. Спрашивать
     разрешение на создание ветки не нужно.
   - Ветка миграции в паспорте указана: ты должен быть на ней. Не на ней и дерево чистое ->
     `git checkout <ветка миграции>`.
   - Есть незакоммиченные изменения, и юнит НЕ `in-progress` -> **СТОП**, сообщи
     пользователю, ничего не откатывай и не коммить чужое.
3. Юнит был `in-progress` -> прочитай в карточке «Где остановился» и продолжай оттуда, уже
   сделанное не переделывай. Юнит `tech`: смотри таблицу «Подшаги» - продолжаешь с первого
   подшага, у которого статус не `done`; подшаг `in-progress` - прочитай его «Сделано» и
   `git status --short`, доделай его.
4. **Сразу запиши:** в карточке `status: in-progress`, в таблице раздела 4 карты - тоже.

## Пачка юнитов (только если передали несколько ID)

Пачка - это несколько юнитов подряд в одном чате. Правила каждого юнита при этом НЕ
меняются: у каждого своя карточка, свои проверки, своя запись в карту, свой коммит.

0. Юниты `tech` в пачку входят: каждый делается целиком, со всеми подшагами, потом -
   следующий юнит пачки. Контекст по ходу сожмётся сам - это нормально, см. правило 3 исполнителя в SKILL.md.
1. Запиши список ID пачки в todo, в порядке таблицы раздела 4. Больше 5 ID - возьми первые
   5, остальные назови в сводке как несделанные.
2. Для ПЕРВОГО юнита пачки выполни Шаги 2-7 полностью.
3. После Шага 7 посмотри статус этого юнита:
   - `done` -> возьми следующий ID из пачки и выполни для него Шаги 2-7 полностью (карточку
     читай заново, `references/` перечитывать не нужно);
   - `in-progress` или `blocked` (работать физически нельзя: не компилируется, тест красный
     из-за миграции после 3 попыток) -> **СТОП пачки**. Следующие юниты НЕ начинай, даже
     если они от этого юнита не зависят. Переходи к Шагу 8. Отложенные места (`решить
     человеку`) пачку НЕ останавливают: юнит с ними закрывается `done`.
4. Перед каждым следующим юнитом проверь: его «Зависит от» все `done`, дерево git чистое
   (`git status --short` пуст), в разделе 6 карты не появилось вопросов без ответа. Не так
   -> СТОП пачки, Шаг 8.
5. Нельзя: объединять юниты пачки в один коммит; пропускать проверки Шага 6 «потому что
   юнит маленький»; делать правки следующего юнита, пока не закрыт текущий.
6. Шаг 8 выполняется ОДИН раз в конце: сводка по каждому юниту пачки отдельной строкой.
