# Правила MR: проверки (matchers)

Правила этого файла: `MR-29`, `MR-41`, `MR-48`.

Прочитай ЦЕЛИКОМ перед тем, как менять хоть одну проверку. Вместе с этим файлом прочитай
`references/matchers.md` - там как устроены проверки во фрейме, пошаговый алгоритм «Как
писать проверку» и какими словами спрашивать документацию про нужный matcher.

Главное в одной фразе: **ответ фрейма - это валидируемый объект; проверка - это готовый
matcher фрейма нужного вида прямо в `.should(...)` у этого объекта. Ничего своего.**

---

### MR-29 · Проверки - на matchers фрейма, `Assertions` уходят

**Правило.** В `usage`-подшаге КАЖДУЮ проверку в файлах юнита переводи на matchers и
conditions фрейма. Переводится всё:
- `Assertions.*`, `assertEquals`, `assertTrue`, `assertFalse`, `assertNotNull`, `assertNull`,
  `assertThat`;
- AssertJ, Hamcrest;
- `SoftAssertions`, `assertAll` -> `.shouldSoft(...)`;
- свои методы `assertXxx`, `checkXxx`, `verifyXxx`, свои assert-классы;
- ручной разбор JSON ради сравнения.

**Почему.** Фрейм проверяет и пишет в отчёт сам; ассерты поверх ответа фрейма дублируют
это и прячут, что именно проверялось.

**Как делать.**
1. Выпиши все РАЗНЫЕ виды проверок из файлов юнита (код ответа, поле-строка, поле-число,
   размер массива, строка в БД, сообщение в Kafka ...).
2. По каждому виду, которого ещё нет в конспекте `doc-notes/<tech>.md`, задай вопрос
   сабагенту документации (слова для вопроса - `references/matchers.md`).
3. Заменяй каждую проверку по алгоритму «Как писать проверку» (`references/matchers.md`) и
   по `MR-48`.
4. Проверяется ровно то же, что раньше (`MR-9`, `MR-11`): то же поле, то же значение.
5. Сообщение старого ассерта переноси в параметр `errorMessage` matcher.

**Исключения.**
- matcher, который покрывает проверку, не нашёлся в документации после 8 формулировок
  запроса -> СТАНДАРТНЫЙ ассерт (`Assertions` JUnit/TestNG, AssertJ, Hamcrest) остаётся, а
  ты пишешь во «Входящие» карты: файл, строка, что не удалось перевести;
- значение посчитал сам тест (сумма, длина своего списка, флаг), а не получено от фрейма ->
  проверки фрейма для него нет, `Assertions` остаётся.
Самописные assert-классы не остаются НИКОГДА.

**Как проверить.**
```
grep -nE "Assertions\.|assert(Equals|True|False|NotNull|Null|That|All)\(|SoftAssertions" <файлы юнита>   # каждая строка либо заменена, либо во «Входящих»
```

### MR-41 · Ответ не превращается в DTO ради проверки. Разбирай всю цепочку

**Правило.** Метод, который делает запрос (REST, БД, Kafka), возвращает валидируемый объект
фрейма наверх, а шаг или тест проверяет его через `.should(...)`. Ответ не превращается в
свой объект, чтобы потом проверить его поля.

**Почему.** Цепочка «запрос -> DTO -> геттер -> ассерт» - это ручная работа, которую фрейм
делает сам. Она плодит DTO, check-методы и ошибки.

**Нельзя / нужно.**
```java
// НЕЛЬЗЯ: ответ -> свой объект -> ассерты по полям
OrderDto order = response.as(OrderDto.class);
Assertions.assertEquals("NEW", order.getStatus());
Assertions.assertEquals(53, order.getCode());

// НУЖНО: метод запроса возвращает валидируемый объект, шаг или тест его проверяет
orderSteps.createOrder(body)               // возвращает ValidatableResponseWrapper
        .should(<matcher кода ответа>)
        .toValidatableJson()
        .should(<matcher строки по пути>("$.status", ...), <matcher числа по пути>("$.code", ...));
```

**Что из этого следует.**
- метод нижнего уровня (общий класс технологии или класс шагов) возвращает валидируемый
  объект фрейма, а не DTO, `String`, `Map` или `Response` старой библиотеки;
- новые DTO ответа не создаются; ответ не оборачивается в свои классы-результаты;
- старый DTO ответа, который был нужен только для ассертов, после перевода проверок никто
  не использует - он удаляется (в этом юните, если ссылок 0, иначе в `cleanup`);
- значение из ответа, нужное ДАЛЬШЕ по сценарию (id созданной сущности для следующего
  запроса), достаётся тем способом, который показывает документация для валидируемого
  объекта, - только это одно значение, без DTO.

**Как делать: не заменяй ассерт механически - разбери всю цепочку.** Увидел ассерт или
проверку значения, которое достали руками (`dto.getStatus()`, `response.jsonPath().get(...)`,
`row.getString(...)`, `record.value()`, свой `checkXxx(dto)`), - пройди от ассерта НАЗАД и
ответь на три вопроса:
1. **Откуда значение?** Из ответа REST, строки БД, сообщения Kafka -> это проверка
   результата обращения, её место - `.should(...)` на валидируемом объекте. Значение
   посчитал сам тест -> `Assertions` остаётся (`MR-29`).
2. **Что стоит между обращением и ассертом?** Обычно: метод делает запрос -> превращает
   ответ в DTO -> возвращает DTO -> геттер достаёт поле -> check-метод или ассерт
   сравнивает. Всё, что между «сделал запрос» и «проверил», - лишнее.
3. **Нужно ли значение ещё кому-то, кроме проверки?** Да (id для следующего запроса) - оно
   достаётся способом из документации у валидируемого объекта.
Потом перепиши цепочку ЦЕЛИКОМ, а не её конец:
- метод, который делает запрос, возвращает валидируемый объект фрейма;
- извлечение, маппинг в DTO и check-метод удаляются;
- проверка - `.should(...)` с matcher на это поле (matcher - из конспекта);
- `grep -rn "<ИмяDto>" <src>`: ссылок не осталось - удали класс DTO (файл вне юнита - пункт
  во «Входящие»);
- метод, возвращавший DTO, вызывают файлы вне юнита, и его нельзя поменять, не сломав их, ->
  не оставляй половину: запиши во «Входящие», какие файлы держат старую цепочку.

**Нельзя.** Оставить DTO и геттер, а `assertEquals(a, dto.getX())` заменить на проверку
строки; достать поле в переменную и проверять переменную; завернуть старый check-метод в
новый.

**Исключения.**
- документация не даёт способа проверить или достать то, что нужно (после 8 формулировок
  запроса) -> DTO остаётся, запись во «Входящие»: файл, что именно фрейм не покрыл;
- DTO, которым СОБИРАЕТСЯ ТЕЛО ЗАПРОСА, - это данные, он остаётся.

**Как проверить.**
```
grep -nE "\.as\([A-Z][A-Za-z0-9_]*\.class\)|readValue\(|fromJson\(|\.getObject\(|\.extract\(\)" <файлы юнита>   # если это ради проверки - замени на .should()
```

### MR-48 · Проверка = готовый matcher фрейма нужного вида прямо в `.should(...)`. Ничего своего

**Правило.** Пиши проверки строго по разделу «Как писать проверку» из
`references/matchers.md`. Для каждой проверки - matcher ИМЕННО ЕЁ вида: код ответа -
matcher кода ответа, число - matcher с условием на число, наличие поля - matcher наличия,
размер - matcher размера. Несколько проверок одного объекта - через запятую в одном
`.should(m1, m2, m3)`.

**Почему.** Matchers во фрейме уже есть на каждый вид проверки, их много. Задача - взять
нужный, а не придумать свой способ проверять. Своя «система проверок» (списки, циклы,
обёртки) скрывает, что проверяется, и ломает отчёт фрейма.

**Нельзя / нужно.**
```java
// НЕЛЬЗЯ: свой подход - список, цикл, всё через сравнение текста, число как строка
List<JsonMatcher> matchers = new ArrayList<>();
matchers.add(<matcher значения по пути>("$.status", <условие текста: равно>("NEW")));
matchers.add(<matcher значения по пути>("$.code", <условие текста: равно>("53")));
for (JsonMatcher matcher : matchers) {
    json.should(matcher);
}

// НУЖНО: каждый вид - своим matcher, все прямо в одном .should(...)
json.should(
        <matcher строки по пути>("$.status", <условие текста: равно>("NEW")),
        <matcher числа по пути>("$.code", <условие числа: равно>(53)),
        <matcher наличия поля>("$.id"));
```

**ЗАПРЕЩЕНО (каждый пункт - нарушение):**
- проверять всё одним matcher (например, всё - сравнением текста значения по пути);
- переводить число или boolean в строку ради сравнения (`String.valueOf`, `toString`,
  `"53"` вместо `53`);
- собирать matchers в `List` или массив, проходить по ним циклом `for` / `forEach`;
- писать метод, который возвращает matcher или набор matchers;
- писать свою обёртку над `.should(...)` (`checkResponse`, `verify`, `assertResponse`);
- писать свои классы matcher или condition, фабрики, утилиты, enum'ы и `Map` «поле ->
  ожидаемое значение» ради проверок;
- «заодно» перестраивать шаги и классы, когда переводишь проверки.

**Исключения.** Старый тест сам проверял в цикле (например, каждую строку выборки) ->
сначала спроси документацию, есть ли matcher на всю коллекцию. Есть - он. Нет - цикл по
ДАННЫМ теста остаётся, а внутри matcher пишется прямо в `.should(...)`.

**Как проверить.**
```
grep -nE "List<[A-Za-z]*(Matcher|Condition)|(Matcher|Condition)\[\]|for *\([A-Za-z<>]*(Matcher|Condition)|forEach\([a-z]*::should|(implements|extends) +[A-Za-z]*(Matcher|Condition)|(String\.valueOf|toString)\(.*\)" <файлы юнита> | grep -E "Matcher|Condition|should"   # пусто
grep -nE "^\s*(public|private|protected)[^=(]*(Matcher|Condition)[A-Za-z<>?, ]* +[a-z][A-Za-z0-9]*\(" <файлы юнита>   # метод возвращает matcher: пусто
```
