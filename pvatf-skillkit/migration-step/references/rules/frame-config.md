# Правила MR: фрейм, конфигурация, логирование, Spring

Правила этого файла: `MR-12`, `MR-13`, `MR-14`, `MR-15`, `MR-16`, `MR-31`, `MR-36`,
`MR-43`, `MR-46`, `MR-47`, `MR-50`.

Прочитай перед `env`-, `core`-, `usage`-подшагом и перед любой правкой файлов сборки и
настроек.

### MR-12 · В коде только то, что подтверждено документацией

**Правило.** Каждое имя из PVATF в коде (класс, аннотация, метод, настройка, зависимость)
есть в «Таблице подтверждений» карточки со ссылкой на запись конспекта `D-<tech>-n`. Нет
строки в таблице - не имеешь права это писать.

**Почему.** Слабая модель уверенно выдумывает правдоподобные имена методов. Код с
выдуманным API не компилируется или, хуже, компилируется и делает не то.

**Как делать.** Нужно имя из фрейма -> ищи в конспекте -> нет -> вопрос сабагенту
документации -> записал в таблицу -> пишешь в код. Документация не ответила -> блокер, см.
«Если упёрся» в SKILL.md. Не подбирай имя «по аналогии».

### MR-13 · Не пиши своё там, где фрейм уже даёт

**Правило.** Не создавай свои утилиты, обёртки, базовые классы, ожидания, ретраи, парсеры,
если в документации есть готовый механизм. Старую самописную обёртку не «адаптируй», а
заменяй на механизм фрейма - если так велит карточка.

**Почему.** Свой код поверх фрейма - это то, от чего миграция избавляет.

**Как делать.** Прежде чем написать служебный код (ожидание, повтор, чтение файла,
подстановка параметров в SQL, сериализация), спроси документацию: «есть ли во фрейме
механизм для <что нужно>». Есть - используй. Нет - запись во «Входящие», а не свой код.

**Исключения.** Общий класс технологии из архитектурного плана (`MR-49`) - это не «своё
вместо фрейма», он построен на фрейме.

### MR-14 · Без `Thread.sleep`

**Правило.** Ожидания - только механизмом фрейма из документации.

**Как делать.** Нужно дождаться (сообщения, смены статуса, строки в БД) -> вопрос
документации про ожидание для этой технологии. Не нашёл - НЕ добавляй `sleep`, это блокер.
Старый `Thread.sleep` в файле юнита заменяй на механизм фрейма.

**Как проверить.** `grep -n "Thread.sleep\|TimeUnit.*sleep" <файлы юнита>` - пусто.

### MR-15 · Без хардкода

**Правило.** Адреса, хосты, порты, логины, пароли, таймауты, имена стендов, алиасы - не в
коде. Куда их класть - по документации фрейма (раздел про конфигурацию).

**Как делать.** Значение подключения -> файл настроек фрейма (`MR-47`). Тестовые данные
(номер договора для теста) - константа в тест-классе или класс данных, это не хардкод.

**Исключения.** Существующий хардкод, о котором нет шага в карточке, не трогай - запиши во
«Входящие».

### MR-16 · Зависимости - только из документации

**Правило.** Не добавляй библиотеку или плагин, которых нет в документации фрейма или в
шагах карточки. Версии - там, где их держит проект (BOM, `dependencyManagement`, каталог
версий), а не в модуле. Номера версий фрейма и perfeccionista - из строки «Версии фрейма»
паспорта карты (`get_pvat_release_notes`), не из головы и не из старого кода.

**Нельзя.** «Добавлю Jackson/Awaitility/Lombok, так удобнее» - нельзя, если этого нет в
документации или карточке.

### MR-31 · Технологии `keep` не трогай

**Правило.** Код, зависимости и конфиги технологии с решением `keep` в паспорте карты не
мигрируются и не удаляются.

**Исключения.** `arch`-юнит, строго по шагам карточки. Spring с решением `keep` - см.
`MR-50`: его код остаётся, но фрейм к нему подключается.

### MR-36 · Классы конфигурации фрейма лежат в пакете `config`

**Правило.** `ApiEnvironmentConfiguration` и все остальные классы конфигурации фрейма
(`*EnvironmentConfiguration`, `*ServiceConfiguration`, `*Configuration` для сервисов
фрейма) кладутся в пакет `config`.

**Как делать.**
1. Ищи существующий пакет:
   `find . -type d -name config -path "*src*" | grep -v "/target/\|/build/"`.
2. Есть (в `src/main/java` или в `src/test/java`) -> туда. Нет -> создай `<базовый пакет проекта>.config` там, где документация велит
   держать конфигурацию; документация не уточняет - в `src/main/java`.
3. Нашёл класс конфигурации фрейма не в `config`, и он в файлах юнита -> перенеси.

**Нельзя.** Класть конфигурацию в корень `src/main/java` без пакета, рядом с тестами, в
`utils`/`helpers`, размазывать по нескольким пакетам.

### MR-43 · Запросы и ответы руками не логируются - это делает фрейм

**Правило.** Фрейм сам пишет в лог каждое обращение и ответ: запрос и ответ REST, запрос в
БД и результат, отправку и чтение сообщений Kafka. Старое ручное логирование этого НЕ
переносится, а удаляется.

**Что удаляется.**
- вызовы логгера и `System.out.println`, которые печатают URL, метод, заголовки, тело
  запроса или ответа, код статуса, текст SQL и его результат, сообщение Kafka;
- фильтры и настройки логирования старых библиотек (`.log().all()`, `RequestLoggingFilter`,
  `ResponseLoggingFilter`, `.prettyPrint()`, `.peek()`), свои фильтры и перехватчики ради
  логирования;
- строки «Отправляем запрос...», «Получен ответ...», «Выполняем SQL...» вокруг вызова
  фрейма;
- поле логгера (`Logger log`, `@Slf4j`), которым после этого никто не пользуется, и его
  импорты.

**Логирование настраивается в одном месте - `simplelogger.properties`** в ресурсах тестов
(`src/test/resources/`). Фрейм пишет лог через простой логгер SLF4J (`SimpleLogger`).
Нужно больше или меньше подробностей - меняется уровень в этом файле, а не код. Обычное
содержимое:
```
org.slf4j.simpleLogger.defaultLogLevel=INFO
org.slf4j.simpleLogger.showShortLogName=true
org.slf4j.simpleLogger.showDateTime=true
org.slf4j.simpleLogger.dateTimeFormat=HH:mm:ss:SSS
org.slf4j.simpleLogger.logFile=System.out

#org.slf4j.simpleLogger.log.ru.sber.at=INFO
```
Файл обязателен в каждом мигрированном проекте: нет его - создай с этим содержимым (в
юните, где это записано в карточке). Последняя строка - закомментированный пример уровня
для пакета. Если в конспекте `doc-notes/common.md` или в проекте-примере файл выглядит
иначе - бери оттуда. Уровень для пакета - `org.slf4j.simpleLogger.log.<пакет>=<уровень>`.

**Всё остальное логирование проекта - старое и удаляется** (в юнитах, где это записано):
конфигурации `logback.xml`, `logback-test.xml`, `log4j.xml`, `log4j2.xml`,
`log4j.properties`, `log4j2.properties`, `logging.properties`; зависимости логгеров и их
связок с SLF4J (`logback-classic`, `logback-core`, `log4j-core`, `log4j-api`,
`log4j-slf4j-impl`, `log4j-slf4j2-impl`, `slf4j-log4j12`, `slf4j-reload4j`, `jul-to-slf4j`
и подобные); свои аппендеры, фильтры, форматтеры. Не добавляй конфигурацию или зависимость
другого логгера.

**Что можно оставить.** Сообщение о том, чего фрейм знать не может: ход сценария и
предметные значения («создан заказ <id>», «ждём смены статуса»). Логгер - только
`org.slf4j.Logger` (или `@Slf4j`), не `org.apache.logging.log4j`, не `java.util.logging`,
не `ch.qos.logback`. Сомневаешься, дублирует ли строка лог фрейма, - удаляй.

**Как проверить.**
```
grep -nE "\b(log|logger|LOG|LOGGER)\.(info|debug|trace|warn|error)\(|System\.(out|err)\.print|\.log\(\)\.(all|body|headers|ifValidationFails)|(Request|Response)LoggingFilter|\.prettyPrint\(|\.prettyPeek\(|\.peek\(" <файлы юнита>   # остаётся только ход сценария
```

### MR-46 · Аннотации фрейма - один раз, в базовом тест-классе

**Правило.** Аннотации подключения фрейма одинаковы для всех тестов одной конфигурации
окружения. Их ставят на базовый тест-класс, тесты от него наследуются. Точные аннотации - из
конспекта `doc-notes/common.md`.

```java
@ExtendWith(PerfeccionistaExtension.class)
@SetEnvironmentConfiguration(ApiEnvironmentConfiguration.class)
public class BaseTest {
}

public class OrderTests extends BaseTest {   // аннотаций фрейма на самом тесте нет
    @Test
    void whenOrderCreatedExpectStatusNew() { ... }
}
```

**Что можно и нельзя в базовом тест-классе.**
- **Такой базовый класс нужен.** Запрет на «базовые классы» (`MR-25`, `MR-30`, `MR-49`) -
  про базовый класс с клиентами и методами, от которого наследуются ради доступа к ним.
- можно: аннотации фрейма и тест-фреймворка (расширения, конфигурация окружения, общие
  теги), общие для всех тестов константы, общие `@BeforeAll`/`@BeforeEach`/`@AfterEach`,
  если они нужны ВСЕМ наследникам;
- нельзя: клиенты и сервисы фрейма в полях, методы запросов, методы проверок, чтение
  файлов, хелперы «для удобства» - это место классов шагов;
- один базовый тест-класс на одну конфигурацию окружения (API-тесты - один, UI-тесты -
  другой). Какой есть в проекте - в архитектурном плане. Второй для той же конфигурации не
  создавай;
- в проекте уже есть базовый тест-класс (`TestBase`, `BaseTest`) - используй его: имя
  сохраняется, из него убирается старое (клиенты, хелперы), остаются аннотации фрейма.

**Как делать.** Пишешь или переписываешь тест-класс -> он наследуется от базового,
аннотации фрейма с него самого убери. Базового класса нет ни в проекте, ни в карточке, ни в
плане -> пункт во «Входящие», аннотации пока ставь на тест-класс.

**Как проверить.**
```
grep -nE "@ExtendWith\(PerfeccionistaExtension|@SetEnvironmentConfiguration" <тест-класс>   # пусто, если есть базовый тест-класс
```

### MR-47 · Настройки подключений читает фрейм - старое чтение конфигурации не переезжает

**Правило.** У фрейма свои файлы настроек (`*.properties` в ресурсах тестов: общий файл
фрейма и файлы технологий). Фрейм сам их находит, читает и по ним настраивает сервисы:
адрес, логин, алиас базы, брокеры и топики Kafka, таймауты.

**Как делать.**
1. Значения из старых конфигов (адреса, алиасы, топики, учётные данные, таймауты)
   ПЕРЕНОСЯТСЯ в файлы настроек фрейма. Имена файлов и ключей - только из конспекта
   документации по технологии (вопрос «как настроить»), не придумывай их.
2. Старый КОД чтения настроек НЕ переносится и удаляется: свои `ConfigReader`,
   `PropertyReader`, `PropertiesLoader`, интерфейсы Owner (`ConfigFactory.create`),
   `new Properties().load(...)`, `ResourceBundle`, `System.getProperty` / `System.getenv`
   ради адреса или логина, `@Value`, классы-держатели настроек (`KafkaConfig`, `DbConfig`,
   `Endpoints` с хостами).
3. Подключение руками не собирается: никаких своих `Properties` для Kafka-клиента
   (`bootstrap.servers`, сериализаторы, SSL), своей строки JDBC, своего `DataSource`, своего
   базового URL в коде. Клиент берётся у сервиса фрейма по алиасу.
4. Старые файлы настроек, из которых значения перенесены, удаляются (строки `L`).
5. «Переходник», который читает старый конфиг и отдаёт значения фрейму, - нельзя.

**Свои конфигурационные классы проекта после миграции не нужны.** Класс, который хранит
или отдаёт настройки подключения (`DbConfig`, `DatabaseProperties`, `KafkaConfig`,
`ApiConfig`, `Endpoints` с хостами, `TestConfig` с url/login/password):
- технология переведена -> её часть класса больше никто не читает: убери обращения к нему
  из файлов юнита;
- класс обслуживал одну технологию -> удаляется в `cleanup` этой технологии;
- класс общий на несколько технологий -> убирается по частям: в каждом юните технологии -
  поля и методы своей технологии; опустел - удаляется. Не жди конца миграции;
- в классе есть и подключения, и собственные параметры проекта (тестовые данные) ->
  подключения уходят, параметры переезжают способом из документации; потом класс
  удаляется;
- не путай с классами конфигурации ФРЕЙМА (`*EnvironmentConfiguration`,
  `*ServiceConfiguration`, пакет `config`, `MR-36`) - они нужны. Отличие: класс фрейма
  описывает, какие сервисы подключены; свой класс хранит значения или читает их из файла.
Перед удалением - `grep -rn "<ИмяКласса>" <src>`: ссылок быть не должно; остались вне юнита
- не удаляй, запиши во «Входящие».

**Что остаётся.** Собственные параметры проекта, которые к подключениям не относятся
(тестовые данные, идентификаторы). Как их хранить и получать - способом из документации
(вопрос сабагенту: «как получить свой параметр проекта из настроек, ConfigurationService»),
а не своим читателем.

**Как проверить.**
```
grep -nE "ConfigFactory\.create|new Properties\(\)|getResourceAsStream\(|ResourceBundle\.getBundle|System\.(getProperty|getenv)\(|@Value\(|PropertiesLoader|ConfigReader|PropertyReader" <файлы юнита>   # пусто
```

### MR-50 · Spring - строго по решению в паспорте: оставляем со стартером фрейма или убираем полностью

**Правило.** Если в проекте есть Spring, в паспорте карты стоит строка «Spring: keep» или
«Spring: remove» - это решение человека, принятое при построении карты. Делай ровно по нему.
Смешанного состояния («частично на Spring, частично без») в конце миграции быть не должно.

**Почему.** Фрейм умеет работать со Spring через свой стартер, а умеет и без него. Оба пути
рабочие, но каждый по-своему подключает фрейм и получает сервисы. Если смешать, будет два
способа получать одно и то же, и тесты начнут падать от порядка инициализации.

#### Решение `keep` - Spring остаётся, фрейм подключается через Spring-стартер

1. Как подключать фрейм к Spring - ТОЛЬКО по записи конспекта `D-common-9` (раздел
   документации «Работа с Spring»): зависимость стартера, аннотации, как получать сервисы и
   классы шагов. Нет записи - вопрос сабагенту документации, не придумывай.
2. Spring-контекст, `@SpringBootTest`, внедрение зависимостей остаются - но только там, где
   их показывает документация фрейма для Spring.
3. Классы шагов и общий класс технологии - бины или обычные классы, как показывает
   `D-common-9`. Один способ на весь проект.
4. Не подключай фрейм двумя способами сразу (стартер и `PerfeccionistaExtension` на одном
   тест-классе), если документация прямо этого не требует.
5. Настройки подключений - всё равно у фрейма (`MR-47`), если `D-common-9` не говорит иное.
   Свои `RestTemplate`, `WebClient`, `JdbcTemplate`, `KafkaTemplate` для обращений, которые
   переводятся на фрейм, уходят - обращаются через фрейм.

#### Решение `remove` - Spring убирается полностью, тесты на JUnit 5

1. Тест-фреймворк - JUnit 5 (если человек не выбрал иное в вопросе про Spring).
2. Spring уходит из тестового кода целиком:
   - `@SpringBootTest`, `@ContextConfiguration`, `@ExtendWith(SpringExtension.class)`,
     `@RunWith(SpringRunner.class)`, `AbstractTestNGSpringContextTests`,
     `@TestPropertySource`, `@ActiveProfiles`, `@DirtiesContext`;
   - `@Autowired`, `@Component`, `@Service`, `@Configuration`, `@Bean`, `@Value`,
     `@Lazy`, `@Scope` в тестовом коде;
   - `RestTemplate`, `WebClient`, `JdbcTemplate`, `KafkaTemplate` - обращения переходят на
     фрейм (в юнитах своих технологий);
   - Spring-конфигурации тестов (классы с `@Configuration`/`@Bean`), `application*.yml` /
     `application*.properties`, которыми пользовались только тесты: значения подключений -
     в файлы настроек фрейма (`MR-47`), остальное - удаляется;
   - зависимости `spring-boot-starter-test`, `spring-test`, `spring-boot-starter-*`,
     `spring-kafka`, `spring-jdbc` и плагин `spring-boot-maven-plugin`, если они больше
     никому не нужны.
3. Чем заменить внедрение. Было `@Autowired private OrderSteps orderSteps;` - стало
   обычное поле `private final OrderSteps orderSteps = new OrderSteps();`. Бин со
   сложной сборкой (зависит от других бинов) - класс создаёт то, что ему нужно, сам, в
   поле, так же. Свой «контейнер», фабрика или синглтон вместо Spring - НЕЛЬЗЯ.
4. Порядок. Пока технологии мигрируются, Spring ещё живёт: новые классы шагов и общий класс
   технологии пишутся сразу БЕЗ Spring-аннотаций, а тесты, переведённые на них, получают
   их обычным полем. Окончательно Spring вычищает юнит технологии `spring` (последний
   среди технологий): переводит оставшееся внедрение на поля, удаляет конфигурации и
   зависимости.
5. Spring нужен самому продукту (код в `src/main` - это сервис, а не автотесты) - эти правила
   его не касаются: убирается только Spring из тестового кода и тестовых зависимостей.

**Нельзя.** Оставить «на всякий случай» `@SpringBootTest` на части тестов; написать свой
DI, фабрику бинов, `ApplicationContext`-заменитель; держать и Spring-конфиг, и файлы
настроек фрейма для одних и тех же подключений.

**Как проверить (решение `remove`, по файлам юнита; в конце юнита `spring` - по всему проекту).**
```
grep -rnE "org\.springframework|@Autowired|@SpringBootTest|@ContextConfiguration|@Component|@Configuration|@Bean|@Value\(" <файлы>   # пусто
```
