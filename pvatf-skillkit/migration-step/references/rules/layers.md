# Правила MR: слои, шаги, структура классов

Правила этого файла: `MR-49`, `MR-30`, `MR-42`, `MR-35`, `MR-38`, `MR-44`.

Прочитай ЦЕЛИКОМ перед тем, как создавать или менять класс шагов, общий класс технологии,
тест-класс или класс-флоу. Здесь самое частое место ошибок: модель начинает строить «свою
архитектуру» - обёртки над обёртками, вложенные классы, по десять одинаковых методов. Этого
делать нельзя. Слоёв ровно столько, сколько описано ниже, и у каждого своя работа.

---

## Схема слоёв (запомни её, это основа всех правил ниже)

```
тест-класс            OrderTests                 сценарий: данные -> шаг -> проверка
    |  вызывает
    v
класс шагов           OrderSteps                 действия предметной области: createOrder, getOrder
    |  вызывает
    v
общий класс           RestRequests               одинаковая механика технологии: get, post, put, delete
технологии            (только если он есть
    |                  в архитектурном плане)
    |  вызывает
    v
фрейм                 сервис фрейма, клиент фрейма
```

Вызовы идут ТОЛЬКО сверху вниз и ТОЛЬКО на один уровень ниже. Снизу вверх - никогда.
Через уровень - нельзя (тест не вызывает общий класс технологии; класс шагов не вызывает
фрейм сам, если в плане есть общий класс этой технологии).

| Уровень | Что в нём лежит | Чего в нём НЕТ |
|---------|-----------------|----------------|
| тест-класс | тестовые методы, `@BeforeEach`/`@AfterEach`, константы тестовых данных, вызовы шагов, `.should(...)` | приватных методов, запросов, SQL, чтения файлов, маппинга |
| класс шагов | методы с именами действий предметной области; эндпоинты, тела запросов, SQL этой области; возвращают валидируемый объект фрейма | сборки запроса с нуля (заголовки, авторизация, базовые настройки - это общий класс), проверок, DTO ответа |
| общий класс технологии | по одному методу на ВИД операции технологии (`get`, `post`, `put`, `delete`; `select`, `update`; `send`, `read`), получение сервиса фрейма, общие заголовки и настройки запроса | имён предметной области (`order`, `client`), эндпоинтов, SQL конкретных таблиц, проверок, DTO |
| фрейм | - (не твой код) | - |

### MR-49 · Слоёв ровно три, у каждого своя работа. Своих уровней и вложенных классов не строй

**Правило.** Код после миграции раскладывается строго по схеме выше: тест-класс -> класс
шагов -> (общий класс технологии, если он есть в плане) -> фрейм. Других уровней нет.
Одинаковая механика обращения к технологии пишется ОДИН раз - в общем классе технологии, а
не копируется в каждый метод каждого класса шагов.

**Почему.** Старый код часто содержит по 10 почти одинаковых методов («отправить POST на
/orders», «отправить POST на /clients», ...), которые отличаются только адресом и телом.
Если перенести их как есть, получится 10 копий одной механики. Если вместо этого строить
«свою архитектуру» (обёртка над обёрткой, вложенные классы, абстрактные базовые классы),
код становится нечитаемым и его невозможно проверить. Правильно - одна механика в одном
месте, действия предметной области над ней в классах шагов.

**Как делать.**
1. Открой архитектурный план (`ARCHITECTURE.md`, разделы 1 и 3). Найди, какие классы
   шагов и какой общий класс технологии в нём есть. Пишешь ТОЛЬКО их.
2. **Общий класс технологии есть в плане** -> создай/дополни его:
   - один публичный метод на вид операции: для REST - `get`, `post`, `put`, `patch`,
     `delete` (только те, которыми пользуются потребители); для БД - `select`, `update`;
     для Kafka - `send`, `read`. Имена - простые, по виду операции;
   - параметры метода - только то, что меняется от вызова к вызову: путь, тело, параметры
     запроса, дополнительные заголовки; SQL и параметры; топик и сообщение;
   - внутри - обращение к фрейму (как в конспекте `D-<tech>-n`) и всё, что одинаково для
     ВСЕХ вызовов: общие заголовки, тип содержимого, авторизация, алиас подключения;
   - метод возвращает валидируемый объект фрейма (`MR-41`), а не DTO, не строку, не `Map`;
   - сервис фрейма получается в одном приватном методе класса (`MR-35`).
3. **Класс шагов** - методы с именами действий предметной области (`createOrder`,
   `getOrderById`, `selectClientByInn`). Тело метода - это:
   - подготовка того, что отличает этот вызов: путь, тело, SQL;
   - ОДИН вызов общего класса технологии (или фрейма, если общего класса в плане нет);
   - `return` валидируемого объекта.
   Обычно это 1-5 строк. Если метод шага получился длиннее 15 строк - ты собираешь запрос
   руками, а это работа общего класса.
4. **Общего класса технологии в плане нет** -> класс шагов вызывает фрейм напрямую, как в
   документации. Свой общий класс «по ходу» НЕ создавай: это решение архитектурного плана.
   Видишь, что два и более класса шагов собирают запрос одинаково, - запиши во «Входящие»
   карты: «нужен общий класс технологии <tech>: одинаковая сборка запроса в <классы>».
5. Тест-класс вызывает методы класса шагов и проверяет результат через `.should(...)`.

**Как класс шагов получает общий класс технологии.** Полем, созданным один раз:
```java
public class OrderSteps {
    private final RestRequests restRequests = new RestRequests();

    public ValidatableResponseWrapper createOrder(OrderRequest body) {
        return restRequests.post(ORDERS_PATH, body);
    }

    public ValidatableResponseWrapper getOrder(String orderId) {
        return restRequests.get(ORDERS_PATH + "/" + orderId);
    }
}
```
Если документация фрейма показывает другой способ (внедрение, `Environment`) - делай как
в документации. Наследование ради доступа (`OrderSteps extends RestRequests`) - нельзя.

**Нельзя / нужно.**
```java
// НЕЛЬЗЯ: 10 методов с одинаковой механикой, отличаются только адресом
public ValidatableResponseWrapper createOrder(OrderRequest body) {
    RestService rest = Environment.getForCurrentThread().getService(RestService.class);
    return rest.client(ALIAS).request()
            .header("Content-Type", "application/json")
            .header("X-Request-Id", UUID.randomUUID().toString())
            .body(body)
            .post("/orders");
}
public ValidatableResponseWrapper createClient(ClientRequest body) {
    RestService rest = Environment.getForCurrentThread().getService(RestService.class);
    return rest.client(ALIAS).request()
            .header("Content-Type", "application/json")
            .header("X-Request-Id", UUID.randomUUID().toString())
            .body(body)
            .post("/clients");
}
// ... и так ещё 8 раз

// НУЖНО: механика один раз в общем классе технологии
public class RestRequests {
    public ValidatableResponseWrapper post(String path, Object body) {
        return restService().client(ALIAS).request()
                .header(...)                 // общие заголовки - один раз здесь
                .body(body)
                .post(path);
    }
    ...
    private RestService restService() {
        return Environment.getForCurrentThread().getService(RestService.class);
    }
}
// а в классах шагов - только действие предметной области
public ValidatableResponseWrapper createOrder(OrderRequest body) {
    return restRequests.post(ORDERS_PATH, body);
}
```
(Имена методов фрейма в примере условные - настоящие бери из конспекта `D-<tech>-n`.)

**ЗАПРЕЩЕНО (каждый пункт - нарушение, ревью вернёт юнит):**
- **Вложенные и внутренние классы.** Нельзя объявлять класс внутри класса: `static class`,
  `class` внутри класса, `record` и `enum` внутри класса шагов, анонимные классы вместо
  лямбды. Нужен отдельный класс - он есть в архитектурном плане отдельным файлом; нет в
  плане - он не нужен. Исключение одно: статический вложенный `Builder` по `MR-34`, когда в
  проекте нет Lombok.
- **Обёртка над обёрткой.** Класс, который только передаёт вызов в другой свой класс
  (`OrderService.create()` -> `OrderSteps.create()` -> `RestRequests.post()`). Каждый
  уровень должен делать свою работу; уровень, который просто пробрасывает вызов, удаляется.
- **Четвёртый уровень.** Никаких `*Service`, `*Facade`, `*Manager`, `*Executor`,
  `*Processor`, `*Handler` между тестом и шагами или между шагами и общим классом.
- **Общий класс технологии с предметной областью.** В `RestRequests` нет методов
  `createOrder`, нет эндпоинтов `/orders`, нет проверок. Только механика.
- **Несколько общих классов на одну технологию.** Один общий класс на технологию (на одно
  подключение). Не `RestRequests` + `RestRequestsV2` + `AuthorizedRestRequests`.
- **Абстрактные классы и наследование ради общего кода.** `abstract class BaseSteps` с
  методами запросов, `OrderSteps extends BaseSteps` - нельзя. Общее - в общем классе
  технологии, подключённом полем. (Базовый тест-класс по `MR-46` - не про это, он
  разрешён.)
- **Интерфейс с одной реализацией.** `interface OrderSteps` + `class OrderStepsImpl` - нельзя,
  если документация фрейма прямо этого не требует (во `flow` - см. `MR-44`).
- **Статические утилиты.** `static` методы запросов (`RestUtils.post(...)`) - нельзя: общий
  класс технологии - обычный класс с методами экземпляра.
- **Дубли методов в классах шагов.** Два метода, которые отличаются только константой
  (адресом, именем таблицы), а тело одинаковое на 5+ строк, - механика не вынесена.
  Вынеси механику в общий класс технологии (если он в плане) или во «Входящие».
- **Общий метод «на всё».** Один метод шагов `send(String method, String path, Object body,
  Map<String, String> headers, boolean auth, ...)` с ветвлением внутри - нельзя. Виды
  операций - отдельными методами общего класса технологии, действия - отдельными методами
  шагов.

**Исключения.**
- Стиль `flow` (`MR-44`): уровень «класс шагов» - это класс-флоу; общий класс технологии
  подключается к нему полем так же. Готовые интерфейсы технологий фрейма (`RestFlow` и
  подобные, запись `D-common-8`) - это фрейм, а не четвёртый уровень.
- Разовое обращение к шагу или фрейму прямо в теле теста - по `MR-42`.

**Как проверить (Шаг 6).**
```
grep -nE "^\s+(public |private |protected )?(static )?(final )?(class|interface|enum|record) [A-Z]" <файлы юнита>   # вложенные классы: пусто (кроме Builder по MR-34)
grep -nE "new [A-Z][A-Za-z0-9]*\(\) *\{" <файлы юнита>                                                           # анонимные классы: пусто
grep -nE "abstract class|extends [A-Z][A-Za-z0-9]*(Steps|Requests|Client|Helper|Base)\b" <файлы юнита>          # наследование ради общего кода: пусто (кроме тест-класс extends BaseTest)
grep -nE "class [A-Z][A-Za-z0-9]*(Service|Facade|Manager|Executor|Processor|Handler|Wrapper|Helper|Utils)\b" <файлы юнита>   # лишний уровень или прослойка: пусто
```
И вопрос себе по КАЖДОМУ новому методу класса шагов: «чем он отличается от соседнего
метода, кроме адреса и тела?» Ничем, а тело одинаковое на 5+ строк - механика не вынесена.

### MR-30 · К фрейму обращаются только общий класс технологии или класс шагов. Своих прослоек нет

**Правило.** Обращение к сервису или клиенту фрейма пишется ровно в одном месте:
- в общем классе технологии, если он есть в архитектурном плане;
- иначе - в классе шагов, напрямую, как в документации.
Старые прослойки (`RestHelper`, `ApiClient`, `DbUtils`, `KafkaHelper`, базовые классы с
клиентами, статические утилиты) не переносятся и не «адаптируются» - они удаляются в
`cleanup`.

**Почему.** Прослойка «чтобы было как раньше» прячет фрейм и тащит старую архитектуру
(`MR-25`). Общий класс технологии - это НЕ прослойка: он появляется в архитектурном плане по
правилам (одинаковая механика в двух и более классах шагов), строится на фрейме по
документации, содержит только механику и ничего не повторяет из старого кода.

**Как отличить разрешённое от запрещённого.**

| Что | Можно? | Почему |
|-----|--------|--------|
| `RestRequests.post(path, body)` из архитектурного плана, внутри - фрейм | да | общий класс технологии по `MR-49` |
| `OrderSteps.createOrder(body)` -> `restRequests.post(...)` | да | шаг предметной области |
| `OrderSteps.createOrder(body)` -> фрейм напрямую (общего класса в плане нет) | да | шаг обращается к фрейму сам |
| старый `RestHelper`, переписанный внутри на фрейм, с прежними методами | НЕТ | старая прослойка переехала (`MR-25`) |
| новый `ApiClient`, которого нет в плане | НЕТ | свой уровень «по ходу» |
| `BaseApiTest` с полем клиента, тесты наследуются ради доступа | НЕТ | наследование ради доступа |
| `static` метод `RestUtils.send(...)` | НЕТ | статическая утилита |
| `RestHelper.post(url, body)`, `DbUtils.select(sql)`, `KafkaHelper.send(topic, msg)` - старые или новые, вне плана | НЕТ | прослойка общего вида, повторяющая фрейм |
| `postExecutionReport(body, headers)`, `selectExecutionReportConfig()` в классе шагов | да | действие предметной области |

**Как делать.**
1. Перед тем как писать обращение к фрейму, посмотри в архитектурном плане, есть ли общий
   класс этой технологии.
2. Есть -> обращение к фрейму только внутри него. В классах шагов - вызовы его методов.
3. Нет -> обращение к фрейму в методе класса шагов, как в конспекте.
4. Старый класс-прослойку не трогай (его удалит `cleanup`) - просто переведи вызывающих на
   новые шаги. Исключение: `core`-юнит режима `in-place` (`MR-23`, `MR-28`): там старый
   класс ядра временно живёт со старыми публичными методами и фреймом внутри.

**Как проверить.** `grep -rlE "<обращение к сервису фрейма из D-<tech>-n>" <src>` - в списке
только общий класс технологии (если он в плане) или классы шагов. Тест-классы - только
разовые обращения по `MR-42`.

### MR-42 · Тест-класс чистый: только сценарий, без вспомогательных методов

**Правило.** В классе с `@Test` лежат: тестовые методы, аннотации, константы тестовых
данных, при необходимости методы подготовки и очистки (`@BeforeEach`, `@AfterEach`,
`@BeforeAll`, `@AfterAll`). Тело теста читается как сценарий: подготовил данные -> вызвал
шаг -> проверил через `.should(...)`.

**Почему.** Тест - это описание сценария. Если в тест-классе лежат приватные методы с
запросами, SQL и маппингом, логика размазывается по тестам, копируется и не
переиспользуется. Её место - класс шагов технологии или предметной области (слой и пакет -
из целевой картины `T-common`, `T-<tech>` и архитектурного плана).

**Нельзя: вспомогательные (не тестовые) методы в тест-классе**, которые:
- отправляют запросы, ходят в БД или Kafka (`postExecutionReport(...)`, `selectXxx(...)`,
  `queryTable(...)`);
- читают файлы и собирают запросы (`loadSqlFile`, `Files.readString`,
  `replaceSqlPlaceholders`), выбирают схему или алиас по условиям (`if ... return "..."`);
- маппят ответ или строку таблицы в объект (`toXxxRow(...)`, `cellValue(...)`, пачки
  `dto.setXxx(...)`), сериализуют (`JacksonHelper`, `ObjectMapper`).

**Нельзя / нужно.**
```java
// НЕЛЬЗЯ
class OrderTests extends BaseTest {
    @Test
    void whenOrderCreatedExpectStatusNew() {
        ValidatableResponseWrapper response = postOrder(body());
        response.should(<matcher кода ответа>);
    }
    private ValidatableResponseWrapper postOrder(OrderRequest body) { ... запрос ... }
    private OrderRequest body() { ... 20 сеттеров ... }
}

// НУЖНО
class OrderTests extends BaseTest {
    private final OrderSteps orderSteps = new OrderSteps();

    @Test
    void whenOrderCreatedExpectStatusNew() {
        orderSteps.createOrder(OrderData.newOrder())
                .should(<matcher кода ответа>);
    }
}
```

**Можно: обратиться к фрейму прямо в ТЕЛЕ тестового метода** - когда это разовое короткое
действие только этого теста (один вызов и проверка), и подходящего шага нет. Как только то
же действие нужно второму тесту или вызов обрастает подготовкой (чтение файла, сборка SQL,
маппинг, ветвление) - это шаг, выноси в класс шагов.

**Куда выносить.**
1. Нужный метод шага уже есть -> тест вызывает его.
2. Класс шагов есть, метода нет -> добавь метод туда (файл - в карточке или «добавлен по
   ходу», если правка механическая).
3. Класса шагов нет и его нет в карточке -> НЕ складывай логику приватными методами в
   тест-класс «временно». Это блокер юнита: пункт во «Входящие» и вопрос в карту - нужен
   `core`-подшаг, который создаст класс шагов.

Одинаковая служебная логика (загрузка SQL из файла, подстановка параметров) лежит в ОДНОМ
месте, а не копируется в каждый тест-класс.

**Как проверить.**
```
grep -nE "^\s*(private|protected|static) .*\(.*\)\s*(throws [A-Za-z, ]+)?\{" <тест-класс>   # пусто (кроме @BeforeEach/@AfterEach и подобных)
grep -cE "getForCurrentThread\(\)|restClient\(\)|dataBaseClient\(|executeSelect\(|consumerClient\(|producerClient\(" <тест-класс>   # одно и то же действие в 2+ тестах - вынеси в шаг
```

### MR-35 · Сервис фрейма получается в одном месте класса

**Правило.** Цепочка получения сервиса фрейма (`Environment.getForCurrentThread()
.getService(...)`) пишется в классе ОДИН раз - в приватном методе на каждый сервис. Все
остальные методы вызывают этот приватный метод.

**Почему.** Одинаковая цепочка в каждом методе - это дубль (`MR-39`); при изменении способа
получения сервиса придётся править десятки мест.

**Нельзя / нужно.**
```java
// НЕЛЬЗЯ: одна и та же цепочка в каждом методе
private void sendToKafka(...) {
    KafkaProducerClient producer = Environment.getForCurrentThread()
            .getService(KafkaService.class).producerClient(KAFKA_ALIAS);
    ...
}
private ConsumerRecord<String, String> receiveFromKafka(...) {
    KafkaConsumerClient<String, String> consumer = Environment.getForCurrentThread()
            .getService(KafkaService.class).consumerClient(KAFKA_ALIAS, ...);
    ...
}
// НУЖНО: один приватный метод на сервис, остальные вызывают его
private KafkaService kafkaService() {
    return Environment.getForCurrentThread().getService(KafkaService.class);
}
```

**Как делать.**
- Один приватный метод на сервис (`kafkaService()`, `restService()`, `databaseService()`),
  в конце класса (`MR-1`).
- Документация показывает другой способ получить сервис один раз (поле, параметр) - делай
  как в документации.
- Не клади результат `getForCurrentThread()` в `static`-поле: окружение привязано к потоку.
- Есть общий класс технологии (`MR-49`) - сервис получается в нём, в классах шагов
  обращений к сервису нет вообще.

**Исключения.** Клиенты с РАЗНЫМИ алиасами (`producerClient(ALIAS_A)` и
`producerClient(ALIAS_B)`) - разные клиенты, их можно получать в разных местах; сам сервис
всё равно берётся через тот же один метод. Такой приватный метод - не обёртка и `MR-30` не
нарушает; отдельный класс-хелпер ради этого создавать нельзя.

**Как проверить.** `grep -c "getForCurrentThread()" <файл>` - не больше, чем разных
сервисов в файле.

### MR-38 · Класс делает одно дело

**Правило.** Один класс - одна технология и одна предметная область (или одна механика -
для общего класса технологии). Не больше 500 строк. Нет классов `Utils` / `Helper` /
`Common` с несвязанными методами.

**Почему.** Класс «обо всём» невозможно прочитать целиком и нельзя переиспользовать по
частям; слабая модель в нём теряется.

**Как делать.**
- Новый код так не пиши: каждый новый класс - строка в разделе 3 архитектурного плана с
  ответственностью в одно предложение.
- Сценарию нужны две технологии -> тест вызывает шаги двух классов, а не один класс
  «всё сразу».
- Существующий большой класс в юните миграции сам НЕ дели - это работа `arch`-юнита:
  запиши во «Входящие».

**Исключения.** Класс-флоу (`MR-44`) ведёт один сценарий и может работать с несколькими
технологиями этого сценария.

**Как проверить.** `wc -l <файл>` - не больше 500; импорты двух технологий (REST и БД, БД
и Kafka) в одном классе шагов - нарушение.

### MR-44 · Стиль шагов `flow`: тест - цепочка шагов FlowRunner, логика - в классе-флоу

**Правило.** Действует, только если в паспорте карты «Стиль шагов: flow». Тест - цепочка
именованных шагов FlowRunner; действия, проверки и состояние между шагами - в классе-флоу.
Точные имена классов и методов - из записи `D-common-7` конспекта. Стиль в паспорте
`steps` - FlowRunner не вводи, пиши обычные классы шагов.

**Схема.**
```java
// тест: только названия шагов и вызовы методов флоу
FlowRunner.flowRunnerFor(OrderFlow.class)
        .step("Создаём заказ", f -> f.createOrder(body))
        .step("Проверяем ответ", OrderFlow::validateResponse)
        .step("Проверяем запись в БД", OrderFlow::validateOrderRow)
        .run();

// класс-флоу: клиенты фрейма, действия, проверки, состояние между шагами
public class OrderFlow implements Flow, RestFlow, DataBaseFlow {
    private final RestRequests restRequests = new RestRequests();   // если общий класс есть в плане
    private ValidatableResponseWrapper response;                      // нужно следующим шагам
    ...
    public void createOrder(OrderRequest body) { response = restRequests.post(ORDERS_PATH, body); }
    public void validateResponse() { response.should(<matchers>); }
}
```

**Как делать.**
1. Старый тест с шагами (`@Step`, `Allure.step`, комментарии «Шаг 1») переписывается в
   цепочку: один старый шаг - один `.step(...)`, название шага и порядок сохраняются.
2. В шаге - вызов ОДНОГО метода флоу (ссылка на метод или короткая лямбда с параметрами).
   Лямбда длиннее 3 строк, условие или цикл в ней - это логика: вынеси в метод флоу.
3. Метод-действие флоу может ничего не возвращать и сохранять валидируемый объект в поле,
   а проверка через `.should(...)` лежит в методе-проверке флоу - это не нарушение `MR-41`
   и `MR-42`. DTO ответа по-прежнему не создаются.
4. **Флоу собирается из готового.** Сначала смотри, что дают готовые интерфейсы технологий
   фрейма, подключённые через `implements` (запись `D-common-8`: готовые шаги для БД,
   REST, запрос из шаблона SQL и так далее), и вызывай их. Свой метод или класс, который
   делает то же самое (свой «выполнить select», своя загрузка SQL из файла и подстановка
   параметров), не пиши.
5. Логика, которая нужна нескольким флоу, пишется один раз - в своей подключаемой части
   (интерфейс или класс шагов из архитектурного плана), и флоу её подключают. Копировать
   методы из флоу во флоу нельзя.
6. Какой флоу за что отвечает - в архитектурном плане; новый флоу «по ходу» не заводи,
   если подходящий есть в плане.

**Нельзя.** Один флоу на весь проект; отдельный флоу на каждый тест; два флоу с
одинаковыми методами; лямбда-шаг с логикой; вложенные классы во флоу (`MR-49`).

**Исключения.** Класс-флоу ведёт один сценарий и может работать с несколькими технологиями -
это не нарушение `MR-38`.
