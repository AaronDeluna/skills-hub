# Правила MR: структура класса, импорты, имена

Правила этого файла: `MR-1`, `MR-2`, `MR-3`, `MR-4`, `MR-5`, `MR-6`, `MR-7`, `MR-8`,
`MR-28`, `MR-40`, `MR-45`.

Прочитай перед тем, как писать или менять любой класс.

---

### MR-1 · Порядок членов класса

**Правило.** Сверху вниз:
1. константы (`static final`);
2. статические поля;
3. поля экземпляра;
4. конструкторы;
5. публичные методы;
6. `protected` и package-private методы;
7. **приватные методы - в самом конце класса.**

**Почему.** Класс читается сверху: сначала что он хранит, потом что умеет снаружи, потом
детали. Приватный метод посреди публичных рвёт чтение.

**Как делать.** Добавляешь приватный метод - ставь его в конец класса, даже если в классе
был другой порядок и ты добавляешь всего 1-2 метода. Вложенных классов нет (`MR-49`);
единственное исключение - `Builder` по `MR-34`, он идёт после всех методов.

**Нельзя.**
```java
public class OrderSteps {
    public ValidatableResponseWrapper createOrder(...) { ... }
    private RestService restService() { ... }        // НЕЛЬЗЯ: приватный между публичными
    public ValidatableResponseWrapper getOrder(...) { ... }
}
```

**Как проверить.** Глазами по каждому изменённому классу: после первого `private`-метода
не должно быть ни одного `public`.

---

### MR-2 · Поля приватные

**Правило.** Новые поля - `private`, по возможности `final`. Видимость существующих членов
не расширяй без необходимости.

**Почему.** Открытое поле - это доступ к состоянию в обход методов класса; его начинают
менять снаружи.

**Как делать.** `private final OrderSteps orderSteps = new OrderSteps();`. Нужно значение
снаружи - метод, а не открытое поле.

---

### MR-3 · В мигрируемый класс не добавляется новая ответственность

**Правило.** Не складывай в мигрируемый класс то, чем он раньше не занимался. Новый класс
создавай только если он есть в таблице «Файлы юнита» карточки (или в архитектурном плане
и добавлен в карточку по правилу «добавлено по ходу»).

**Почему.** «Заодно положу сюда» - главный путь к классам на 2000 строк.

**Как делать.** Код не подходит под ответственность класса -> его место в другом классе
плана; такого класса нет -> «Входящие».

---

### MR-4 · Классы - через `import`, а не полным именем в коде

**Правило.** Не пиши полное имя класса с пакетом прямо в коде - добавь импорт.

**Нельзя / нужно.**
```java
// НЕЛЬЗЯ
org.apache.kafka.common.header.Header header = record.headers().lastHeader("id");
// НУЖНО
import org.apache.kafka.common.header.Header;
...
Header header = record.headers().lastHeader("id");
```

**Исключения.** Конфликт двух классов с одинаковым именем в одном файле - тогда один из них
полным именем.

**Как проверить.**
```
grep -nE "^[^/*]*[^A-Za-z0-9_.\"](org|com|ru|io|java)\.[a-z0-9_]+\.[a-z0-9_.]+\.[A-Z]" <файлы юнита> | grep -v "^[0-9]*:\(import\|package\)"   # пусто
```

---

### MR-5 · Чистые импорты

**Правило.** Импорты, которые после миграции не используются, удаляются. Импорт со
звёздочкой (`import x.y.*;`) не добавляй, если в проекте так не принято.

**Как делать.** После правки файла пройди по списку импортов: для каждого - есть ли имя
класса в теле файла (`grep -c "<ИмяКласса>" <файл>` больше 1).

---

### MR-6 · Старых импортов не остаётся

**Правило.** В файле юнита после миграции нет импортов, которые карточка велит заменить.
Grep из «Критериев готовности» карточки пуст.

**Как проверить.** Выполни grep из «Критериев готовности» по файлам юнита - вывод пустой.

---

### MR-7 · Не переименовывай

**Правило.** Имена классов, методов, тестов, пакетов остаются прежними, если
переименование не записано в шагах карточки.

**Почему.** Переименование ломает ссылки в файлах вне юнита и историю отчётов.

**Исключения.** Имя нарушает `MR-45` и ты этот метод пишешь или переписываешь - переименуй
и поправь все вызовы (`grep -rn "<старое имя>(" <src>`).

---

### MR-8 · Нет своего кода в пакете фрейма

**Правило.** Не объявляй свои классы в `package ru.sber.qa...`. Импортировать `ru.sber.qa` -
нормально, объявлять там своё - нельзя.

**Как проверить.** `grep -rn "^package ru\.sber\.qa" <src>` - пусто.

---

### MR-28 · В `core`-подшаге режима `in-place` публичные методы не меняются

**Правило.** Имена, параметры, возвращаемые типы и исключения публичных методов ядра
остаются как были - меняется только тело.

**Почему.** Код, который вызывает ядро, не в твоём юните; поменяешь сигнатуру - он
перестанет компилироваться.

**Исключения.** Карточка с пометкой «сигнатура меняется, вызывающие файлы включены».

---

### MR-40 · Имена говорят, что это

**Правило.** Никаких `tmp`, `data1`, `obj`, `res`, `list2`, имён из одной буквы (кроме
счётчика цикла `i`). Метод называется по тому, что он делает: глагол + предмет
(`createOrder`, `selectClientByInn`).

**Нельзя / нужно.** `String s = ...` -> `String orderId = ...`; `void doIt()` ->
`void cancelOrder()`.

---

### MR-45 · Имена - по соглашениям Java, без нижнего подчёркивания

**Правило.** Это Java, а не JavaScript и не Python.

| Что | Как писать | Правильно | Неправильно |
|-----|------------|-----------|-------------|
| метод (в том числе тестовый) | с маленькой буквы, каждое следующее слово с большой | `createOrder`, `whenOrderCreatedExpectStatusNew` | `create_order`, `Create_Order`, `when_order_created_expect_status_new`, `test_create_order` |
| переменная, параметр, поле | так же, с маленькой буквы | `orderId`, `responseWrapper` | `order_id`, `response_wrapper`, `OrderId` |
| класс, интерфейс, enum | каждое слово с большой буквы | `OrderFlow`, `OrderRequest` | `order_flow`, `Order_Flow`, `orderFlow` |
| константа (`static final`) | все буквы большие, слова через `_` | `DEFAULT_TIMEOUT` | `defaultTimeout`, `Default_Timeout` |
| пакет | маленькими буквами, без `_` | `ru.sber.qa.orders` | `ru.sber.qa.order_steps` |

Нижнее подчёркивание допустимо ТОЛЬКО в константах.

**Как делать.** Правило действует на всё, что ты создаёшь или переписываешь в юните,
включая имена тестовых методов, - даже если в старом коде было иначе. Тестовый метод,
который ты не менял, не переименовывай. Переименовал - поправь все вызовы
(`grep -rn "<старое имя>(" <src>`).

**Как проверить.**
```
grep -nE "(^|[ .(])[a-z][A-Za-z0-9]*_[A-Za-z0-9_]*( *\(| *=| *;|,|\))" <файлы юнита>   # смотри только свои строки: пусто
```
