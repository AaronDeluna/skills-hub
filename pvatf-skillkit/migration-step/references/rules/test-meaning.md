# Правила MR: смысл тестов

Правила этого файла: `MR-9`, `MR-10`, `MR-11`.

Эти правила главнее всех остальных. Миграция меняет СПОСОБ записи теста, а не то, что тест
проверяет. Прочитай перед любым `usage`- и `fix`-подшагом.

---

### MR-9 · Тест проверяет то же, что и раньше

**Правило.** После миграции у теста те же шаги, те же проверки, те же тестовые данные, те же
названия и описания для отчёта (`@DisplayName`, `@Description`, имя метода, теги).

**Почему.** Цель миграции - тот же набор проверок на новом фрейме. Тест, который после
миграции проверяет другое, - это потерянная проверка, даже если он зелёный.

**Как делать.**
1. Перед правкой теста выпиши себе: какие действия он делает, с какими данными, что
   проверяет (каждое поле и ожидаемое значение).
2. После правки сверь по этому списку: ничего не пропало, ничего не добавилось, значения
   те же.

**Нельзя.** Поменять ожидаемое значение «потому что так теперь возвращает»; убрать шаг,
«потому что он лишний»; объединить два теста в один; поменять тестовые данные.

---

### MR-10 · Тесты не пропадают

**Правило.** Число тестов после миграции не меньше, чем до.

**Нельзя.** Удалять тестовые методы; ставить `@Disabled`, `@Ignore`, `enabled = false`;
комментировать тело теста; делать тест пустым.

**Как проверить.**
```
grep -c "@Test" <файл>   # до и после правки: после >= до
```
Число до правки записано в карточке («Тестов в файлах юнита сейчас»).

---

### MR-11 · Проверки не ослабляются

**Правило.** Каждая старая проверка остаётся не слабее, чем была.

**Нельзя.**
- убрать проверку;
- заменить точное сравнение на более слабое (`равно` -> `содержит`, `равно 53` -> `не пусто`,
  проверка поля -> проверка только кода ответа);
- обернуть проверку в `try/catch` с пустым `catch`, чтобы тест прошёл;
- перевести `.should(...)` в `.shouldSoft(...)`, если раньше проверка была жёсткой.

**Исключения.** Нет.
