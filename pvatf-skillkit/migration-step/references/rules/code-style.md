# Правила MR: как писать код (жёстко, без исключений по вкусу)

Правила этого файла: `MR-33`, `MR-34`, `MR-37`, `MR-39`, `MR-19`.

Прочитай перед тем, как писать код. Правила действуют на весь файл юнита, а не только на
твои строки.

---

### MR-33 · `var` запрещён. Только явные типы

**Правило.** Нигде: ни в локальных переменных, ни в `for`, ни в `try`, ни в лямбдах.

**Нельзя / нужно.**
```java
// НЕЛЬЗЯ
var entity = new EridProductExecEntity();
for (var entry : headers.entrySet()) { ... }
// НУЖНО
EridProductExecEntity entity = ...;
for (Map.Entry<String, String> entry : headers.entrySet()) { ... }
```

**Как делать.** Тип не знаешь - посмотри сигнатуру метода справа или в документации, а не
ставь `var`. В файле юнита уже есть `var` - замени на явный тип.

**Как проверить.**
```
grep -nE "(^|[^A-Za-z0-9_])var +[A-Za-z_][A-Za-z0-9_]* *(=|:)" <файлы юнита>   # пусто
```

### MR-34 · Объект с несколькими полями создаётся билдером, а не пачкой сеттеров

**Правило.** Нельзя: `new Foo()` и следом 4 и более вызовов `foo.setXxx(...)`.

**Нельзя / нужно.**
```java
// НЕЛЬЗЯ
EridProductExecEntity entity = new EridProductExecEntity();
entity.setId(...);
entity.setProductId(...);
entity.setDebtorId(...);
// ... ещё 25 строк
return entity;
// НУЖНО
return EridProductExecEntity.builder()
        .id(...)
        .productId(...)
        .debtorId(...)
        .build();
```

**Откуда взять билдер.**
1. У класса он уже есть -> используй.
2. Класс свой (лежит в проекте), билдера нет, в проекте есть Lombok (`grep lombok` в файлах
   сборки) -> аннотация `@Builder` на класс.
3. Класс свой, Lombok нет -> статический вложенный класс `Builder` с методами по полям и
   `build()` (единственный разрешённый вложенный класс, `MR-49`).
Файл класса допиши в карточку с пометкой `добавлен по ходу`.

**Исключения.** Класс чужой (из библиотеки) и билдера у него нет -> сеттеры остаются.

**Как проверить.** `grep -cE "\.set[A-Z][A-Za-z0-9]*\(" <файл>` - 4 и больше подряд на один
объект - переделай на билдер.

### MR-37 · Метод делает одно дело и читается с экрана

**Правило.** Метод не длиннее 40 строк; вложенность (`if` / `for` / `try` друг в друге) не
глубже 3 уровней. Отправка, ожидание, разбор и проверка не смешиваются в одном методе, если
читаются как отдельные шаги.

**Как делать.** Длиннее или глубже - вынеси части в приватные методы ЭТОГО ЖЕ класса с
говорящими именами (в конец класса, `MR-1`). Новый класс ради этого не создавай. Метод шага
по `MR-49` и так короткий (1-5 строк); длинный метод шага - признак, что ты собираешь
запрос руками.

### MR-39 · Без дублей и мёртвого кода

**Правило.**
- Один и тот же блок из 5 и более строк в двух местах - вынеси.
- Приватные методы, поля, параметры и переменные, которые никто не использует, - удали.

**Куда выносить дубль.**
1. Дубль внутри одного класса -> приватный метод этого класса.
2. Дубль механики технологии в разных классах шагов (сборка запроса, заголовки, получение
   клиента) -> общий класс технологии из архитектурного плана (`MR-49`); его нет в плане ->
   «Входящие».
3. Дубль в разных тест-классах -> метод класса шагов (`MR-42`).
НЕ выносить в: статическую утилиту, базовый класс с методами, вложенный класс, новый класс
вне плана.

**Как проверить.** По каждому мёртвому кандидату: `grep -rn "<имя>" <src>` - кроме
объявления нет ни одной строки -> удали.

### MR-19 · Кодстайл проекта

**Правило.** Отступы, длина строки, фигурные скобки - как в этом файле и в checkstyle
проекта. Не добавляй `final` к параметрам и переменным, если в проекте так не делают, и
наоборот. Про `var` - отдельное жёсткое правило `MR-33`.
