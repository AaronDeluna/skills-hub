# Проверка миграции на PVATF (migration-review)

Миграцию делали маленькими кусками, в разных чатах. Ты смотришь на результат ЦЕЛИКОМ и
отвечаешь на один вопрос: проект действительно чисто переведён на фрейм или где-то осталось
старое и нарушены правила? **Ты ничего не исправляешь и код проекта не меняешь.** Ты
находишь проблемы, записываешь отчёт и заводишь на них юниты исправления. Исправляет потом
`migration-step`, в других чатах. После исправлений проверка запускается снова - и так, пока
не станет чисто.

## Работай по шагам

1. Занеси Шаги 1-7 в todo.
2. Иди по порядку. Результат каждого шага СРАЗУ дописывай в файл отчёта - чат может
   оборваться.
3. Сбился - см. «Если потерял нить».

## Железные правила

1. **Только чтение.** Код проекта, файлы сборки и конфиги не меняешь. Пишешь только в
   `.gigacode/data/migration/`: отчёт, карточки новых юнитов, таблицу юнитов и шапку карты.
2. **Проверяешь по чек-листу, а не по вкусу.** Находка - это нарушение конкретного пункта
   (`V1`..`V24` из `references/review-subagent.md` или `P1`..`P10` из Шага 3) с файлом и
   номером строки. Нет пункта или нет строки - это не находка.
3. **Файлы читают сабагенты, не ты.** Исходники целиком в свой контекст не открывай. Ты
   считаешь командами и собираешь таблицы от сабагентов ревью.
4. **Технологии `keep` не проверяются на миграцию.** У технологии в паспорте карты решение
   `keep` - её старый код, зависимости и конфиги остались законно. Старое по ней находкой
   не считай. Правила кода (`V1`, `V2`, `V10`..`V16`) к ней применимы только если файл
   менялся при миграции.
5. **API фрейма не изучаешь.** Не открывай `.jar`, не лазь в `~/.m2`, не вызывай MCP. Как
   должно быть - записано в карте (блоки `T`, таблицы `G` и `L`); если карты нет - тебе
   хватает чек-листа, см. режим «без карты».
8. **Карта и служебные файлы миграции не обязательны.** Нет карты - это не причина
   отказаться от проверки.
6. **Не вызывай другие скиллы миграции,** если пользователь прямо не попросил.
7. **Пиши на русском, короткий дефис `-`.** ID и статусы - латиницей.
9. **Сабагенты только читают и отвечают - код они не пишут.** Сабагент работает на
   слабой модели. Он нужен, чтобы быстро что-то узнать: прочитать документацию, найти и
   посчитать в проекте, проверить файлы по чек-листу - и вернуть ответ текстом. ЗАПРЕЩЕНО
   поручать сабагенту: писать или править код, тесты, файлы сборки и конфиги; создавать и
   удалять файлы; выполнять юнит или его часть («перепиши эти три теста», «исправь
   находки»); делать коммиты; запускать сборку и тесты. Всё это делаешь только ты сам, в
   основном чате. Виды сабагентов и их промпты заданы в этом скилле - своих не придумывай
   и готовые промпты заданиями на правку не дополняй.

## Шаг 1 - Открой карту и проверь вход

Прочитай из `.gigacode/data/migration/MIGRATION-MAP.md`: шапку, «1. Паспорт проекта»
(команды, таблица технологий, ветки), «2. Что мигрируем» (таблицы `G`, `L`, блоки `T`),
«4. Юниты работ».

Ворота:
- карты нет (папки `.gigacode/data/migration/` нет или в ней нет `MIGRATION-MAP.md`) -> это
  НЕ остановка: работай в режиме **«без карты»**, см. раздел ниже, и возвращайся на Шаг 2.
- карта есть, но `map_status` не `approved` -> **СТОП**: карта ещё строится, проверять рано.
- есть юниты `todo` / `in-progress` / `blocked` (кроме тех, что ждут из-за `scope: core`):
  - пользователь сам попросил проверить сейчас -> проверяй, но только технологии, у которых
    все юниты `cleanup` в статусе `done`; в отчёте напиши «проверка частичная» и перечисли
    непроверенные технологии;
  - иначе -> **СТОП**: сначала доделать юниты.
- `scope: core` -> проверяется только ядро: пункты `P1`, `P2`, `P3` Шага 3 пропусти (тесты
  и legacy ещё не переводились), в отчёте напиши «проверка для scope core».

Определи номер круга: `review_round` в шапке карты + 1 (поля нет - это круг 1). Создай файл
отчёта `.gigacode/data/migration/MIGRATION-REVIEW.md` по шаблону из
`references/report-template.md`. Если файл уже есть - старый круг не стирай, допиши новый
раздел «Круг <n>» в конец.

## Режим «без карты» (служебных файлов миграции нет)

Проверку можно запустить на любом проекте, который уже переведён на PVATF, даже если
служебную папку миграции удалили или её никогда не было. Карта для проверки не обязательна:
всё нужное ты собираешь из самого проекта.

1. Создай папку: `mkdir -p .gigacode/data/migration/units`.
2. **Паспорт собери сам** (запиши в начало отчёта, раздел «Паспорт для проверки»):
   - сборка и команда компиляции: есть `pom.xml` -> `./mvnw -q -DskipTests test-compile`
     (нет wrapper - `mvn ...`); есть `build.gradle(.kts)` -> `./gradlew compileTestJava -x test`
     (нет wrapper - `gradle ...`);
   - каталоги исходников: `find . -type d -path "*src*" -name java -not -path "*/target/*" -not -path "*/build/*"`;
   - текущая ветка: `git branch --show-current`; основная ветка:
     `git symbolic-ref --short refs/remotes/origin/HEAD 2>/dev/null` (пусто - `master` или
     `main`, какая есть в `git branch -a`).
3. **Что считать старым.** Списка `G` и `L` у тебя нет. Возьми его так:
   - пользователь в запросе назвал старые библиотеки или пакеты -> это и есть список;
   - не назвал -> используй типовой список библиотек, которые фрейм заменяет:
     `io.restassured`, `org.assertj`, `org.hamcrest`, `org.skyscreamer.jsonassert`,
     `net.javacrumbs.jsonunit`, `org.awaitility`, `org.sql2o`, `org.springframework.jdbc`,
     `com.github.tomakehurst.wiremock`. Находки по типовому списку помечай в отчёте
     `предположительно старое`: возможно, что-то оставлено намеренно.
4. **Какие проверки меняются:**
   - `P1` - по списку из п.3;
   - `P2`, `P3` - пропусти, в отчёте напиши `не проверялось: нет карты, список legacy неизвестен`.
     Вместо них выполни: `grep -rn "<artifactId библиотеки из п.3>" --include=pom.xml
     --include=*.gradle --include=*.kts --include=*.toml .` - зависимость осталась в сборке,
     а импортов её пакетов в исходниках нет -> находка `P2`;
   - `P5` - сравнивать не с чем: проверь только отключённые тесты;
   - `P7` - версию Java найди командой:
     `grep -rnE "maven\.compiler\.(source|target|release)|<java\.version>|sourceCompatibility|targetCompatibility|languageVersion|jvmTarget" --include=pom.xml --include=*.gradle --include=*.kts --include=gradle.properties .`;
   - технологий `keep` ты не знаешь: считай, что мигрировалось всё. В итоговой сводке
     напиши: «Если что-то оставлено на старой реализации намеренно - скажите, уберу эти
     находки».
5. **Список файлов (Шаг 2):** текущая ветка не основная -> `git diff --name-only` между
   основной веткой и текущей, как в Шаге 2. Ты на основной ветке или diff пуст -> все
   исходники: `find <каталоги исходников> \( -name "*.java" -o -name "*.kt" \)`. Номер
   круга - 1 (или следующий, если `MIGRATION-REVIEW.md` уже есть).
6. **Если нужны юниты исправления (Шаг 6)**, сначала создай минимальную карту
   `.gigacode/data/migration/MIGRATION-MAP.md`, чтобы их мог выполнять `migration-step`.
   Шаблон - в `references/fix-unit-template.md`, раздел «Минимальная карта». В карточках
   `fix` в поле «Целевая картина» пиши `-`.

Всё остальное (Шаги 3-7, чек-лист, отчёт) - как обычно.

## Шаг 2 - Собери список проверяемых файлов

```
git diff --name-only <основная ветка из паспорта>...<ветка миграции из паспорта> -- '*.java' '*.kt' | while read f; do [ -f "$f" ] && echo "$f"; done
```

Это файлы, которые миграция создала или изменила и которые существуют сейчас. Запиши их
число в отчёт. Команда не сработала (нет ветки) -> возьми файлы из таблиц «Файлы юнита»
карточек `core`, `usage`, `arch`, `review`, `fix` (действие `создать` / `изменить`).

Круг 2 и дальше: проверяй только файлы из юнитов `fix` и `arch` прошлого круга плюс
проектные проверки Шага 3 целиком.

## Шаг 3 - Проектные проверки командами (P1-P10)

Каталоги исходников и файлы сборки - из паспорта. Из вывода бери числа и первые 30 строк,
сырой вывод целиком в отчёт не копируй. Каталоги `target/`, `build/` исключай.

| № | Что проверяем | Как | Находка, если |
|---|---------------|-----|---------------|
| P1 | Старые импорты | Для каждой строки `G` с решением «заменить»: `grep -rln "import <старый пакет>" --include=*.java --include=*.kt <src> \| grep -v "/target/\\|/build/"` | список не пуст (кроме технологий `keep`) |
| P2 | Legacy не удалено | Для каждой строки `L`: класс/файл - `find . -name "<Имя>.java" -not -path "*/target/*"`; зависимость/плагин - `grep -rn "<artifactId>" --include=pom.xml --include=*.gradle --include=*.kts --include=*.toml --include=gradle.properties .` | что-то нашлось |
| P3 | Ссылки на удалённое | Для каждого класса из `L` и из «Чего НЕ будет» блоков `T`: `grep -rln "\\b<Имя>\\b" --include=*.java --include=*.kt <src>` | список не пуст |
| P4 | Компиляция | команда компиляции из паспорта | не компилируется |
| P5 | Тесты не пропали | `grep -rE "^\\s*@Test\\b" --include=*.java --include=*.kt <src> \| wc -l` и сравни с суммой «Тестов» из `inventory/*.md`; `grep -rnE "@Disabled\|@Ignore\|enabled *= *false" --include=*.java --include=*.kt <src>` | тестов стало меньше; появились отключённые |
| P6 | Конфигурация фрейма в `config` | `grep -rlE "class [A-Za-z0-9_]*(EnvironmentConfiguration\|ServiceConfiguration)" --include=*.java <src>` | файл лежит не в каталоге `config` |
| P7 | Версия Java | команда из паспорта (grep версии в сборке) | где-то осталась версия ниже 17 |
| P8 | Хвосты в рабочем дереве | `git status --short` | есть незакоммиченные изменения |
| P9 | Классы вне архитектурного плана | `git diff --name-only --diff-filter=A <основная ветка>...<ветка миграции>` - для каждого нового исходного файла ищи имя класса в `ARCHITECTURE.md` (`grep -c "<ИмяКласса>"`). Файла плана нет - проверку пропусти, в отчёте `плана нет` | новый класс не записан ни в разделе 3, ни в разделе 5 плана; в разделе 5 больше 5 классов (план не продуман - покажи список человеку) |
| P10 | Старое логирование | три команды под таблицей | осталась конфигурация или зависимость другого логгера (logback, log4j); нет файла `simplelogger.properties` в ресурсах тестов |

Команды для `P10`:
```
find . \( -name "logback*.xml" -o -name "log4j*.xml" -o -name "log4j*.properties" \) -not -path "*/target/*" -not -path "*/build/*"
grep -rnE "logback|log4j|slf4j-(log4j12|reload4j)" --include=pom.xml --include=*.gradle --include=*.gradle.kts .
find . -name simplelogger.properties -not -path "*/target/*" -not -path "*/build/*"
```

Быстрые счётчики по правилам кода (только по файлам из Шага 2; нужны, чтобы сверить потом с
находками сабагентов):

```
grep -cE "(^|[^A-Za-z0-9_])var +[A-Za-z_][A-Za-z0-9_]* *(=|:)" <файл>
grep -cE "Assertions\.|assert(Equals|True|False|NotNull|Null|That|All)\(|SoftAssertions" <файл>
grep -cE "\.as\([A-Z][A-Za-z0-9_]*\.class\)|readValue\(|fromJson\(" <файл>
grep -c "getForCurrentThread()" <файл>
grep -cE "Thread\.sleep|TODO|FIXME" <файл>
grep -cE "\b(log|logger|LOG|LOGGER)\.(info|debug|trace|warn|error)\(|System\.(out|err)\.print|\.log\(\)\.(all|body|headers|ifValidationFails)|(Request|Response)LoggingFilter|\.prettyPrint\(|\.prettyPeek\(|\.peek\(" <файл>   # ручное логирование (V21)
grep -cE "ConfigFactory\.create|new Properties\(\)|getResourceAsStream\(|ResourceBundle\.getBundle|System\.(getProperty|getenv)\(|@Value\(|PropertiesLoader|ConfigReader|PropertyReader" <файл>   # своё чтение настроек (V24)
# только для файлов с @Test: вспомогательные методы в тест-классе (должно быть 0)
grep -cE "^\s*(private|protected|static) .*\(.*\)\s*(throws [A-Za-z, ]+)?\{" <тест-класс>
# обращения к фрейму в тест-классе: само по себе не находка (в теле теста разово - можно); находка, если счётчик вспомогательных методов не ноль или одно действие повторяется в нескольких тестах
grep -cE "getForCurrentThread\(\)|restClient\(\)|dataBaseClient\(|executeSelect\(|consumerClient\(|producerClient\(" <тест-класс>
```

Запиши в отчёт таблицу «файл - счётчики» только для файлов, где хоть один счётчик не ноль.

## Шаг 4 - Ревью кода сабагентами

Прочитай `references/review-subagent.md`.

1. Раздели файлы из Шага 2 на группы не больше 8 файлов (по пакетам, чтобы связанные классы
   были вместе).
2. Запускай сабагентов ревью волнами: не больше 3 одновременно, промпт дословно.
3. Таблицу находок каждого сабагента СРАЗУ дописывай в отчёт и отмечай группу как
   проверенную в разделе «Проверенные группы».
4. **Остановка по размеру.** За один чат - не больше 6 групп (48 файлов). Файлов больше ->
   остановись после шестой группы, в отчёте поставь `состояние: проверка не закончена`,
   скажи: «Открой новый чат и напиши: продолжи проверку миграции». В новом чате продолжай с
   первой непроверенной группы; Шаг 3 повторно не выполняй.
5. Инструмента сабагентов нет физически -> пройди чек-лист `V1`..`V24` сам, по одному
   файлу, не больше 10 файлов за чат; запиши это в отчёт.

Сверка: если счётчик из Шага 3 по файлу не ноль, а сабагент по этому файлу ничего не
нашёл по соответствующему правилу (`V1`, `V4`, `V19`, `V6`, `V9`/`V18`, `V21`, `V20`) - добавь находку
сам по строке из grep.

## Шаг 5 - Вердикт

Посчитай находки и запиши в отчёт сводку: по каждому пункту `P` и `V` - сколько находок.

- находок нет (ни `P`, ни `V`) -> вердикт `clean`;
- находки есть -> вердикт `findings`.

Не занижай: «мелочь» и «и так сойдёт» - тоже находка, если нарушен пункт чек-листа.

## Шаг 6 - Заведи юниты исправления

Только при вердикте `findings`. Прочитай `references/fix-unit-template.md`.

1. Сгруппируй находки в юниты. Сложная логика уже мигрирована, поэтому юниты исправления
   среднего размера - крупнее, чем юниты миграции:
   - находки `просто` и находки `P1`, `P2`, `P3`, `P6`, `P7` -> юниты типа `fix`: до 10 файлов
     и до 30 находок на юнит; группируй по технологии, внутри неё - по пакету;
   - каждая находка `крупно` (разделить класс, убрать прослойку, перенести код между
     классами) -> отдельный юнит типа `arch`, по лимиту `arch` (до 6 файлов);
   - `P4` (не компилируется) -> первым юнитом `fix`, один, остальные зависят от него;
   - `P5` (пропали или отключены тесты) и `P8` -> не юнит, а вопрос человеку в раздел 6 карты.
2. Номера - следующие свободные `M-<nnn>` после последнего юнита карты.
3. На каждый юнит: карточка `.gigacode/data/migration/units/M-<nnn>.md` по шаблону и строка
   в конец таблицы раздела 4 карты (фаза `6`, статус `todo`). Юниты `arch` ставь после всех
   `fix` этого круга.
4. Последним юнитом круга добавь один юнит типа `review` на файлы всех `arch`-юнитов этого
   круга (если `arch`-юнитов нет - не добавляй).

## Шаг 7 - Запиши итог и останови

1. В шапке карты: `review_round: <номер круга>`, `review_status: clean | findings`,
   `updated`. Строка в «7. Журнал сессий».
2. Покажи пользователю:
   - вердикт и номер круга;
   - сводку: сколько находок по каждому пункту, 5 самых частых;
   - сколько юнитов исправления заведено (`fix` / `arch`) и их номера;
   - вопросы к человеку, если появились;
   - путь к отчёту.
3. Что дальше:
   - `findings` -> «Открой новый чат и напиши: продолжи миграцию» (оркестратор будет
     выполнять юниты исправления, потом снова запустит проверку). Мелкие `fix`-юниты можно
     запускать пачкой: «сделай с M-<a> по M-<b>»;
   - `clean` -> «Миграция проверена, замечаний нет». Служебную папку
     `.gigacode/data/migration/` сам не удаляй - это решает человек (спросит оркестратор);
   - круг 3 и вердикт всё ещё `findings` -> скажи прямо: за три круга не сошлось, перечисли
