# Разметка тестов (allure-annotations)

Общий файл кита: источник - `shared/markup-rules.md`, копии в скиллах раскладывает
`scripts/SyncShared.java`. Правишь - правь только источник.

Разметка - аннотации библиотеки `allure-annotations` (`ru.sber.qa`), по которым Allure
TestOps фильтрует тесты и строит статистику. Документации фрейма она не касается: всё, что
нужно для разметки, - в этом файле. Других аннотаций разметки не придумывай.

Кто пользуется файлом:
- `orchestrator`, отдельная проверка разметки (`references/markup.md`) - проверяет проект и
  по согласию человека ставит недостающее, без миграции;
- `migration-map`, Этап 2, шаг 1б - смотрит, размечен ли проект, и собирает значения;
- `migration-step`, юнит `markup` - ставит аннотации (агент `pvatf-marker`);
- `migration-review`, пункт `P16` - проверяет, что разметка стоит.

## 0. Где искать - только в проекте

Разметка - это пять-семь аннотаций из таблицы раздела 1. Всё, что о них нужно знать, - в
этом файле. Искать про них нечего.

Все команды разметки - из корня проекта, по его файлам (путь `.` или каталог тестов).
**Запрещено:**
- выходить за корень проекта: `find /`, `find ~`, `cd ..`, абсолютные пути вне проекта,
  другие проекты на компьютере;
- проект фреймворка, его исходники, проект-пример, документация MCP - разметке они не нужны;
- `~/.m2`, `~/.gradle`, содержимое .jar (`unzip`, `jar tf`, `javap`), декомпиляция,
  интернет.
Не нашёл в проекте пакет, версию или значение -> дальше не ищи, это нормальный случай, и
для него есть правило: пакет - раздел 2, п.5; зависимость и версия - только дерево
зависимостей (раздел 5); значение - вопрос человеку (раздел 4) или `-`.

## 1. Обязательные аннотации

Основа разметки - пять аннотаций: контур, слой, КЭ, команда, TMS-link. Для тестовой модели
в Allure TestOps к ним добавляются регресс и задача. Где хранится модель (Allure TestOps,
Zephyr или другая TMS) - вопрос `model` (раздел 4).

| Аннотация | Что значит | Обязательна | Кто ставит и откуда значение |
|-----------|------------|-------------|------------------------------|
| `@TestStage` (или готовая: `@IsolatedTest`, `@DevStandTest`, `@StStandTest`, `@IftStandTest`, `@PsiStandTest`, `@PromStandTest`) | контур, где работает автотест | всегда | агент, вопрос `stage` |
| `@TestLayer` (или готовая: `@ApiTest`, `@DbTest`, `@MqTest`, `@UiTest`) | слой, на котором запускается тест (раздел 3) | всегда | агент, без вопроса |
| `@System("<КЭ>")` | КЭ тестируемой системы | всегда | агент, вопрос `system` |
| `@Team("<команда>")` | команда, которой принадлежит автотест | всегда | агент, вопрос `team` |
| `@TmsLink("<ключ>")` | связь автотеста с ручным тестом в TMS | всегда, над каждым тест-методом | **человек**: ключ ручного теста есть только в TMS. Агент ставит её в одном случае: ключ уже записан в `@DisplayName` этого тест-метода (раздел 2а). Сам ключ агент не придумывает, остальные тест-методы без неё показывает в отчёте |
| `@Regress` или `@CriticalRegress` | тест входит в регресс / критичный регресс; обе сразу не ставятся | только модель в Allure TestOps | агент, вопрос `regress` |
| `@Story("<задача>")` или `@Issue("<задача>")` | связь теста с задачей | только модель в Allure TestOps | агент, вопрос `story` |

**Набор агента** - все строки таблицы, кроме `@TmsLink`. По нему решается, размечен ли
проект (раздел 5). `@TmsLink` проверяется отдельно: ключи из `@DisplayName` агент переносит
сам (раздел 2а), остальное попадает в отчёт как работа человека.

Готовые аннотации и значения:

| Готовая аннотация | То же самое |
|-------------------|-------------|
| `@ApiTest` | `@TestLayer("api")` |
| `@DbTest` | `@TestLayer("db")` |
| `@MqTest` | `@TestLayer("mq")` |
| `@UiTest` | `@TestLayer("ui")` |
| `@IsolatedTest` | `@TestStage("code")` |
| `@DevStandTest` | `@TestStage("dev")` |
| `@StStandTest` | `@TestStage("st")` |
| `@IftStandTest` | `@TestStage("ift")` |
| `@PsiStandTest` | `@TestStage("psi")` |
| `@PromStandTest` | `@TestStage("prom")` |

## 2. Как ставить - каскадом

Аннотация над классом действует на все его тесты, над абстрактным базовым классом - на все
тесты наследников. Над каждым методом весь набор не ставится.

1. Значение одно на весь проект (`@System`, `@Team`, `@TestStage`, общий `@Regress`,
   общая `@Story`) -> ставь над базовым тест-классом - классом, от которого наследуются
   тест-классы (из `ARCHITECTURE.md`; без карты - тот, что стоит после `extends` в
   тест-классах). Ставь над ним, даже если он не абстрактный, а над наследниками эти
   аннотации не ставь. Тест-классы наследуются от разных базовых классов -> над каждым из
   них. Тест-класс без базового класса -> над ним самим.
2. `@TestLayer` - над тест-классом или над базовым классом слоя, если тесты одного слоя
   наследуются от него. Тест-класс работает с системой через несколько слоёв - слой по
   тому, что он проверяет (куда уходит запрос, чей ответ проверяется).
3. `@TmsLink` - только над тест-методом, своя на каждый тест. Агент ставит её только по
   разделу 2а - ключ из `@DisplayName`.
4. Аннотация уже стоит (над методом, классом или базовым классом) -> не трогай её и не
   дублируй ниже по иерархии.
5. Импорты - явные, без `*`. Полные имена в коде не пишутся. Пакет аннотаций бери только
   из проекта. У всех аннотаций библиотеки один пакет, поэтому хватит импорта любой из них:
   `grep -rhE "^import .*\.(TestStage|TestLayer|ApiTest|DbTest|MqTest|UiTest|IsolatedTest|DevStandTest|StStandTest|IftStandTest|PsiStandTest|PromStandTest|System|Team|TmsLink|Regress|CriticalRegress|Story|Issue);" --include='*.java' --include='*.kt' . | sort -u`.
   Пакет - всё, что между `import ` и `.<Аннотация>;`. Пакет найден -> импорт любой
   аннотации библиотеки пиши из него; ошибку компиляции «cannot find symbol» на этом
   импорте не чини поиском - убери аннотацию и запиши в отчёт. Ни одного импорта в проекте
   нет -> аннотации не ставь, в отчёте: `<аннотация> - не поставлена: пакет не найден в
   проекте`. Пакет не ищи в .jar, в `~/.m2`, `~/.gradle`, в
   исходниках библиотеки и в интернете, не угадывай его по памяти.
6. Зависимость `ru.sber.qa:allure-annotations` и её версию проверяют до любых правок, первым
   шагом, по дереву зависимостей (раздел 5, «Зависимость и версия»). В модуле с тестами её
   нет -> добавь в сборку этого модуля с нуля, scope `test` (Gradle - `testImplementation`),
   версия - из значений разметки (там `2.0.2`, если человек не назвал другую). Уже есть (в
   том числе пришла через другую библиотеку) -> не трогай: ни версию, ни scope. Одно
   исключение: в значениях разметки `версия: поднять <старая> -> 2.0.2` (раздел 2б, п.2) ->
   замени номер версии на `2.0.2` там, где он записан в проекте (в зависимости или в
   свойстве; команда «Где записан номер версии», раздел 5). В проекте номер не записан
   (версию задаёт BOM, родительский pom или она пришла через другую библиотеку) -> добавь
   зависимость в сборку модуля с тестами явно, с версией `2.0.2`. Больше в сборке ничего не
   меняй. Версию не ищи в .jar, в `~/.m2` и в интернете.

## 2а. Ключ тест-кейса в `@DisplayName`

Бывает, что ключ ручного теста записан в названии теста:
`@DisplayName("[PVATF-4567] Создание заказа")`. Такой ключ агент переносит в `@TmsLink` этого
тест-метода и убирает из `@DisplayName`. Ключ - слово вида `<буквы>-<цифры>`, большими
буквами: `PVATF-4567`, `TC-12`.

Переносишь, только если выполнены все условия:
1. в `@DisplayName` тест-метода ровно один ключ;
2. ключ стоит в начале или в конце названия и отделён от текста: пробелом, `:`, `-`, `|`
   или скобками `[...]`, `(...)`. Подходят: «[PVATF-1] Создание», «PVATF-1: Создание»,
   «Создание заказа PVATF-1» (в конце). Не подходит: «Создание PVATF-1 заказа» (в середине);
3. у тест-метода ещё нет `@TmsLink`;
4. такого же ключа нет в `@DisplayName` другого тест-метода;
5. ключ не совпадает со значением `story` (это задача, а не тест-кейс).
Хоть одно условие не выполнено -> ничего не трогай: тест-метод попадает в отчёт как работа
человека.

Как переносишь:
- над тест-методом - `@TmsLink("<ключ>")`;
- из `@DisplayName` убери ключ вместе с его скобками и разделителем, остальной текст не
  меняй: `@DisplayName("[PVATF-4567] Создание заказа")` -> `@TmsLink("PVATF-4567")` и
  `@DisplayName("Создание заказа")`;
- без ключа от названия ничего не остаётся -> `@DisplayName` не меняй, только поставь
  `@TmsLink`;
- `@DisplayName` над классом не трогай: это не ключ тест-метода.

## 2б. Перед правками - три проверки

Разметку ставят только по правилам этого файла, а правила рассчитаны на allure-annotations
2.x. Поэтому до первой правки по порядку:

1. **Незакоммиченные изменения.** Из корня проекта:
   `git status --porcelain -- . ':(exclude).gigacode'`. Вывод не пустой -> правок не делай,
   остановись. Человеку: «В проекте есть незакоммиченные изменения: <файлы из вывода>.
   Закоммитьте их, и я продолжу разметку». Почему: разметка - отдельный коммит, чужие правки
   в него попасть не должны, а при откате разметки они пропадут.
2. **Версия библиотеки.** Версия - из дерева зависимостей (раздел 5, «Зависимость и
   версия»), не из поиска по файлам. Первое число версии (до первой точки) - мажорная
   версия: `1.8.3` -> 1, `2.0.2` -> 2.
   - зависимости нет -> её добавят с версией `2.0.2`, проверка пройдена;
   - мажорная версия 2 или больше -> проверка пройдена;
   - дерево не построилось (раздел 5: команда упала) -> зависимость не определена: правок
     не делай, остановись. Человеку: «Не удалось построить дерево зависимостей, поэтому
     не понять, есть ли allure-annotations и какой версии: <первые строки ошибки>.
     Исправьте сборку и повторите запрос»;
   - мажорная версия 0 или 1 -> разметить по правилам нельзя. Предложи человеку поднять
     версию до 2.0.2 (вопрос `upgrade`, раздел 4). `да` -> в значениях разметки
     `версия: поднять <старая> -> 2.0.2`, версию поднимают вместе с разметкой (раздел 2,
     п.6). `нет` -> правок не делай, остановись. Человеку: «Разметить тесты по правилам не
     получится: в проекте allure-annotations <версия>, а нужна 2.x».
   Кто спрашивает: в миграции - `migration-map` на Этапе 2 (шаг 1б), в отдельной проверке
   разметки - `orchestrator` перед значениями. Агент разметки не спрашивает, а сверяет: в
   сборке мажорная версия 0 или 1, а в значениях разметки нет `поднять` -> остановиться со
   статусом «не сделан: allure-annotations <версия>, нужна 2.x».
3. **Компиляция.** Выполни команду компиляции проекта до правок. Ошибка -> правок не делай,
   остановись. Человеку: «Проект не компилируется, поэтому разметку поставить нельзя:
   <первые строки ошибки>. Исправьте сборку и повторите запрос». Почему: иначе после
   разметки не понять, чья ошибка - твоя или та, что была.

Все три проверки пройдены -> можно ставить разметку. Ошибка компиляции после правок теперь
точно из-за разметки: чини её сам.

Проверки 1 и 3 делает тот, кто ставит разметку: агент `pvatf-marker` или ты сам, если
ставишь без агента. Агент человеку не пишет: он возвращает статус «не сделан: <причина>»,
а сообщение человеку из этого раздела пишет тот, кто его запустил.

## 3. Слой

Слой - это не технология, а уровень, на котором тест работает с системой. Смотри, через что
тест обращается к системе и чей ответ проверяет. Метка технологии в карте лишь подсказывает
слой:

| Через что тест работает с системой | Аннотация | Подсказка: технология карты |
|------------------------------------|-----------|-----------------------------|
| API системы: HTTP-запросы, gRPC, GraphQL, WebSocket, заглушки API | `@ApiTest` | `rest`, `grpc`, `graphql`, `websocket`, `sbermock` |
| пользовательский интерфейс: браузер, мобильное приложение | `@UiTest` | `ui-selenide`, `ui-playwright`, `appium-android`, `appium-ios` |
| база данных напрямую | `@DbTest` | `db`, `datasource` |
| очереди сообщений | `@MqTest` | `kafka` и другие очереди |
| другое | `@TestLayer("<слой>")` | - |

## 4. Вопросы человеку

Вопрос `upgrade` - про версию библиотеки (раздел 2б, п.2). Остальные задаются только по
аннотациям, которых в проекте нет. Значение есть в проекте (аннотация
уже стоит или КЭ / команда записаны в настройках, README, Jenkinsfile) -> бери оттуда,
вопрос не задаётся. Порядок - как в таблице. Когда задаются: в миграции - на Этапе 2 карты
(шаг 1б); в отдельной проверке разметки - перед правками (`orchestrator`,
`references/markup.md`).

| Ключ | Вопрос | Когда задаётся | Ответ |
|------|--------|----------------|-------|
| `upgrade` | В проекте allure-annotations версии ниже 2.x, а разметка по правилам требует 2.x. Поднять версию до 2.0.2? Напишите в поле ввода: да или нет. | мажорная версия в сборке 0 или 1 (раздел 2б, п.2); задаётся первым | `да` / `нет`. `нет` -> остальные вопросы не задаются, разметку не ставят |
| `model` | Где хранится тестовая модель? Напишите в поле ввода: Allure TestOps, Zephyr или название другой TMS. | всегда, если разметка нужна | Allure TestOps -> `testops`; другое -> `tms: <название>` |
| `system` | Укажите КЭ тестируемой системы в поле ввода, например CI02546875. | нет `@System` | КЭ |
| `stage` | Укажите контур, на котором работают автотесты, в поле ввода: code, dev, st, ift, psi или prom. | нет `@TestStage` и готовых аннотаций контура | одно значение |
| `team` | Укажите название команды в поле ввода - полное, как в справочнике команд. | нет `@Team` | название команды |
| `regress` | Тесты входят в регресс? Напишите в поле ввода: regress - в регрессе, critical - в критичном регрессе, `-` - не входят. | `model: testops`, нет `@Regress`/`@CriticalRegress` | `regress` / `critical` / `-` |
| `story` | Укажите задачу для тестов в поле ввода, например PVATF-4567, или `-`, если задачи нет. | `model: testops`, нет `@Story`/`@Issue` | задача / `-` |

Как задавать: обычным сообщением, ровно текстом из колонки «Вопрос», один вопрос за раз.
Не перефразируй, не добавляй пояснений и своих вариантов ответа, не предлагай выбор из
списка вместо поля ввода. Ответ не подходит под колонку «Ответ» -> повтори тот же вопрос
один раз.

В миграции ответ записывается в паспорт карты, строка «Разметка» (шаблон карты). Ответ `-` -
эту аннотацию не ставят, так и пиши. Про `@TmsLink` вопросов нет: ключи ручных тестов
человек ставит сам.

## 5. Когда разметка не нужна

Разметка (юнит `markup` или правки в отдельной проверке) не нужна, если:
- каждый тест-класс уже размечен набором агента (раздел 1, сам или через базовый класс) и
  нет ключей в `@DisplayName`, которые можно перенести (раздел 2а);
- `scope: core` - тесты в этом режиме не меняются (только миграция);
- allure-annotations в сборке ниже 2.x, а поднять версию человек отказался (раздел 2б,
  п.2): разметить по правилам нельзя.

Проверка, что размечено (по каталогу тестов):
```
grep -rlE "@(TestLayer|ApiTest|DbTest|MqTest|UiTest|UnitTest|CdcConsumerTest|CdcProviderTest|PerformanceTest)\b" --include='*.java' --include='*.kt' <каталог тестов>
grep -rlE "@(TestStage|IsolatedTest|DevStandTest|StStandTest|IftStandTest|PsiStandTest|PromStandTest)\b" --include='*.java' --include='*.kt' <каталог тестов>
grep -rlE "@System\(" --include='*.java' --include='*.kt' <каталог тестов>
grep -rlE "@Team\(" --include='*.java' --include='*.kt' <каталог тестов>
grep -rlE "@(Regress|CriticalRegress|Story|Issue)\b" --include='*.java' --include='*.kt' <каталог тестов>
```

Зависимость и версия - по дереву зависимостей сборки, не поиском по файлам. Дерево
показывает версию, которая реально попадёт в тесты, даже если её задают свойство,
родительский pom, BOM или другая библиотека. Из корня проекта:
- Maven (нет `mvnw` -> `mvn`):
  ```
  ./mvnw dependency:tree -Dincludes=ru.sber.qa:allure-annotations
  ```
  Дерево печатается по каждому модулю (строка `--- ... @ <модуль> ---`). Строка
  `ru.sber.qa:allure-annotations:jar:<версия>:<scope>` в блоке модуля -> в модуле есть, версия -
  четвёртое поле. Строки нет -> в модуле нет;
- Gradle (нет `gradlew` -> `gradle`), по каждому модулю с тестами (один модуль - без
  `:<модуль>`):
  ```
  ./gradlew -q :<модуль>:dependencies --configuration testRuntimeClasspath | grep "ru.sber.qa:allure-annotations"
  ```
  Строка `ru.sber.qa:allure-annotations:<версия>` -> есть. В строке есть `->`
  (`...:1.8.3 -> 2.0.2` или `ru.sber.qa:allure-annotations -> 2.0.2`) -> версия - то, что
  после `->`. Пометки `(*)`, `(c)` в конце строки не часть версии. Пусто -> в модуле нет:
  grep ничего не нашёл - это не ошибка команды.
Запомни по каждому модулю с тестами: `есть <версия>` или `нет`. В разных модулях разные
версии -> для раздела 2б, п.2 бери самую низкую.
Команда упала (Maven - `BUILD FAILURE`, Gradle - `FAILURE:` или `What went wrong`: нет сети,
не скачались зависимости, ошибка сборки) -> зависимость не
определена: покажи первые строки ошибки; что делать - раздел 2б, п.2. По файлам, .jar,
`~/.m2` и в интернете зависимость не ищи - только дерево.

Где записан номер версии (нужно только для подъёма версии, раздел 2, п.6):
```
grep -rn "allure-annotations" --include=pom.xml --include='*.gradle' --include='*.kts' --include='*.toml' . | grep -v "/target/\|/build/"
```
Версия записана свойством (`${allure.annotations.version}`, `libs.versions.toml`) -> место -
это свойство: `grep -rn "<имя свойства>" --include=pom.xml --include='*.gradle' --include='*.kts' --include='*.properties' --include='*.toml' .`.

Ключи в `@DisplayName` тест-методов (кандидаты для раздела 2а):
```
grep -rnE '@DisplayName\("[^"]*[A-Z][A-Z0-9]+-[0-9]+' --include='*.java' --include='*.kt' <каталог тестов>
```

Тест-методы без `@TmsLink` (работа человека, не повод для правок агента):
```
grep -rhoE "@(Test|ParameterizedTest)\b" --include='*.java' --include='*.kt' <каталог тестов> | wc -l
grep -rhoE "@TmsLink\(" --include='*.java' --include='*.kt' <каталог тестов> | wc -l
grep -rlE "@(Test|ParameterizedTest)\b" --include='*.java' --include='*.kt' <каталог тестов> | xargs grep -LE "@TmsLink\("
```
Первые две команды - сколько всего тест-методов и сколько из них связаны с TMS, третья -
тест-классы, где нет ни одной `@TmsLink`.
