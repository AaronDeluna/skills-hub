# Как делать правку каждого типа

Справка агента `pvatf-generator` для заданий «ПРАВКА» скилла `autotest-review`. Читай только
раздел, который назван в задании. Каждая правка меняет только то место, которое названо в
строке «Где», и только файлы из задания. Смысл теста не меняется (правила `MR-9`, `MR-10`,
`MR-11`): те же шаги, те же данные, те же проверки.

## MR

Нарушение правила кода. Номер правила - в строке «Правка». Прочитай текст правила в «Правилах
кода» (`grep -n "MR-<n> ·"`) и исправь строку из «Где».

| Правило | Как исправить | Нельзя -> нужно |
|---------|---------------|-----------------|
| `MR-33` | явный тип из объявления метода, который вернул значение | `var user = steps.user();` -> `User user = steps.user();` |
| `MR-29` | matcher фрейма из конспекта в `.should(...)`; matcher нет в конспекте -> статус `blocked`, вопрос «каким matcher проверить <что>» | `assertEquals(200, code)` -> `.should(<matcher из D-rest-n>)` |
| `MR-4` | `import` в начало файла, в коде - простое имя | `new java.util.ArrayList<>()` -> `import java.util.ArrayList;` и `new ArrayList<>()` |
| `MR-14` | ожидание фрейма из конспекта; нет в конспекте -> `blocked`, вопрос «как дождаться <чего> в <технологии>» | `Thread.sleep(1000);` -> ожидание из `D-timeouts-n` |
| `MR-15` | ключ настроек способом из конспекта; нет -> `blocked` | `"https://host/api"` -> значение из ключа настроек `D-env-n` |
| `MR-41`, `MR-48` | проверка по ответу фрейма без DTO и разбора руками, matcher из конспекта | `response.as(User.class).getName()` -> `.should(<matcher по полю из D-rest-n>)` |
| `MR-42` | метод из тест-класса переносится в класс шагов этой технологии, в тесте остаётся вызов | `private Response sendPay()` в тесте -> `PaySteps.sendPay()` |
| `MR-43` | строку логирования удали: фрейм пишет запросы в отчёт сам | `log.info("ответ " + body);` -> строки нет |
| `MR-45` | переименуй в lowerCamelCase и все использования в этом файле | `user_id` -> `userId` |
| `MR-47` | чтение настроек - способом фрейма из конспекта; нет -> `blocked` | `System.getProperty("url")` -> способ из `D-env-n` |

## SQL

Значение подставляется в текст SQL склейкой строк. Перепиши запрос с параметрами тем
способом, который даёт фрейм (запись конспекта про запросы с параметрами, метка `db`). Записи
нет -> статус `blocked`, вопрос «как выполнить запрос с параметрами в DatabaseService».
Нельзя: `"SELECT name FROM pay WHERE id = '" + id + "'"`. Нужно: текст запроса с
параметром и значение отдельным аргументом - способом из `D-db-n`. `SELECT *` не пишешь:
перечисли колонки, которые тест проверяет.

## MR-22

Пустой `catch` глушит ошибку. Если исключение не ожидается тестом - убери `try/catch`, пусть
тест падает. Если тест проверяет, что исключение есть, - проверка способом фрейма из
конспекта; нет -> `blocked`. Нельзя: `catch (Exception e) {}`. Нужно: без `try/catch`.

## CONST

Литерал выносится в константу тест-класса (правило `MR-42` разрешает константы тестовых
данных в тест-классе). Задание даёт объявление; `<ИМЯ>` - имя придумываешь ты по смыслу
значения в этом месте (правило `MR-40`): UPPER_SNAKE_CASE, 1-4 слова, не совпадает с
именами в файле. Объявление ставь к остальным `private static final` в начале класса
(правило `MR-1`), литерал во всех строках из «Где» замени именем.
Нельзя: `private static final int VALUE_1 = 1500;`. Нужно: `private static final int PAY_AMOUNT = 1500;`.

## SHARED-CONST

Литерал есть в тест-классе и ещё в 2 и более тестах. Константа - в общий класс констант:
1. Класс констант в проекте уже есть (`*Constants`, `*TestData` в пакете тестов) - добавь
   константу туда. Нет - создай `<Предметная область>Constants` в пакете
   `<пакет теста без последней части>.constants`: `public final class`, приватный конструктор,
   поля `public static final`.
2. Замени литерал именем константы в тест-классе (строки из «Где») и в зависимых тестах из
   задания - только если они перечислены в строке «Зависимые тесты, которые эта правка тоже
   меняет». Строка `-` или «НЕ меняй» -> меняешь только тест-класс.
3. Добавь `import` константы в каждый изменённый файл.

## DUP

Блок из 5 и более строк повторяется. Вынеси его в метод класса шагов (правило `MR-42`: в
тест-классе вспомогательных методов нет; правило `MR-39`: дублей нет):
1. Класс шагов этой технологии уже есть в проекте - добавь метод в него. Нет - создай
   `<Предметная область>Steps` в пакете `<пакет теста без последней части>.steps`.
2. Имя метода - что делает блок (правило `MR-40`), параметры - значения, которыми повторы
   отличаются. Существующие методы проекта не меняй и не переименовывай.
3. Замени каждый повтор в тест-классе вызовом метода. Зависимые тесты - как в п.2 раздела
   «SHARED-CONST».
Нельзя: `private void doStuff()` в тест-классе. Нужно: `PaySteps.payAndConfirm(PHONE, AMOUNT)`.

## FIX

Прошлый `check` нашёл ошибки после правок: новое нарушение правила кода (строка
`MR-<n> <файл>:<строка>`) или ошибку компиляции (строка `КОМПИЛЯЦИЯ ...`). Исправь каждую
строку из «Что сделать» в названном файле и месте: нарушение - по разделу «MR» этой справки,
ошибку компиляции - по тексту ошибки (нет `import`, опечатка в имени, неверный тип). Менять
можно только файлы, которые уже изменила эта проверка. Ошибку не исправить без смены смысла
теста -> статус `failed` с этой строкой в причине.
