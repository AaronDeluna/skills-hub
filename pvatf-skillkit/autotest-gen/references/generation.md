# Цикл генерации одного G и исправление находок

Часть скилла `autotest-gen`. Открывай, только когда SKILL.md направил сюда.

Скрипт: `python3 .gigacode/skills/autotest-gen/scripts/at_tools.py` (ниже - `at_tools.py`).

## Один G

1. Вывод `at_tools.py next <ключ>` после строки «ЗАДАНИЕ для агента pvatf-generator» -
   это задание. Передай его агенту `pvatf-generator` дословно, ничего не добавляя.
2. Ответ агента - строка `Статус:`:

| Статус | Что делаешь |
|--------|-------------|
| `ok` | `at_tools.py mark <ключ> <G-n> ok`, дальше `next` |
| `stub` | `at_tools.py mark <ключ> <G-n> stub`; причину из ответа - строкой в раздел 7 плана «Решения и блокеры»: `<G-n>: stub - <причина>`; дальше `next` |
| `blocked` | раздел «Вопросы документации» ниже, потом то же задание агенту ещё раз |

3. Второй `blocked` на тот же G (документация не помогла) -> `mark <ключ> <G-n> stub`,
   строка в раздел 7 плана `<G-n>: stub - нет в документации: <вопросы>`.

## Вопросы документации (статус blocked)

1. Вопросы - из строки «Нужно из документации» ответа агента, не больше 5.
2. По каждому сначала конспект:
   `python3 .gigacode/skills/autotest-gen/scripts/notes.py find <метка G> <2-4 слова>`.
   Нашлась запись `найден`, а агент её не увидел -> переходи к п.5.
3. Остальные - агенту `pvatf-docs` по шаблону `references/autotest-rules.md`, правило 3;
   метка и раздел - из таблицы того же правила.
4. Каждый блок ответа - запись в `.gigacode/data/doc-notes/<метка>.md`:
   `## <ID> · <вопрос>`, ID - `notes.py next <метка>`, дальше поля ответа агента без
   изменений. Раздел «Ключевые слова документации» в конце файла замени новым словарём.
5. `at_tools.py rules <ключ>` - обновляет `docs-now.md` для агента.

## Исправление находок check

Строка вывода `check` - одна находка. Правь только файл из строки и только это место.

| Находка | Как исправить |
|---------|---------------|
| `MR-33` var | явный тип из объявления метода, который вернул значение |
| `MR-29` assert | matcher из конспекта (`docs-now.md`); matcher нет -> вопрос документации «каким matcher проверить <что>», ответа нет - строка оставляется и уходит в итог |
| `MR-4` полное имя | `import` в начало файла, в коде - простое имя |
| `MR-15` адрес или секрет | ключ настроек из конспекта вместо строки |
| `MR-14` sleep | ожидание фрейма из конспекта |
| `MR-42` метод в тест-классе | перенеси метод в класс шагов этой технологии, в тесте - вызов |
| `MR-21` TODO | доделай место по фрагменту или замени на `// STUB <G-n>: <причина>` и строку в раздел 7 плана |
| `ПОКРЫТИЕ шаг <n>` | шага нет в теле: `at_tools.py mark <ключ> <G шага> todo`, `next`, агент заново (п. «Один G») |
| `КОМПИЛЯЦИЯ ...` | файл и строка из ошибки: правь, если файл есть во «Файлах шагов» фрагментов или это тест-класс; тест-класс правишь через фрагмент `fragments/G-<n>.md` (блоки imports / fields / body) и `assemble`, сам файл теста не правишь |

После правок фрагментов - `at_tools.py assemble <ключ>`, потом `check`.
