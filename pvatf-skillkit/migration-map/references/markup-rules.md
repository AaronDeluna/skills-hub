# Разметка тестов (allure-annotations)

Общий файл кита: источник - `shared/markup-rules.md`, копии в скиллах раскладывает
`scripts/SyncShared.java`. Правишь - правь только источник.

Разметка - аннотации библиотеки `allure-annotations` (`ru.sber.qa`), по которым Allure
TestOps фильтрует тесты и строит статистику. Документации фрейма она не касается: всё, что
нужно для разметки, - в этом файле. Других аннотаций разметки не придумывай.

Кто пользуется файлом:
- `migration-map`, Этап 2, шаг 1б - смотрит, размечен ли проект, и собирает значения;
- `migration-step`, юнит `markup` - ставит аннотации (агент `pvatf-marker`).
- `migration-review`, пункт `P16` - проверяет, что разметка стоит.

## 1. Обязательные аннотации

Обязательный набор зависит от того, где хранится тестовая модель. Это вопрос `model`
(раздел 4).

| Аннотация | Что значит | Обязательна | Откуда значение |
|-----------|------------|-------------|-----------------|
| `@TestLayer` (или готовая: `@ApiTest`, `@DbTest`, `@MqTest`, `@UiTest`) | тип (слой) теста | всегда | из технологии теста, раздел 3, без вопроса |
| `@TestStage` (или готовая: `@IsolatedTest`, `@DevStandTest`, `@StStandTest`, `@IftStandTest`, `@PsiStandTest`, `@PromStandTest`) | стенд, на котором запускаются тесты | всегда | вопрос `stage` |
| `@System("<КЭ>")` | КЭ тестируемой системы | всегда | вопрос `system` |
| `@Regress` или `@CriticalRegress` | тест входит в регресс / критичный регресс; обе сразу не ставятся | только модель в Allure TestOps | вопрос `regress` |
| `@Story("<задача>")` или `@Issue("<задача>")` | связь теста с задачей | только модель в Allure TestOps | вопрос `story` |

Готовые аннотации и значения:

| Готовая аннотация | То же самое |
|-------------------|-------------|
| `@ApiTest` | `@TestLayer("api")` - REST, gRPC, GraphQL, WebSocket |
| `@DbTest` | `@TestLayer("db")` - проверки на уровне БД |
| `@MqTest` | `@TestLayer("mq")` - Kafka и другие очереди |
| `@UiTest` | `@TestLayer("ui")` - UI, Selenide, Playwright, Appium |
| `@IsolatedTest` | `@TestStage("code")` |
| `@DevStandTest` | `@TestStage("dev")` |
| `@StStandTest` | `@TestStage("st")` |
| `@IftStandTest` | `@TestStage("ift")` |
| `@PsiStandTest` | `@TestStage("psi")` |
| `@PromStandTest` | `@TestStage("prom")` |

## 2. Как ставить - каскадом

Аннотация над классом действует на все его тесты, над абстрактным базовым классом - на все
тесты наследников. Над каждым методом весь набор не ставится.

1. Значение одно на весь проект (`@System`, `@TestStage`, общий `@Regress`) -> ставь над
   базовым тест-классом из `ARCHITECTURE.md`. Базового класса нет -> над каждым тест-классом.
2. `@TestLayer` - над тест-классом или над базовым классом технологии, если тесты одной
   технологии наследуются от него. Тест-класс ходит в несколько технологий - слой по той,
   которую он проверяет (куда уходит запрос, чей ответ проверяется).
3. Аннотация уже стоит (над методом, классом или базовым классом) -> не трогай её и не
   дублируй ниже по иерархии.
4. Импорты - из пакета библиотеки, без `*`. Полные имена в коде не пишутся.
5. Зависимости `ru.sber.qa:allure-annotations` в сборке нет -> добавь её в каждое место
   сборки тестового модуля, scope `test` (Gradle - `testImplementation`), версия - из
   строки «Разметка» паспорта (там `2.0.2`, если человек не назвал другую). Уже есть -> не
   трогай: ни версию, ни scope.

## 3. Слой по технологии

| Технология карты | Аннотация |
|------------------|-----------|
| `rest`, `grpc`, `graphql`, `websocket`, `sbermock` | `@ApiTest` |
| `db`, `datasource` | `@DbTest` |
| `kafka` и другие очереди | `@MqTest` |
| `ui-selenide`, `ui-playwright`, `appium-android`, `appium-ios` | `@UiTest` |
| другая | `@TestLayer("<метка технологии>")` |

## 4. Вопросы человеку

Задаются только на Этапе 2 карты (шаг 1б) и только по аннотациям, которых в проекте нет.
Значение есть в проекте (аннотация уже стоит или КЭ записан в настройках, README,
Jenkinsfile) -> бери оттуда, вопрос не задаётся. Порядок - как в таблице. Как именно
задавать - Этап 2 карты, шаг 1б.

| Ключ | Вопрос | Когда задаётся | Ответ |
|------|--------|----------------|-------|
| `model` | Где хранится тестовая модель: во внешней TMS или в Allure TestOps? | всегда, если разметка нужна | `tms` / `testops` |
| `system` | Укажите КЭ тестируемой системы для аннотации `@System`, например `CI02546875`. | нет `@System` | КЭ |
| `stage` | На каком стенде запускаются автотесты: `code`, `dev`, `st`, `ift`, `psi`, `prom`? | нет `@TestStage` и готовых аннотаций стенда | одно значение |
| `regress` | Тесты проекта входят в регресс? Ответ: `regress` - все в регрессе, `critical` - все в критичном регрессе, `-` - не входят. | `model: testops`, нет `@Regress`/`@CriticalRegress` | `regress` / `critical` / `-` |
| `story` | Укажите задачу для `@Story` (например, `PVATF-4567`) или `-`, если связи с задачей нет. | `model: testops`, нет `@Story`/`@Issue` | задача / `-` |

Ответ записывается в паспорт карты, строка «Разметка» (шаблон карты). Ответ `-` - эту
аннотацию не ставят, так и пиши в паспорт.

## 5. Когда разметка не нужна

Юнит `markup` не создаётся, если:
- каждый тест-класс уже размечен обязательным набором (сам или через базовый класс);
- `scope: core` - тесты в этом режиме не меняются.

Проверка, что размечено (по каталогу тестов):
```
grep -rlE "@(TestLayer|ApiTest|DbTest|MqTest|UiTest|UnitTest|CdcConsumerTest|CdcProviderTest|PerformanceTest)\b" --include=*.java --include=*.kt <каталог тестов>
grep -rlE "@(TestStage|IsolatedTest|DevStandTest|StStandTest|IftStandTest|PsiStandTest|PromStandTest)\b" --include=*.java --include=*.kt <каталог тестов>
grep -rlE "@System\(" --include=*.java --include=*.kt <каталог тестов>
grep -rlE "@(Regress|CriticalRegress|Story|Issue)\b" --include=*.java --include=*.kt <каталог тестов>
grep -rlE "allure-annotations" --include=pom.xml --include=*.gradle --include=*.kts .
```
