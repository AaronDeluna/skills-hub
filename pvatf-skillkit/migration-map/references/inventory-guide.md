# Как провести инвентаризацию проекта (и не съесть контекст)

Прочитай перед Этапом 2. Главная идея: **считать и искать командами, а не читать файлы**.
Вывод каждой команды сразу сворачивай в короткую запись в `inventory/<модуль>.md`. Длинный
вывод ограничивай через `| head -<n>`.

Чего НЕ делать:
- не открывай подряд все классы «чтобы понять проект»;
- не читай `target/`, `build/`, `.gradle/`, `.idea/`, `node_modules/`, `*.jar`, `*.class`;
- не смотри в `~/.m2` и кэши - API фрейма берётся только из документации MCP.

Во всех командах `<SRC>` - корень исходников модуля (например `module-a/src`).

## 1. Паспорт

```
ls                                                  # что в корне
ls pom.xml build.gradle build.gradle.kts settings.gradle settings.gradle.kts 2>/dev/null
ls mvnw gradlew 2>/dev/null                         # есть ли wrapper
git branch -a | head -30                            # ветки, основная ветка, конвенция имён
git log --oneline -15                               # конвенция коммитов
ls checkstyle.xml config/checkstyle .editorconfig 2>/dev/null
```

Модули: Maven - `grep -n "<module>" pom.xml`; Gradle - `grep -n "include" settings.gradle*`.

Тест-фреймворк - по импортам, а не по зависимостям:
```
grep -rhoE "import org\.(junit\.jupiter\.api|junit|testng\.annotations)\.Test" --include=*.java --include=*.kt . | sort | uniq -c
```

Раннер: предпочитай wrapper (`./mvnw` / `./gradlew`). Проверь, что он запускается
(`<RUN> -v` / `<RUN> --version`). Команды для паспорта:
```
<RUN> -q -DskipTests compile test-compile      # Maven
<RUN> compileJava compileTestJava              # Gradle
```
Можно ли запускать тесты локально - не выясняй запуском всего проекта. Посмотри README/CI
(`Jenkinsfile`, `.gitlab-ci.yml`) и спроси пользователя, если неясно. Запиши в паспорт как есть.

## 2. Инвентаризация одного модуля

Делай по одному модулю. После каждого - сразу пиши `inventory/<модуль>.md`.

Размер:
```
find <SRC> -name "*.java" -o -name "*.kt" | wc -l
find <SRC> \( -name "*.java" -o -name "*.kt" \) -exec cat {} + | wc -l
```

Топ импортов по пакетам (первые 3 сегмента) - главный вход для матрицы `G`:
```
grep -rhoE "^import (static )?[a-zA-Z0-9_]+\.[a-zA-Z0-9_]+\.[a-zA-Z0-9_]+" --include=*.java --include=*.kt <SRC> | sed -E "s/^import (static )?//" | sort | uniq -c | sort -rn | head -60
```

Для каждого не-JDK пакета из топа - сколько файлов его используют:
```
grep -rlE "^import (static )?<пакет>\." --include=*.java --include=*.kt <SRC> | wc -l
```

Базовые классы и интерфейсы (от чего наследуются):
```
grep -rhoE "(extends|implements) [A-Z][A-Za-z0-9_<>, ]+" --include=*.java <SRC> | sort | uniq -c | sort -rn | head -40
```

Аннотации (какие и сколько):
```
grep -rhoE "^\s*@[A-Z][A-Za-z0-9_]+" --include=*.java --include=*.kt <SRC> | sed -E "s/^\s+//" | sort | uniq -c | sort -rn | head -40
```

Сколько тестов:
```
grep -rE "^\s*@Test\b" --include=*.java --include=*.kt <SRC> | wc -l
```

Большие файлы (кандидаты в отдельные юниты и в проблемы архитектуры):
```
find <SRC> \( -name "*.java" -o -name "*.kt" \) -exec wc -l {} + | sort -rn | head -20
```

Структура пакетов (только каталоги, 4 уровня):
```
find <SRC> -type d -maxdepth 8 | head -80
```

Конфиги и ресурсы:
```
find <SRC> -path "*resources*" -type f | head -60
```

Что уже на PVATF (пакет фрейма - `ru.sber.qa`, под ним `io.perfeccionista.framework`):
```
grep -rlE "^import (static )?(ru\.sber\.qa|io\.perfeccionista)\." --include=*.java --include=*.kt <SRC> | wc -l
```
Импорт этих пакетов - это использование фрейма. Правильно ли оно - сверяй с документацией.

## 3. Образцы

На каждый шаблон использования (строка будущей матрицы `G`) открой 1-3 файла-образца: самый
типичный, по возможности небольшой. Читай столько, сколько нужно, чтобы описать шаблон в
одной строке матрицы. Путь к образцу запиши в колонку «Образец в проекте».

## 4. Формат inventory/<модуль>.md

```markdown
# Инвентаризация: <модуль>

- Файлов: <n> · Строк: <n> · Тестов (@Test): <n>
- Уже на PVATF файлов: <n>

## Топ импортов (пакет - файлов)
- <пакет> - <n>

## Базовые классы / интерфейсы (имя - сколько наследников)
- <имя> - <n>

## Аннотации (имя - сколько)
- <имя> - <n>

## Большие файлы (путь - строк)
- <путь> - <n>

## Конфиги
- <путь> - <что это, 3-5 слов>

## Заметки
- <что бросилось в глаза: самописные обёртки, дубли, странности>
```

## 5. Архитектура (для Этапа 4)

Целевую архитектуру бери из документации (запись `D-common-3` в `doc-notes/common.md`; не хватает - через сабагента документации).
Сначала прочитай её, выпиши слои и правила в 5-10 строк в заметки, потом проверяй проект.
Что обычно проверять (каждое - командой, с числом и 1-2 примерами):

| Что проверять | Как искать |
|---------------|-----------|
| Тесты напрямую работают с низким уровнем (драйвер, HTTP-клиент, SQL), минуя слой, который велит документация | `grep -rl` по импортам низкого уровня внутри каталога тестов |
| Самописные обёртки над тем, что фрейм уже даёт | классы `*Utils`, `*Helper`, `*Wrapper`, `Base*` - сверить с документацией |
| Классы-гиганты | список больших файлов (> 500 строк) |
| Дублирование (один и тот же код в нескольких модулях) | одинаковые имена классов: `find . -name "*.java" -exec basename {} \; \| sort \| uniq -d` |
| Хардкод (адреса, логины, таймауты в коде) | `grep -rnE "https?://\|Thread\.sleep\|password" --include=*.java <SRC> \| head -30` |
| Общее изменяемое статическое состояние | `grep -rnE "static [^f(]*=" --include=*.java <SRC> \| grep -v final \| head -30` |
| Код лежит не в том слое/пакете, что велит документация | структура пакетов против структуры из документации |
| Свой код в пакете фрейма | `grep -rlE "^package ru\.sber\.qa" --include=*.java <SRC>` |

Нашёл проблему, но в документации нет правила про неё - это не твоё решение: основание
`нет в доке - на решение человека`, вопрос в раздел 6 карты.
