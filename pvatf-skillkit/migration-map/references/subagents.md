# Сабагенты при построении карты (для migration-map)

Сабагентов здесь всего ЧЕТЫРЕ вида, других не придумывай:

| Сабагент | Когда | Обязателен |
|----------|-------|------------|
| **Документация** (справка по вопросам) | Этапы 1, 3, 4 - любое обращение к документации фрейма | всегда |
| **Технологии проекта** | Этап 2, п.0 - какие технологии использует проект | только если пользователь сам не назвал технологии |
| **Инвентаризация модулей** | Этап 2 - подсчёты по исходникам модулей | всегда |
| **Примеры** (проект-пример или исходники фрейма) | Этапы 3, 4 - когда документации не хватило; раздел 4 этого файла | только по пути, который дал человек |

Всё остальное (паспорт, матрица, архитектура, юниты, карточки) делаешь ты сам.

# 1. Сабагент документации

## Как устроена документация (важно понять)

Документация фрейма лежит в **векторной базе**. Инструмент `get_pv_at_doc` принимает
текстовый запрос и возвращает куски документации, похожие на этот запрос. В самой базе
оглавления нет; список разделов документации лежит в `references/frame-topics.md`.
Поэтому:
- один и тот же вопрос, заданный разными словами, возвращает РАЗНЫЕ куски;
- одна формулировка может ничего не дать, хотя ответ в документации есть;
- вопрос надо задавать несколькими формулировками и собирать ответ из всех кусков.

Этим занимается сабагент. Твоё дело - дать ему конкретные вопросы и записать ответ.

## Обязательное требование

Любое обращение к документации фрейма (инструмент `get_pv_at_doc`) выполняется **ТОЛЬКО
через сабагента**. Сам, в своём контексте, ты этот инструмент НЕ вызываешь - это **нарушение
протокола**. Причина: на каждый вопрос нужно несколько запросов, ответы большие, и если
читать их самому, контекст закончится раньше, чем работа. Сабагент делает запросы у себя и
возвращает тебе только короткий ответ по шаблону.

Это правило часто пытаются пропустить («быстрее сам», «один вопрос») - не пропускай.

Единственное исключение: инструмент запуска сабагентов (Task/Agent) физически отсутствует в
твоём окружении, ИЛИ сабагент ответил, что инструмент документации ему недоступен. Только
тогда вызывай `get_pv_at_doc` сам - по тем же правилам, что в промпте ниже (несколько
формулировок на вопрос), сразу выписывай нужное в конспект и явно напиши в журнале
карты/карточки «сабагенты недоступны, документация прочитана напрямую». Больше исключений нет.

## Сначала конспект, потом сабагент

Всё, что сабагент уже достал, лежит в конспекте:
`.gigacode/data/migration/doc-notes/<технология>.md` (общее про фрейм - `doc-notes/common.md`).
Одна запись конспекта = один вопрос и ответ на него, ID вида `D-<tech>-<n>` (`D-rest-3`).

Порядок всегда один:
1. Открой файл конспекта нужной технологии. Нужный ответ там есть со статусом `найден` ->
   бери его, сабагента НЕ запускай.
2. Ответа нет, он неполный или не про то -> запусти сабагента с этим вопросом. Если в
   конспекте по этому вопросу уже есть формулировки, которые ничего не дали, - передай их в
   промпт, чтобы сабагент спросил ИНАЧЕ.
3. Ответ сабагента СРАЗУ запиши в конспект новой записью (шаблон записи - ниже), вместе со
   всеми формулировками запросов. Потом работай по записи.
4. Запись со статусом `НЕТ В ДОКЕ`, у которой меньше 8 формулировок, - не приговор: запусти
   сабагента ещё раз, передав уже испробованные формулировки. 8 и больше формулировок и всё
   ещё `НЕТ В ДОКЕ` -> документация этого не знает. Не подбирай ответ сам и не лезь в jar.
   Дальше два случая:
   - молчит про технологию ЦЕЛИКОМ (нет модуля, нет раздела) -> технология получает решение
     `keep`: не мигрируется, остаётся на старой реализации. Вопрос человеку не нужен;
   - технология во фрейме есть, но нет ответа на отдельный вопрос (чем заменить конкретный
     шаблон, как донастроить, процесс описан не до конца) -> иди по лестнице источников
     (раздел 4 этого файла): проект-пример, исходники фрейма, потом вопрос человеку с
     вариантами. В матрице пока `НЕТ В ДОКЕ`.

## Как формулировать вопросы

- **Конкретно и про одно.** Не «как работает Kafka», а «как отправить сообщение в топик»,
  «как прочитать сообщение из топика и проверить его», «какая зависимость нужна для модуля
  Kafka», «как настроить подключение к брокеру (адрес, сертификаты)».
- **Про действие, а не про старый класс.** Документация не знает ваших старых классов. Не
  «чем заменить KafkaHelper», а «как <то, что делает KafkaHelper>» - например «как дождаться
  сообщения в топике по ключу».
- **Про настройку - отдельным вопросом:** «как сконфигурировать ...», «какие параметры ...»,
  «в каком файле задаётся ...».
- **Назови раздел документации.** Перед запуском сабагента открой
  `references/frame-topics.md`, найди раздел своей технологии и впиши его название в строку
  промпта «Раздел документации» символ в символ. Раздела нет - впиши `нет в списке`.
- Называй технологию так, как она называется в проекте, И общим словом (например: «Kafka,
  брокер сообщений»; «PostgreSQL, база данных»; «OpenShift, контейнерная платформа»).

Лимит на один запуск сабагента: не больше 5 вопросов. Больше - несколько запусков по очереди.

## Промпт сабагенту (копируй дословно, подставь <...>)

```
Ты достаёшь справку из документации фрейма PVATF (фрейм для отдельных проектов автотестов).
Документация лежит в векторной базе. Единственный источник - инструмент get_pv_at_doc
MCP-сервера автогенерации автотестов (имя сервера оканчивается на autotest-generation-remote).
Инструмент принимает текстовый запрос и возвращает подходящие куски документации. Один и тот
же вопрос разными словами даёт разные куски - поэтому КАЖДЫЙ вопрос ты задаёшь несколькими
формулировками.

Запрещено: читать файлы проекта, открывать jar, искать в интернете, отвечать по памяти и по
аналогии с другими фреймами, менять файлы. Верни ТОЛЬКО заполненные блоки по шаблону, без
рассуждений и без пересказа всей документации.

Технология: <метка и обычное название, напр. kafka - Kafka, брокер сообщений>
Раздел документации: <название из frame-topics.md, напр. Работа с Kafka; или: нет в списке>
Вопросы:
1. <вопрос>
2. <вопрос>
Формулировки, которые уже пробовали и они НИЧЕГО не дали (не повторяй их): <список или: нет>

Перед первым запросом прочитай описание инструмента get_pv_at_doc и его параметры.

Для КАЖДОГО вопроса выполни:

Шаг 1. Составь 3 РАЗНЫЕ формулировки запроса:
  (а) вопрос как есть;
  (б) другими словами: замени слова на близкие по смыслу (настроить / сконфигурировать /
      подключить / параметры / конфигурация; отправить / выполнить / вызвать; проверить /
      валидация / ожидание), добавь название технологии по-русски и по-английски;
  (в) название раздела документации (если дано) + 2-3 ключевых слова вопроса
      (напр. «Работа с Kafka чтение сообщения из топика», «Работа с Rest API зависимость»,
      «Работа с Базами Данных подключение параметры»). Раздел не дан - просто ключевыми
      словами, как заголовок.
Шаг 2. Вызови инструмент по одному разу на каждую из 3 формулировок.
Шаг 3. Собери ответ из ВСЕХ полученных кусков. Ответ полный - переходи к шаблону.
Шаг 4. Ответа нет или он неполный - составь ещё 2 формулировки, НЕ похожие на прежние
  (спроси про пример кода; про название модуля; про класс или аннотацию), и вызови
  инструмент ещё 2 раза.
Шаг 5. Только если после 5 формулировок ответа нет - статус «НЕТ В ДОКЕ».

На КАЖДЫЙ вопрос верни РОВНО такой блок (заголовки полей сохрани):

### Вопрос <номер>: <текст вопроса>
- Статус: найден | найден частично | НЕТ В ДОКЕ
- Что использовать: <точные имена модулей / классов / аннотаций / методов вместе с пакетом, как в документации; нет - напиши: ->
- Как подключить: <зависимость group:artifact, плагин - как в документации; нет - напиши: ->
- Как настроить: <файл, параметры, значения - как в документации; нет - напиши: ->
- Пример из документации (дословно, не больше 15 строк):
- Условия и ограничения: <что документация требует или запрещает; нет - напиши: ->
- Чего не хватило: <только для «найден частично»: что именно в документации не нашлось>
- Формулировки запросов:
  - «<формулировка>» - дала ответ | пусто
  - «<формулировка>» - дала ответ | пусто

Правила ответа:
- Чего нет в полученных кусках документации - не пиши. Ничего не добавляй от себя.
- Имена пиши символ в символ, как в документации. Не исправляй и не «улучшай».
- Перечисли ВСЕ формулировки, которые ты отправлял, с пометкой, дала ли каждая ответ.
- Инструмент не найден или вернул ошибку - верни одной строкой: MCP НЕДОСТУПЕН: <текст ошибки>.
```

## Шаблон записи конспекта

Файл `.gigacode/data/migration/doc-notes/<технология>.md`. Первая строка файла:
`# Конспект документации PVATF: <технология>`. Записи только дописываются в конец; номер
`<n>` - следующий по порядку в этом файле.

```markdown
### D-<tech>-<n> · <вопрос>
- Статус: найден | найден частично | НЕТ В ДОКЕ
- Что использовать: <...>
- Как подключить: <...>
- Как настроить: <...>
- Пример:
- Условия и ограничения: <...>
- Чего не хватило: <...>
- Формулировки запросов: «<...>» - дала ответ; «<...>» - пусто
- Записано: <ГГГГ-ММ-ДД> · <этап карты или юнит M-nnn>
```

## Что делать с ответом

- `найден` -> запиши запись в конспект, используй. ID записи - это и есть док-основание.
- `найден частично` -> запиши; на то, чего не хватило, задай сабагенту отдельный, более
  узкий вопрос.
- `НЕТ В ДОКЕ` -> запиши (с формулировками!) и действуй по п.4 раздела «Сначала конспект».
- `MCP НЕДОСТУПЕН` -> СТОП, сообщи пользователю.
- Ответ не по шаблону или без списка формулировок -> не используй, запусти сабагента ещё
  раз с тем же промптом.

# 2. Сабагент инвентаризации модулей

## Обязательное требование

Подсчёты по исходникам модулей (Этап 2, п.2) выполняются **только через сабагентов**. Вывод
grep по большому модулю огромный - к тебе он попадать не должен, тебе нужен только свёрнутый
результат. Единственное исключение - инструмент сабагентов физически отсутствует: тогда
считай сам по `references/inventory-guide.md`, по одному модулю, и запиши это в журнал карты.

## Сколько сабагентов

```
число сабагентов = min(3, число модулей)
```

Раздели модули между ними как можно ровнее, без пересечений, чтобы вместе покрыть ВСЕ модули.
Один модуль в проекте - один сабагент.

## Промпт (копируй дословно, подставь <...>)

```
Ты делаешь инвентаризацию исходников для СПИСКА модулей одного проекта. Только считаешь и
ищешь командами. Не меняй файлы. Не читай target/, build/, .gradle/, .idea/, *.jar, *.class.
Не открывай файлы целиком, кроме случаев, когда это прямо сказано. Верни ТОЛЬКО заполненные
шаблоны (по одному на модуль), без рассуждений и без сырого вывода команд.

Проект: <абсолютный путь к корню проекта>
Модули (обработай КАЖДЫЙ): <модуль: путь к его каталогу src>, <модуль: путь>

Для КАЖДОГО модуля (SRC - его каталог src) выполни команды:

1. find SRC \( -name "*.java" -o -name "*.kt" \) | wc -l
2. find SRC \( -name "*.java" -o -name "*.kt" \) -exec cat {} + | wc -l
3. grep -rE "^\s*@Test\b" --include=*.java --include=*.kt SRC | wc -l
4. grep -rhoE "^import (static )?[a-zA-Z0-9_]+\.[a-zA-Z0-9_]+\.[a-zA-Z0-9_]+" --include=*.java --include=*.kt SRC | sed -E "s/^import (static )?//" | sort | uniq -c | sort -rn | head -40
5. grep -rhoE "(extends|implements) [A-Z][A-Za-z0-9_<>, ]+" --include=*.java SRC | sort | uniq -c | sort -rn | head -30
6. grep -rhoE "^\s*@[A-Z][A-Za-z0-9_]+" --include=*.java --include=*.kt SRC | sed -E "s/^\s+//" | sort | uniq -c | sort -rn | head -30
7. find SRC \( -name "*.java" -o -name "*.kt" \) -exec wc -l {} + | sort -rn | head -15
8. find SRC -path "*resources*" -type f | head -40
9. grep -rlE "^import (static )?(ru\.sber\.qa|io\.perfeccionista)\." --include=*.java --include=*.kt SRC | wc -l
10. find SRC -name "*Utils.java" -o -name "*Helper.java" -o -name "*Wrapper.java" -o -name "Base*.java" -o -name "Abstract*.java" | head -40

Верни на каждый модуль РОВНО такой шаблон (заголовки сохрани):

# Инвентаризация: <модуль>

- Файлов: <n> · Строк: <n> · Тестов (@Test): <n>
- Уже на PVATF файлов: <n>

## Топ импортов (пакет - сколько раз)
- <пакет> - <n>      (JDK-пакеты java.*, javax.* не перечисляй)

## Базовые классы / интерфейсы (имя - сколько наследников)
- <имя> - <n>

## Аннотации (имя - сколько)
- <имя> - <n>

## Большие файлы (путь - строк)
- <путь> - <n>

## Конфиги и ресурсы
- <путь>

## Самописные обёртки и базовые классы (кандидаты в legacy)
- <путь>

## Команды, которые не выполнились
- <номер команды: ошибка>   (если все выполнились - напиши: нет)
```

## Что делать с результатами

1. Каждый шаблон запиши как есть в `.gigacode/data/migration/inventory/<модуль>.md`.
2. **Ворота:** шаблон должен быть на КАЖДЫЙ модуль из паспорта. Не хватает - дозапусти
   сабагента на недостающие модули.
3. Файлы-образцы для матрицы (Этап 3) выбираешь и читаешь ты сам - не больше 3 на шаблон.

# 3. Сабагент технологий проекта

## Когда запускать

Этап 2, п.0, **только если пользователь сам не назвал технологии**. Назвал - сабагент не
нужен, бери список пользователя. Сабагент один, запускается один раз на весь проект.

## Промпт (копируй дословно, подставь <...>)

```
Ты определяешь, с какими технологиями работает проект автотестов. Только считаешь и ищешь
командами. Не меняй файлы. Не читай target/, build/, .gradle/, .idea/, *.jar, *.class. Файлы
исходников целиком не открывай. Верни ТОЛЬКО заполненный шаблон отчёта, без рассуждений и
без сырого вывода команд.

Выполни команды из корня проекта:

2. Для каждого найденного файла сборки:
   grep -hoE "<artifactId>[^<]+</artifactId>|['\"][a-zA-Z0-9_.-]+:[a-zA-Z0-9_.-]+(:[^'\"]*)?['\"]" <файл> | sort -u

## Что делать с отчётом

1. Запиши отчёт как есть в `.gigacode/data/migration/inventory/technologies.md`.
2. Каждая строка таблицы отчёта -> строка таблицы «Технологии проекта» в паспорте карты
   (метку сверь с `references/frame-topics.md`, порядок расставь по правилу из Этапа 2).
3. «Пакеты, которые не удалось отнести» - не выбрасывай: на Этапе 3 каждый такой пакет
   должен попасть либо в строку `G`, либо в «остаётся как есть».
4. Отчёт не по шаблону -> запусти сабагента ещё раз с тем же промптом. Инструмента
   сабагентов нет физически -> выполни команды промпта сам и запиши это в журнал карты.

# 4. Когда документации не хватило (лестница источников)

Документация из MCP - первый и главный источник. Но она бывает неполной: процесс описан не
до конца, непонятно, как что-то вызвать или донастроить. Тогда НЕ выдумывай и НЕ бросай, а
иди по лестнице сверху вниз:

| Ступень | Что делаешь | Нужен человек |
|---------|-------------|---------------|
| 1 | Сабагент документации, как обычно (до 8 формулировок на вопрос - правила выше) | нет |
| 2 | В паспорте карты заполнена строка «Проект-пример» -> запусти сабагента примеров на этот путь (промпт ниже) | нет |
| 3 | В паспорте заполнена строка «Исходники фрейма» -> запусти сабагента примеров на этот путь | нет |
| 4 | Ответа всё ещё нет -> вопрос человеку с вариантами (текст ниже). До ответа это место не делается | да |

Ступени 2 и 3 пропускай, если соответствующая строка паспорта пустая (`-`).

**Пути даёт ТОЛЬКО человек.** Сам проект-пример и исходники фрейма не ищи: не лазь по
диску, в `~/.m2`, `.gradle`, не распаковывай и не декомпилируй `.jar`. Исходники - это
папка с `.java`-файлами фрейма, которую человек скачал и путь к которой назвал. Jar-файлы
исходниками не считаются.

## Текст вопроса человеку (ступень 4, копируй, подставь <...>)

```
В документации фрейма не хватает: <что именно непонятно, 1-2 строки> (технология <метка>).
Что уже пробовал: <сколько формулировок запроса; смотрел ли проект-пример / исходники>.
Выбери, как поступить:
1) запустить поиск по документации ещё 1-2 раза другими формулировками;
2) дать полный путь к проекту-примеру (драфт-проект фрейма) - изучу, как это сделано там;
3) скачать исходники фрейма и дать полный путь к ним - изучу там;
4) объяснить самому, как это делается;
5) не мигрировать это место, оставить как есть.
```

Запиши этот вопрос в раздел 6 карты. Что делать с ответом:
- `1` -> запусти сабагента документации ещё раз (до 2 запусков), передав все уже
  испробованные формулировки; не помогло -> задай вопрос снова, без варианта 1;
- `2` или `3` + путь -> впиши путь в паспорт карты (строка «Проект-пример» или «Исходники
  фрейма») - он пригодится и в следующих чатах; запусти сабагента примеров;
- `4` -> запиши объяснение человека записью конспекта со статусом `найден` и источником
  `человек`; работай по ней;
- `5` -> отметь это место в карте как «остаётся как есть», в юниты не включай.

## Сабагент примеров - промпт (копируй дословно, подставь <...>)

```
Ты ищешь в чужом проекте, как на фрейме PVATF делается конкретная вещь. Проект только
читаешь: ничего не меняй, не запускай сборку и тесты. Не читай target/, build/, .gradle/,
.idea/, *.jar, *.class. Не отвечай по памяти и по аналогии с другими фреймами - только то,
что нашёл в файлах по указанному пути. Верни ТОЛЬКО заполненные блоки по шаблону.

Путь: <полный путь, который дал человек>
Что это: <проект-пример (драфт) | исходники фрейма>
Технология: <метка и обычное название>
Вопросы:
1. <вопрос>
2. <вопрос>

Для КАЖДОГО вопроса:
Шаг 1. Найди файлы по ключевым словам вопроса и технологии (имена классов, аннотаций,
  модулей - по-английски):
  grep -rlE "<слово1>|<слово2>|<слово3>" --include=*.java --include=*.kt --include=*.md --include=*.xml --include=*.gradle --include=*.kts --include=*.properties --include=*.yml <путь> | head -30
  Пусто - попробуй другие слова (до 3 попыток).
Шаг 2. Открой не больше 5 самых подходящих файлов. В первую очередь - тесты и примеры
  (каталоги test, example, sample, draft), README и docs; потом - сами классы.
Шаг 3. Выпиши ответ по шаблону. Каждое имя - символ в символ, как в файле.

На КАЖДЫЙ вопрос верни РОВНО такой блок (заголовки полей сохрани):

### Вопрос <номер>: <текст вопроса>
- Статус: найден | найден частично | НЕТ В ПРИМЕРЕ
- Что использовать: <точные имена классов / аннотаций / методов вместе с пакетом; нет - напиши: ->
- Как подключить: <зависимость group:artifact, как в файле сборки проекта; нет - напиши: ->
- Как настроить: <файл, параметры, значения; нет - напиши: ->
- Пример (дословно из файла, не больше 15 строк):
- Откуда: <путь к файлу>:<строки>

Ответ сабагента примеров записывай в конспект той же записью `D-<tech>-<n>`, что и ответы
документации, с дополнительной строкой `- Источник: проект-пример <путь к файлу>:<строки>`
(или `исходники фрейма ...`). Такая запись - полноценное док-основание. Если документация и
пример расходятся - права документация, расхождение запиши в ту же запись.
