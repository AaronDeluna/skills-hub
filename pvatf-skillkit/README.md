# PVATF Skillkit

Набор скиллов для агента (GigaCode CLI), который работает с проектами автотестов на
Platform V AT Framework (PVATF). Сейчас в наборе - миграция существующего проекта автотестов
на фрейм, проверка её результата, разметка тестов аннотациями allure-annotations, проверка,
настройка и обновление окружения и генерация автотестов по тест-кейсам.

Скиллы рассчитаны на агента с ограниченным контекстом: большая работа режется на маленькие
задачи (юниты), всё состояние хранится в файлах проекта, каждая задача делается в отдельном
чате.

## Что умеет

**Миграция на PVATF**

| Задача | Как попросить |
|--------|---------------|
| Перевести проект автотестов на PVATF целиком | `/orchestrator Мигрируй проект на PVATF` |
| То же, с подсказками: технологии проекта и проект-пример | `/orchestrator Мигрируй проект на PVATF. Технологии: REST, Kafka, БД. Проект-пример: /home/user/pvatf-draft` |
| Перевести только ядро, тесты не трогать | `/orchestrator Переведи только ядро, тесты не трогай` |
| После ядра перевести и тесты | `/orchestrator Теперь переводи тесты` |
| Продолжить с того места, где остановились | `/orchestrator Продолжи миграцию` |
| Сделать один юнит | `/orchestrator Сделай юнит M-012` |
| Сделать несколько мелких юнитов за один чат | `/orchestrator Сделай с M-001 по M-003` или `/orchestrator Сделай M-001, M-002, M-005` |
| Посмотреть, что сделано и что дальше | `/orchestrator Покажи статус миграции` |
| Ответить на вопросы карты | ответ в чате: номер вопроса и вариант, например `Q-1: вариант 2, путь /home/user/pvatf-draft` |
| Подшаги делать сабагентами (режим менеджера) или самому | `/orchestrator Подшаги делай сабагентами` / `/orchestrator Подшаги делай сам` |
| Обновить карту, если проект сильно изменился | `/orchestrator Обнови карту миграции` |
| Сжать разросшуюся карту: выполненное уходит в архив | `/orchestrator Сожми карту` |
| Проверить результат миграции и завести задачи на исправление | `/orchestrator Проверь миграцию` |
| Проверить миграцию, когда карты уже нет | `/orchestrator Проверь миграцию. Старые библиотеки: io.restassured, org.assertj` |

**Разметка тестов (без миграции)**

| Задача | Как попросить |
|--------|---------------|
| Проверить разметку по правилам и получить отчёт с проблемами, без правок | `/orchestrator Проверь разметку в проекте` |
| Исправить то, что нашла проверка разметки | `/orchestrator Поправь разметку по отчёту` |
| Сразу поставить недостающую разметку | `/orchestrator Разметь тесты` или `/orchestrator Настрой разметку` |
| Продолжить разметку с той части, где остановились | `/orchestrator Продолжи разметку` |

**Окружение**

| Задача | Как попросить |
|--------|---------------|
| Проверить окружение: сборка, зависимости фрейма, конфигурация, плагины, компиляция | `/orchestrator Проверь окружение` |
| Понять, почему проект не компилируется | `/orchestrator Почему не компилируется` |
| Доставить недостающее в окружение по документации фрейма | `/orchestrator Настрой окружение` |
| То же, по проекту-примеру | `/orchestrator Настрой окружение. Проект-пример: /home/user/pvatf-draft` |
| Обновить фрейм до последней версии и исправить код после обновления | `/orchestrator Обнови окружение` |
| Обновить фрейм до конкретной версии | `/orchestrator Обнови фрейм до 3.5.0` |
| Продолжить прерванное обновление | `/orchestrator Продолжи обновление` |
| Вернуть версию фрейма и правки к состоянию до обновления | `/orchestrator Откати обновление` |

**Генерация автотеста по тест-кейсу**

| Задача | Как попросить |
|--------|---------------|
| Сгенерировать автотест по тест-кейсу из TMS (md, xml или json Zephyr / TestOps / Allure) | `/orchestrator Сгенерируй автотест по ТК tc/CMN-T120.xml` |
| Только оценить тест-кейс: PASS / WARNING / FAIL и что исправить | `/orchestrator Проверь тест-кейс tc/CMN-T120.md` |
| Продолжить генерацию с того места, где остановились | `/orchestrator Продолжи генерацию CMN-T120` |
| Собрать и проверить тест-класс, когда все шаги сгенерированы | `/orchestrator Собери автотест CMN-T120` |

**Проверка существующего автотеста**

| Задача | Как попросить |
|--------|---------------|
| Проверить автотест и привести к правилам: нарушения, константы, дубли, зависимые тесты | `/orchestrator Проверь автотест src/test/java/ru/demo/tests/PayTest.java` |
| Вынести литералы теста в константы | `/orchestrator Вынеси константы из теста src/test/java/ru/demo/tests/PayTest.java` |
| Продолжить прерванную проверку | `/orchestrator Продолжи проверку автотеста` |
| Вернуть тест и связанные файлы к состоянию до правок | `/orchestrator Откати правки теста src/test/java/ru/demo/tests/PayTest.java` |

Не умеет: переносить тесты из старого проекта в новый отдельный проект. На такую просьбу
агент ответит, что это не поддерживается.

## Скиллы

| Скилл | Что делает | Меняет код |
|-------|------------|------------|
| `orchestrator` | Единая точка входа. Смотрит состояние миграции и запускает нужный скилл; сам ведёт отдельную проверку разметки | только разметку, по согласию |
| `migration-map` | Строит карту миграции: технологии проекта, что на что меняется, целевая картина, список юнитов | нет |
| `migration-step` | Выполняет один юнит: правит код, проверяет, коммитит в ветку миграции | да |
| `migration-review` | Проверяет результат миграции целиком и заводит юниты исправления | нет |
| `env-check` | Проверяет окружение проекта (E1-E6) и, по просьбе, доставляет недостающее по документации | только сборку и конфигурацию, режим setup |
| `env-update` | Обновляет фрейм до последней версии: release notes, замена версии, компиляция, правки по changelog, откат | сборку и код, связанный с обновлением |
| `autotest-plan` | Разбирает тест-кейс: единый вид, оценка пригодности, план генерации | нет |
| `autotest-gen` | Генерирует автотест по плану: классы шагов, тест-класс, проверка и компиляция | да (новые файлы и методы) |
| `autotest-review` | Проверяет существующий автотест: нарушения правил кода, SQL со склейкой, литералы для констант, дубли, зависимые тесты; правит одобренное, компилирует до и после, откатывает при ошибке | да (только одобренные правки) |

Вызывать напрямую нужно только `orchestrator` - остальные он запускает сам.

### Как устроен набор

- **Короткий SKILL.md + части по требованию.** В каждом скилле SKILL.md - навигация и
  свои правила, подробности - в `references/`, которые модель открывает только на нужном
  этапе. Так меньше текста в контексте и меньше забывается.
- **Общие правила - один файл** `shared/core-rules.md` (10 правил на все скиллы). В
  скиллах лежат его копии `references/core-rules.md`.
- **Детерминированное - в скриптах, а не в словах.** Скрипты на Python 3.8+ (только
  стандартная библиотека, работают на Windows, macOS и Linux; на Windows без `python3` -
  `python` или `py -3`):

  | Скрипт | Что делает |
  |--------|------------|
  | `orchestrator/scripts/next_action.py` | читает файлы процесса и печатает одно следующее действие: миграция (юнит, пачка), `env check/setup/update`, `autotest [ключ или файл ТК]`; ставит агентов набора |
  | `migration-step/scripts/unit.py recite` | напоминание перед каждым подшагом: подшаг, файлы, итог, чекпоинт, правила |
  | `migration-step/scripts/unit.py rules` | кладёт текст правил текущего подшага в `tmp/rules-now.md`, а записи конспекта, на которые он ссылается, - в `tmp/docs-now.md` |
  | `migration-step/scripts/unit.py check` | самопроверка правил кода по файлам подшага и изменённые файлы вне карточки |
  | `migration-step/scripts/markup_keys.py` | ключи тест-кейсов в тест-методах и разметка тест-классов: `missing`, `dup`, `count`, `classes` |
  | `migration-map/scripts/card.py` | механическая проверка карточек: поля, лимиты, пустые слова, покрытие потребителей, `L`, записи конспекта |
  | `scripts/notes.py` (в скиллах миграции, окружения и генерации) | поиск по конспекту документации: `list`, `find`, `show`, `next` (следующий свободный ID). Запускается перед каждым сабагентом документации |
  | `env-check/scripts/env_check.py` | проверка окружения E1-E6: сборка, каталог тестов, зависимости фрейма, конфигурация, плагины, компиляция; пишет `ENV.json` |
  | `env-update/scripts/env_update.py` | `versions` - где объявлена версия фрейма; `latest` - новейшая версия из release notes; `bump` - замена версии с копией файлов; `rollback`; `usages` - где в коде имена из changelog; `errors` - ошибки компиляции по файлам |
  | `autotest-plan/scripts/tc_convert.py` | тест-кейс из TMS (md, xml, json Zephyr / TestOps / Allure) -> единый `TC.md` |
  | `autotest-plan/scripts/tc_check.py` | оценка ТК по правилам TC-0..TC-13: PASS / WARNING / FAIL |
  | `autotest-plan/scripts/tc_plan.py` | `build` - план генерации: шаги, типы, технологии, шаги генерации G, константы, классы проекта; `validate` - проверка плана |
  | `autotest-gen/scripts/at_tools.py` | `rules`, `next` (задание генератору), `mark`, `assemble` (тест-класс из фрагментов), `check` (правила кода, покрытие шагов ТК, компиляция) |
  | `autotest-review/scripts/review.py` | `find` (находки и план), `approve`, `start` (компиляция до правок, копия исходников, константы), `next` (задание генератору), `mark`, `check` (новые нарушения и компиляция, до 3 кругов), `rollback` |
  | `scripts/java_checks.py` (в `autotest-gen` и `autotest-review`) | общие проверки правил кода и компиляция командой из `ENV.json` |

- **Агенты набора - файлы, а не пересказ.** Сабагенты, которые запускаются чаще всего, описаны
  агентами GigaCode в `orchestrator/agents/`: инструкция лежит в агенте, основной чат
  передаёт только задание. Инструменты ограничены самим GigaCode (`disallowedTools`), а не
  словами в промпте:

  | Агент | Что делает | Что ему нельзя |
  |-------|------------|----------------|
  | `pvatf-docs` | справка из документации MCP по вопросам | менять файлы, запускать команды |
  | `pvatf-examples` | как сделано в проекте-примере или исходниках фрейма | менять файлы |
  | `pvatf-checker` | проверяющий после каждого подшага | менять файлы |
  | `pvatf-executor` | исполнитель подшага в режиме менеджера | - (правки разрешены, `approvalMode: auto-edit`) |
  | `pvatf-generator` | код одного шага генерации автотеста (методы классов шагов и фрагмент тест-метода) или одна правка существующего теста | менять план и `.gigacode/` (правки кода разрешены, `approvalMode: auto-edit`) |
  | `pvatf-markup-analyst` | анализ разметки и карта разметки по частям (отдельная проверка разметки) | менять код проекта: пишет только `.gigacode/data/markup/` |
  | `pvatf-marker` | разметка тестов аннотациями allure-annotations (юнит `markup` и отдельная разметка - часть за частью по карте разметки) | - (правки разрешены, `approvalMode: auto-edit`) |

  `next_action.py` при каждом запуске копирует их в `.gigacode/agents/` проекта, если их там
  нет или они устарели, и просит перезапустить GigaCode. Править агентов - только в наборе: копия в
  проекте перезаписывается.
- **Карточки технологий строят сабагенты из файлов**, а не основной чат по памяти: разбор
  технологии -> составитель карточки -> `card.py` -> проверяющий карточки.

### Для разработчиков набора

Общие файлы правьте только в `shared/`; что в какой скилл копируется - `shared/copies.json`
(правила миграции, `code-rules.md`, `matchers.md`, `markup-rules.md`, `autotest-rules.md`,
`scripts/notes.py`, `scripts/frame_versions.py`). Потом разложите копии, проверьте и прогоните
золотой набор скриптов (36 проверок на временных проектах):
```
python3 scripts/sync_shared.py
python3 scripts/sync_shared.py --check
python3 scripts/selftest.py
```
Тестовые промпты оркестратора и ожидаемые действия - `tests/golden-prompts.md`. После смены
модели или текста скилла прогоните их заново.

## Что нужно для работы

- GigaCode CLI с подключённым MCP-сервером `ai-pdlc-autotest-generation-remote`
  (документация фрейма - `get_pv_at_doc`, версии - `get_pvat_release_notes`, изменения между
  версиями - `get_pvat_changelog`).
- Python 3.8 или выше - для скриптов скиллов.
- Скиллы из этой папки установлены в агента (видны по команде `/skills`).
- Проект автотестов - git-репозиторий, локально установлен JDK 17 или выше, Maven или Gradle
  (или обёртка `mvnw` / `gradlew` в проекте).
- Желательно: локальный git-клон исходников фрейма и драфт-проекта Platform V
  (`platform-v-at-maven-draft`). Агент сам находит их на диске и обновляет (`git pull`) при
  построении карты; не нашёл - один раз спрашивает путь или адрес репозитория. Когда в
  документации нет ответа, агент ищет так: документация -> исходники фрейма (их `docs`,
  тесты, примеры) -> драфт-проект -> и только потом спрашивает вас.

## Быстрый старт

Каждый шаг - новый чат в корне мигрируемого проекта.

1. **Запуск.**
   ```
   /orchestrator Мигрируй проект на PVATF
   ```
   Агент начнёт строить карту. Технологии проекта он определит сам. Если хотите задать их
   явно:
   ```
   /orchestrator Мигрируй проект на PVATF. Технологии: REST, PostgreSQL, Kafka. Начни с REST.
   ```
   Путь к драфт-проекту можно дать сразу:
   ```
   /orchestrator Мигрируй проект на PVATF. Драфт-проект лежит в /home/user/platform-v-at-maven-draft
   ```

2. **Построение карты.** На большом проекте занимает несколько чатов. Агент сам говорит,
   когда открыть новый:
   ```
   /orchestrator Продолжи миграцию
   ```

3. **Вопросы.** Если агенту чего-то не хватило, он покажет список вопросов с вариантами
   ответа. Пока на них нет ответа, работа не продолжается. Если тесты не размечены,
   в начале карты агент по одному спросит значения для разметки, которых нет в проекте:
   где хранится тестовая модель, КЭ системы, контур, команду и, для Allure TestOps, регресс и задачу.
   ```
   Q-1: вариант 2, путь /home/user/platform-v-at-maven-draft
   Q-2: вариант 1 - таймаут задаётся в perfeccionista.properties, ключ ...
   ```

4. **Утверждение карты.** Агент покажет сводку и спросит «Карту утверждаем?». Перед ответом
   откройте `.gigacode/data/migration/MIGRATION-MAP.md` и посмотрите блоки `T-<технология>`
   («целевая картина»): там должны стоять конкретные имена классов и matchers из
   документации, а не общие слова. Посмотрите и `ARCHITECTURE.md` - архитектурный план: какие
   классы появятся и за что каждый отвечает. Его можно поправить до утверждения. Если всё в
   порядке:
   ```
   Да
   ```

5. **Выполнение юнитов.** Один чат - один юнит:
   ```
   /orchestrator Продолжи миграцию
   ```
   Технология (REST, БД, Kafka) - это один большой юнит, внутри он разбит на подшаги. Агент
   делает все подшаги подряд в одном чате, контекст по ходу сжимается сам. Вопросов во
   время работы он не задаёт: все вопросы - на этапе карты, до её утверждения. Спорные
   места он откладывает строками «решить человеку» в карте и идёт дальше.
   Можно поставить пачку, до 5 юнитов подряд, и заниматься своими делами:
   ```
   /orchestrator Сделай с M-001 по M-004
   ```

6. **Проверка.** Когда все юниты выполнены, агент сам запустит проверку миграции. Если
   найдёт проблемы - заведёт юниты исправления, и дальше снова:
   ```
   /orchestrator Продолжи миграцию
   ```
   Проверка повторяется после исправлений, до трёх кругов.

7. **Завершение.** После чистой проверки агент предложит удалить служебную папку миграции.
   Пуш и слияние ветки делаете вы.

## Разметка тестов без миграции

Разметку можно проверить и поставить отдельно, без карты миграции:
```
/orchestrator Проверь разметку в проекте
```
Агент найдёт тест-классы, проверит пять основных аннотаций - контур (`@TestStage`), слой
(`@TestLayer`), КЭ (`@System`), команду (`@Team`), TMS-link (`@TmsLink`) - и, для модели в
Allure TestOps, регресс и задачу. Потом проверит разметку по правилам (15 пунктов):
`@Team` (одна команда - `<команда> (<ФОС>)`, несколько - название), КЭ, контур, слой не технология, противоречия у
тест-класса, `@TmsLink` над методом, одинаковые ключи, импорты и другие. Ничего не меняет.

Отчёт - `.gigacode/data/markup/MARKUP-REPORT.md`. В разделе «Проблемы» каждая находка - одной
строкой `MK-<n>`: правило, файл и строка, что не так, как исправить, кто исправит (агент или
человек). По отчёту можно быстро перепроверить себя, а потом попросить:
```
/orchestrator Поправь разметку по отчёту
```
Агент проверит проект заново, по одному спросит недостающие значения, покажет план, после
«да» исправит строки «агент» агентом `pvatf-marker` (коммит на часть плана) и перепроверит. Строки
«человек» (одинаковые ключи, противоречия, настройка Allure) остаются вам. Логика тестов не
меняется.

`/orchestrator Разметь тесты` (или `Настрой разметку`) ставит недостающее - так же, как
миграция, через карту:
1. **Вопросы - сразу, до анализа**, по одному: одна команда или несколько, команда, ФОС, КЭ,
   контур, где тестовая модель (и для Allure TestOps - регресс и задача). Спрашивает всегда,
   даже если разметка в проекте уже есть. Ответы - в раздел «Значения разметки» отчёта.
2. **Анализ** - агент `pvatf-markup-analyst`. Скрипт `markup_keys.py classes` выписывает
   каждый тест-класс: что у него есть (своё или от базового класса) и чего нет (`НЕТ`).
   Агент сверяет ответы с проектом и пишет карту разметки: тест-классы без разметки,
   расхождения, проблемы по правилам и план - строка на файл, каждая аннотация полностью со
   значением, частями по 15 файлов.
3. **Расхождения** - если ответы не сходятся с проектом, агент спросит отдельно. Например,
   вы назвали один КЭ, а в проекте их три: оставить один на все тесты или разметить тесты
   двух других КЭ их КЭ. После ответов план строится заново.
4. **Разметка** - агент `pvatf-marker` по плану, одна часть - один запуск и один коммит. По
   каждой строке плана - «сделано» или причина. Основной чат проверяет каждую аннотацию в
   файле и в конце прогоняет `classes` по всем тест-классам: всё, что осталось `НЕТ`, - в
   итоговом ответе с причиной. Прервалось - `/orchestrator Продолжи разметку`.

Вопросы с вариантами: в окне вопроса последним пунктом всегда есть поле для своего ответа,
поэтому пунктов «укажу своё значение» агент не добавляет. Свой ответ - в поле ввода.

- `@Team`: агент сначала спросит, одна команда в проекте или несколько. Одна - название и
  ФОС в круглых скобках, строго так: `@Team("uwptext (00CG0000)")` (система берёт ФОС из
  скобок). Несколько - только название, без ФОС: `@Team("uwptext")`, у каждой команды над
  своими тестами; агент спросит, чьи какие тесты. Название - официальное, из справочника.
- `@TmsLink` агент ставит, только если ключ тест-кейса уже записан в аннотации тест-метода
  (`@DisplayName`, `@Zephyr` или другой): копирует его в `@TmsLink`, саму аннотацию не меняет. Ключ тест-кейса - с буквой `T`
  перед цифрами (`SBOLCRM-T1234`); ключ без неё (`PVATF-4567`) - задача, его агент не берёт.
  Остальные ключи есть только в TMS: агент покажет, в каких тестах их нет, - их ставите вы.
- Если в проекте идёт миграция, разметку поставит её шаг: агент только проверит и скажет,
  какой юнит это сделает.
- Перед правками агент проверяет три вещи и без них не начинает:
  - в проекте нет незакоммиченных изменений - иначе попросит их закоммитить;
  - allure-annotations версии 2.x - если ниже, предложит поднять до 2.0.2, а при отказе
    скажет, что разметить по правилам не получится;
  - проект компилируется - иначе покажет ошибку и попросит сначала исправить сборку.

## Как идёт миграция

Порядок работ зашит в карту:

1. **Java 17** - если в проекте версия ниже, это первый юнит.
2. **Зависимости** - подключение фрейма и его модулей под все технологии, одним юнитом.
3. **Технологии по одной, от простой к сложной** (REST, потом БД, потом Kafka и т.д.).
   На каждую технологию - один юнит. Он доводится до конца, и только потом начинается
   следующая. Подшаги внутри юнита идут строго по порядку:
   - разбор: кто и как обращается к технологии сейчас;
   - окружение и конфигурация;
   - новое основание: конфигурация фрейма и классы шагов;
   - перевод на них шагов и тестов, проверки - на matchers, снизу вверх;
   - удаление всего старого по этой технологии: классы, зависимости, конфиги;
   - ревью кода этой технологии (не всего проекта) сабагентами. На находки агент сам
     дописывает в карточку новые подшаги и выполняет их.
   У каждого подшага в карточке записано, что сделать, какой должен быть итоговый
   результат и чекпоинт - команда, которая это проверяет. В конце юнита выполняются общие
   чекпоинты: старого кода нет, к фрейму обращаются только классы шагов, каждый созданный
   класс кто-то вызывает, тесты не пропали. Пока хоть один не сошёлся, юнит не закрыт.
4. **Архитектура** - правки устройства проекта после миграции.
5. **Финальная зачистка** - общее старое, не привязанное к одной технологии.
6. **Разметка тестов** - аннотации allure-annotations (контур, слой, КЭ системы, команда и,
   для Allure TestOps, регресс и задача). Ставит агент `pvatf-marker`, каскадом: общее - над базовым тест-классом. Юнита нет,
   если проект уже размечен или выбран режим «только ядро».
7. **Финальная проверка** - когда все юниты выполнены, весь проект проверяется целиком;
   на найденное заводятся юниты исправления.

Файлы, которые используют сразу несколько технологий (например, тест ходит и в REST, и в
БД), мигрируются один раз - в последней из своих технологий. Старые классы, которые им
нужны, удаляются вместе с ними.

До начала работ агент проектирует проект «как должно быть в конце» и записывает это в
архитектурный план (`ARCHITECTURE.md`): слои, дерево пакетов и таблица классов - за что
отвечает каждый класс и кто его вызывает. Юниты создают только классы из плана, а код
кладётся в класс с подходящей ответственностью. Если по ходу понадобился класс, которого в
плане нет, агент может добавить не больше одного за юнит и записывает его в план.

Если тесты написаны для ИФТ или уже разбиты на шаги, агент строит архитектуру вокруг
FlowRunner фрейма: тест становится цепочкой именованных шагов, а действия и проверки лежат в
классах-флоу. В остальных случаях используются обычные классы шагов. Способ можно задать
явно: `/orchestrator Мигрируй через FlowRunner` или `/orchestrator Мигрируй без флоу`.

Технология, про которую в документации фрейма ничего нет (например, конкретная СУБД), не
мигрируется и остаётся на старой реализации.

## Режимы

| Режим | Как включить | Что происходит |
|-------|--------------|----------------|
| Полная миграция | по умолчанию | Все шаги выше |
| Только ядро | `/orchestrator Переведи только ядро, тесты не трогай` | Внутренности классов ядра переводятся на фрейм, их публичные методы сохраняются, тесты не меняются. Удаление старого и перевод тестов ждут |
| Переход к полной | «теперь переводи тесты» | Продолжение по полной схеме |
| Режим менеджера (по умолчанию) | ничего не нужно; переключить: `/orchestrator Подшаги делай сам` или `/orchestrator Подшаги делай сабагентами` - в любой момент | Каждый подшаг делает отдельный сабагент-исполнитель с чистым контекстом, строго по одному; основной чат готовит пакет, проверяет и коммитит. Если на первом подшаге окажется, что сабагенты не умеют менять файлы, агент сам переключится на режим «сам» и запишет причину в паспорт карты |

### Проверка сабагентов (по желанию)

Режим менеджера работает, только если сабагенты GigaCode умеют менять файлы и запускать
команды. Агент проверяет это сам на первом подшаге. Агенты набора видны по команде
`/agents manage` (после первого запуска оркестратора в проекте). Проверить права заранее
можно так, в любом git-проекте:
```
Запусти сабагента с таким заданием и покажи его ответ дословно:
«1) Создай файл subagent-check.txt с текстом ok. 2) Выполни команду java -version и
верни первую строку вывода. 3) Попробуй запустить ещё одного сабагента с заданием
"ответь ok" и напиши, получилось ли. Верни три строки: файл - создан/нет; java - <строка>;
вложенный сабагент - да/нет.»
Потом проверь сам, что файл subagent-check.txt есть, и удали его.
```
Файл создан и `java` ответила -> режим менеджера будет работать. Вложенный сабагент не
нужен: документацию для исполнителя добывает основной чат.

## Правила, по которым агент пишет код

Полный список - в `migration-step/references/code-rules.md`. Главное:

- Сабагенты используются только для анализа: прочитать документацию, найти в проекте,
  проверить код. Писать и править код сабагентам не поручается - это делает основной агент.
- Источник знаний о фрейме - только документация из MCP. В jar и `~/.m2` агент не лезет,
  по памяти не пишет.
- Старая архитектура не переносится: обёртки над библиотеками, свои ассерты, базовые классы с клиентами и методами
  удаляются, а не «адаптируются».
- Проверки - через matchers фрейма (`.should(...)`), а не через `Assertions`. Ответ не
  превращается в DTO ради сравнения полей: если значение доставали руками и потом
  сравнивали, цепочка переписывается целиком, а лишний DTO удаляется.
- Тест-класс содержит только сценарий. Запросы, SQL, маппинг лежат в классах шагов.
- Проверки пишутся готовыми matchers фрейма: matcher выбирается по типу значения (текст,
  число, дата, boolean, null, размер), вызывается прямо в `.should(...)`. Свои обёртки над
  matchers, свои классы matchers, списки matchers в цикле, разбор ответа в `JsonNode` и
  `assertAll` запрещены (группа проверок - `.shouldSoft(...)`, именованный шаг -
  `Allure.step(...)`); на финальной проверке это ищется отдельно (`P13`).
- Слои фиксированы: тест -> шаги предметной области -> базовый слой технологии (один
  класс на технологию с общими `get`/`post`/`put`/`delete`, выполнением SQL) -> фрейм.
  Фасадов-делегатов, вложенных классов и методов-близнецов нет (`P14`).
- В настройках фрейма стоят те же адреса, учётные данные и сертификаты, что были в
  проекте; пустых ключей и заглушек нет (`P15`).
- Агент не спрашивает очевидное: адреса и учётные данные берёт те, с которыми проект уже
  работал (они записаны в карте), технологией пользуется так же, как раньше, а для типовых
  развилок у него есть таблица решений по умолчанию. Вопрос - только если ответ меняет то,
  что делает тест.
- Если в проекте есть Spring, агент спрашивает: убрать его полностью (тесты на JUnit 5,
  рекомендуем) или оставить и подключить фрейм через его Spring-стартер.
- Технология ведётся одной цепочкой внутри одного юнита: нашли всех, кто к ней обращается,
  -> создали классы шагов -> перевели на них каждого -> удалили старое -> ревью. Класс не
  создаётся «впрок»: это проверяется после подшага, на ревью и чекпоинтами в конце юнита.
- Классы создаются по архитектурному плану: у класса одна ответственность, одно действие
  живёт в одном месте, классов `Utils`, `Helper`, `Common` нет.
- Запросы и ответы руками не логируются: это делает фрейм. Логирование настраивается одним
  файлом `simplelogger.properties`; старые конфигурации логгеров (logback, log4j) и их
  зависимости удаляются.
- Настройки подключений (адреса, алиасы БД, брокеры Kafka) читает фрейм из своих файлов
  настроек: значения переносятся туда; старый код чтения конфигурации и свои
  конфигурационные классы (`DbConfig`, `KafkaConfig` и подобные) удаляются по мере миграции.
- Аннотации подключения фрейма стоят один раз, в базовом тест-классе; тесты от него
  наследуются. Клиентов и методов в базовом классе нет.
- Имена по соглашениям Java: `createOrder`, `orderId`; нижнее подчёркивание только в константах.
- `var` запрещён, классы подключаются через `import`, объекты с несколькими полями
  создаются билдером, сервис фрейма берётся в одном месте класса.
- Классы конфигурации фрейма лежат в пакете `config`.
- Методы до 40 строк, классы с одной ответственностью, без дублей и мёртвого кода.

Свои правила команды можно дописать в конец `code-rules.md`, в блок «Правила: добавлено
человеком».

## Как проверяется результат

- Юниты с зависимостями и конфигурацией проверяются компиляцией, тесты не запускаются.
- Юниты, где менялась логика, - компиляция и один быстрый тест (одним методом, с
  ограничением 10 минут). Весь набор тестов агент не запускает.
- После каждого юнита и каждого подшага - самопроверка grep-командами по правилам кода,
  чекпоинт из карточки и сабагент «проверяющий» со свежим контекстом: он смотрит изменения
  этого подшага по его правилам кода и итоговому результату. Находки агент исправляет сразу,
  до коммита: подшаг - проверка - подшаг - проверка.
- Правила кода агент читает не все сразу, а только правила текущего подшага (5-9 штук, их
  номера записаны в карточке): так они не теряются в длинном контексте.
- После каждой технологии - ревью её кода сабагентами; в конце - проверка миграции целиком.

## Окружение и генерация автотестов

Окружение и генерация - отдельный процесс, без карты миграции. Состояние - в
`.gigacode/data/autotest/`, поэтому оборванный чат продолжается с того же места.

**Окружение.**
- `/orchestrator Проверь окружение` - скрипт `env_check.py` проверяет E1-E6 (файл сборки,
  каталог тестов, зависимости фрейма, конфигурация окружения и `perfeccionista.properties`,
  плагины, компиляция тестов) и пишет `ENV.json`. Ничего не меняет.
- `/orchestrator Настрой окружение` - то же, плюс недостающее доставляется по документации
  фрейма (агент `pvatf-docs`) или проекту-примеру: зависимости, класс конфигурации, ключи
  настроек. После правок проверка повторяется.
- `/orchestrator Обнови окружение` - обновление фрейма по этапам 1-9: проверка до обновления
  -> текущая версия -> release notes из MCP -> самая новая версия (скрипт, не модель) ->
  changelog между версиями и места в коде, которые он затрагивает -> замена версии в файлах
  сборки (с копией) -> компиляция -> до 3 кругов исправлений по changelog и документации ->
  итог. Не сошлось - автоматический откат версии и правок. Версию можно назвать:
  `/orchestrator Обнови фрейм до 3.5.0`.

**Генерация автотеста по тест-кейсу.**
1. `/orchestrator Сгенерируй автотест по ТК <файл>` - сначала проверка окружения (без неё
   генерация не начнётся), потом `autotest-plan`: ТК в единый вид, оценка PASS / WARNING /
   FAIL (при FAIL - что исправить в ТК), план `PLAN.md`: тип и технология каждого шага, шаги
   генерации G, константы и откуда их брать, классы шагов проекта для переиспользования.
2. `/orchestrator Продолжи генерацию <ключ>` - `autotest-gen`: по каждому G агент
   `pvatf-generator` пишет методы классов шагов и фрагмент теста; чего нет в документации -
   основной чат спрашивает `pvatf-docs` и пополняет конспект. Тест-класс собирает скрипт
   (`@Test`, `@TmsLink`, `@DisplayName` с ключом ТК, наследник базового тест-класса проекта),
   проверяет правила кода, покрытие каждого шага ТК и компиляцию.
3. В конце агент предложит `/orchestrator Разметь тесты` - разметка нового класса по
   правилам allure-annotations - и `/orchestrator Проверь автотест <файл>`.

**Проверка существующего автотеста.** `/orchestrator Проверь автотест <файл>` - скилл
`autotest-review`:
1. Скрипт находит нарушения правил кода (те же проверки, что у генерации), SQL со склейкой
   строк, пустые `catch`, тест без `@TmsLink` / `@DisplayName`, литералы для констант
   (числа кроме 0 и 1, строки с цифрами, повторы), блоки из 5 и более строк, которые
   повторяются, и зависимые тесты - где тот же литерал или блок.
2. Агент показывает план и спрашивает: какие правки делать (все / никакие / номера) и
   менять ли зависимые тесты.
3. Скрипт компилирует проект до правок (не компилируется - правок нет), снимает копию
   исходников и сам выносит константы с понятным именем. Остальное по одной правке делает
   агент `pvatf-generator`; чего нет в документации - вопрос `pvatf-docs`.
4. Скрипт ищет новые нарушения и компилирует. До 3 кругов исправлений, потом откат всех
   правок к копии. Итог - `REVIEW.md`.

Поддерживаются технологии: REST, gRPC, GraphQL, WebSocket, базы данных и OpenSearch, Kafka,
UI (Playwright, Selenide), мобильные (Appium Android, iOS), аудит, журналы, PVM-ABYSS,
метрики, Fixtures, TestContainers, SberMock, OpenShift, Toggler, Launcher, ValueService, сессии.

| `MIGRATION-MAP.md` | Карта: паспорт проекта, технологии, что на что меняется, целевая картина, юниты и их статусы, открытые вопросы, журнал |
| `ARCHITECTURE.md` | Архитектурный план: пакеты и классы проекта после миграции, какой класс за что отвечает |
| `units/M-<nnn>.md` | Карточка юнита: файлы, шаги, критерии готовности, журнал выполнения. У юнита технологии - разбор, подшаги со статусами и чекпоинты |
| `CONNECTIONS.md` | Реестр подключений: адреса, учётные данные, сертификаты, топики, переменные окружения - как в проекте сейчас, и куда они переезжают в настройках фрейма |
| `doc-notes/<технология>.md` | Конспект документации фрейма: вопросы, ответы, ключевые слова |
| `inventory/` | Результаты анализа проекта |
| `review/M-<nnn>.md` | Отчёты ревью кода |
| `archive/MAP-ARCHIVE.md` | Архив карты: выполненные юниты, закрытые вопросы, старый журнал |
| `MIGRATION-REVIEW.md` | Отчёт проверки миграции |

Окружение и генерация автотестов - в `.gigacode/data/autotest/`, конспект документации для
них - в `.gigacode/data/doc-notes/<метка>.md`:

| Файл | Что в нём |
|------|-----------|
| `ENV.json` | Последняя проверка окружения: E1-E6, версии фрейма, паспорт тестов, команда компиляции |
| `ENV-SETUP.md` / `ENV-UPDATE.md` | Журнал настройки и обновления окружения |
| `env-update/` | Release notes, changelog, список имён, копии файлов сборки до обновления |
| `<ключ ТК>/TC.md`, `TC-CHECK.md` | Тест-кейс в едином виде и его оценка |
| `<ключ ТК>/PLAN.md` | План генерации: шаги, технологии, G, константы, статусы |
| `<ключ ТК>/fragments/G-<n>.md`, `CHECK.md` | Фрагменты от генератора и итог проверки тест-класса |

Проверка существующих автотестов - в `.gigacode/data/autotest-review/<класс>/`:
`REVIEW-PLAN.md` (находки, выбор, статусы правок), `backup/` (копия исходников до правок),
`REVIEW.md` (отчёт).

Код меняется в отдельной ветке миграции (по умолчанию `pvatf-migration`). Агент коммитит в
неё после каждого юнита и подшага без вопросов. `git push` и слияние он не делает.

## Если что-то пошло не так

| Ситуация | Что делать |
|----------|------------|
| Агент пишет, что есть открытые вопросы | Ответьте на каждый: номер вопроса и вариант. Без ответов работа не идёт |
| Юнит в статусе `blocked` | В карточке юнита, в разделе «Блокер», написано, чего не хватило. Ответьте на вопрос в карте и напишите `/orchestrator Продолжи миграцию` |
| Юнит остался `in-progress` | Чат оборвался или работать стало физически нельзя (не компилируется, тест красный из-за миграции). Напишите `/orchestrator Продолжи миграцию` - агент продолжит с первого несделанного подшага |
| В карте есть строки «решить человеку» | Это места, которые агент отложил, чтобы не останавливать работу. Посмотрите их, когда удобно, и напишите решение - агент заведёт по ним работу |
| Агент не находит что-то в документации | Дайте путь к драфт-проекту или объясните сами - он предложит эти два варианта |
| MCP недоступен | Миграция без документации не идёт. Проверьте подключение MCP-сервера |
| Агент пишет «Агенты набора установлены или обновлены» | Это нормально после установки или обновления набора. Перезапустите GigaCode (выйдите и запустите заново) и введите команду, которую покажет агент, - это ваш же запрос, работа продолжится с того же места |
| Режим сам переключился на «сам»: исполнитель не смог менять файлы | Частая причина - GigaCode запущен в режиме plan: из него сабагенту нельзя дать права на правки. Перезапустите в обычном режиме и напишите `/orchestrator Подшаги делай сабагентами` |
| Проект сильно изменился, карта устарела | `/orchestrator Обнови карту миграции` |
| Агент уже что-то намигрировал, и результат плохой | `/orchestrator Проверь миграцию` - проверка работает и без карты, находит свои конструкции вокруг проверок, лишние слои, остатки старого и заводит юниты исправления. Начать заново: удалите ветку миграции и папку `.gigacode/data/migration`, вернитесь на основную ветку и напишите `/orchestrator Мигрируй проект на PVATF` |
| Карта разрослась и съедает контекст | `/orchestrator Сожми карту` - выполненные юниты, закрытые вопросы и старый журнал уйдут в архив, ничего не теряется |
| Проверка три круга подряд находит проблемы | Агент остановится и покажет повторяющиеся находки - их нужно посмотреть человеку |
| Карта построена старой версией скиллов | Переименуйте `.gigacode/data/migration/` и постройте карту заново: формат карты менялся |
| Генерация пишет «окружение не проверено» или «failed» | `/orchestrator Проверь окружение`, потом `/orchestrator Настрой окружение`; генерация идёт только при статусе ok или warning |
| Тест-кейс получил FAIL | Исправьте ТК по находкам из `TC-CHECK.md` (в ответе агента - что именно) и дайте файл заново |
| В сгенерированном тесте есть `// STUB` | Шаг не удалось написать: причина - в разделе 7 `PLAN.md`. Ответьте на вопрос или допишите вручную |
| Обновление фрейма не сошлось | Агент сам откатит версию и правки (`update_status: rolled-back`); что не удалось - в `ENV-UPDATE.md`, раздел «Осталось человеку» |
| Проверка автотеста пишет «проект не компилируется до правок» | Сначала `/orchestrator Настрой окружение` или почините сборку; правки на неработающем проекте не делаются |
| После проверки автотеста что-то сломалось | `/orchestrator Откати правки теста <файл>` - все файлы вернутся к копии до правок, новые файлы удалятся |
| Скриптам нужен Python, а `python3` нет (Windows) | Установите Python 3.8+; агент запускает `python` или `py -3` |

## Ограничения

- Перенос тестов из одного проекта в другой не поддерживается.
- Скиллы держатся на строгих шаблонах: файлы карты и плана руками лучше не
  переформатировать - заголовки и названия колонок читают скрипты и другие скиллы.
- Качество миграции зависит от целевой картины и архитектурного плана. Если они написаны
  общими словами или в плане есть классы с размытой ответственностью, не утверждайте карту.
- Если в проекте большинство тестов используют сразу несколько технологий, основная работа
  придётся на юнит последней из них: такие тесты мигрируются один раз, в конце.
