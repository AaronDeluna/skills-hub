# PVATF Skillkit

Набор скиллов для агента (GigaCode CLI), который работает с проектами автотестов на
Platform V AT Framework (PVATF). Сейчас в наборе - миграция существующего проекта автотестов
на фрейм и проверка её результата.

Скиллы рассчитаны на агента с ограниченным контекстом: большая работа режется на маленькие
задачи (юниты), всё состояние хранится в файлах проекта, каждая задача делается в отдельном
чате.

## Что умеет

| Задача | Как попросить |
|--------|---------------|
| Перевести проект автотестов на PVATF целиком | «мигрируй проект на PVATF» |
| Перевести только ядро, тесты не трогать | «переведи только ядро, тесты не трогай» |
| Продолжить с того места, где остановились | «продолжи миграцию» |
| Сделать несколько мелких задач за один чат | «сделай с M-001 по M-003» |
| Посмотреть, что сделано и что дальше | «покажи статус миграции» |
| Проверить результат миграции и завести задачи на исправление | «проверь миграцию» |
| Сжать разросшуюся карту: выполненное уходит в архив | «сожми карту» |

Не умеет: переносить тесты из старого проекта в новый отдельный проект. На такую просьбу
агент ответит, что это не поддерживается.

## Скиллы

| Скилл | Что делает | Меняет код |
|-------|------------|------------|
| `orchestrator` | Единая точка входа. Смотрит состояние миграции и запускает нужный скилл | нет |
| `migration-map` | Строит карту миграции: технологии проекта, что на что меняется, целевая картина, список юнитов | нет |
| `migration-step` | Выполняет один юнит: правит код, проверяет, коммитит в ветку миграции | да |
| `migration-review` | Проверяет результат миграции целиком и заводит юниты исправления | нет |

Вызывать напрямую нужно только `orchestrator` - остальные он запускает сам.

## Что нужно для работы

- GigaCode CLI с подключённым MCP-сервером `ai-pdlc-autotest-generation-remote`
  (документация фрейма - инструмент `get_pv_at_doc`, версии - `get_pvat_release_notes`).
- Скиллы из этой папки установлены в агента (видны по команде `/skills`).
- Проект автотестов - git-репозиторий, локально установлен JDK 17 или выше.
- Желательно: локальная копия драфт-проекта Platform V
  (`platform-v-at-maven-draft`). Она нужна, когда в документации не хватает ответа.

## Быстрый старт

Каждый шаг - новый чат в корне мигрируемого проекта.

1. **Запуск.**
   ```
   Мигрируй проект на PVATF
   ```
   Агент начнёт строить карту. Технологии проекта он определит сам. Если хотите задать их
   явно:
   ```
   Мигрируй проект на PVATF. Технологии: REST, PostgreSQL, Kafka. Начни с REST.
   ```
   Путь к драфт-проекту можно дать сразу:
   ```
   Мигрируй проект на PVATF. Драфт-проект лежит в /home/user/platform-v-at-maven-draft
   ```

2. **Построение карты.** На большом проекте занимает несколько чатов. Агент сам говорит,
   когда открыть новый:
   ```
   Продолжи миграцию
   ```

3. **Вопросы.** Если агенту чего-то не хватило, он покажет список вопросов с вариантами
   ответа. Пока на них нет ответа, работа не продолжается.
   ```
   Q-1: вариант 2, путь /home/user/platform-v-at-maven-draft
   Q-2: вариант 1 - таймаут задаётся в perfeccionista.properties, ключ ...
   ```

4. **Утверждение карты.** Агент покажет сводку и спросит «Карту утверждаем?». Перед ответом
   откройте `.gigacode/data/migration/MIGRATION-MAP.md` и посмотрите блоки `T-<технология>`
   («целевая картина»): там должны стоять конкретные имена классов и matchers из
   документации, а не общие слова. Посмотрите и `ARCHITECTURE.md` - архитектурный план: какие
   классы появятся и за что каждый отвечает. Его можно поправить до утверждения. Если всё в
   порядке:
   ```
   Да
   ```

5. **Выполнение юнитов.** Один чат - один юнит:
   ```
   Продолжи миграцию
   ```
   Технология (REST, БД, Kafka) - это один большой юнит, внутри он разбит на подшаги. За
   один чат он обычно не заканчивается: агент делает несколько подшагов, оставляет юнит в
   статусе `in-progress` и просит открыть новый чат. В новом чате снова пишете «Продолжи
   миграцию» - он открывает карточку и продолжает с первого несделанного подшага.
   Мелкие юниты (Java 17, зависимости) можно делать пачкой, до 5 за раз:
   ```
   Сделай с M-001 по M-004
   ```

6. **Проверка.** Когда все юниты выполнены, агент сам запустит проверку миграции. Если
   найдёт проблемы - заведёт юниты исправления, и дальше снова:
   ```
   Продолжи миграцию
   ```
   Проверка повторяется после исправлений, до трёх кругов.

7. **Завершение.** После чистой проверки агент предложит удалить служебную папку миграции.
   Пуш и слияние ветки делаете вы.

## Как идёт миграция

Порядок работ зашит в карту:

1. **Java 17** - если в проекте версия ниже, это первый юнит.
2. **Зависимости** - подключение фрейма и его модулей под все технологии, одним юнитом.
3. **Технологии по одной, от простой к сложной** (REST, потом БД, потом Kafka и т.д.).
   На каждую технологию - один юнит. Он доводится до конца, и только потом начинается
   следующая. Подшаги внутри юнита идут строго по порядку:
   - разбор: кто и как обращается к технологии сейчас;
   - окружение и конфигурация;
   - новое основание: конфигурация фрейма и классы шагов;
   - перевод на них шагов и тестов, проверки - на matchers, снизу вверх;
   - удаление всего старого по этой технологии: классы, зависимости, конфиги;
   - ревью кода этой технологии (не всего проекта) сабагентами. На находки агент сам
     дописывает в карточку новые подшаги и выполняет их.
   У каждого подшага в карточке записано, что сделать, какой должен быть итоговый
   результат и чекпоинт - команда, которая это проверяет. В конце юнита выполняются общие
   чекпоинты: старого кода нет, к фрейму обращаются только классы шагов, каждый созданный
   класс кто-то вызывает, тесты не пропали. Пока хоть один не сошёлся, юнит не закрыт.
4. **Архитектура** - правки устройства проекта после миграции.
5. **Финальная зачистка** - общее старое, не привязанное к одной технологии.
6. **Финальная проверка** - когда все юниты выполнены, весь проект проверяется целиком;
   на найденное заводятся юниты исправления.

Файлы, которые используют сразу несколько технологий (например, тест ходит и в REST, и в
БД), мигрируются один раз - в последней из своих технологий. Старые классы, которые им
нужны, удаляются вместе с ними.

До начала работ агент проектирует проект «как должно быть в конце» и записывает это в
архитектурный план (`ARCHITECTURE.md`): слои, дерево пакетов и таблица классов - за что
отвечает каждый класс и кто его вызывает. Юниты создают только классы из плана, а код
кладётся в класс с подходящей ответственностью. Если по ходу понадобился класс, которого в
плане нет, агент может добавить не больше одного за юнит и записывает его в план.

Если тесты написаны для ИФТ или уже разбиты на шаги, агент строит архитектуру вокруг
FlowRunner фрейма: тест становится цепочкой именованных шагов, а действия и проверки лежат в
классах-флоу. В остальных случаях используются обычные классы шагов. Способ можно задать
явно: «мигрируй через FlowRunner» или «мигрируй без флоу».

Технология, про которую в документации фрейма ничего нет (например, конкретная СУБД), не
мигрируется и остаётся на старой реализации.

## Режимы

| Режим | Как включить | Что происходит |
|-------|--------------|----------------|
| Полная миграция | по умолчанию | Все шаги выше |
| Только ядро | «переведи только ядро, тесты не трогай» | Внутренности классов ядра переводятся на фрейм, их публичные методы сохраняются, тесты не меняются. Удаление старого и перевод тестов ждут |
| Переход к полной | «теперь переводи тесты» | Продолжение по полной схеме |

## Правила, по которым агент пишет код

Полный список - в `migration-step/references/code-rules.md`. Главное:

- Сабагенты используются только для анализа: прочитать документацию, найти в проекте,
  проверить код. Писать и править код сабагентам не поручается - это делает основной агент.
- Источник знаний о фрейме - только документация из MCP. В jar и `~/.m2` агент не лезет,
  по памяти не пишет.
- Старая архитектура не переносится: обёртки над библиотеками, свои ассерты, базовые классы с клиентами и методами
  удаляются, а не «адаптируются».
- Проверки - через matchers фрейма (`.should(...)`), а не через `Assertions`. Ответ не
  превращается в DTO ради сравнения полей: если значение доставали руками и потом
  сравнивали, цепочка переписывается целиком, а лишний DTO удаляется.
- Тест-класс содержит только сценарий. Запросы, SQL, маппинг лежат в классах шагов.
- Технология ведётся одной цепочкой внутри одного юнита: нашли всех, кто к ней обращается,
  -> создали классы шагов -> перевели на них каждого -> удалили старое -> ревью. Класс не
  создаётся «впрок»: это проверяется после подшага, на ревью и чекпоинтами в конце юнита.
- Классы создаются по архитектурному плану: у класса одна ответственность, одно действие
  живёт в одном месте, классов `Utils`, `Helper`, `Common` нет.
- Запросы и ответы руками не логируются: это делает фрейм. Логирование настраивается одним
  файлом `simplelogger.properties`; старые конфигурации логгеров (logback, log4j) и их
  зависимости удаляются.
- Настройки подключений (адреса, алиасы БД, брокеры Kafka) читает фрейм из своих файлов
  настроек: значения переносятся туда; старый код чтения конфигурации и свои
  конфигурационные классы (`DbConfig`, `KafkaConfig` и подобные) удаляются по мере миграции.
- Аннотации подключения фрейма стоят один раз, в базовом тест-классе; тесты от него
  наследуются. Клиентов и методов в базовом классе нет.
- Имена по соглашениям Java: `createOrder`, `orderId`; нижнее подчёркивание только в константах.
- `var` запрещён, классы подключаются через `import`, объекты с несколькими полями
  создаются билдером, сервис фрейма берётся в одном месте класса.
- Классы конфигурации фрейма лежат в пакете `config`.
- Методы до 40 строк, классы с одной ответственностью, без дублей и мёртвого кода.

Свои правила команды можно дописать в конец `code-rules.md`, в блок «Правила: добавлено
человеком».

## Как проверяется результат

- Юниты с зависимостями и конфигурацией проверяются компиляцией, тесты не запускаются.
- Юниты, где менялась логика, - компиляция и один быстрый тест (одним методом, с
  ограничением 10 минут). Весь набор тестов агент не запускает.
- После каждого юнита и каждого подшага - самопроверка grep-командами по правилам кода и
  чекпоинт из карточки.
- После каждой технологии - ревью её кода сабагентами; в конце - проверка миграции целиком.

## Что появляется в проекте

Всё служебное лежит в `.gigacode/data/migration/`:

| Файл | Что в нём |
|------|-----------|
| `MIGRATION-MAP.md` | Карта: паспорт проекта, технологии, что на что меняется, целевая картина, юниты и их статусы, открытые вопросы, журнал |
| `ARCHITECTURE.md` | Архитектурный план: пакеты и классы проекта после миграции, какой класс за что отвечает |
| `units/M-<nnn>.md` | Карточка юнита: файлы, шаги, критерии готовности, журнал выполнения. У юнита технологии - разбор, подшаги со статусами и чекпоинты |
| `doc-notes/<технология>.md` | Конспект документации фрейма: вопросы, ответы, ключевые слова |
| `inventory/` | Результаты анализа проекта |
| `review/M-<nnn>.md` | Отчёты ревью кода |
| `archive/MAP-ARCHIVE.md` | Архив карты: выполненные юниты, закрытые вопросы, старый журнал |
| `MIGRATION-REVIEW.md` | Отчёт проверки миграции |

Код меняется в отдельной ветке миграции (по умолчанию `pvatf-migration`). Агент коммитит в
неё после каждого юнита и подшага без вопросов. `git push` и слияние он не делает.

## Примеры запросов

```
Покажи статус миграции
```
```
Сделай юнит M-012
```
```
Сделай M-001, M-002, M-005
```
```
Проверь миграцию
```
```
Проверь миграцию. Старые библиотеки: io.restassured, org.assertj
```
Последний вариант - для проекта, где служебной папки миграции уже нет: проверка работает и
без карты, но проверяет меньше (неизвестно, что именно должно было быть удалено).

## Если что-то пошло не так

| Ситуация | Что делать |
|----------|------------|
| Агент пишет, что есть открытые вопросы | Ответьте на каждый: номер вопроса и вариант. Без ответов работа не идёт |
| Юнит в статусе `blocked` | В карточке юнита, в разделе «Блокер», написано, чего не хватило. Ответьте на вопрос в карте и напишите «продолжи миграцию» |
| Юнит остался `in-progress` | Для юнита технологии это обычное дело: он делается за несколько чатов. Напишите «продолжи миграцию» - агент продолжит с первого несделанного подшага |
| Агент не находит что-то в документации | Дайте путь к драфт-проекту или объясните сами - он предложит эти два варианта |
| MCP недоступен | Миграция без документации не идёт. Проверьте подключение MCP-сервера |
| Проект сильно изменился, карта устарела | «Обнови карту миграции» |
| Карта разрослась и съедает контекст | «Сожми карту» - выполненные юниты, закрытые вопросы и старый журнал уйдут в архив, ничего не теряется |
| Проверка три круга подряд находит проблемы | Агент остановится и покажет повторяющиеся находки - их нужно посмотреть человеку |
| Карта построена старой версией скиллов | Переименуйте `.gigacode/data/migration/` и постройте карту заново: формат карты менялся |

## Ограничения

- Перенос тестов из одного проекта в другой не поддерживается.
- Скиллы написаны под слабую модель и строгие шаблоны: файлы карты руками лучше не
  переформатировать - заголовки и названия колонок читают другие скиллы.
- Качество миграции зависит от целевой картины и архитектурного плана. Если они написаны
  общими словами или в плане есть классы с размытой ответственностью, не утверждайте карту.
- Если в проекте большинство тестов используют сразу несколько технологий, основная работа
  придётся на юнит последней из них: такие тесты мигрируются один раз, в конце.
