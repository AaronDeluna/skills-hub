# Отдельная проверка разметки

Открывай, когда человек просит проверить или поставить разметку тестов, а не мигрировать
проект: «проверь разметку», «разметь тесты», «поставь разметку». Скиллы миграции не
запускаешь, карту миграции не создаёшь и не меняешь. Это не миграция: вопросы человеку
здесь задаются по ходу (правило 8 `references/core-rules.md` относится к миграции).

Правила разметки - `references/markup-rules.md`. Прочитай его целиком до первой команды.
Отчёт - `.gigacode/data/markup/MARKUP-REPORT.md`, каждый запуск переписывает его заново.

**Где искать - только в проекте** (раздел 0 правил разметки). Не выходи за корень проекта
(`find /`, `find ~`, другие проекты), не ходи в проект и исходники фреймворка, проект-пример,
`~/.m2`, `~/.gradle`, .jar и интернет. Исключение - jar самой allure-annotations версии
2.x, и только для аннотации не из таблицы импортов (раздел 0 правил). Не нашёл пакет, версию или
значение в проекте -> дальше не ищи: делай по правилу для этого случая.

## 1. Подготовка

1. Агенты: выполни `java -Dfile.encoding=UTF-8 .gigacode/skills/orchestrator/scripts/NextAction.java`.
   `ДЕЙСТВИЕ: агенты установлены` -> скажи «Агенты установлены или обновлены. Перезапустите
   GigaCode (выйдите и запустите заново) и введите, чтобы продолжить с того же места:
   `/orchestrator <запрос человека дословно>`» и закончи. Вместо `<запрос человека
   дословно>` подставь текст, который человек написал после `/orchestrator`, без изменений. Любое другое
   действие к этой просьбе не относится: не выполняй его и не показывай. Агентов сам не
   копируй и `.gigacode/agents/` не проверяй: это делает скрипт.
2. **Зависимость и версия - первым делом.** Построй дерево зависимостей - команда
   «Зависимость и версия» из раздела 5 правил. По файлам сборки зависимость не ищи - только
   дерево. Запомни: `есть <версия>` или `нет`. Нет -> версия для значений разметки -
   `2.0.2`, агент подключит зависимость с нуля. Команда упала -> скажи «Не удалось
   построить дерево зависимостей, поэтому не понять, есть ли allure-annotations и какой
   версии: <первые строки ошибки>. Исправьте сборку и повторите запрос» и закончи. Мажорная версия (число до
   первой точки) 0 или 1 -> запомни `ниже 2.x`: перед правками нужен вопрос `upgrade`
   (раздел 3, п.1).
3. Идёт ли миграция: есть `.gigacode/data/migration/MIGRATION-MAP.md` и в его таблице юнитов
   есть юнит `markup` не в статусе `done` -> разметку поставит миграция. Проверку (раздел 2)
   сделай, а план и правки (разделы 4-5) - нет: в итоге скажи «Разметку поставит шаг
   миграции M-<nnn>: `/orchestrator Продолжи миграцию`».
4. Каталоги тестов:
   `find . -type d \( -path "*/src/test/java" -o -path "*/src/test/kotlin" \) | grep -v "/target/\|/build/\|\.gigacode"`.
   Тест-классы - файлы с тестами:
   `grep -rlE "@(Test|ParameterizedTest)\b" --include='*.java' --include='*.kt' <каталог>`.
   Тест-классов нет -> скажи «В проекте не нашлось тестов для разметки» и закончи.

## 2. Проверка

1. Выполни команды раздела 5 правил по каждому каталогу тестов: «Проверка, что размечено»,
   «Ключи тест-кейсов без `@TmsLink`», «Одинаковые ключи тест-кейсов» и «Тест-методы без
   `@TmsLink`».
2. Для каждого тест-класса найди базовый класс: Java - имя после `extends`, Kotlin - имя
   после `:` в объявлении класса (`class ApiTests : BaseTest()`):
   `grep -nE "class [A-Za-z0-9_]+.*( extends |\) *: *| : )[A-Za-z0-9_.]+" <файл>`. Его файл -
   `grep -rlE "(class|interface) <Имя>\b" <каталог>`. Иди вверх, пока предок есть в проекте;
   предок не из проекта (из библиотеки) - конец цепочки, его аннотаций не знаешь. Запомни, кто от
   кого наследуется: это нужно для плана (раздел 4).
3. Для каждого тест-класса и каждой аннотации набора агента (раздел 1 правил): класс есть в
   выводе команды -> размечен сам. Нет -> проверь его базовые классы так же. Ни сам, ни
   предки не размечены -> аннотации нет. `@Team` желательная (раздел 1 правил): её нет -> строка
   таблицы заполняется как обычно, но итог «размечен» из-за неё не меняется.
4. `@Regress`/`@CriticalRegress` и `@Story`/`@Issue` нужны только при модели в Allure
   TestOps. Модель ещё не известна -> в отчёте эти строки с пометкой «только для Allure
   TestOps». Хоть одной из них нет -> итог «размечен» сказать нельзя, пока нет ответа на
   `model`: в п.7 сначала вопрос `model` (раздел 4 правил), потом итог.
5. Ключи в аннотациях тест-методов (`@DisplayName`, `@Zephyr` и другие, раздел 2а правил): каждую найденную строку проверь по условиям раздела 2а правил.
   Строка «значение не разобрать, проверьте вручную» -> `не взят: значение аннотации не разобрать скриптом`.
   Все условия выполнены -> `взять`; хоть одно нет -> `не взят: <причина словами>` (раздел 2а
   правил). Одинаковые ключи найди командой «Одинаковые ключи тест-кейсов» (раздел 5 правил)
   и покажи каждый одной строкой со всеми его тест-методами.
   Ключ без `T` перед цифрами (`PVATF-4567`) - не тест-кейс: в таблицу не попадает.
6. Запиши отчёт `.gigacode/data/markup/MARKUP-REPORT.md` ровно по шаблону:
   ```
   # Проверка разметки
   Дата: <ГГГГ-ММ-ДД>
   Каталоги тестов: <пути через запятую>
   Тест-классов: <N> · тест-методов: <N> · с @TmsLink: <N>
   Зависимость allure-annotations (дерево зависимостей): <есть <версия> / нет - подключим с нуля><; ниже 2.x - нужно поднять до 2.0.2>
   Базовые классы: <базовый класс - сколько тест-классов от него наследуется; нет - "нет">

   ## Набор агента
   | Аннотация | Размечено тест-классов | Без неё |
   |-----------|------------------------|---------|
   | контур - @TestStage | <n> из <N> | <классы через запятую / -> |
   | слой - @TestLayer | <n> из <N> | <...> |
   | КЭ - @System | <n> из <N> | <...> |
   | команда - @Team | <n> из <N> | <...> |
   | регресс - @Regress (только для Allure TestOps) | <n> из <N> | <...> |
   | задача - @Story / @Issue (только для Allure TestOps) | <n> из <N> | <...> |

   ## TMS-link
   Ключи тест-кейсов в аннотациях тест-методов - агент скопирует в @TmsLink, аннотации не меняются: <N>
   | Тест-метод | Ключ | Решение |
   |------------|------|---------|
   | <Класс.метод> | <ключ> | <взять / не взят: причина словами> |
   Ключи не взяты - решите вы: <N>
   <по строке на ключ, причина словами (раздел 2а правил), например:
   `SBOLCRM-T1234 - одинаковый в CreateOrderTest.create, CreateOrderUiTest.create: @TmsLink не поставлен ни одному, решите, какому тесту он принадлежит`; нет - "нет">
   Тест-методов без @TmsLink и без ключа - ставите вы: <N>
   Тест-классы без @TmsLink: <классы / ->

   ## Значения разметки
   <пусто до раздела 3>

   ## План разметки
   <пусто до раздела 4>

   ## Итог
   <размечен / не размечен: каких аннотаций не хватает, сколько ключей взять в @TmsLink>
   ```
   Без неё больше 15 классов или ключей больше 15 -> первые 15 и «и ещё <n>».
7. Покажи человеку таблицу набора агента, раздел про TMS-link и итог.
   - Нет регресса или задачи, а модель не известна -> сначала вопрос `model` (п.4). Ответ
     не `testops` -> эти строки в итог не входят.
   - Размечен и брать нечего -> закончи: итоговый ответ (раздел 6).
   - Не размечен или есть ключи `взять`, а просили только проверить -> спроси
     «Поставить недостающие аннотации и @TmsLink по ключам тест-кейсов из аннотаций тестов? да/нет».
     «нет» -> итоговый ответ. «да» -> раздел 3.
   - Не размечен или есть ключи `взять`, просили поставить -> раздел 3.

## 3. Значения

Сначала две проверки из раздела 2б правил - до вопросов, чтобы человек не отвечал зря:
1. Git: `git status --porcelain -- . ':(exclude).gigacode'` не пустой -> скажи «В проекте
   есть незакоммиченные изменения: <файлы из вывода>. Закоммитьте их, и я продолжу
   разметку», запиши это в итог отчёта и закончи.
2. Версия `ниже 2.x` (раздел 1, п.2) -> задай вопрос `upgrade` из раздела 4 правил, ровно
   его текстом. `нет` -> скажи «Разметить тесты по правилам не получится: в проекте
   allure-annotations <версия>, а нужна 2.x», запиши это в итог отчёта и закончи. `да` ->
   версия для значений - `поднять <версия> -> 2.0.2`.

Значения нужны только для аннотаций, которых не хватает. По каждому ключу раздела 4 правил,
кроме `upgrade`:
1. Поищи значение в проекте: аннотации, настройки, README, Jenkinsfile
   (`grep -rniE "CI[0-9]+|@Team|team|testops|zephyr|allure" --include='*.md' --include='*.properties' --include='*.yml' --include='Jenkinsfile*' . | grep -v "/target/\|/build/\|\.gigacode" | head`).
   Нашёл -> бери с пометкой `из проекта: <файл>`. КЭ (`system`) - только по подразделу
   «КЭ» раздела 4 правил: все КЭ по `CI[0-9]+`; несколько КЭ -> у каждого тест-класса свой,
   без явной принадлежности - вопрос с найденными КЭ пунктами.
2. Не нашёл -> спроси человека. Перед первым вопросом скажи: «Для разметки нужны значения,
   которых нет в проекте. Задам несколько вопросов по одному». Вопросы задавай по правилам
   раздела 4 правил: по одному, в порядке таблицы, обычным сообщением, ровно текстом из
   колонки «Вопрос», без своих пояснений и вариантов. Ответ на `model` убирает вопросы
   `regress` и `story`, если модель не в Allure TestOps.
3. Версия - из раздела 1, п.2 и вопроса `upgrade`: `версия: есть в сборке <версия>`,
   `версия: поднять <версия> -> 2.0.2` или `версия: 2.0.2`.
4. Запиши в раздел «Значения разметки» отчёта одну строку:
   `model: <testops / tms: название> · system: <КЭ / <КЭ> - <тест-классы>; ... / -> · stage: <контур / -> · team: <команда / -> · regress: <regress / critical / -> · story: <задача / -> · версия: <...>`.
   Ответ `-` - эту аннотацию не ставят.

## 4. План разметки

До правок составь план и запиши его в раздел «План разметки» отчёта. По нему работает агент
и по нему же ты потом проверяешь результат.

1. Разложи аннотации по правилам раздела 2 правил:
   - общие для всех тестов (`@System`, `@Team`, `@TestStage`, общие `@Regress` и `@Story`)
     -> над базовым классом из раздела 2, п.2. Несколько КЭ -> `@System` по подразделу «КЭ»
     раздела 4 правил: наследники с разными КЭ получают его каждый над собой. Тест-классы наследуются от разных базовых
     классов -> строка на каждый базовый класс. Тест-класс без базового класса -> над ним;
   - `@TestLayer` -> над тест-классом или над базовым классом слоя (раздел 3 правил);
   - ключи `взять` -> `@TmsLink` над тест-методом; `@DisplayName` не меняется. Тест-класс с
     такими ключами входит в план своей строкой, даже если все остальные аннотации он
     получает через базовый класс (например, UI-тесты под `@UiTest` на базовом классе);
   - зависимости нет -> файлы сборки (раздел 2, п.6 правил);
   - `версия: поднять` -> файл сборки, где записан номер версии (в зависимости или в
     свойстве; команда «Где записан номер версии», раздел 5 правил): `поднять
     allure-annotations <версия> -> 2.0.2`. В проекте номер не записан -> файл сборки модуля
     с тестами: `добавить allure-annotations 2.0.2 явно`.
   Аннотация уже стоит (сам класс или предок) -> в план не входит.
2. Запиши план таблицей, строка на файл:
   ```
   | # | Файл | Что сделать | Правило | Сделано |
   |---|------|-------------|---------|---------|
   | 1 | <путь> | <аннотации со значениями / какой ключ тест-кейса взять в @TmsLink из какого метода / зависимость с версией> | <раздел правил: 2.1 / 2.2 / 2а / 2.6> | [ ] |
   | <N> | все каталоги тестов | перепроверка: ключи тест-кейсов без @TmsLink, набор агента, импорты, @DisplayName не изменён | 6 | [ ] |
   ```
   Последняя строка плана - всегда перепроверка (раздел 6 правил), даже если план из
   одной строки.
3. Сверь план с правилами, пока не отправил агенту:
   - общие аннотации стоят над базовым классом и ни в одной строке не повторяются над
     его наследниками;
   - в плане нет аннотаций, которые уже стоят в классе или его предке;
   - каждый ключ из плана - со статусом `взять` в отчёте и с `T` перед цифрами;
   - `@TmsLink` нет нигде, кроме строк с ключом `взять`; правок `@DisplayName` в плане нет;
   - значение `-` -> этой аннотации в плане нет;
   - `версия: поднять` -> в плане есть строка с подъёмом версии, других правок сборки нет;
   - аннотации в плане есть, даже если в проекте нет ни одного импорта библиотеки:
     неразмеченный проект - как раз то, что нужно разметить. Импорты агент возьмёт из
     таблицы в разделе 2, п.5 правил. Из плана аннотации из-за пакета не убирай.
   Нашёл ошибку -> исправь план и сверь заново.

## 5. Правки

1. Git: ещё раз `git status --porcelain -- . ':(exclude).gigacode'`. Не пустой -> скажи «В
   проекте есть незакоммиченные изменения: <файлы из вывода>. Закоммитьте их, и я продолжу
   разметку» и закончи.
2. База: `git rev-parse HEAD` - запомни хэш. По нему ты проверяешь правки, даже если
   агент уже закоммитил.
3. Команда компиляции: есть `pom.xml` -> `./mvnw -q test-compile` (нет `mvnw` -> `mvn -q
   test-compile`); есть `build.gradle` или `build.gradle.kts` -> `./gradlew testClasses`
   (нет `gradlew` -> `gradle testClasses`).
4. Запусти агента `pvatf-marker` по имени (правило 7 `references/core-rules.md`) с заданием:
   ```
   Проект: <абсолютный путь>
   Юнит: без карты · markup · отдельная проверка разметки
   Файлы: <путь - изменить, по строке на файл из плана>
   Значения разметки: <строка из раздела «Значения разметки» отчёта>
   Что сделать: <строки плана по порядку: номер - файл - что сделать>
   Компиляция: <команда>
   Коммит: markup: разметка тестов allure-annotations
   ```
   Агент вернул «не сделан» по проверкам перед правками (раздел 2б правил) -> не делай
   разметку сам и не повторяй агента. Скажи человеку сообщение из раздела 2б правил:
   - `есть незакоммиченные изменения` -> «В проекте есть незакоммиченные изменения:
     <файлы>. Закоммитьте их, и я продолжу разметку»;
   - `allure-annotations <версия>, нужна 2.x` -> «Разметить тесты по правилам не получится:
     в проекте allure-annotations <версия>, а нужна 2.x»;
   - `проект не компилируется до разметки` -> «Проект не компилируется, поэтому разметку
     поставить нельзя: <строки ошибки из отчёта>. Исправьте сборку и повторите запрос»;
   - `не построилось дерево зависимостей` -> «Не удалось построить дерево зависимостей,
     поэтому не понять, есть ли allure-annotations и какой версии: <строки ошибки из
     отчёта>. Исправьте сборку и повторите запрос».
   Запиши причину в итог отчёта и закончи.
   Вызов сабагента вернул ошибку (агент не запустился) -> покажи её в чате и сделай строки
   плана сам, по разделам 2-3 правил, начав с проверок раздела 2б (п.1 и п.3), потом
   закоммить так же.
5. Проверь результат сам, по каждой строке плана:
   - `git diff --name-only <база> -- . ':(exclude).gigacode'` и `git status --porcelain --
     . ':(exclude).gigacode'` (свой отчёт в `.gigacode/` - не нарушение) - изменены только файлы плана
     и файлы `добавлен по перепроверке` из отчёта агента (в них - только `@TmsLink` и его
     импорт);
   - `git diff <база>` - добавлены только аннотации, их импорты и зависимость;
     `@DisplayName` не тронут; логика тестов не тронута;
   - компиляция - команда из п.3;
   - раздел 2, пп.1-3 заново: каждый тест-класс размечен набором агента (аннотации со
     значением `-` не требуются), у каждого
     взятого ключа есть `@TmsLink`, `@DisplayName` не изменился;
   - сверка из раздела 4, п.3 - теперь по коду, а не по плану;
   - отчёт агента - блок `=== ОТЧЁТ PVATF-MARKER ===` ... `=== КОНЕЦ ОТЧЁТА ===`, все
     строки на месте. Блока нет или строки нет -> повтор агента: «Верни отчёт по шаблону»;
   - перепроверка из раздела 6 правил - сам, не по отчёту агента. Команда «Ключи
     тест-кейсов без `@TmsLink`» вывела строку без причины в отчёте агента -> это
     невыполненная строка плана, повтор агента с ней;
   - одинаковые ключи - сам: команда «Одинаковые ключи тест-кейсов» (раздел 5 правил) по
     всем каталогам тестов. Каждый ключ из её вывода - в отчёт (раздел «TMS-link», «Ключи не
     взяты») и в итоговый ответ со всеми тест-методами, даже если агент его не назвал.
   Строка плана выполнена -> в колонке «Сделано» `[x]`. Что-то не так -> один повтор
   `pvatf-marker` со списком невыполненных строк. Не вышло и во второй раз -> верни к базе только
   файлы разметки, остальное не трогай (`git reset --hard` не используй: он сотрёт и
   незакоммиченные правки в `.gigacode/`):
