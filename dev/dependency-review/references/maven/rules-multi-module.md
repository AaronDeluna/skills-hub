# Правила Maven - мультимодульные проекты

Применяй ПОСЛЕ того, как закончишь `rules-common.md`. Процедура та же: правило за
правилом, подтверждай каждое совпадение, по строке заметок на результат.

Перед началом построй **карту модулей** и запиши её в файл заметок:
1. Выпиши все `<module>` из корневого `pom.xml` (и из промежуточных агрегаторов, если есть).
2. Для каждого POM модуля запиши: его `<parent>`, его собственную `<version>` (если есть)
   и от каких соседних модулей он зависит (зависимости, чей groupId совпадает с groupId
   проекта).

Пример записи карты: `orders-service (parent=acme-parent) -> [orders-api, common-util]`

---

### M-M-01 - У агрегатора/родителя `packaging=pom`

**Уровень:** CRITICAL (иначе сборка ломается или ведёт себя непредсказуемо)
**Почему это важно:** POM с `<modules>` обязан объявлять `<packaging>pom</packaging>`.
Всё остальное - misconfiguration.

**Как проверять:** открой каждый POM, где есть `<modules>`; убедись, что там
`<packaging>pom</packaging>`.

**Исправление для отчёта:** поставить packaging `pom`.

---

### M-M-02 - Все внешние версии менеджатся в родителе; дети без версий

**Уровень:** CRITICAL, когда есть расхождение; WARNING иначе
**Почему это важно:** ГЛАВНОЕ мультимодульное правило. Если дети пиннят версии сами, одна
и та же библиотека расходится по модулям; какая бы версия ни победила в рантайме,
какой-то модуль работает против версии, с которой не компилировался. Баги всплывают
только на интеграции.

**Как проверять (самая ценная проверка файла - делай тщательно):**
1. В каждом **дочернем** POM выпиши каждый `<dependency>` из обычных `<dependencies>`,
   несущий тег `<version>` (литерал или свойство). Каждый - кандидат в нарушение паттерна
   «родитель менеджит, дети объявляют без версий».
2. Построй таблицу `groupId:artifactId → версия` по ВСЕМ модулям (ссылки на свойства
   разрешай, находя их в `<properties>`, при необходимости поднимаясь к родителю).
3. Один `groupId:artifactId` с разными версиями в разных модулях → CRITICAL VIOLATION;
   перечисли каждое место.
4. Версии совпадают, но объявлены по-детски вместо родительского `dependencyManagement`
   → WARNING VIOLATION.
5. Исключение: ребёнок, импортирующий **дополнительный BOM** в собственном
   dependencyManagement (например, только persistence-модуль импортирует BOM jOOQ), - это
   нормально.

**Исправление для отчёта:** перенести все версии в `<dependencyManagement>` родителя;
удалить теги `<version>` у детей.

---

### M-M-03 - Родитель (почти) не навязывает детям реальные зависимости

**Уровень:** WARNING
**Почему это важно:** обычные `<dependencies>` родителя наследуются КАЖДЫМ ребёнком -
включая будущие, которым они не понадобятся. `common-lang` там кажется безобидным, пока
родитель не притащит spring-web в batch-job-модуль. Единственное более-менее принятое
исключение - универсальные тестовые утилиты (и даже это спорно).

**Как проверять:** открой родительский POM. Смотри обычные `<dependencies>` (НЕ
dependencyManagement). Пусто или отсутствует → PASS. 1-3 истинно универсальных записи
(slf4j-api, lombok, член тестового BOM) → INFO с пометкой. Фреймворковые/доменные
библиотеки там → VIOLATION.

**Исправление для отчёта:** спустить каждую зависимость в модули, которые её реально
используют; родителю оставить только dependencyManagement.

---

### M-M-04 - Межмодульные зависимости через `${project.version}`

**Уровень:** WARNING
**Почему это важно:** модуль, зависящий от соседа с зашитой версией
(`<version>1.3.0</version>` при проекте на 1.4.0), либо тянет протухший артефакт из
репозитория, либо ломает реактор. Зависимости от соседей всегда должны следовать за
текущей сборкой.

**Как проверять:**
```
grep -rn -B2 -A3 "<groupId>THE_PROJECT_GROUPID</groupId>" --include="pom.xml" .
```
(подставь реальный groupId). У каждой зависимости от соседа версия должна быть
`${project.version}` или `${revision}` - числовой литерал это VIOLATION.

**Исправление для отчёта:** заменить на `${project.version}`.

---

### M-M-05 - Единая версия проекта по модулям; `${revision}` настроен правильно

**Уровень:** WARNING
**Почему это важно:** модули с индивидуально ведущимися версиями (модуль A на 1.4,
модуль B на 1.2 в одном реакторе) - минное поле для релиз-менеджмента, если только команда
сознательно не ведёт независимое версионирование. А CI-friendly `${revision}` **требует**
flatten-maven-plugin - без него опубликованные POM содержат буквальную строку
`${revision}` и не резолвятся потребителями.

**Как проверять:**
1. Сравни `<version>` по всем POM модулей (ребёнок, наследующий версию от родителя -
   без собственного тега `<version>` - самый чистый вариант).
2. Если используется `${revision}`:
   `grep -rn "flatten-maven-plugin" --include="pom.xml" .` - отсутствует → VIOLATION
   (CRITICAL, если артефакты публикуются для внешних потребителей).

**Исправление для отчёта:** наследовать версию от родителя везде; при `${revision}` -
добавить flatten-maven-plugin в build родителя.

---

### M-M-06 - Никаких циклов зависимостей между модулями

**Уровень:** CRITICAL
**Почему это важно:** прямые циклы реактор отвергает, но циклы просачиваются через `test`
scope, optional-зависимости и артефакты с classifier - а любой цикл означает, что модули
на самом деле неразделимы.

**Как проверять:** используй карту модулей. Для каждого модуля иди по зависимостям от
соседей вглубь; если вернулся в модуль, уже лежащий на текущем пути, - запиши полный путь
цикла. Включай в обход и рёбра test-scope (помечай их в находке как test-scope).

**Исправление для отчёта:** вынести общий код в новый модуль ниже уровнем или развернуть
одно ребро (интерфейсы внизу, реализации выше).

### M-M-07 - `<modules>` и `<parent>` согласованы с реальностью

**Уровень:** WARNING
**Почему это важно:** запись `<module>`, указывающая на несуществующий каталог, ломает
сборку; каталог модуля, не попавший в список, молча выпадает из CI. Неправильный
`<relativePath>` заставляет Maven резолвить родителя из репозитория, а не из рабочей
копии - изменения родителя перестают применяться локально.

**Как проверять:**
1. Каждая запись `<module>` соответствует существующему каталогу с `pom.xml`.
2. Каждый каталог модуля с `pom.xml` числится в каком-то агрегаторе (или он намеренно
   самостоятельный - уточни через NEEDS-HUMAN).
3. `<parent><relativePath>` каждого ребёнка указывает на реальное расположение
   родительского POM (умолчание `../pom.xml` работает, когда родитель уровнем выше;
   нестандартные значения проверь).

**Исправление для отчёта:** выровнять списки; исправить или убрать неверные relativePath.

---

### M-M-08 - Версии плагинов запиннены в `pluginManagement` родителя

**Уровень:** WARNING
**Почему это важно:** незапинненные версии плагинов плывут вместе с дистрибутивом Maven -
сборка становится невоспроизводимой по-другому (тот же коммит, другое поведение плагина).
Один блок `pluginManagement` в родителе пиннит их для всех модулей.

**Как проверять:** есть ли в родителе `<pluginManagement>` с перечислением используемых
плагинов? Не носят ли `<plugins>` детей лишние теги `<version>` (должны приходить из
pluginManagement)? Не используется ли какой-то плагин вообще без запинненной где-либо
версии?
```
grep -rn -A2 "<plugin>" --include="pom.xml" . | grep -B1 -A1 artifactId
```

**Исправление для отчёта:** добавить/дополнить `pluginManagement` в родителе; убрать
версии из использований плагинов у детей.

---

### M-M-09 - Дети не перекрывают управляемые версии молча

**Уровень:** WARNING
**Почему это важно:** ребёнок, повторно объявляющий `<version>` библиотеки, которую уже
менеджит родитель, побеждает молча - центральный путь обновления сломан ровно для этого
модуля, и никто об этом не знает.

**Как проверять:** сверь кандидатов из шага 1 правила M-M-02 со списком
`<dependencyManagement>` родителя. Тег версии у ребёнка для управляемого родителем
артефакта → VIOLATION (если рядом нет комментария-обоснования; с обоснованием - INFO,
но обоснование обязано быть).

**Исправление для отчёта:** убрать перекрытие; если модулю правда нужна другая версия -
это архитектурное решение, которое надо поднять на поверхность: помести его в «Требует
внимания человека».

### M-M-10 - Направление зависимостей модулей соответствует архитектуре

**Уровень:** INFO (по своей природе NEEDS-HUMAN - суди осторожно, не переусердствуй)
**Почему это важно:** стрелки зависимостей и есть архитектура. Типичная задуманная
слоистость: `web/api → service → domain ← persistence`, всем можно `common`. Стрелки
«вверх» (domain → web) или `common`, зависящий от бизнес-модулей, переворачивают дизайн.

**Как проверять:** смотри карту модулей. Эвристики ролей по имени: `*-api`, `*-web`,
`*-rest` (край) → могут зависеть от service/domain; `*-domain`, `*-model`, `*-core`
(центр) → не должны зависеть почти ни от чего прикладного; `*-common`, `*-util` (база)
→ не должны зависеть ни от одного бизнес-модуля. Любое ребро против эвристик → запиши как
NEEDS-HUMAN с конкретной стрелкой и вопросом, задумано ли так.

**Исправление для отчёта:** ничего директивного; покажи подозрительные стрелки - решает
команда.
