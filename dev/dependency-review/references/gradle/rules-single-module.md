# Правила Gradle - одномодульные проекты (монолиты)

Применяй ПОСЛЕ того, как закончишь `rules-common.md`. В монолите основную работу делают
общие правила; этот файл добавляет специфичные для монолита проверки. Процедура та же:
правило за правилом, подтверждай каждое совпадение, по строке заметок на результат.

---

### G-S-01 - Версии всё равно централизованы

**Уровень:** INFO
**Почему это важно:** даже с одним build-файлом 40 инлайновых литералов версий делают
обновления рискованными (пропустить один из трёх артефактов Jackson) и прячут расхождения
внутри семейств. Version catalog ничего не стоит и делает будущую модуляризацию
безболезненной.

**Как проверять:** посчитай зашитые версии в `dependencies { }` (переиспользуй поиск из
G-C-03). Больше ~10 инлайновых версий и нет ни каталога, ни `ext`, ни механизма в
`gradle.properties` → VIOLATION.

**Исправление для отчёта:** завести `gradle/libs.versions.toml`; первыми перенести версии
семейств (Spring, Jackson, JUnit).

### G-S-02 - Никакого `api` в модуле-приложении

**Уровень:** WARNING
**Почему это важно:** у одномодульного приложения нет потребителей, поэтому `api` не
делает ничего, кроме как сигнализирует о копипасте из документации какой-то библиотеки.
Сегодня это бесплатно, но в день, когда проект начнут резать на модули, превратится в
утечку - и уже сейчас вводит читателя в заблуждение о публичной поверхности модуля.

**Как проверять:** `grep -rnE "^\s*api\s*[('\"]" --include="build.gradle" --include="build.gradle.kts" .`
Исключение: если проект на самом деле публикуемая **библиотека** (есть `java-library` +
конфигурация публикации), `api` легитимна - оценивай её по G-C-05, а это правило пометь N/A.

**Исправление для отчёта:** заменить `api` на `implementation`.

### G-S-03 - Блок зависимостей организован

**Уровень:** INFO
**Почему это важно:** один несортированный блок `dependencies { }` на 80 строк - место,
где прячутся дубли и заброшенные зависимости. Группировка (по конфигурации, затем по
назначению, с однострочными комментариями) сохраняет список пригодным для код-ревью.

**Как проверять:** открой блок `dependencies { }`. Сгруппированы ли объявления по
конфигурациям (все `implementation` вместе, тесты вместе)? Есть ли вперемешку куски
несвязанных библиотек? Суди мягко - это правило о читабельности, а не догма.

**Исправление для отчёта:** предложить порядок группировки: сначала platform/BOM-импорты,
затем implementation, compileOnly/annotationProcessor, runtimeOnly, затем тестовые scope-ы.

### G-S-04 - Следи за раздуванием и неиспользуемыми зависимостями

**Уровень:** INFO (WARNING, когда найдены явно заброшенные зависимости)
**Почему это важно:** монолиты накапливают зависимости, которые код уже не использует.
Каждая всё равно стоит: поверхность атаки, работа при обновлениях, ревью лицензий, время
старта.

**Как проверять (статическое приближение):**
1. Выбери 5-10 самых необычных/тяжёлых зависимостей из списка (не очевидное ядро
   фреймворка).
2. Для каждой поищи в исходниках характерный импорт её пакета:
   ```
   grep -rn "import com.google.common" --include="*.java" --include="*.kt" src/ | head -3
   ```
   Импортов нет → кандидат в неиспользуемые (NEEDS-HUMAN - может использоваться через
   рефлексию, SPI или только в рантайме).
3. Для точного ответа рекомендуй Gradle-плагин `com.autonomousapps.dependency-analysis` -
   не пытайся быть исчерпывающим вручную.

**Исправление для отчёта:** перечислить кандидатов; предложить включить плагин
dependency-analysis в CI.

### G-S-05 - Сигналы здоровья монолита

**Уровень:** INFO
**Почему это важно:** это ранние предупреждения о том, что управление зависимостями скоро
станет болезненным; отметить их сейчас дёшево, обнаружить потом - дорого.

**Как проверять - отметь в отчёте любой из признаков:**
- Больше ~60 прямых зависимостей в одном модуле (посчитай объявления): модуль делает
  слишком много работ; внутри прячется будущая граница модуляризации.
- Дублирующие библиотеки (уже покрыто G-C-13 - не дублируй находку, просто сошлись на неё).
- Нет BOM/platform при 3+ семействах библиотек (сошлись на G-C-07).
- Смешанные поколения фреймворков (например, артефакты и `javax.*`, и `jakarta.*`) -
  зависшая миграция; флажь пару.
  ```
  grep -rnE "['\"](javax|jakarta)\." --include="build.gradle" --include="build.gradle.kts" .
  ```

**Исправление для отчёта:** ничего обязательного; подай как «наблюдения» («watch items»)
с одним предложением на каждое.
