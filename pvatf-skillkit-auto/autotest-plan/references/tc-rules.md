# Правила проверки тест-кейса

Часть скилла `autotest-plan`. Оценку считает `scripts/tc_check.py`; здесь - что значит каждая
находка и что сказать человеку. Сам баллы не пересчитываешь.

## Оценки и вердикт

Пять оценок, каждая с 100 баллов: `determinism`, `independence`, `reproducibility`,
`objective_verifiability`, `parametrizability`. Средняя - среднее пяти.
- **FAIL** (`blocking: true`) - есть находка «БЛОКИРУЕТ» или `determinism` / `objective_verifiability` ниже 60.
- **PASS** - нет блокирующих, средняя не ниже 80, все обязательные и рекомендуемые поля есть.
- **WARNING** - всё остальное. Генерация идёт, находки попадают в итог.

## Правила

| ID | Что ищет скрипт | Вычет | Блокирует | Как исправить ТК (скажи человеку) |
|----|-----------------|-------|-----------|-----------------------------------|
| TC-0 | шагов нет или таблица не читается | - | да | Добавьте таблицу «Шаги выполнения»: № / действие / тестовые данные / ожидаемый результат |
| TC-1 | нет поля: обязательные - Название, Ключ, Цель; рекомендуемые - КЭ, Приоритет, Требования к тестовым данным | - | обязательные - да | Заполните поле «<имя>» в TMS |
| TC-2 | название из 1-2 слов | - | нет | Название - что проверяется: «Авторизация пользователя с верным логином и паролем», а не «Авторизация» |
| TC-3 | в названии два действия через «и» | - | нет | Разделите на два тест-кейса, если это два бизнес-сценария |
| TC-4 | в одном шаге несколько действий | 30 reproducibility | нет | Один шаг - одно действие (план разобьёт шаг сам) |
| TC-5 | размытые слова: «валидные данные», «корректный формат», «тестовые данные», «все поля»... | 15 objective | нет | Замените на конкретное значение: «логин user_admin» |
| TC-6 | ожидаемый результат без проверяемого значения: «работает», «отображается корректно» | 20 objective | нет | Укажите, что именно проверить: «код ответа 200», «поле status = ACTIVE» |
| TC-7 | случайные значения без правила | 30 determinism | нет | Укажите формат или правило генерации: «UUID, pattern ^[0-9a-f]{32}$» |
| TC-8 | текущее время без формата | 20 determinism | нет | Укажите формат: «yyyy-MM-dd'T'HH:mm:ss, сейчас минус 1 день» |
| TC-9 | ожидание без предела времени | 20 determinism | нет | Укажите предел: «запись появляется не позже 30 секунд» |
| TC-10 | запрос без адреса (путь, топик, таблица) | - | да | Укажите адрес: путь `/api/v1/orders`, топик, таблицу |
| TC-11 | логин или пароль прямо в шаге | 10 parametrizability | нет | Укажите учётную запись по роли: «пользователь с ролью ADMIN из тестовых данных» |
| TC-12 | ссылка на шаг, которого раньше нет; опора на «созданное ранее» без предусловий | 30 independence | да | Добавьте шаг или предусловие, которое создаёт нужное состояние |
| TC-13 | `determinism` или `objective_verifiability` ниже 60 | - | да | Исправьте находки TC-5..TC-9 |

Атомарность всего ТК (TC-3) и шага (TC-4) скрипт видит по глаголам; это подсказка, а не
решение. Тест-кейс с TC-3 генерируется как один тест, если человек не попросил иначе.

## Формат ТК

`tc_convert.py` читает:
- Markdown: поля `**Название:**`, `**Ключ:**`, `**КЭ:**`, `**Приоритет:**`, раздел `### Цель`,
  таблица `### Шаги выполнения` с колонками №, описание шага, тестовые данные, ожидаемый результат
  (порядок колонок любой);
- XML и JSON выгрузки Zephyr Scale и TestOps: `testCase` / `name` / `key` / `objective` /
  `precondition` / `testScript.steps[]` (`description`, `testData`, `expectedResult`);
- результат Allure `*-result.json`: `name`, `steps[].name`, ключ - из `links`.
