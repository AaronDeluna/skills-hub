# Разметка тестов (allure-annotations)

Общий файл набора: источник - `shared/markup-rules.md`, копии в скиллах раскладывает
`scripts/sync_shared.py`. Правишь - правь только источник.

Разметка - аннотации библиотеки `allure-annotations` (`ru.sber.qa`), по которым Allure
TestOps фильтрует тесты и строит статистику. Документации фрейма она не касается: всё, что
нужно для разметки, - в этом файле. Других аннотаций разметки не придумывай.

Кто пользуется файлом:
- `migration-map`, Этап 2, шаг 1б - смотрит, размечен ли проект, и собирает значения;
- `migration-step`, юнит `markup` - ставит аннотации (агент `pvatf-marker`);
- `migration-review`, пункт `P16` - проверяет, что разметка стоит.

## 0. Где искать - только в проекте

Разметка - это пять-семь аннотаций из таблицы раздела 1. Всё, что о них нужно знать, - в
этом файле. Искать про них нечего.

Все команды разметки - из корня проекта, по его файлам (путь `.` или каталог тестов).
**Запрещено:**
- выходить за корень проекта: `find /`, `find ~`, `cd ..`, абсолютные пути вне проекта,
  другие проекты на компьютере;
- проект фреймворка, его исходники, проект-пример, документация MCP - разметке они не нужны;
- `~/.m2`, `~/.gradle`, содержимое .jar (`unzip`, `jar tf`, `javap`), декомпиляция,
  интернет - кроме одного исключения ниже.
Не нашёл в проекте пакет, версию или значение -> дальше не ищи, это нормальный случай, и
для него есть правило: пакеты - таблица в разделе 2, п.5; зависимость и версия - только дерево
зависимостей (раздел 5); значение - вопрос человеку (раздел 4) или `-`.

**Одно исключение - jar самой библиотеки allure-annotations.** Когда в сборке её версия 2.x
(была, подключена с нуля или поднята), можно посмотреть её jar - только чтобы проверить
аннотацию, которой нет в таблице импортов (раздел 2, п.5; раздел 5, «Пакет и аннотации - из
jar библиотеки»). Для аннотаций из таблицы jar не нужен. Только этот один
jar, только командами оттуда: путь - из сборки, `jar tf`, `javap`. Другие jar, остальной
`~/.m2` и `~/.gradle`, исходники и распаковка - по-прежнему нельзя. Версия ниже 2.x -> jar
не смотришь.

**Только Java и Kotlin.** Правила - для тестов на Java и Kotlin. Тесты на Cucumber (файлы
`.feature`) размечаются тегами `@allure.label.<лейбл>:<значение>` в самих `.feature`: этот набор
их не размечает. Есть `.feature`-файлы (`find . -name "*.feature" -not -path "*/target/*" -not -path "*/build/*" | head -3`)
-> размечай только Java/Kotlin-тесты, а в отчёт строкой `решить человеку: в проекте есть
сценарии Cucumber (.feature) - их разметку тегами @allure.label ставит человек`.

## 1. Обязательные аннотации

Основа разметки - пять аннотаций: контур, слой, КЭ, команда, TMS-link. Для тестовой модели
в Allure TestOps к ним добавляются регресс и задача. Где хранится модель (Allure TestOps,
Zephyr или другая TMS) - вопрос `model` (раздел 4).

| Аннотация | Что значит | Обязательна | Кто ставит и откуда значение |
|-----------|------------|-------------|------------------------------|
| `@TestStage` (или готовая: `@IsolatedTest`, `@DevStandTest`, `@StStandTest`, `@IftStandTest`, `@PsiStandTest`, `@PromStandTest`) | контур, где работает автотест | всегда | агент, вопрос `stage` |
| `@TestLayer` (или готовая: `@ApiTest`, `@DbTest`, `@MqTest`, `@UiTest`) | слой, на котором запускается тест (раздел 3) | всегда | агент, без вопроса |
| `@System("<КЭ>")` | КЭ тестируемой системы | всегда | агент, вопрос `system` |
| `@Team("<команда> (<ФОС>)")` - команда в проекте одна; `@Team("<команда>")` - команд несколько | команда, которой принадлежит автотест; одна команда - с ФОС в скобках, например `@Team("uwptext (00CG0000)")` | желательно: по документации библиотеки не обязательна | агент, вопросы `teams`, `team`, `fos` (подраздел «Команда и ФОС», раздел 4) |
| `@TmsLink("<ключ>")` | связь автотеста с ручным тестом в TMS | всегда, над каждым тест-методом | **человек**: ключ ручного теста есть только в TMS. Агент ставит её в одном случае: ключ тест-кейса (`<КОД>-T<цифры>`) уже записан в аннотации этого тест-метода - `@DisplayName`, `@Zephyr` или другой (раздел 2а), сама аннотация при этом не меняется. Сам ключ агент не придумывает, остальные тест-методы без неё показывает в отчёте |
| `@Regress` или `@CriticalRegress` | тест входит в регресс / критичный регресс; обе сразу не ставятся | только модель в Allure TestOps | агент, вопрос `regress` |
| `@Story("<задача>")` или `@Issue("<задача>")` | связь теста с задачей | только модель в Allure TestOps | агент, вопрос `story` |

**Набор агента** - все строки таблицы, кроме `@TmsLink`. По нему решается, размечен ли
проект (раздел 5). `@TmsLink` проверяется отдельно: ключи тест-кейсов из аннотаций тест-метода агент копирует
сам (раздел 2а), остальное попадает в отчёт как работа человека.

**`@Team` - желательная, не обязательная** (так в документации библиотеки). Вопросы `teams`,
`team`, `fos` задаются как обычно, значение есть -> агент ставит `@Team` вместе с остальными.
Значение `@Team`: команда в проекте одна -> строго `<команда> (<ФОС>)` - название, пробел,
ФОС в круглых скобках. Скобки обязательны: система берёт ФОС именно из них. Команд несколько
-> только название, без ФОС и без скобок: `<команда>`. Но размечен ли
проект, решается без неё: тест-класс, у которого из набора агента нет только `@Team`, - размечен
(раздел 5, итог проверки, `P16`). В отчёт - отдельной строкой: `желательно: @Team нет у <классы>`.

Готовые аннотации и значения:

| Готовая аннотация | То же самое |
|-------------------|-------------|
| `@ApiTest` | `@TestLayer("api")` |
| `@DbTest` | `@TestLayer("db")` |
| `@MqTest` | `@TestLayer("mq")` |
| `@UiTest` | `@TestLayer("ui")` |
| `@UnitTest` | `@TestLayer("unit")` |
| `@PerformanceTest` | `@TestLayer("performance")` |
| `@CdcConsumerTest` | `@TestLayer("cdcConsumer")` |
| `@CdcProviderTest` | `@TestLayer("cdcProvider")` |
| `@IsolatedTest` | `@TestStage("code")` |
| `@DevStandTest` | `@TestStage("dev")` |
| `@StStandTest` | `@TestStage("st")` |
| `@IftStandTest` | `@TestStage("ift")` |
| `@PsiStandTest` | `@TestStage("psi")` |
| `@PromStandTest` | `@TestStage("prom")` |

## 2. Как ставить - каскадом

Аннотация над классом действует на все его тесты, над абстрактным базовым классом - на все
тесты наследников. Над каждым методом весь набор не ставится.

1. Значение одно на весь проект (`@System`, `@Team`, `@TestStage`, общий `@Regress`,
   общая `@Story`) -> ставь над базовым тест-классом - классом, от которого наследуются
   тест-классы (из `ARCHITECTURE.md`; там его нет - тот, что стоит после `extends` в
   тест-классах). Ставь над ним, даже если он не абстрактный, а над наследниками эти
   аннотации не ставь. Тест-классы наследуются от разных базовых классов -> над каждым из
   них. Тест-класс без базового класса -> над ним самим.
2. `@TestLayer` - над тест-классом или над базовым классом слоя, если тесты одного слоя
   наследуются от него. Тест-класс работает с системой через несколько слоёв - слой по
   тому, что он проверяет (куда уходит запрос, чей ответ проверяется).
3. `@TmsLink` - только над тест-методом, своя на каждый тест. Агент ставит её только по
   разделу 2а - ключ из аннотации тест-метода.
4. Аннотация уже стоит (над методом, классом или базовым классом) -> не трогай её и не
   дублируй ниже по иерархии. Над базовым классом её нет, но она уже стоит над частью его
   наследников -> над базовым классом не ставь: поставь над теми наследниками, где её нет
   (ни своей, ни через предка). Чужие аннотации не переносишь и не удаляешь.
   Исключение - исправление по отчёту проверки: строка `MK-<n>` с `агент` (раздел 7).
5. Импорты - явные, без `*`, по одному на аннотацию: **у каждой аннотации свой пакет**.
   Импорты - ровно из этой таблицы, искать их не нужно:

   | Аннотация | Импорт |
   |-----------|--------|
   | `@TestLayer` | `ru.sber.qa.allure.layer.TestLayer` |
   | `@ApiTest`, `@DbTest`, `@MqTest`, `@UiTest` | `ru.sber.qa.allure.layer.layers.<Имя>` |
   | `@TestStage` | `ru.sber.qa.allure.stage.TestStage` |
   | `@DevStandTest`, `@StStandTest`, `@IftStandTest`, `@PsiStandTest`, `@PromStandTest` | `ru.sber.qa.allure.stage.stages.<Имя>` |
   | `@System` | `ru.sber.qa.allure.system.System` |
   | `@Team` | `ru.sber.qa.allure.team.Team` |
   | `@Regress`, `@CriticalRegress` | `ru.sber.qa.allure.regress.<Имя>` |
   | `@TmsLink`, `@Story`, `@Issue` | `io.qameta.allure.<Имя>` - это аннотации самого Allure, не allure-annotations |

   Аннотации не из таблицы - `@IsolatedTest` (по аналогии с соседями -
   `ru.sber.qa.allure.stage.stages.IsolatedTest`) и `@UnitTest`, `@PerformanceTest`,
   `@CdcConsumerTest`, `@CdcProviderTest` (по аналогии - `ru.sber.qa.allure.layer.layers.<Имя>`).
   Перед тем как ставить, проверь, что класс есть в jar
   (раздел 5, «Пакет и аннотации - из jar библиотеки»). Нет в jar -> не ставь, в отчёте:
   `<аннотация> - не поставлена: нет в allure-annotations <версия>`. Похожую по смыслу не
   подставляй.

   **`@System` и `java.lang.System`.** Импорт `ru.sber.qa.allure.system.System` закрывает в
   файле стандартный `System`: `System.getProperty(...)`, `System.out`, `System::currentTimeMillis`
   перестанут компилироваться. Перед тем как ставить `@System`, проверь файл - любое
   упоминание `System`, кроме самой аннотации и импортов:
   `grep -nE "\bSystem\b" <файл> | grep -vE "@System\(|^[0-9]+:[[:space:]]*import "`. Пусто -> обычный импорт. Нашлось -> этот файл -
   единственное место, где пишется полное имя без импорта:
   `@ru.sber.qa.allure.system.System("<КЭ>")`.

   Ошибку «cannot find symbol» на импорте аннотации не чини поиском - убери эту аннотацию и
   запиши в отчёт.
6. Зависимость `ru.sber.qa:allure-annotations` и её версию проверяют до любых правок, первым
   шагом, по дереву зависимостей (раздел 5, «Зависимость и версия»). В модуле с тестами её
   нет -> добавь в сборку этого модуля с нуля, scope `test` (Gradle - `testImplementation`),
   версия - из значений разметки (там `2.0.2`, если человек не назвал другую). Уже есть (в
   том числе пришла через другую библиотеку) -> не трогай: ни версию, ни scope. Одно
   исключение: в значениях разметки `версия: поднять <старая> -> 2.0.2` (раздел 2б, п.2) ->
   замени номер версии на `2.0.2` там, где он записан в проекте (в зависимости или в
   свойстве; команда «Где записан номер версии», раздел 5). В проекте номер не записан
   (версию задаёт BOM, родительский pom или она пришла через другую библиотеку) -> добавь
   зависимость в сборку модуля с тестами явно, с версией `2.0.2`. Больше в сборке ничего не
   меняй. Версию не ищи в .jar, в `~/.m2` и в интернете.

## 2а. Ключ тест-кейса в аннотациях тест-метода

Ключи ищутся во **всех** тест-классах проекта, а не только в тех, где ставятся другие
аннотации: тест-класс, который размечен через базовый класс, всё равно может нуждаться в
`@TmsLink` над своими методами. Список таких методов - команда «Ключи тест-кейсов без
`@TmsLink`» (раздел 5).

Бывает, что ключ ручного тест-кейса уже записан в аннотации над тест-методом. В каждом проекте
по-своему, например:
- в названии теста: `@DisplayName("[SBOLCRM-T1234] Создание заказа")`;
- в шаблоне имени параметризованного теста: `@ParameterizedTest(name = "[SBOLCRM-T1234] {0}")`;
- в своей аннотации проекта: `@Zephyr("SBOLCRM-T1234")`, `@TestCase(id = "SBOLCRM-T1234")` и т.п.

Ищи ключ по его виду (ниже), а не по имени аннотации: годится любая аннотация тест-метода, кроме
`@TmsLink`. Не считаются: источники данных (`@CsvSource`, `@ValueSource`, `@MethodSource` и другие
`@...Source`), `@Disabled...` и ссылки на задачи (`@Link`, `@Issue`, `@Story`). Такой ключ агент
**копирует** в `@TmsLink` этого тест-метода. **Аннотация с ключом не меняется**: ни ключ, ни текст
из неё не убираются, `@Zephyr` и подобные не удаляются.

**Ключ тест-кейса** - `<КОД ПРОЕКТА>-T<цифры>`: код проекта (первая - большая латинская
буква, дальше большие латинские буквы и цифры), дефис, буква `T` и сразу цифры. Подходят: `SBOLCRM-T1234`, `PVATF-T12`, `AB2-T7`. Буква `T` перед цифрами - это и
есть признак тест-кейса. Без неё (`PVATF-4567`, `SBOLCRM-123`) - это задача, баг или история,
а не тест-кейс: такой ключ не бери, даже если он единственный у метода.

Берёшь, только если выполнены все условия:
1. в аннотациях тест-метода вместе ровно один ключ тест-кейса (`-T<цифры>`): один и тот же ключ
   в `@DisplayName` и в `@Zephyr` - один ключ, разные ключи - два. Где ключ стоит в значении - неважно;
2. у тест-метода ещё нет `@TmsLink`;
3. такого же ключа тест-кейса нет у другого тест-метода - ни в одной его аннотации, ни в
   его `@TmsLink` (параметризованный тест - один
   метод, его запуски не считаются; `@DisplayName` над классом не считается).
Условие 3 проверяй до того, как ставить `@TmsLink`: сначала команда «Одинаковые ключи
тест-кейсов» (раздел 5), потом правки. Поставленный `@TmsLink` не снимают (раздел 6).
Хоть одно условие не выполнено -> ничего не ставь: тест-метод попадает в отчёт как работа
человека. **В отчёте - причина словами, а не номер условия**, чтобы было видно, что это не
сбой агента:
- одинаковый ключ (условие 3) - одной строкой на ключ, со всеми его тест-методами:
  `<ключ> - одинаковый в <Класс.метод>, <Класс.метод>: новый @TmsLink не поставлен,
  уже стоит у <Класс.метод / никого>, решите, какому тесту он принадлежит` (найти - команда «Одинаковые ключи тест-кейсов»,
  раздел 5);
- два ключа у одного метода (условие 1): `<Класс.метод> - в аннотациях два ключа
  тест-кейса: <ключ>, <ключ>`;
- `@TmsLink` уже есть с другим ключом (условие 2): `<Класс.метод> - уже @TmsLink("<ключ>"),
  в аннотации <ключ>`;
- скрипт не смог прочитать значение аннотации (константа, вызов метода): `<Класс.метод> - значение
  аннотации не разобрать скриптом, проверьте вручную`.

**Параметризованный тест (`@ParameterizedTest`) - такой же тест-метод.** Он запускается
много раз с разными данными, но это один метод и один тест-кейс: `@TmsLink` ставится над ним
так же, как над `@Test`. Это не одинаковый ключ (условие 3) - условие 3 про ключ в двух
разных методах. Ключ берётся из его аннотаций, в том числе из шаблона имени
`@ParameterizedTest(name = "[SBOLCRM-T1234] {0}")`:
```java
@TmsLink("SBOLCRM-T1234")
@ParameterizedTest(name = "[SBOLCRM-T1234] {0}")
@ValueSource(strings = {"a", "b"})
void create(String value) { ... }
```
Ключ в `@DisplayName` и в `name` того же метода один и тот же - это один ключ, не два. Разные - два ключа (условие 1).

Как ставишь:
- над тест-методом - `@TmsLink("<ключ>")`, ключ - ровно как в аннотации, без скобок и
  разделителей: `@DisplayName("[SBOLCRM-T1234] Создание заказа")` -> `@TmsLink("SBOLCRM-T1234")`,
  `@Zephyr("SBOLCRM-T1234")` -> `@TmsLink("SBOLCRM-T1234")`; аннотация с ключом остаётся как была;
- аннотации над классом (`@DisplayName`, `@Zephyr` и другие) не трогай и ключи из них не бери: это не тест-метод.

## 2б. Перед правками - три проверки

Разметку ставят только по правилам этого файла, а правила рассчитаны на allure-annotations
2.x. Здесь и дальше «2.x» - мажорная версия 2 или больше (`2.0.2`, `2.5.0`, `3.0.0`); «ниже
2.x» - мажорная 0 или 1. Поэтому до первой правки по порядку:

1. **Незакоммиченные изменения.** Из корня проекта:
   `git status --porcelain -- . ':(exclude).gigacode'`. Вывод не пустой -> правок не делай,
   остановись. Человеку: «В проекте есть незакоммиченные изменения: <файлы из вывода>.
   Закоммитьте их, и я продолжу разметку». Почему: разметка - отдельный коммит, чужие правки
   в него попасть не должны, а при откате разметки они пропадут.
2. **Версия библиотеки.** Версия - из дерева зависимостей (раздел 5, «Зависимость и
   версия»), не из поиска по файлам. Первое число версии (до первой точки) - мажорная
   версия: `1.8.3` -> 1, `2.0.2` -> 2.
   - зависимости нет -> её добавят с версией `2.0.2`, проверка пройдена;
   - мажорная версия 2 или больше -> проверка пройдена;
   - дерево не построилось (раздел 5: команда упала) -> зависимость не определена: правок
     не делай, остановись. Человеку: «Не удалось построить дерево зависимостей, поэтому
     не понять, есть ли allure-annotations и какой версии: <первые строки ошибки>.
     Исправьте сборку и повторите запрос»;
   - мажорная версия 0 или 1 -> разметить по правилам нельзя. Предложи человеку поднять
     версию до 2.0.2 (вопрос `upgrade`, раздел 4) - это вопрос разметки, он разрешён.
     `да` -> в значениях разметки `версия: поднять <старая> -> 2.0.2`, версию поднимают
     вместе с разметкой (раздел 2, п.6). `нет` -> правок не делай, остановись. Человеку:
     «Разметить тесты по правилам не получится: в проекте allure-annotations <версия>, а
     нужна 2.x».
   Кто спрашивает: `migration-map` на Этапе 2 (шаг 1б), в блоке вопросов разметки. Агент
   разметки не спрашивает, а сверяет: в сборке мажорная версия 0 или 1, а в значениях
   разметки нет `поднять` -> остановиться со статусом «не сделан: allure-annotations
   <версия>, нужна 2.x».
3. **Компиляция.** Выполни команду компиляции проекта до правок. Ошибка -> правок не делай,
   остановись. Человеку: «Проект не компилируется, поэтому разметку поставить нельзя:
   <первые строки ошибки>. Исправьте сборку и повторите запрос». Почему: иначе после
   разметки не понять, чья ошибка - твоя или та, что была.

Все три проверки пройдены -> можно ставить разметку. Ошибка компиляции после правок теперь
точно из-за разметки: чини её сам.

Проверки 1 и 3 делает тот, кто ставит разметку: агент `pvatf-marker` или ты сам, если
ставишь без агента. Агент человеку не пишет: он возвращает статус «не сделан: <причина>»,
а сообщение человеку из этого раздела пишет тот, кто его запустил.

## 3. Слой

Слой - это не технология, а уровень, на котором тест работает с системой. Смотри, через что
тест обращается к системе и чей ответ проверяет. Метка технологии в карте лишь подсказывает
слой:

| Через что тест работает с системой | Аннотация | Подсказка: технология карты |
|------------------------------------|-----------|-----------------------------|
| API системы: HTTP-запросы, gRPC, GraphQL, WebSocket, заглушки API | `@ApiTest` | `rest`, `grpc`, `graphql`, `websocket`, `sbermock` |
| пользовательский интерфейс: браузер, мобильное приложение | `@UiTest` | `ui-selenide`, `ui-playwright`, `appium-android`, `appium-ios` |
| база данных напрямую | `@DbTest` | `db`, `datasource` |
| очереди сообщений | `@MqTest` | `kafka` и другие очереди |
| код проекта напрямую, без поднятого приложения: unit-тесты, модульные тесты | `@UnitTest` | - |
| нагрузка: нагрузочные тесты | `@PerformanceTest` | - |
| контракт со стороны потребителя (consumer-driven contract) | `@CdcConsumerTest` | - |
| контракт со стороны поставщика | `@CdcProviderTest` | - |
| другое | `@TestLayer("<слой>")` | - |

## 4. Вопросы человеку

Задаются только на Этапе 2 карты (шаг 1б). Вопрос `upgrade` - про версию библиотеки (раздел
2б, п.2), остальные - только по аннотациям, которых в проекте нет.
Значение есть в проекте (аннотация уже стоит или КЭ / команда записаны в настройках, README,
Jenkinsfile) -> бери оттуда, вопрос не задаётся. Порядок - как в таблице. Как именно
задавать (одним блоком для терминального приложения) - Этап 2 карты, шаг 1б.

| Ключ | Вопрос | Когда задаётся | Ответ |
|------|--------|----------------|-------|
| `upgrade` | В проекте allure-annotations версии ниже 2.x, а разметка по правилам требует 2.x. Поднять версию до 2.0.2: да или нет? | мажорная версия в сборке 0 или 1 (раздел 2б, п.2); задаётся первым | `да` / `нет`. `нет` -> остальные вопросы не задаются, разметку не ставят |
| `teams` | Сколько команд пишут автотесты в этом проекте: одна или несколько? | нет `@Team`; задаётся первым из вопросов о значениях | `одна` / `несколько`. `несколько` -> `team` вторым текстом, `fos` не задаётся (подраздел «Команда и ФОС») |
| `team` | Первый текст (`teams: одна`): Как называется команда? Полное название, как в справочнике команд. Второй текст (`teams: несколько`): Какие команды пишут автотесты и чьи это тесты? Названия - полные, как в справочнике команд. Например: payments - модуль payments-tests; cards - каталог src/test/java/cards | после `teams` | одна - название; несколько - `<команда> - <тест-классы, модуль или каталог>; ...` |
| `fos` | Первый текст: Какой ФОС у команды? Например, 00CG0000. Второй текст - найденные ФОС пунктами (подраздел «Команда и ФОС») | `teams: одна` | ФОС: две цифры, буква, буква или цифра, цифры (`[0-9]{2}[a-zA-Z][a-zA-Z0-9][0-9]+`) |
| `system` | Первый текст: Какой КЭ у тестируемой системы? Например, CI02546875. Второй текст - найденные КЭ пунктами (подраздел «КЭ» ниже) | нет `@System`, и КЭ не найден в проекте или найдено несколько КЭ без явной принадлежности (подраздел «КЭ» ниже) | КЭ; несколько КЭ - `<КЭ> - <тест-классы>; ...` |
| `model` | Где хранится тестовая модель: в Allure TestOps (testops) или в другой TMS, например Zephyr (tms)? | всегда, если разметка нужна | `testops` / `tms` |
| `stage` | На каком контуре работают автотесты: code, dev, st, ift, psi или prom? | нет `@TestStage` и готовых аннотаций контура | одно значение |
| `regress` | Тесты входят в регресс: regress - в регрессе, critical - в критичном регрессе, `-` - не входят? | `model: testops`, нет `@Regress`/`@CriticalRegress` | `regress` / `critical` / `-` |
| `story` | Какая задача у тестов? Например, PVATF-4567, или `-`, если задачи нет. | `model: testops`, нет `@Story`/`@Issue` | задача / `-` |

Текст вопроса - ровно из колонки «Вопрос»: не перефразируй и не добавляй пояснений.
Допустимые ответы - только из колонки «Ответ». Варианты - только настоящие значения (из
колонки «Ответ» или найденные в проекте). **Поле для своего ответа в окне вопроса есть
всегда, последним пунктом.** Поэтому НЕ добавляй варианты «Укажу своё значение», «Введу
сам», «Напишу в чате», «Другое», «Свой вариант», «Иное»: человек выберет такой пункт, и
ответа не будет. Вопрос со свободным ответом без найденных значений - без вариантов, в
конце текста - «Укажите в поле ввода.».

**Опросник - строго по шагам, ни одного вопроса не пропускать.**
1. До первого вопроса составь список: пройди таблицу выше сверху вниз и про КАЖДЫЙ ключ
   реши - значение есть в проекте, вопрос нужен или вопрос не нужен (колонка «Когда
   задаётся»). Пропускать ключ без решения нельзя. `model` нужен всегда, если разметка
   нужна; `teams`, `system`, `stage` - всегда, если их аннотации нет в проекте.
2. В блок вопросов (Этап 2 карты, шаг 1б) попадает КАЖДЫЙ ключ из списка с «вопрос нужен»,
   в порядке таблицы. `team` первым текстом и `fos` - с `when` `{"teams": "одна"}`, `team`
   вторым текстом - с `when` `{"teams": "несколько"}`, если `teams` спрашивается в этом же блоке.
3. Ответы пришли -> запиши каждый и вычеркни лишнее (`teams: несколько` убирает `fos` и
   `team` первым текстом; `model: tms` убирает `regress` и `story`).
Сверка перед тем, как закончить с вопросами: в значениях разметки есть ВСЕ ключи - `team`,
`system`, `model`, `stage`, `regress`, `story`, у каждого значение: из проекта, ответ, `-`
или `не нужно (<почему>)`. `team` - `<команда> (<ФОС>)` (одна команда), `<команда> - <тесты>; ...` (несколько) или `-`: сначала
`teams`, потом `team` и `fos`. Хоть одного ключа нет -> добавь его вопрос в блок. Чаще всего
забывают команду (`teams`, `team`, `fos`), КЭ (`system`), контур (`stage`) и модель (`model`)
- проверяй их первыми.

Ответ записывается в паспорт карты, строка «Разметка» (шаблон карты). Ответ `-` -
эту аннотацию не ставят, так и пиши. Про `@TmsLink` вопросов нет: ключи ручных тестов
человек ставит сам.

### Команда и ФОС

`@Team` пишется так: `@Team("<команда> (<ФОС>)")`, например `@Team("uwptext (00CG0000)")`.
ФОС - код команды: две цифры, буква, буква или цифра, дальше цифры
(`[0-9]{2}[a-zA-Z][a-zA-Z0-9][0-9]+`, пример `00CG0000`).

1. `@Team` уже стоит в проекте (команда «Проверка, что размечено», раздел 5) -> значение
   бери оттуда, вопросов `teams`, `team`, `fos` нет.
2. `@Team` нет -> **первый вопрос о значениях - `teams`**: «Сколько команд пишут автотесты в
   этом проекте: одна или несколько?».
3. `несколько` -> вопрос `team`, второй текст (таблица выше): какие команды и чьи тесты.
   ФОС не спрашивается и не ставится: `@Team("<команда>")` - только название, без скобок.
   Значение `team: <команда> - <тест-классы, модуль или каталог>; <команда> - <...>`. Куда
   ставить - как `@System` при нескольких КЭ (подраздел «КЭ», п.5): все наследники базового
   класса одной команды -> над базовым классом, иначе - над каждым тест-классом своей
   команды. Тесты, про которые человек не сказал, чьи они, - без `@Team`, в отчёт:
   `желательно: @Team нет у <классы> - команда не названа`.
4. `одна` -> вопрос `team` (название), затем `fos`. Перед `fos` найди ФОС в проекте, из
   корня:
   `grep -rnowE "[0-9]{2}[a-zA-Z][a-zA-Z0-9][0-9]+" --include='*.java' --include='*.kt' --include='*.properties' --include='*.yml' --include='*.yaml' --include='*.xml' --include='*.md' --include='Jenkinsfile*' . | grep -v "/target/\|/build/\|\.gigacode" | head -20`
   Строка вывода - `<файл>:<строка>:<ФОС>`. Одинаковые - один ФОС. Сам ФОС из вывода не
   выбирай и в разметку без ответа не ставь: под этот шаблон попадают и посторонние строки.
   - ничего не нашлось -> вопрос `fos`, первый текст;
   - нашлось -> вопрос `fos`, второй текст - найденные ФОС пунктами, каждый на своей строке:
     ```
     Какой ФОС у команды? В проекте найдено:
     1) <ФОС> - <файл>
     2) <ФОС> - <файл>
     ```
     Ответ - номер пункта или ФОС. Человек написал свой ФОС -> бери его.
   Ответ не похож на ФОС (шаблон выше) -> повтори вопрос `fos` один раз.
5. Значение: `team: <команда> (<ФОС>)` - его агент и ставит в `@Team`, ровно так: название,
   пробел, ФОС в круглых скобках. Без скобок или без ФОС при одной команде - ошибка. Ответ `-` на `team`
   или `fos` -> `team: -`, `@Team` не ставят.

### КЭ: поиск, несколько КЭ в проекте

В одном проекте может быть несколько КЭ (2-4 - это нормально). Каждый тест-класс
размечается КЭ той системы, к которой он относится.

1. Найди все КЭ, из корня проекта:
   `grep -rnowE "CI[0-9]+" --include='*.java' --include='*.kt' --include='*.properties' --include='*.yml' --include='*.yaml' --include='*.xml' --include='*.gradle' --include='*.kts' --include='*.md' --include='Jenkinsfile*' . | grep -v "/target/\|/build/\|\.gigacode"`
   Строка вывода - `<файл>:<строка>:<КЭ>`. Одинаковые КЭ - один КЭ.
2. Принадлежность. КЭ относится к тест-классу, если найден явно там, где этот класс:
   - в файле тест-класса (`@System`, константа, комментарий, URL, строка) -> этот тест-класс;
   - в файле базового класса -> все его наследники;
   - в настройках или файле сборки модуля (`<модуль>/src/test/resources/`, `<модуль>/pom.xml`,
     `<модуль>/build.gradle`) -> все тест-классы этого модуля.
   Ближнее место главнее: файл класса, потом базовый класс, потом модуль. КЭ в README,
   Jenkinsfile, корневых настройках - КЭ проекта: принадлежность класса он не задаёт.
3. Итог:
   - КЭ не найден -> вопрос `system`, первый текст (таблица выше);
   - найден один КЭ -> он у всех тест-классов, `из проекта: <файл>`, вопроса нет;
   - найдено несколько -> тест-класс с явной принадлежностью (п.2) получает свой КЭ, вопроса
     про него нет. Тест-классы без явной принадлежности, а также класс, у которого в одном
     месте два разных КЭ, -> вопрос `system`, второй текст: по вопросу на группу (модуль,
     каталог или список классов). Сам КЭ по смыслу не выбирай.
   Второй текст вопроса - найденные КЭ пунктами, каждый на своей строке:
   ```
   В проекте найдено несколько КЭ:
   1) <КЭ> - <где найден: файл>
   2) <КЭ> - <где найден: файл>
   К какому КЭ относятся тесты <модуль / каталог / классы>?
   ```
   Ответ - номер пункта или КЭ. Человек написал КЭ не из списка -> бери его.
4. Значение `system`: один КЭ -> `<КЭ>`; несколько -> `<КЭ> - <тест-классы, модуль или
   каталог>; <КЭ> - <...>`.
5. Куда ставить `@System`: все наследники базового класса с одним КЭ -> над базовым
   классом. Наследники с разными КЭ -> над каждым тест-классом, над базовым классом не ставь.

## 5. Когда разметка не нужна

Юнит `markup` не создаётся, если:
- каждый тест-класс уже размечен набором агента (раздел 1, сам или через базовый класс;
  `@Team` не считается - она желательная, раздел 1) и
  нет ключей тест-кейсов в аннотациях тест-методов, которые можно взять в `@TmsLink` (раздел 2а);
- `scope: core` - тесты в этом режиме не меняются;
- allure-annotations в сборке ниже 2.x, а поднять версию человек отказался (раздел 2б,
  п.2): разметить по правилам нельзя.

Проверка, что размечено (по каталогу тестов):
```
grep -rlE "@(TestLayer|ApiTest|DbTest|MqTest|UiTest|UnitTest|CdcConsumerTest|CdcProviderTest|PerformanceTest)\b" --include='*.java' --include='*.kt' <каталог тестов>
grep -rlE "@(TestStage|IsolatedTest|DevStandTest|StStandTest|IftStandTest|PsiStandTest|PromStandTest)\b" --include='*.java' --include='*.kt' <каталог тестов>
grep -rlE "@(ru\.sber\.qa\.allure\.system\.)?System\(" --include='*.java' --include='*.kt' <каталог тестов>
grep -rlE "@Team\(" --include='*.java' --include='*.kt' <каталог тестов>
grep -rlE "@(Regress|CriticalRegress)\b" --include='*.java' --include='*.kt' <каталог тестов>
grep -rlE "@(Story|Issue)\b" --include='*.java' --include='*.kt' <каталог тестов>
```
Файл есть в выводе -> аннотация стоит над его классом (проверь глазами, что над `class`, а
не над одним методом). Регресс и задача - две разные строки набора: каждая проверяется
отдельно.

Зависимость и версия - по дереву зависимостей сборки, не поиском по файлам. Дерево
показывает версию, которая реально попадёт в тесты, даже если её задают свойство,
родительский pom, BOM или другая библиотека. Из корня проекта:
- Maven (нет `mvnw` -> `mvn`):
  ```
  ./mvnw dependency:tree -Dincludes=ru.sber.qa:allure-annotations
  ```
  Дерево печатается по каждому модулю (строка `--- ... @ <модуль> ---`). Строка
  `ru.sber.qa:allure-annotations:jar:<версия>:<scope>` в блоке модуля -> в модуле есть, версия -
  четвёртое поле. Строки нет -> в модуле нет;
- Gradle (нет `gradlew` -> `gradle`), по каждому модулю с тестами (один модуль - без
  `:<модуль>`):
  ```
  ./gradlew -q :<модуль>:dependencies --configuration testRuntimeClasspath | grep "ru.sber.qa:allure-annotations"
  ```
  Строка `ru.sber.qa:allure-annotations:<версия>` -> есть. В строке есть `->`
  (`...:1.8.3 -> 2.0.2` или `ru.sber.qa:allure-annotations -> 2.0.2`) -> версия - то, что
  после `->`. Пометки `(*)`, `(c)` в конце строки не часть версии. Пусто -> в модуле нет:
  grep ничего не нашёл - это не ошибка команды.
Запомни по каждому модулю с тестами: `есть <версия>` или `нет`. В разных модулях разные
версии -> для раздела 2б, п.2 бери самую низкую.
Команда упала (Maven - `BUILD FAILURE`, Gradle - `FAILURE:` или `What went wrong`: нет сети,
не скачались зависимости, ошибка сборки) -> зависимость не
определена: покажи первые строки ошибки; что делать - раздел 2б, п.2. По файлам, .jar,
`~/.m2` и в интернете зависимость не ищи - только дерево.

«Allure в сборке» - есть ли `allure-java-commons` (раздел 6, п.5), тем же деревом зависимостей:
- Maven: `./mvnw dependency:tree -Dincludes=io.qameta.allure:allure-java-commons` - строка
  `io.qameta.allure:allure-java-commons:jar:<версия>:<scope>` в блоке модуля -> есть;
- Gradle: `./gradlew -q :<модуль>:dependencies --configuration testRuntimeClasspath | grep "io.qameta.allure:allure-java-commons"` -
  строка есть -> есть, пусто -> нет.
Команда упала -> не определено: в отчёт первые строки ошибки, разметку это не останавливает.

Пакет и аннотации - из jar библиотеки (раздел 0, исключение; только когда версия 2.x уже
в сборке и только для аннотации, которой нет в таблице импортов раздела 2, п.5). Сначала путь к jar - его даёт сама сборка, по папкам не ищи:
- Maven:
  ```
  ./mvnw -q dependency:build-classpath -Dmdep.outputFile=/dev/stdout | tr ':' '\n' | grep "allure-annotations-.*\.jar" | sort -u
  ```
- Gradle - ровно эта папка, с версией из дерева:
  ```
  find ~/.gradle/caches/modules-2/files-2.1/ru.sber.qa/allure-annotations/<версия> -name "allure-annotations-<версия>.jar"
  ```
Потом список аннотаций и их пакет:
```
jar tf <путь к jar> | grep '\.class$' | grep -v '\$'
```
Каждая строка - одна аннотация со своим пакетом: `ru/sber/qa/allure/layer/layers/UiTest.class`
-> класс `UiTest`, импорт `ru.sber.qa.allure.layer.layers.UiTest` (косые черты - точки, без
`.class`). Запиши пакет для каждой аннотации из раздела 1 отдельно, пакеты разные. Что принимает аннотация (есть ли `value`), если неясно, как её писать:
`javap -cp <путь к jar> <пакет>.<Аннотация>`. Больше в jar ничего не смотри: не распаковывай,
не декомпилируй, другие jar не открывай.

Где записан номер версии (нужно только для подъёма версии, раздел 2, п.6):
```
grep -rn "allure-annotations" --include=pom.xml --include='*.gradle' --include='*.kts' --include='*.toml' . | grep -v "/target/\|/build/"
```
Версия записана свойством (`${allure.annotations.version}`, `libs.versions.toml`) -> место -
это свойство: `grep -rn "<имя свойства>" --include=pom.xml --include='*.gradle' --include='*.kts' --include='*.properties' --include='*.toml' .`.

Ключи тест-кейсов - скриптом, не grep-ом. Скрипт берёт только тест-методы (`@Test`,
`@ParameterizedTest`, `@RepeatedTest`, `@TestFactory`, `@TestTemplate`) и ищет ключ в значениях
всех их аннотаций (раздел 2а): строки, текстовые блоки и их склейка через `+`. Понимает многострочные
аннотации, перенос строки перед `(`, полные имена аннотаций, аннотации на одной строке с методом
и Kotlin. Не берёт комментарии, аннотации над классом, `@...Source`, `@Disabled...`, `@Link`,
`@Issue`, `@Story`. Последняя строка вывода - всегда `итого: <n>`, это не тест-метод: остальные
строки - находки, `итого: 0` - находок нет. Каталогов тестов несколько -> перечисли все через пробел.

Ключи тест-кейсов без `@TmsLink` (кандидаты для раздела 2а):
```
python3 .gigacode/skills/migration-step/scripts/markup_keys.py missing <каталог тестов>...
```
Строка: `<файл>:<строка>: <метод> - <ключи> - нет @TmsLink (из <аннотации>)`. Ключей в строке два
и больше - условие 1 раздела 2а не выполнено. Строка `<файл>:<строка>: <метод> - значение не
разобрать, проверьте вручную` - ключ стоит в значении, которое скрипт не прочитал (константа,
вызов метода): `@TmsLink` не ставь, это работа человека (раздел 2а). Последняя строка - `итого: <n>`.

Одинаковые ключи тест-кейсов у разных тест-методов (условие 3 раздела 2а; считаются ключи
из всех аннотаций тест-метода и из `@TmsLink`):
```
python3 .gigacode/skills/migration-step/scripts/markup_keys.py dup <каталог тестов>...
```
Строка: `<ключ> - <файл>:<строка>:<метод> <файл>:<строка>:<метод> ...`. Строка
`<файл>:<строка>:<метод> - значение не разобрать, проверьте вручную` - ключ этого метода неизвестен,
в отчёт человеку. `итого: 0` - одинаковых ключей нет.

Разметка каждого тест-класса - скриптом, не grep-ом (наследование grep не видит):
```
python3 .gigacode/skills/migration-step/scripts/markup_keys.py classes --need <ключи> <каталог тестов>...
```
`--need` - какие аннотации набора нужны, через запятую, без пробелов: `stage` (контур), `layer`
(слой) - всегда; `system` (КЭ), `team` (команда) - если значение не `-`; `regress`, `story` -
только при `model: testops` и значении не `-`. Пример: `--need stage,layer,system,team`.
Строка на тест-класс:
`<файл>:<строка>: <Класс> · база: <Base <- Lib (не из проекта) / нет> · контур: <аннотация / аннотация (в <базовый класс>) / НЕТ / нет> · слой: ... · КЭ: ... · команда: ... · регресс: ... · задача: ...`.
`(в BaseTest)` - аннотация стоит над предком из проекта. `НЕТ` - нужной аннотации нет ни над
классом, ни над его предками: класс не размечен. `нет` - аннотации нет, но она не нужна
(не в `--need`). Предок `(не из проекта)` - из библиотеки, его аннотаций скрипт не знает.
Предпоследняя строка - `тест-классов: <n>, с НЕТ: <n>`, последняя - `итого: <n>` (классов с
`НЕТ`). Каталогов тестов несколько -> перечисли все: базовый класс может лежать в другом.

Тест-методы без `@TmsLink` (работа человека, не повод для правок агента):
```
grep -rhoE "@(Test|ParameterizedTest)\b" --include='*.java' --include='*.kt' <каталог тестов> | wc -l
grep -rhoE "@TmsLink\(" --include='*.java' --include='*.kt' <каталог тестов> | wc -l
grep -rlE "@(Test|ParameterizedTest)\b" --include='*.java' --include='*.kt' <каталог тестов> | xargs grep -LE "@TmsLink\("
```
Первые две команды - сколько всего тест-методов и сколько из них связаны с TMS, третья -
тест-классы, где нет ни одной `@TmsLink`.

## 6. Перепроверка в конце - обязательна

Последний шаг любой разметки - после всех правок, до коммита. Без него работа не сделана.
Частая ошибка: аннотации над классом поставлены, а `@TmsLink` над тест-методами с ключом в
аннотации (`@DisplayName`, `@Zephyr` и другие) пропущены. Перепроверка ловит именно это.

1. **Ключи тест-кейсов без `@TmsLink`.** Сначала команда «Одинаковые ключи тест-кейсов»
   (раздел 5) по всем каталогам тестов: ключи из её вывода не ставь никому (условие 3
   раздела 2а). Потом из корня проекта команда «Ключи тест-кейсов без `@TmsLink`»
   (раздел 5) по всем каталогам тестов:
   ```
   python3 .gigacode/skills/migration-step/scripts/markup_keys.py missing <каталог тестов>...
   ```
   Каждая строка вывода - тест-метод, где есть ключ тест-кейса, а `@TmsLink` нет. По каждой строке: условия раздела 2а выполнены -> поставь `@TmsLink` с
   этим ключом; не выполнены -> в отчёт с причиной словами (раздел 2а: одинаковый ключ -
   со всеми его тест-методами). Каждая строка вывода должна быть либо исправлена, либо
   объяснена в отчёте - молча пропускать нельзя. `итого: 0` -> всё взято.
   **`@TmsLink` не снимай и не переноси никогда** - ни чужой, ни свой, поставленный в этой
   же разметке. Строка вывода про метод, над которым `@TmsLink` с этим ключом уже стоит, -
   ошибка проверки, а не повод для правки: ничего не меняй, в отчёт -
   `<Класс.метод> - перепроверка показала «нет @TmsLink», но он стоит`.
   **Файла нет в плане (или в «Файлах юнита») - всё равно ставь.** Так бывает с тест-классами,
   которые получают аннотации через базовый класс (например, UI-тесты под `@UiTest` на
   базовом UI-классе): в план они не попали, а ключи в них есть. В таком файле можно менять
   только это: `@TmsLink` над тест-методом и импорт `io.qameta.allure.TmsLink`. В отчёте:
   `<файл> - добавлен по перепроверке`.
   Каждый ключ из вывода команды «Одинаковые ключи тест-кейсов» - в отчёт со всеми
   тест-методами. Это обязательная строка отчёта, даже если вывод пустой.
2. **Набор агента.** Команды «Проверка, что размечено» из раздела 5 - по тест-классам этой
   разметки: файлы из плана (пакета) и наследники базовых классов из него. Каждый такой
   тест-класс размечен (сам или через базовый класс) каждой аннотацией набора агента, у
   которой есть значение (не `-`). Остальные тест-классы проекта размечает другой юнит
   (юнитов разметки несколько): их не трогай и в находки не пиши. Ключи тест-кейсов (п.1) -
   наоборот, по всем каталогам тестов.
3. **Импорты.** У каждой поставленной аннотации - импорт из таблицы раздела 2, п.5 (или
   полное имя `@System` по тому же пункту); импортов со `*` нет.
4. **Существующие строки кода не изменились:** разметка только добавляет строки (аннотации
   и импорты), поэтому в исходниках тестов не должно быть ни одной удалённой или изменённой
   строки - так `@DisplayName` и логика тестов точно не тронуты:
   `git diff HEAD -- '*.java' '*.kt' | grep -E "^-[^-]"` - пусто (до коммита разметки все её
   правки ещё не закоммичены; после коммита вместо `HEAD` - база).
   Исключение - исправление по отчёту (раздел 7): удалённые и изменённые строки есть, но
   только аннотации и импорты из строк `MK-<n>` плана. Любая другая - ошибка.
5. **Настройка Allure** (только проверка, правок не делай). По документации библиотеки:
   - ссылка из `@TmsLink` собирается из шаблона в `allure.properties`. Есть хоть один `@TmsLink` ->
     `grep -rn "allure.link.tms.pattern" --include='allure.properties' . | grep -v "/target/\|/build/"`.
     Пусто -> в отчёт строкой `решить человеку: в allure.properties нет
     allure.link.tms.pattern - ссылка из @TmsLink в отчёте Allure не соберётся, адрес TMS задаёт человек`.
     Адрес TMS не придумывай и файл не создавай;
   - библиотеке нужна зависимость `allure-java-commons`. Команда «Allure в сборке» (раздел 5).
     Её нет ни в одном модуле с тестами -> в отчёт строкой `решить человеку: в сборке нет
     io.qameta.allure:allure-java-commons - разметка не попадёт в отчёт Allure, подключите Allure
     к проекту`. Сам не добавляй.
6. Что-то поправил -> компиляция и пп.1-4 заново, пока не останутся только строки,
   объяснённые в отчёте (одинаковый ключ, два ключа, уже другой `@TmsLink`). Их не
   «дочищай»: `@TmsLink` им не ставится.

## 7. Проверка по правилам - отчёт для человека

Нужна, когда человек просит проверить разметку («проверь разметку»). Итог - список проблем
в отчёте: человек по нему быстро перепроверяет себя, а потом просит поправить
(`/orchestrator Поправь разметку по отчёту`). Здесь ничего не правишь - только находишь.

Все команды - из корня проекта, по каждому каталогу тестов (`<каталог>`). Строка вывода -
`<файл>:<строка>:<текст>`.

**Проблема** - нарушение одного пункта ниже, с файлом и строкой. Нет файла и строки - это
не проблема. Сомневаешься - это `замечание`, а не `ошибка`. Значения, которых нет в проекте,
не придумывай: проблема пишется, а значение спросят при исправлении (раздел 4).

Пункты проверки. У каждого: правило, как искать, вид (`ошибка` / `замечание`), кто
исправит (`агент` / `человек`).

- **П-1. allure-annotations 2.x** (раздел 2б, п.2). Дерево зависимостей (раздел 5): мажорная
  версия 0 или 1, или зависимости нет. `ошибка`, `агент` (вопрос `upgrade`).
- **П-2. Набор агента у каждого тест-класса** - сам или через предка (разделы 1, 5). Команда
  «Разметка каждого тест-класса» (`markup_keys.py classes`, раздел 5), `--need
  stage,layer,system,team` (+ `regress,story` при `model: testops`): каждое `НЕТ` в выводе.
  Одна строка на аннотацию со списком тест-классов без неё. `ошибка`, `агент` (значения - вопросы раздела 4); нет только
  `@Team` - `замечание`.
- **П-3. `@Team` по правилу команды** (раздел 1; раздел 4, «Команда и ФОС»). Сначала
  все значения `@Team` в проекте:
  ```
  grep -rnoE '@Team\("[^"]*"\)' --include='*.java' --include='*.kt' <каталог> | sed 's/.*@Team/@Team/' | sort | uniq -c
  ```
  Названия сравнивай без части в скобках: `uwptext` и `uwptext (00CG0000)` - одна команда.
  Одно название (команда одна) -> каждая `@Team` должна быть `<команда> (<ФОС>)`:
  ```
  grep -rnE "@Team\(" --include='*.java' --include='*.kt' <каталог> | grep -vE '@Team\("[^"(]+ \([0-9]{2}[a-zA-Z][a-zA-Z0-9][0-9]+\)"\)'
  ```
  Строка вывода - `ошибка`, `агент` (вопрос `fos`). Названий несколько (команд несколько) ->
  ФОС не нужен, проверка формата не делается; `@Team` со скобками при нескольких командах -
  `замечание`, `человек`.
- **П-4. `@System` - КЭ вида `CI<цифры>`** (раздел 1; раздел 4, «КЭ»):
  ```
  grep -rnE "@(ru\.sber\.qa\.allure\.system\.)?System\(" --include='*.java' --include='*.kt' <каталог> | grep -vE 'System\("CI[0-9]+"\)'
  ```
  `ошибка`, `агент` (вопрос `system`). Значение - константа или вызов -> `замечание: значение
  не разобрать, проверьте`.
- **П-5. `@TestStage` - code, dev, st, ift, psi или prom** (раздел 1):
  ```
  grep -rnE "@TestStage\(" --include='*.java' --include='*.kt' <каталог> | grep -vE '@TestStage\("(code|dev|st|ift|psi|prom)"\)'
  ```
  `ошибка`, `агент` (вопрос `stage`).
- **П-6. Слой - не технология** (раздел 3):
  ```
  grep -rnE "@TestLayer\(" --include='*.java' --include='*.kt' <каталог> | grep -vE '@TestLayer\("(api|db|mq|ui|unit|performance|cdcConsumer|cdcProvider)"\)'
  ```
  Значение - технология (`rest`, `http`, `grpc`, `kafka`, `selenide`, `sql` и т.п.) -> `ошибка`,
  `агент` (слой по таблице раздела 3). Другое значение -> `замечание: свой слой, проверьте`.
- **П-7. Нет противоречий у тест-класса** - у него самого и у предков (разделы 1, 2). По
  цепочке наследования: два разных контура, два разных слоя, два разных КЭ, `@Regress` и
  `@CriticalRegress` вместе. `ошибка`, `человек` - решает, что оставить.
- **П-8. `@TmsLink` - только над тест-методом** (раздел 2, п.3):
  ```
  grep -rnE -A4 "^[[:space:]]*@TmsLink\(" --include='*.java' --include='*.kt' <каталог> | grep -E "^[^:]+-[0-9]+-.*\b(class|interface|object)\b"
  ```
  Строка вывода - `@TmsLink` над классом. `ошибка`, `человек` - ключ какого тест-метода.
- **П-9. Ключ в `@TmsLink` - тест-кейс `<КОД>-T<цифры>`** (раздел 2а):
  ```
  grep -rnoE '@TmsLink\("[^"]*"\)' --include='*.java' --include='*.kt' <каталог> | grep -vE '@TmsLink\("[A-Z][A-Z0-9]*-T[0-9]+"\)'
  ```
  `замечание`, `человек`: ключ задачи (`PVATF-4567`) - её место в `@Issue` или `@Story`.
- **П-10. Одинаковых ключей тест-кейсов нет** (раздел 2а, условие 3). Команда «Одинаковые
  ключи тест-кейсов» (раздел 5). Одна строка на ключ со всеми тест-методами. `ошибка`,
  `человек` - какому тесту ключ.
- **П-11. Ключ тест-кейса из аннотации метода взят в `@TmsLink`** (раздел 2а). Команда
  «Ключи тест-кейсов без `@TmsLink`» (раздел 5), условия раздела 2а выполнены. `ошибка`,
  `агент`. Условия не выполнены - это П-10 или работа человека, не П-11.
- **П-12. Импорты аннотаций - из таблицы раздела 2, п.5, без `*`**:
  ```
  grep -rnE "^import (ru\.sber\.qa\.allure|io\.qameta\.allure)\.[a-zA-Z0-9_.]*\*;" --include='*.java' --include='*.kt' <каталог>
  grep -rnE "^import [a-zA-Z0-9_.]+\.(TestLayer|TestStage|System|Team|Regress|CriticalRegress|ApiTest|DbTest|MqTest|UiTest|TmsLink|Story|Issue);" --include='*.java' --include='*.kt' <каталог>
  ```
  Первая команда находит импорт со `*` - это `ошибка`. Вторая печатает все импорты этих
  аннотаций: сравни пакет каждой строки с таблицей раздела 2, п.5. Пакет совпал - не находка.
  Не совпал - `ошибка`. Исправляет `агент`.
- **П-13. Общие аннотации - над базовым классом, без дублей** (раздел 2, пп.1, 4).
  `@System`, `@Team`, `@TestStage` с одним значением стоят над каждым наследником, а над
  базовым классом нет; или та же аннотация с тем же значением и над классом, и над его
  предком. `замечание`, `агент` - только если человек согласен.
- **П-14. Настройка Allure** (раздел 6, п.5): `allure.link.tms.pattern` и
  `allure-java-commons`. `замечание`, `человек`.
- **П-15. Сценарии Cucumber** (раздел 0): есть `.feature`. `замечание`, `человек` - их
  размечают тегами `@allure.label`.

Модель (Allure TestOps или другая TMS) при проверке не известна -> `@Regress` и `@Story`
в П-2 не проверяются: в отчёт строкой `только для Allure TestOps: регресс и задача не
проверялись`.

Каждую проблему запиши в раздел «Проблемы» отчёта строкой, нумерация `MK-<n>` по порядку:
```
- [ ] MK-<n> · П-<n> · <ошибка / замечание> · <агент / человек> · <файл>:<строка> · <что не так, одна фраза> · <как исправить, одна фраза>
```
Одна строка - одно место. Одинаковая проблема больше чем в 15 местах -> первые 15 и строкой
`и ещё <n> мест: <файлы через запятую>`. Проблем нет -> `нет`.

**Исправление по отчёту** (`/orchestrator Поправь разметку по отчёту`) меняет только то, что
названо в строке `MK-<n>` с `агент`: исключение из раздела 2, п.4 - ровно эту аннотацию или
этот импорт можно поправить или убрать. Строки с `человек` агент не трогает - они остаются в
отчёте. Ключи `@TmsLink` по-прежнему не снимаются и не переносятся (раздел 6, п.1).
