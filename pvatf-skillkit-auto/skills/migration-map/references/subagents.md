# Сабагенты при построении карты (для migration-map)

Это полный список сабагентов карты - других не придумывай. Где сабагент назван, он
ОБЯЗАТЕЛЕН: эту работу ты сам не делаешь (`references/core-rules.md`, правило 7).

| Сабагент | Когда | Обязателен | Промпт или агент |
|----------|-------|------------|--------|
| **Документация** (справка по вопросам) | Этапы 1, 3, 4 - любое обращение к документации фрейма | всегда | агент `pvatf-docs`, задание - этот файл, раздел 1 |
| **Технологии проекта** | Этап 2, п.0 - какие технологии использует проект | если пользователь сам не назвал технологии | `references/inventory-subagents.md`, раздел 2 |
| **Инвентаризация модулей** | Этап 2 - подсчёты по исходникам модулей | всегда | `references/inventory-subagents.md`, раздел 1 |
| **Примеры** (исходники фрейма или проект-пример) | Этапы 3, 4 - когда документации не хватило | если пути есть в паспорте (их находит Этап 1, п.6) | агент `pvatf-examples`, задание - `references/sources-ladder.md` |
| **Составитель карточки** | Этап 5 - пишет карточку юнита `tech` (ровно один файл) | всегда | `references/card-subagents.md` |
| **Проверяющий карточки** | Этап 5 - после `card.py` | всегда | `references/card-subagents.md` |

Сам ты делаешь: паспорт, реестр подключений, матрицу, архитектурный план, таблицу юнитов,
разбор технологии и заготовку карточки (скриптами `analyze.py` и `card.py new`) и
запуск сабагентов по порядку. Карточки `tech` пишет составитель, не ты.

# 1. Сабагент документации

## Как устроена документация (важно понять)

Документация фрейма лежит в **векторной базе**. Инструмент `get_pv_at_doc` принимает
текстовый запрос и возвращает куски документации, похожие на этот запрос. В самой базе
оглавления нет; список разделов документации лежит в `references/frame-topics.md`.
Поэтому:
- один и тот же вопрос, заданный разными словами, возвращает РАЗНЫЕ куски;
- одна формулировка может ничего не дать, хотя ответ в документации есть;
- вопрос надо задавать несколькими формулировками и собирать ответ из всех кусков.

Этим занимается сабагент. Твоё дело - дать ему конкретные вопросы и записать ответ.

## Обязательное требование

Любое обращение к документации фрейма (инструмент `get_pv_at_doc`) выполняется **ТОЛЬКО
через сабагента**. Сам, в своём контексте, ты этот инструмент НЕ вызываешь - это **нарушение
протокола**. Причина: на каждый вопрос нужно несколько запросов, ответы большие, и если
читать их самому, контекст закончится раньше, чем работа. Сабагент делает запросы у себя и
возвращает тебе только короткий ответ по шаблону.

Это правило часто пытаются пропустить («быстрее сам», «один вопрос») - не пропускай.

Единственное исключение: инструмент запуска сабагентов (Task/Agent) физически отсутствует в
твоём окружении (ответ сабагента `MCP НЕДОСТУПЕН` сюда не относится: это СТОП). Только
тогда вызывай `get_pv_at_doc` сам - по инструкции из `.gigacode/agents/pvatf-docs.md` (несколько
формулировок на вопрос), сразу выписывай нужное в конспект и явно напиши в журнале
карты/карточки «сабагенты недоступны, документация прочитана напрямую». Больше исключений нет.

## Сначала конспект, потом сабагент

**Файл конспекта целиком не открываешь никогда** - ни инструментом чтения файлов, ни
`cat`, `sed`, `head`, `grep` по `doc-notes/*.md`. В нём десятки записей, тебе нужна одна.
Нельзя: прочитать `.gigacode/data/migration/doc-notes/db.md`, чтобы найти matcher ячейки.
Нужно: `notes.py find db cell value matcher` -> одна строка на запись -> `notes.py show <ID>`
только этой записи. Сабагенты (составитель, проверяющий) читают конспект сами - это их работа.

Всё, что сабагент уже достал, лежит в конспекте:
`.gigacode/data/migration/doc-notes/<технология>.md` (общее про фрейм - `doc-notes/common.md`).
Одна запись конспекта = один вопрос и ответ на него, ID вида `D-<tech>-<n>` (`D-rest-3`).

Порядок всегда один. **Сабагента документации без шага 1 не запускай никогда** - иначе он
заново изучает то, что уже изучено:
1. По КАЖДОМУ вопросу поищи в конспекте скриптом - двумя наборами слов: словами вопроса и
   словами документации (имя класса или сервиса фрейма, раздел, ключевые слова из второй
   строки конспекта). Латиницей ищется надёжнее:
   ```
   python3 .gigacode/skills/migration-map/scripts/notes.py find <tech> <слова>
   python3 .gigacode/skills/migration-map/scripts/notes.py show <D-id>
   ```
   (`notes.py list <tech>` - оглавление всего конспекта, одна строка на запись.)
   Нашлась запись со статусом `найден`, и она про то же -> бери её, сабагента НЕ запускай.
2. Ничего не нашлось, запись `найден частично` или `НЕТ В ДОКЕ` -> запусти сабагента с этим
   вопросом. В задание, в строку «Уже есть в конспекте», вставь вывод `notes.py find`: что
   уже известно и какие формулировки ничего не дали, - чтобы сабагент спросил ИНАЧЕ и не
   повторял найденное.
3. Ответ сабагента СРАЗУ переносится в конспект скриптом `notes.py merge` (порядок - раздел
   «Задание агенту `pvatf-docs`» ниже), вместе со всеми формулировками запросов. Потом работай по записи.
4. Запись со статусом `НЕТ В ДОКЕ`, у которой меньше 8 формулировок, - не приговор: запусти
   сабагента ещё раз, передав уже испробованные формулировки. 8 и больше формулировок и всё
   ещё `НЕТ В ДОКЕ` -> документация этого не знает. Не подбирай ответ сам и не лезь в jar.
   Дальше два случая:
   - молчит про технологию ЦЕЛИКОМ (нет модуля, нет раздела) -> технология получает решение
     `keep`: не мигрируется, остаётся на старой реализации. В раздел 6 ничего не пиши;
   - технология во фрейме есть, но нет ответа на отдельный вопрос (чем заменить конкретный
     шаблон, как донастроить, процесс описан не до конца) -> иди по лестнице источников
     (`references/sources-ladder.md`): исходники фрейма, проект-пример. Ответа нет и там -> место не
     мигрируется (ступень 4). В матрице `НЕТ В ДОКЕ`.

## Как формулировать вопросы

- **Конкретно и про одно.** Не «как работает Kafka», а «как отправить сообщение в топик»,
  «как прочитать сообщение из топика и проверить его», «какая зависимость нужна для модуля
  Kafka», «как настроить подключение к брокеру (адрес, сертификаты)».
- **Про действие, а не про старый класс.** Документация не знает ваших старых классов. Не
  «чем заменить KafkaHelper», а «как <то, что делает KafkaHelper>» - например «как дождаться
  сообщения в топике по ключу».
- **Про настройку - отдельным вопросом:** «как сконфигурировать ...», «какие параметры ...»,
  «в каком файле задаётся ...».
- **Дай якорь и ключевые слова.** У каждой технологии во фрейме свой сервис (`RestService`,
  `DatabaseService`, `KafkaService` ...). Имя сервиса - лучший первый запрос: по нему база
  возвращает куски, в которых видно, какими словами написана документация. В задание впиши
  «Якорь технологии» из `references/frame-topics.md`. В конспекте технологии уже есть строка
  «Ключевые слова» -> впиши её в задание, тогда якорный запрос сабагент пропустит.
- **Вопросы пиши словами документации, а не своими.** Когда в конспекте уже есть ключевые
  слова (имена классов и методов), используй их в тексте вопроса: не «как прочитать
  сообщение из очереди», а «как через `KafkaConsumerClient` прочитать запись из топика».
- **Назови раздел документации.** Перед запуском агента открой
  `references/frame-topics.md`, найди раздел своей технологии и впиши его название в строку
  задания «Раздел документации» символ в символ. Раздела нет - впиши `нет в списке`.
- Называй технологию так, как она называется в проекте, И общим словом (например: «Kafka,
  брокер сообщений»; «PostgreSQL, база данных»; «OpenShift, контейнерная платформа»).

Лимит на один запуск сабагента: не больше 5 вопросов. Больше - несколько запусков по очереди.

## Задание агенту `pvatf-docs` (подставь <...>, больше ничего не добавляй)

Как искать в документации и в каком виде отвечать, написано в самом агенте
(`.gigacode/agents/pvatf-docs.md`). Ты передаёшь только задание. Как запускать агента по
имени - `references/core-rules.md`, правило 7.

```
Технология: <метка и обычное название, напр. kafka - Kafka, брокер сообщений>
Раздел документации: <название из frame-topics.md, напр. Работа с Kafka; или: нет в списке>
Вопросы:
1. <вопрос>
2. <вопрос>
Якорь технологии: <слово-якорь из frame-topics.md, напр. KafkaService; или: нет>
Ключевые слова из прошлых ответов документации: <слова из строки «Ключевые слова» конспекта; или: нет>
Формулировки, которые уже пробовали и они НИЧЕГО не дали (не повторяй их): <список или: нет>
Уже есть в конспекте (это не ищи заново, ищи только недостающее): <вывод notes.py find по этим вопросам; или: нет>
- Записать в: <первая строка вывода notes.py task>
- Номер первой записи: <вторая строка вывода notes.py task>
```

**Ответ агент пишет в файл сам, к тебе он не приходит.** Так текст ответа не ложится в твой
контекст дважды. Порядок на каждый запуск агента:
1. До запуска: `python3 .gigacode/skills/migration-map/scripts/notes.py task <tech> migration/doc-notes`.
   Обе строки вывода впиши в конец задания дословно.
2. Запусти агента. Одновременно - не больше одного агента на технологию (у технологии один
   файл ответа); агенты разных технологий можно запускать параллельно.
3. Агент вернул строку `ЗАПИСАНО: ...` -> запусти
   `python3 .gigacode/skills/migration-map/scripts/notes.py merge <tech> migration/doc-notes <этап карты или юнит M-nnn>`
   (таймаут 60 секунд).
   - Код 0, строка `ОК: ...` - записи уже в конспекте. Под ней - по строке на запись: ID,
     статус, вопрос, «Что использовать», «Как подключить», а у записей не «найден» - «Чего
     не хватило». На Этапах 1-4 этих строк хватает: `notes.py show` и `notes.py list` после
     `merge` не запускаешь, файл ответа не читаешь.
     Нельзя: после `merge` вызвать `notes.py show D-rest-1 D-rest-2 D-rest-3 ...` или
     `for id in D-rest-3 D-rest-9; do notes.py show $id; done`, чтобы «посмотреть, что
     записалось». Нужно: взять ID, статус, «Что использовать» и «Как подключить» из строк
     вывода `merge` и вписать в карту.
     `notes.py show <ID>` - только для одной записи и только когда нужно поле «Пример»
     (Этап 5, карточка юнита).
   - Код 1 - запусти агента ещё раз с тем же заданием и строкой
     `- Прошлый файл не прошёл проверку: <строки ошибок из вывода>`, потом снова `merge`.
     Снова 1 -> строка в журнал карты «конспект <tech> не записан: <ошибки>», вопросы считай
     `НЕТ В ДОКЕ`.
4. Агент вернул блоки текстом вместо строки `ЗАПИСАНО` -> не переписывай их сам: запусти
   агента ещё раз с тем же заданием и строкой «Ответ - в файл из строки «Записать в», в ответе
   одна строка ЗАПИСАНО».
   Нельзя: скопировать блоки из ответа агента в конспект правкой файла. Нужно: `notes.py merge`.

## Как выглядит конспект

Файл `.gigacode/data/migration/doc-notes/<технология>.md` пишет только `notes.py merge`, сам
его не правишь. Первая строка файла: `# Конспект документации PVATF: <технология>`. Вторая
строка: `Ключевые слова: <слова через запятую>` - словарь документации по технологии (имена
классов, методов, настроек, заголовки); `merge` дописывает в неё новые слова из ответа
агента. Записи только дописываются в конец, номера идут по порядку.

```markdown
### D-<tech>-<n> · <вопрос>
- Статус: найден | найден частично | НЕТ В ДОКЕ
- Что использовать: <...>
- Как подключить: <...>
- Как настроить: <...>
- Пример:
- Условия и ограничения: <...>
- Чего не хватило: <...>
- Формулировки запросов: «<...>» - дала ответ; «<...>» - пусто
- Записано: <ГГГГ-ММ-ДД> · <этап карты или юнит M-nnn>
```

## Что делать с ответом

Статусы записей - в строке `ОК: ...` вывода `merge`.
- `найден` -> используй. ID записи - это и есть док-основание.
- `найден частично` -> на то, чего не хватило (поле «Чего не хватило» в строке вывода `merge`),
  задай сабагенту отдельный, более узкий вопрос.
- `НЕТ В ДОКЕ` -> действуй по п.4 раздела «Сначала конспект» (формулировки уже в записи).
- `MCP НЕДОСТУПЕН` -> СТОП, сообщи пользователю.
