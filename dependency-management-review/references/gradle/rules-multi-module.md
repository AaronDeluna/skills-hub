# Правила Gradle - мультимодульные проекты

Применяй ПОСЛЕ того, как закончишь `rules-common.md`. Процедура та же: правило за
правилом, подтверждай каждое совпадение, по строке заметок на результат. «Модуль» ниже -
проект, подключённый через `include(...)` в settings-файле.

Перед началом построй **карту модулей** и запиши её в файл заметок:
1. Выпиши все модули из `settings.gradle(.kts)`.
2. Для каждого модуля найди в его build-файле `project(":` и запиши, от каких модулей он
   зависит и через какую конфигурацию (`api` / `implementation` / `testImplementation`).

Пример записи карты: `:app -> [:core (implementation), :api (implementation)]`

---

### G-M-01 - Репозитории объявлены централизованно, а не по модулям

**Уровень:** WARNING
**Почему это важно:** списки репозиториев, скопированные в каждый модуль, расходятся
(один модуль тихо добавляет случайный репозиторий), и их невозможно аудировать. Место,
задуманное Gradle для них, - `dependencyResolutionManagement { repositories { ... } }`
в settings-файле.

**Как проверять:**
1. Есть ли в `settings.gradle(.kts)` блок `dependencyResolutionManagement` с репозиториями?
2. Объявляют ли build-файлы модулей ТАКЖЕ свои `repositories { }`?
   ```
   grep -rnE "^\s*repositories\s*\{" --include="build.gradle" --include="build.gradle.kts" .
   ```
3. Центральное объявление + нет помодульных блоков → PASS. Помодульные блоки повсюду →
   VIOLATION. Есть `repositoriesMode.set(RepositoriesMode.FAIL_ON_PROJECT_REPOS)` →
   упомяни как сильную сторону.

**Исправление для отчёта:** перенести репозитории в `dependencyResolutionManagement` в
settings; по желанию закрепить через `FAIL_ON_PROJECT_REPOS`.

### G-M-02 - Никакого расхождения версий между модулями

**Уровень:** CRITICAL
**Почему это важно:** это ГЛАВНЫЙ провал мультимодульных проектов. Модуль A использует
`jackson-databind:2.17.1`, модуль B - `2.15.0`; какая бы ни победила в рантайме, один из
модулей работает против версии, с которой никогда не компилировался. Баги всплывают только
на интеграции, и отлаживать их мучительно.

**Как проверять (делай тщательно - это самая ценная проверка файла):**
1. Извлеки все зашитые координаты из build-файлов всех модулей:
   ```
   grep -rnoE "['\"][A-Za-z0-9_.\-]+:[A-Za-z0-9_.\-]+:[0-9][^'\"]*['\"]" --include="build.gradle" --include="build.gradle.kts" .
   ```
2. Запиши список в заметки, отсортировав по `group:artifact`.
3. Любой `group:artifact`, встречающийся с двумя разными версиями, → VIOLATION
   (перечисли каждое место).
4. Сравни и с version catalog: библиотека, которая есть в каталоге, но зашита с другой
   версией в каком-то модуле, - то же самое нарушение.

**Исправление для отчёта:** единый источник истины (каталог); удалить зашитые копии.

### G-M-03 - Один общий механизм версий во всех модулях

**Уровень:** WARNING
**Почему это важно:** каталог в половине модулей, `ext`-свойства в других, зашитые строки
в остальных - обновление превращается в археологию. Какой именно механизм - менее важно,
чем то, что он ОДИН.

**Как проверять:** классифицируй каждый модуль: использует каталог (`libs.`) / использует
ext или gradle.properties (`"$springVersion"`, `property(...)`) / зашивает версии. Больше
одного стиля на проект → VIOLATION; перечисли модули по стилям.

**Исправление для отчёта:** сойтись на version catalog; мигрировать модуль за модулем.

### G-M-04 - Никакой логики зависимостей и плагинов в `allprojects` / `subprojects`

**Уровень:** WARNING
**Почему это важно:** `subprojects { dependencies { ... } }` в корне внедряет зависимости
невидимо - читая build-файл модуля, их не увидеть. Кроме того, это навязывает те же
зависимости будущим модулям, которым они могут быть не нужны. Современная замена -
convention-плагины (`buildSrc`/`build-logic`), которые модули подключают явно через
`plugins { }`.

**Как проверять:**
```
grep -rnE "^\s*(allprojects|subprojects)\s*\{" --include="build.gradle" --include="build.gradle.kts" .
```
Прочитай, что внутри каждого блока. Установка `group`/`version` или репозиториев - мягкое
замечание (INFO). Подключение плагинов или добавление зависимостей - VIOLATION.

**Исправление для отчёта:** вынести convention-плагин (например, `my-java-conventions`)
в `build-logic`/`buildSrc` и применять его в блоке `plugins { }` каждого модуля.

### G-M-05 - Никаких циклов зависимостей между модулями

**Уровень:** CRITICAL
**Почему это важно:** цикл означает, что модули на самом деле не разделены - их нельзя
собирать, тестировать и понимать независимо. Прямые циклы compile-classpath Gradle
отвергает, но циклы прячутся между конфигурациями (main ↔ test) и в транзитивных цепочках.

**Как проверять:** используй построенную карту модулей. Для каждого модуля иди по его
зависимостям вглубь; если вернулся в модуль, который уже есть на текущем пути, - этот путь
и есть цикл. Запиши полный путь в находку (например, `:core -> :api -> :core`). Проверь и
рёбра `testImplementation(project(...))` - циклы через тесты тоже дефект дизайна.

**Исправление для отчёта:** вынести общий кусок в третий модуль, от которого зависят оба,
или развернуть одну из зависимостей (интерфейсы в нижнем модуле, реализация выше).

### G-M-06 - Межмодульные зависимости через самую узкую конфигурацию

**Уровень:** WARNING
**Почему это важно:** `api(project(":core"))` реэкспортирует ВЕСЬ core каждому
потребителю, склеивая граф модулей в один ком и убивая инкрементальную компиляцию.

**Как проверять:**
```
grep -rnE "api\s*\(\s*project" --include="build.gradle" --include="build.gradle.kts" .
```
Для каждого совпадения: действительно ли публичный API этого модуля раскрывает типы того
модуля? Если непонятно - NEEDS-HUMAN, а не догадка.

**Исправление для отчёта:** понизить до `implementation(project(...))`.

### G-M-07 - Корневой build-файл тонкий

**Уровень:** WARNING
**Почему это важно:** в корневом проекте обычно нет кода, поэтому блок `dependencies { }`
с прикладными библиотеками в корне - либо мёртвый груз, либо признак того, что модули
втайне полагаются на конфигурацию корня.

**Как проверять:** открой корневой `build.gradle(.kts)`. Там должно быть примерно: блок
`plugins { }` (часто с `apply false`), group/version и почти ничего больше. Прикладные
зависимости в корне → VIOLATION.

**Исправление для отчёта:** перенести зависимости в модули, которым они нужны.

### G-M-08 - `group` и `version` заданы один раз

**Уровень:** INFO
**Почему это важно:** копипаста `group = "com.acme"` и `version = "1.2.0"` в каждый модуль
приводит к расхождению в первый же раз, когда при релизе кто-то забудет одну копию.

**Как проверять:** grep по модулям на `^group\s*=` / `^version\s*=`. Задано централизованно
(корневой build-файл, convention-плагин или `gradle.properties`) → PASS.

**Исправление для отчёта:** задать один раз в корне или convention-плагине.

### G-M-09 - Общий тестовый код едет через test fixtures или отдельный модуль

**Уровень:** INFO
**Почему это важно:** залезание в тестовые исходники другого модуля
(`testImplementation(project(":core").sourceSets.test.output)` и похожие хаки) ломает
инкапсуляцию и случайно ломается при обновлениях Gradle. Поддерживаемые механизмы -
плагин `java-test-fixtures` (`testImplementation(testFixtures(project(":core")))`) или
отдельный модуль `:testing`.

**Как проверять:**
```
grep -rnE "sourceSets\.test\.output|sourceSets\[.test.\]" --include="build.gradle" --include="build.gradle.kts" .
```

**Исправление для отчёта:** внедрить `java-test-fixtures` в модуле-поставщике.

### G-M-10 - Include-список в settings совпадает с реальностью

**Уровень:** INFO
**Почему это важно:** `include(":old-module")`, указывающий на удалённый каталог, или
существующий каталог модуля, который не подключён, - это мёртвая конфигурация или код,
молча выпавший из сборки.

**Как проверять:** сравни список `include` с каталогами, в которых есть build-файл.

**Исправление для отчёта:** убрать протухшие include; подключить или удалить осиротевшие
каталоги модулей.
