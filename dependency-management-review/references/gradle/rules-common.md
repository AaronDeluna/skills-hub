# Правила Gradle - общие (применяются к КАЖДОМУ Gradle-проекту)

Как пользоваться файлом: иди по правилам сверху вниз. Для каждого правила: выполни
«Как проверять», открой и подтверди каждый найденный кандидат, затем допиши по строке на
результат в файл заметок (`ID-ПРАВИЛА | СТАТУС | файл:строка | описание`). Статусы: PASS,
VIOLATION, N/A, NEEDS-HUMAN. Поисковые паттерны применяй ко ВСЕМ файлам инвентаря, включая
`buildSrc/` и `build-logic/`. Паттерны даны для `grep -rnE`; при другом инструменте поиска
адаптируй их.

---

### G-C-01 - Никаких динамических версий

**Уровень:** CRITICAL
**Почему это важно:** `1.+`, `+`, `latest.release` и диапазоны версий делают сборку
невоспроизводимой: один и тот же коммит в разные дни собирается по-разному, а чужой релиз
может сломать сборку или незаметно изменить поведение без единого изменения с вашей стороны.

**Как проверять:**
1. Ищи маркеры динамики в build-файлах и каталоге:
   ```
   grep -rnE "['\"][A-Za-z0-9_.\-]+:[A-Za-z0-9_.\-]+:[^'\"]*\+['\"]" --include="build.gradle" --include="build.gradle.kts" .
   grep -rnE "latest\.(release|integration)" --include="build.gradle" --include="build.gradle.kts" --include="libs.versions.toml" .
   grep -rnE "['\"]\[[0-9][^'\"]*,[^'\"]*['\"]" --include="build.gradle" --include="build.gradle.kts" .
   grep -rnE "=\s*\"[^\"]*\+\"" --include="libs.versions.toml" .
   ```
2. Подтверди, что каждое совпадение - действительно версия (`1.+`, `+`, `[1.0,2.0)`),
   а не конкатенация строк через `+` и не посторонние скобки.

**Нарушение выглядит так:** `implementation 'com.foo:bar:1.+'` ·
`testImplementation 'io.qameta.allure:allure-junit5:2.+'` · `version = "2.+"` в каталоге
**Правильно выглядит так:** `implementation 'com.foo:bar:1.4.2'`,
`testImplementation 'io.qameta.allure:allure-junit5:2.25.0'` или ссылка на каталог
**Исправление для отчёта:** зафиксировать точную версию; если команда хочет управляемые
обновления - предложить Dependabot/Renovate вместо динамических версий.

### G-C-02 - Никаких SNAPSHOT / changing-зависимостей в стабильных ветках

**Уровень:** WARNING (CRITICAL, если это релизная ветка)
**Почему это важно:** артефакт `-SNAPSHOT` перепубликуется под той же версией, поэтому
результат сборки зависит от того, *когда* она запущена. Ненадолго допустимо при совместной
разработке двух компонентов; опасно во всех остальных случаях.

**Как проверять:**
```
grep -rn "SNAPSHOT" --include="build.gradle" --include="build.gradle.kts" --include="libs.versions.toml" --include="gradle.properties" .
grep -rn "changing\s*=\s*true" --include="build.gradle" --include="build.gradle.kts" .
```
**Собственная** версия проекта `version = "1.0.0-SNAPSHOT"` - нормальная практика
версионирования в стиле Maven, это НЕ нарушение. Флажь только SNAPSHOT-версии
**зависимостей**.

**Исправление для отчёта:** заменить на зарелиженную версию; если SNAPSHOT временно
необходим - завести тикет с владельцем и пометкой TODO.

### G-C-03 - У версий единый источник истины

**Уровень:** WARNING (CRITICAL, если найдено фактическое расхождение - см. ниже)
**Почему это важно:** когда литералы версий разбросаны по build-файлам модулей, обновление
библиотеки превращается в охоту за каждой копией; пропущенные копии дают расхождение версий
и конфликты в рантайме.

**Как проверять:**
1. Есть ли центральный механизм? Ищи `gradle/libs.versions.toml`, свойства версий в
   `gradle.properties`/`ext { }` или использование platform/BOM.
2. Посчитай зашитые координаты в build-файлах модулей:
   ```
   grep -rnE "(implementation|api|compileOnly|runtimeOnly|testImplementation|testRuntimeOnly|annotationProcessor|kapt|ksp)\s*[('\"].*:[0-9]" --include="build.gradle" --include="build.gradle.kts" .
   ```
3. Несколько зашитых версий в одномодульном проекте терпимо (INFO). Зашитые версии,
   размазанные по нескольким модулям, - WARNING. Один и тот же `group:artifact` с
   **разными** версиями в разных местах - CRITICAL; в мультимодульном проекте записывай
   это под G-M-02, иначе здесь.

**Исправление для отчёта:** перенести версии в version catalog (предпочтительно) и
ссылаться из модулей через `libs.<алиас>`.

### G-C-04 - Никаких удалённых легаси-конфигураций

**Уровень:** WARNING
**Почему это важно:** `compile`, `runtime`, `testCompile`, `testRuntime` удалены в
Gradle 7. Их присутствие означает древнюю версию Gradle или мёртвый код, а `compile`
к тому же протекает ко всем потребителям, как `api`.

**Как проверять:**
```
grep -rnE "^\s*(compile|runtime|testCompile|testRuntime)\s*[('\"]" --include="build.gradle" --include="build.gradle.kts" .
```
Осторожно: паттерн НЕ должен ловить `compileOnly`, `runtimeOnly`, `compileClasspath` -
паттерн выше требует `(`, `'` или `"` сразу после слова; каждое совпадение всё равно
проверь глазами.

**Исправление для отчёта:** `compile` → `api` только если потребителям нужны типы, иначе
`implementation`; `runtime` → `runtimeOnly`; `testCompile` → `testImplementation`.

### G-C-05 - Предпочитай `implementation`, а не `api`

**Уровень:** WARNING
**Почему это важно:** см. concepts §3. Каждая лишняя `api` протекает библиотекой ко всем
потребителям, создаёт скрытую связность и замедляет инкрементальную сборку.

**Как проверять:**
1. `grep -rnE "^\s*api\s*[('\"]" --include="build.gradle" --include="build.gradle.kts" .`
2. Для каждого совпадения спроси: раскрывают ли **публичные** сигнатуры модуля
   (возвращаемые типы, параметры, наследуемые классы) типы этой библиотеки? Если быстро
   понять по публичным классам модуля нельзя - записывай NEEDS-HUMAN, а не догадку.
3. `api` в модуле, от которого никто не зависит (приложение / листовой модуль), - всегда
   нарушение: его API никто не потребляет.

**Исправление для отчёта:** заменить на `implementation`; оставлять `api` только с
поясняющим комментарием.

### G-C-06 - Каждая зависимость в правильной конфигурации

**Уровень:** WARNING
**Почему это важно:** неправильная конфигурация либо загрязняет боевой classpath, либо
приводит к падениям в рантайме.

**Как проверять:** просмотри блоки `dependencies { }` по этой таблице:

| Тип библиотеки (примеры) | Должна быть в | Нарушение, если найдена в |
|---|---|---|
| JUnit, Mockito, AssertJ, Testcontainers, WireMock | `testImplementation` / `testRuntimeOnly` | `implementation`, `api` |
| Lombok | `compileOnly` **плюс** `annotationProcessor` | `implementation` |
| Процессор MapStruct, компилятор Dagger | `annotationProcessor` / `kapt` / `ksp` | `implementation` |
| JDBC-драйверы, реализации логирования (logback, log4j-impl) | `runtimeOnly` | `implementation` терпимо (INFO), `api` - нарушение |
| Servlet/API, предоставляемые контейнером | `compileOnly` (или через platform) | `implementation`, когда рантайм и так это поставляет |

Пример поиска тестовых библиотек в боевом scope:
```
grep -rnE "^\s*(implementation|api)\s*[('\"].*(junit|mockito|assertj|testcontainers|wiremock)" --include="build.gradle" --include="build.gradle.kts" .
```

**Исправление для отчёта:** назвать правильную конфигурацию из таблицы.

### G-C-07 - Семейства библиотек выровнены через BOM/platform

**Уровень:** WARNING
**Почему это важно:** смешение версий внутри одного семейства (Jackson, Spring, Kotlin,
JUnit 5, AWS SDK, Testcontainers) даёт `NoSuchMethodError`/`NoClassDefFoundError` в
рантайме - библиотеки тестируются только против собратьев той же версии.

**Как проверять:**
1. Собери все зависимости одного семейства (общий префикс группы, например
   `com.fasterxml.jackson`).
2. Два члена семейства с разными явными версиями → VIOLATION.
3. У семейства 3+ членов, каждый с явной версией, и нигде не видно `platform(...)` /
   Spring-плагина dependency-management → VIOLATION (нет BOM).
4. BOM импортирован и члены без версий → PASS.

**Исправление для отчёта:** импортировать BOM семейства через
`implementation(platform("..."))` и убрать версии у членов.

### G-C-08 - Никаких грубых хаков разрешения конфликтов

**Уровень:** WARNING
**Почему это важно:** `force`, `resolutionStrategy.eachDependency { useVersion(...) }` и
`enforcedPlatform` перекрывают резолюцию Gradle глобально и молча. Они прячут настоящий
конфликт, ломаются при следующем обновлении и удивляют каждого, кто читает только блок
`dependencies`.

**Как проверять:**
```
grep -rnE "force[( ]|\.force\b|eachDependency|enforcedPlatform|failOnVersionConflict" --include="build.gradle" --include="build.gradle.kts" .
```
`failOnVersionConflict()` - наоборот, хорошая практика: упомяни как плюс, а не нарушение.

**Исправление для отчёта:** заменить force/eachDependency на constraint
(`dependencies { constraints { implementation("g:a:1.2.3") { because("...") } } }`)
или platform; у каждого constraint держать причину в `because(...)`.

### G-C-09 - Exclude редки и обоснованы

**Уровень:** INFO (WARNING, если exclude повсюду)
**Почему это важно:** каждый `exclude` - ручная заплатка на графе зависимостей. Несколько
общеизвестных - нормально (например, подмена реализации логирования). Десятки exclude или
один и тот же exclude, скопированный во многие модули, означают, что базовый конфликт так и
не решён - и каждый новый модуль обязан помнить ритуал.

**Как проверять:**
```
grep -rnE "exclude\s*[( ]" --include="build.gradle" --include="build.gradle.kts" .
```
Посчитай. 0-3 с очевидными причинами (commons-logging, log4j против logback, старый junit)
→ PASS. Один и тот же exclude в 3+ модулях → VIOLATION (нужно централизовать или чинить
источник).

**Исправление для отчёта:** централизовать (например, `configurations.all { exclude(...) }`
в одном convention-плагине, с комментарием) или устранить первопричину.

### G-C-10 - Никаких jar-файлов в репозитории как зависимостей

**Уровень:** WARNING
**Почему это важно:** `files("libs/x.jar")`, `fileTree("libs")`, репозитории `flatDir`
полностью обходят управление зависимостями: без версий, без транзитивных зависимостей,
без сканирования уязвимостей, без учёта лицензий.

**Как проверять:**
```
grep -rnE "files\s*\(|fileTree\s*\(|flatDir" --include="build.gradle" --include="build.gradle.kts" .
```
`files(...)` вне зависимостей (например, конфигурация задачи) - не нарушение; считаются
только вхождения внутри `dependencies { }`.

**Исправление для отчёта:** опубликовать артефакт в корпоративный Maven-репозиторий
(или Maven Central) и зависеть от нормальных координат.

### G-C-11 - Репозитории в порядке

**Уровень:** WARNING
**Почему это важно:** `mavenLocal()` ставит сборку в зависимость от содержимого локального
кэша разработчика - источник №1 проблемы «у меня работает». `jcenter()` мёртв (только
чтение с 2021 года, может исчезнуть). Случайные сторонние репозитории - supply-chain-риск.

**Как проверять:**
```
grep -rnE "mavenLocal\s*\(|jcenter\s*\(" --include="build.gradle" --include="build.gradle.kts" --include="settings.gradle" --include="settings.gradle.kts" .
grep -rnE "maven\s*[({]" --include="build.gradle" --include="build.gradle.kts" --include="settings.gradle" --include="settings.gradle.kts" .
```
Для каждого кастомного `maven { url = ... }`: это известный корпоративный или известный
публичный репозиторий (Google, Spring, JitPack)? Неизвестные URL → NEEDS-HUMAN.

**Исправление для отчёта:** убрать `mavenLocal()` (или спрятать за флагом локальной
разработки), заменить `jcenter()` на `mavenCentral()`, завести всё через корпоративный
прокси, если он есть.

### G-C-12 - Никаких дублей объявления одного артефакта

**Уровень:** INFO
**Почему это важно:** один и тот же `group:artifact`, объявленный дважды в одном модуле
(или напрямую и через bundle), путает читателя и провоцирует расхождение, когда обновят
только одну копию.

**Как проверять:** для блока `dependencies { }` каждого модуля выпиши координаты и найди
повторы (при сравнении игнорируй часть с версией).

**Исправление для отчёта:** оставить одно объявление.

---

### G-C-13 - Никаких дублирующих друг друга библиотек

**Уровень:** INFO (WARNING, если обе активно используются)
**Почему это важно:** две JSON-библиотеки (Gson + Jackson), два HTTP-клиента (OkHttp +
Apache HttpClient + RestTemplate), два мок-фреймворка - каждая пара удваивает поверхность
API, стоимость обновлений и путает новичков насчёт «благословлённого способа».

**Как проверять:** просмотри собранный список зависимостей на известные дублирующие пары:
JSON (jackson/gson/moshi), HTTP (okhttp/apache httpclient/retrofit - retrofit+okhttp это
один стек, это нормально), фасады логирования (slf4j - фасад; а вот несколько
**реализаций** вместе, logback+log4j-core, - реальная проблема), коллекции
(guava + commons-collections), DI (spring + guice + dagger вместе).

**Исправление для отчёта:** рекомендовать по одной библиотеке на категорию и запланировать
миграцию; как минимум задокументировать, какая из них каноническая.
