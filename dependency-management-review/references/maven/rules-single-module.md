# Правила Maven - одномодульные проекты (монолиты)

Применяй ПОСЛЕ того, как закончишь `rules-common.md`. В монолите основную работу делают
общие правила; этот файл добавляет специфичные для монолита проверки. Процедура та же:
правило за правилом, подтверждай каждое совпадение, по строке заметок на результат.

---

### M-S-01 - Версии живут в `<properties>` (или dependencyManagement), не инлайном

**Уровень:** WARNING
**Почему это важно:** даже в одном POM инлайновые литералы `<version>` прячут расхождения
внутри семейств (три артефакта Jackson - три места для обновления) и делают
PR с обновлениями шумными и рискованными. Это ужесточение M-C-01 для случая одного POM:
когда файл один, оправданий нет вовсе.

**Как проверять:** переиспользуй находки M-C-01. В одномодульном проекте ЛЮБОЙ литерал
версии в обычных `<dependencies>` - нарушение: секция properties находится в том же файле.

**Исправление для отчёта:** одно свойство на семейство библиотек (`<jackson.version>`),
ссылки через `${...}`; либо блок `dependencyManagement` с импортами BOM.

### M-S-02 - BOM-импорты используются и без модулей

**Уровень:** INFO
**Почему это важно:** команды часто думают, что dependencyManagement - «это про
мультимодуль». Нет: импорт BOM Spring Boot / Jackson / JUnit в единственный POM убирает
десяток свойств версий и бесплатно гарантирует выравнивание семейств.

**Как проверять:** даёт ли POM (или его родитель, например `spring-boot-starter-parent`)
версии через BOM? Если зависимости известного семейства несут явные версии, а BOM не
импортирован → VIOLATION (уровень INFO; повысь до WARNING, если под M-C-06 нашлось
реальное расхождение в семействе - тогда сошлись на ту находку, не дублируй её).

**Исправление для отчёта:** добавить BOM семейства в `dependencyManagement` с
`<type>pom</type><scope>import</scope>`, убрать версии членов.

### M-S-03 - Список зависимостей организован, scope-ы затянуты

**Уровень:** INFO
**Почему это важно:** один POM легко перерастает 100 зависимостей; без сортировки он
становится write-only. Группировка (compile-зависимости по назначению, затем runtime,
provided, test) плюс правильные scope-ы сохраняют список пригодным для ревью и держат
боевой classpath минимальным.

**Как проверять:** прочитай секцию `<dependencies>` как человек: собраны ли тестовые
зависимости вместе в конце? Есть ли комментарии-разделители или очевидный порядок?
Помечены ли runtime-only вещи (драйверы, агенты) как `runtime`? Суди мягко - правило о
читабельности.

**Исправление для отчёта:** предложить конвенцию порядка и однострочные комментарии
групп.

### M-S-04 - Следи за раздуванием и неиспользуемыми зависимостями

**Уровень:** INFO (WARNING, когда найдены явно заброшенные зависимости)
**Почему это важно:** монолиты копят мёртвые зависимости; каждая продолжает стоить:
CVE-разборы, работа при обновлениях, ревью лицензий.

**Как проверять:**
1. Если запускать Maven разрешено: `mvn -q dependency:analyze` - авторитетный ответ;
   читай `Unused declared dependencies`.
2. Иначе статическая выборочная проверка: возьми 5-10 самых необычных/тяжёлых зависимостей
   и поищи в исходниках характерные импорты их пакетов:
   ```
   grep -rn "import com.google.common" --include="*.java" src/ | head -3
   ```
   Импортов нет → кандидат (NEEDS-HUMAN - может использоваться через рефлексию, SPI,
   автоконфигурацию Spring или быть runtime-only артефактом, где отсутствие импортов
   ожидаемо).
3. Больше ~80 прямых зависимостей в одном POM → отметь как сигнал здоровья монолита:
   внутри прячется граница модуляризации.

**Исправление для отчёта:** перечислить кандидатов; предложить подключить
`dependency:analyze` (с настроенным `ignoreNonCompile`) в CI.
