# Правила Maven - общие (применяются к КАЖДОМУ Maven-проекту)

Как пользоваться файлом: иди по правилам сверху вниз. Для каждого правила: выполни
«Как проверять», открой и подтверди каждый найденный кандидат, затем допиши по строке на
результат в файл заметок (`ID-ПРАВИЛА | СТАТУС | файл:строка | описание`). Статусы: PASS,
VIOLATION, N/A, NEEDS-HUMAN. Поиски применяй ко ВСЕМ `pom.xml` из инвентаря. Паттерны даны
для `grep -rnE`; при другом инструменте адаптируй. XML растягивается на несколько строк -
когда паттерн сработал, всегда читай весь окружающий элемент `<dependency>` перед выводом.

### M-C-01 - Никаких литералов версий внутри `<dependencies>`

**Уровень:** WARNING (CRITICAL в мультимодульных проектах - см. M-M-02)
**Почему это важно:** версии должны жить в `<properties>` или `<dependencyManagement>`.
Литеральный `<version>` внутри записи `<dependencies>` невидим для централизованных
обновлений - именно так одна библиотека оказывается в проекте в трёх версиях.

**Как проверять:**
1. В каждом POM смотри `<dependencies>` (НЕ те, что внутри `<dependencyManagement>` -
   литералы там допустимы, это и ЕСТЬ центральное место).
2. Кандидаты: `grep -n "<version>" pom.xml` - затем классифицируй каждое совпадение по
   объемлющему блоку.
3. `<version>${something.version}</version>` (ссылка на свойство) → нормально.
   Литерал `<version>2.17.1</version>` в обычных `<dependencies>` → VIOLATION.

**Исправление для отчёта:** перенести версию в свойство или в dependencyManagement и
ссылаться на неё, либо убрать тег совсем, если версию уже менеджит родитель/BOM.

### M-C-02 - Никаких диапазонов версий, LATEST и RELEASE

**Уровень:** CRITICAL
**Почему это важно:** `[1.0,2.0)`, `LATEST`, `RELEASE` делают сборку невоспроизводимой -
один и тот же коммит со временем резолвится по-разному. `LATEST`/`RELEASE` к тому же
deprecated начиная с Maven 3.

**Как проверять:**
```
grep -rnE "<version>\s*(\[|\()" --include="pom.xml" .
grep -rnE "<version>\s*(LATEST|RELEASE)\s*</version>" --include="pom.xml" .
```

**Исправление для отчёта:** зафиксировать точные версии; управляемые обновления - через
Renovate/Dependabot.

### M-C-03 - Никаких SNAPSHOT-зависимостей в стабильных ветках

**Уровень:** WARNING (CRITICAL на релизной ветке)
**Почему это важно:** SNAPSHOT-артефакты перепубликуются под той же версией; результат
сборки зависит от момента запуска. **Собственная** версия проекта
`<version>x.y.z-SNAPSHOT</version>` - нормальная практика разработки; находками считаются
только SNAPSHOT-версии **зависимостей**.

**Как проверять:**
```
grep -rn "SNAPSHOT" --include="pom.xml" .
```
Классифицируй каждое совпадение: собственная версия / версия родителя (свой родитель в том
же репозитории - нормально; внешний родитель SNAPSHOT - нарушение) / версия зависимости
(нарушение) / свойство, используемое зависимостью (нарушение).

**Исправление для отчёта:** заменить на зарелиженные версии; временные исключения - под
тикет.

### M-C-04 - У каждой зависимости правильный scope

**Уровень:** WARNING
**Почему это важно:** неправильный scope либо протаскивает тестовые библиотеки в прод,
либо роняет рантайм, когда `provided`-библиотеку на самом деле никто не поставляет.

**Как проверять:** сверяй записи `<dependencies>` с таблицей:

Важно: это примеры, а не закрытый список. Общий принцип - смотри, ОТКУДА библиотеку
использует код (`src/main` → `compile`; только `src/test` → `test`), и учитывай назначение
проекта (Шаг 2 SKILL.md). В **проекте автотестов** тестовые библиотеки - это «боевые»
зависимости: если степы/клиенты лежат в `src/main`, junit/selenide в `compile` - НЕ
нарушение (PASS с пояснением). В обычном приложении та же строка - нарушение.

| Тип библиотеки (узнаётся по artifactId) | Правильный scope | Нарушение |
|---|---|---|
| junit, mockito, assertj, testng, hamcrest (в приложении) | `test` | отсутствие scope (= compile) в приложении |
| selenide, selenium, rest-assured, cucumber, wiremock, testcontainers (в приложении) | `test` | compile в приложении |
| aspectjweaver (агент Allure) | `runtime`/`test` как javaagent | обычный compile - агент так не подключить |
| lombok | `provided` (или annotationProcessorPaths в compiler-плагине) | scope compile |
| jakarta.servlet-api, tomcat-embed (когда рантайм это поставляет) | `provided` | compile |
| JDBC-драйверы (postgresql, mysql-connector), logback-classic | `runtime` | compile терпимо (INFO); утечка дальше через POM библиотеки - WARNING |
| Всё с `<systemPath>` | - | всегда CRITICAL, см. M-C-05 |

Пример поиска тестовых библиотек без test scope: найди каждый такой `<dependency>` и
проверь, что в нём есть `<scope>test</scope>`:
```
grep -rnE -A3 "artifactId>(junit|junit-jupiter|mockito-core|assertj-core|testcontainers|wiremock)" --include="pom.xml" .
```

**Исправление для отчёта:** назвать правильный scope из таблицы.

### M-C-05 - Никакого `system` scope

**Уровень:** CRITICAL
**Почему это важно:** scope `system` + `<systemPath>` указывает на jar по фиксированному
пути на диске: ломается на любой другой машине, нет транзитивных зависимостей, deprecated
самим Maven.

**Как проверять:**
```
grep -rnE "<scope>\s*system\s*</scope>|systemPath" --include="pom.xml" .
```

**Исправление для отчёта:** установить артефакт в корпоративный репозиторий и
использовать нормальные координаты.

### M-C-06 - Семейства библиотек выровнены через BOM

**Уровень:** WARNING
**Почему это важно:** Jackson, Spring, JUnit 5, AWS SDK, Testcontainers тестируются только
против собратьев той же версии. Смешанные версии внутри семейства дают в рантайме
`NoSuchMethodError`/`NoClassDefFoundError`, которые юнит-тесты почти не ловят.

**Как проверять:**
1. Сгруппируй все зависимости по семействам (общий префикс groupId:
   `com.fasterxml.jackson`, `org.springframework`, `org.junit`,
   `software.amazon.awssdk`, `org.testcontainers`).
2. Два члена с разными итоговыми версиями (литералы или разные свойства) → VIOLATION.
3. 3+ членов с индивидуальными версиями и без BOM-импорта (`import`) в
   dependencyManagement → VIOLATION.
4. BOM импортирован, члены без версий → PASS; отметь как сильную сторону.

**Исправление для отчёта:** импортировать BOM семейства
(`<type>pom</type><scope>import</scope>` в dependencyManagement), удалить версии членов.

### M-C-07 - Exclusion-ы редки и обоснованы

**Уровень:** INFO (WARNING, если их много повсюду)
**Почему это важно:** каждый блок `<exclusions>` - ручная заплатка на графе. Несколько
канонических (commons-logging, старый транзитивный junit) - нормально; один и тот же
exclusion, скопированный по многим POM, или 10+ exclusion-ов всего - нерешённый корневой
конфликт.

**Как проверять:**
```
grep -rn "<exclusions>" --include="pom.xml" . | wc -l
grep -rn -A4 "<exclusions>" --include="pom.xml" .
```
Посчитай и классифицируй. Одинаковые exclusion-ы в 3+ POM → VIOLATION (централизовать или
чинить источник).

**Исправление для отчёта:** перенести exclusion к управляемой версии в родительский
dependencyManagement (одно место) либо обновить/заменить конфликтующую зависимость.

### M-C-08 - Не полагаться на необъявленные транзитивные; не держать мёртвые объявленные

**Уровень:** WARNING (used-undeclared) / INFO (unused-declared)
**Почему это важно:** код, импортирующий классы библиотеки, которая попала в classpath
только транзитивно, ломается в момент, когда посредник обновится или выбросит её. Мёртвые
объявленные зависимости бесплатно тратят обновления, CVE-разборы и ревью лицензий.

**Как проверять:**
1. Если запускать Maven разрешено: `mvn -q dependency:analyze` - читай секции
   `Used undeclared` / `Unused declared`. Это авторитетная проверка.
2. Если нельзя - статическая выборочная проверка: возьми 5 заметных импортов из исходников
   (`grep -rn "^import " src/main/java | awk '{print $2}' | sort -u | head -30`), сопоставь
   каждый пакет с библиотекой и проверь, что она объявлена в POM этого модуля. Всё
   подозрительное → NEEDS-HUMAN.

**Исправление для отчёта:** объявить то, что код реально импортирует; удалить то, что
никто не импортирует (после проверки рефлексии/SPI).

### M-C-09 - Enforcer-плагин охраняет сходимость версий

**Уровень:** INFO, если просто отсутствует; WARNING, если при этом другие правила нашли
реальные конфликты
**Почему это важно:** медиация Maven по nearest-wins молча даунгрейдит версии
(concepts §6). Стандартная защита - maven-enforcer-plugin с `<dependencyConvergence/>`
или `<requireUpperBoundDeps/>`; `<banDuplicatePomDependencyVersions/>` ловит
копипаст-дубли.

**Как проверять:**
```
grep -rn "maven-enforcer-plugin" --include="pom.xml" .
```
Если есть - прочитай, какие правила настроены. Enforcer с правилами
convergence/upper-bound → PASS, отметь как сильную сторону.

**Исправление для отчёта:** добавить enforcer в родителя с `<requireUpperBoundDeps/>`
(мягче, хорошее начало) или `<dependencyConvergence/>` (строго).

### M-C-10 - Никаких дублей объявления зависимостей

**Уровень:** WARNING
**Почему это важно:** один и тот же groupId:artifactId, объявленный в POM дважды, - Maven
молча берёт один (только предупреждение), а читатель верит другому. Классические следы
merge-конфликта.

**Как проверять:** для каждого POM выпиши пары `groupId:artifactId` из `<dependencies>` и
найди повторы:
```
grep -rn -B1 "<artifactId>" pom.xml
```
(Либо механически извлеки пары и прогони sort/uniq.)

**Исправление для отчёта:** оставить одно объявление - то, у которого правильный scope.

### M-C-11 - Никаких `<repositories>` в POM (или хотя бы обоснованно)

**Уровень:** WARNING
**Почему это важно:** репозитории в POM протекают к каждому потребителю артефакта, обходят
корпоративный mirror и являются supply-chain-риском. Правильное место - `settings.xml` /
менеджер репозиториев (Nexus/Artifactory). Бывают исключения (публичная библиотека со
специализированным репозиторием), так что суди по контексту.

**Как проверять:**
```
grep -rnE "<repositories>|<pluginRepositories>" --include="pom.xml" .
```
Для каждого: известный корпоративный/публичный репозиторий → INFO с пометкой; неизвестный
URL → NEEDS-HUMAN.

**Исправление для отчёта:** перенести в settings.xml / конфигурацию mirror в менеджере
репозиториев.

---

### M-C-12 - Никаких дублирующих друг друга библиотек

**Уровень:** INFO (WARNING, если обе активно используются)
**Почему это важно:** две JSON-библиотеки (Jackson + Gson), несколько HTTP-клиентов, два
мок-фреймворка - двойная поверхность API, двойная цена обновлений и никакого
«благословлённого способа» для команды.

**Как проверять:** просмотри полный список зависимостей на известные дублирующие пары:
JSON (jackson/gson/moshi), HTTP (okhttp/apache-httpclient/смеси эпохи resttemplate),
коллекции (guava + commons-collections4), **реализации** логирования (logback-classic +
log4j-core вместе - CRITICAL, они дерутся за slf4j-байндинг), смешанные DI-контейнеры.

**Исправление для отчёта:** выбрать по одной на категорию, запланировать миграцию или
задокументировать каноническую.
