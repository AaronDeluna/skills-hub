# Разбор дерева зависимостей сабагентами (для мультимодуля)

Этот файл нужен только на шаге «Дерево зависимостей» (Шаг 5 SKILL.md) и только для
**мультимодульных** проектов. Идея: вывод `dependency:tree` по модулю бывает огромным, и
если читать его самому по всем модулям - контекст переполняется, и ты теряешь важные
детали. Поэтому разбор дерева ты отдаёшь сабагентам, а сам собираешь только их короткие
структурированные ответы. Большой вывод дерева к тебе не попадает.

## Обязательное требование

Для мультимодульного проекта разбор дерева выполняется **ТОЛЬКО через сабагентов**. Делать
его самому, инлайном, в своём контексте - **нарушение протокола**. Это правило часто
пытаются пропустить («быстрее сам», «модулей мало», «и так понятно») - не пропускай.

Единственное исключение: инструмент запуска сабагентов (Task/Agent) физически отсутствует
в твоём окружении. Только тогда разбирай сам, последовательно, и явно напиши в отчёте
(«Требует внимания человека»), что сабагенты были недоступны. Больше исключений нет.

## Сколько сабагентов создавать

Не по сабагенту на модуль (их может быть много), а от 1 до 4 сабагентов, между которыми ты
распределяешь модули пакетами:

```
число сабагентов = min(4, число модулей)
```

Раздели модули между сабагентами как можно ровнее (каждому - свой список модулей, без
пересечений, чтобы вместе они покрыли ВСЕ модули). Ориентир:

| Модулей | Сабагентов | Как раздать (модулей на сабагента) |
|---|---|---|
| 1 | 1 | 1 |
| 2 | 2 | 1, 1 |
| 3 | 3 | 1, 1, 1 |
| 4 | 4 | 1, 1, 1, 1 |
| 5 | 4 | 2, 1, 1, 1 |
| 6 | 4 | 2, 2, 1, 1 |
| 7 | 4 | 2, 2, 2, 1 |
| 8 | 4 | 2, 2, 2, 2 |
| 9+ | 4 | распределяй ровно: примерно ceil(модулей / 4) на каждого |

## Как запускать

1. Возьми список модулей из блока «Картина проекта» (карта модулей).
2. Посчитай число сабагентов по формуле выше и разбей модули на столько же
   непересекающихся пакетов.
3. Запусти сабагентов - по возможности параллельно, в одном заходе. Каждому передай промпт
   ниже дословно, подставив путь проекта, систему сборки и **его пакет модулей** (список).
   Ничего лишнего в промпт не добавляй - он узкий специально.
4. Дождись всех ответов. Каждый сабагент возвращает по одному блоку-шаблону на КАЖДЫЙ модуль
   своего пакета. Сложи все блоки в заметки, в блок «Дерево: результаты по модулям».
5. **Ворота (gate):** прежде чем идти дальше, проверь, что суммарно получен блок-результат
   на КАЖДЫЙ модуль из карты (модулей 6 - должно быть 6 блоков). Не хватает - дозапусти
   сабагента на недостающие.
6. Переведи находки в строки правил (обычно G-C-07 / M-C-06 - выравнивание семейств, или
   конфликт версий) с пометкой «транзитивно, из dependency-дерева, модуль <имя>».

## Жёсткий промпт для сабагента (копируй дословно, подставь значения в <...>)

```
Ты анализируешь дерево зависимостей для СПИСКА модулей одного проекта. Действуй строго по
шагам и не делай ничего сверх этого. Не меняй файлы. Верни ТОЛЬКО заполненные шаблоны
(по одному на каждый модуль из списка), без рассуждений и без пересказа всего дерева.

Проект: <абсолютный путь к корню проекта>
Система сборки: <Maven | Gradle>
Модули для разбора (обработай КАЖДЫЙ): <список, напр. web, core-api>

Для КАЖДОГО модуля из списка выполни:

Шаг 1. Построй дерево зависимостей ровно этого модуля:
  - Maven:  mvn -q -pl <модуль> dependency:tree -Dverbose
  - Gradle: ./gradlew :<модуль>:dependencies --configuration runtimeClasspath
  Если команда падает (нет сборщика, нет сети, запуск запрещён) - не выдумывай дерево:
  в шаблоне этого модуля поставь «Статус запуска: НЕ УДАЛОСЬ» и причину, поля оставь пустыми.

Шаг 2. Найди в выводе три вещи:
  (а) КОНФЛИКТЫ ВЕРСИЙ - один и тот же group:artifact в разных ветках дерева с разными
      версиями. В Maven на них указывают пометки «(version omitted for conflict with ...)» /
      «(version managed from ...)»; в Gradle - стрелка «X -> Y» (версия подменена).
  (б) РАЗЪЕХАВШИЕСЯ СЕМЕЙСТВА - члены одного семейства (общий префикс группы: jackson-*,
      spring-*, org.junit*, selenium-*, allure-*, testcontainers-*) с разными версиями.
  (в) ПОДОЗРИТЕЛЬНЫЕ ПОДМЕНЫ - запрошена одна версия, а разрезолвилась заметно другая
      (особенно даунгрейд), что может ломать совместимость.

Шаг 3. Верни на этот модуль РОВНО такой шаблон (заголовки полей сохрани, коротко, дефис
вместо тире):

### Модуль: <имя>
- Команда: <точная команда, которую ты выполнил>
- Статус запуска: OK | НЕ УДАЛОСЬ (<причина>)
- Конфликты версий:
  - <group:artifact>: <верс1> vs <верс2>, победила <верс>; ветки: <кто тянет каждую>
  - (если нет - напиши: нет)
- Разъехавшиеся семейства:
  - <семейство>: <член1 верс1>, <член2 верс2>
  - (если нет - напиши: нет)
- Подозрительные подмены версий:
  - <group:artifact>: запрошена <x>, разрезолвлена <y>
  - (если нет - напиши: нет)
- Итог: OK (находок нет) | ЕСТЬ НАХОДКИ (<число>)

Повтори шаги 1-3 для каждого модуля из списка и верни все шаблоны подряд.
```

## Что делать с результатами

- Каждую строку «Конфликты версий» / «Разъехавшиеся семейства» / «Подозрительные подмены»
  переведи в находку правила (G-C-07 или M-C-06, при явном конфликте версий - под правилом
  про расхождение) с уровнем по обычной логике и пометкой «транзитивно, из
  dependency-дерева, модуль <имя>».
- Если у какого-то модуля «Статус запуска: НЕ УДАЛОСЬ» - вынеси это в отчёт, раздел
  «Требует внимания человека», с точной командой, чтобы человек прогнал вручную.
- После сбора всех модулей всё равно сделай **полный** прогон по проекту
  (`mvn -q dependency:tree -Dverbose` / `./gradlew dependencies`) - сам или отдельным
  сабагентом - он ловит конфликты, возникающие только при сборке всего реактора вместе.
