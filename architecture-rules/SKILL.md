# Майнер архитектурных правил (иерархия, слои, исключения) -> custom-rules.md

Задача: понять, как устроен проект на самом деле (единая архитектура модулей, слои,
направление зависимостей), где из этой иерархии есть **исключения** и по какому признаку
одно исключение отличается от другого, и превратить это в набор **правил по шаблону**. Эти
правила дописываются в `custom-rules.md` скилла `pvatf-code-review`, чтобы ревью потом
проверяло проект по его собственным соглашениям.

Ты не выдумываешь «идеальную» архитектуру - ты **вычленяешь ту, что уже есть** (по
повторяемости), и аккуратно фиксируешь её вместе с законными исключениями.

## Работай по плану, шаг за шагом

Это длинная задача, слабая модель легко теряет нить. Поэтому:
1. В начале составь план из шагов ниже (Шаг 1 ... Шаг 6). Есть todo - занеси туда; нет -
   выпиши первым блоком в файл заметок как чек-лист `[ ]`.
2. Иди строго по порядку, по одному шагу. Отмечай выполненное.
3. Сбился - вернись к чек-листу (см. «Если потерял нить» в конце).

## Базовые правила

1. **Ничего в проекте не меняй.** Ты только читаешь исходники. Пишешь свой файл заметок и,
   в самом конце и только с согласия пользователя, дописываешь `custom-rules.md` ревьюера.
2. **Правило = наблюдение, подтверждённое повторяемостью.** Не заноси в правила единичный
   случай. Норма - это то, что соблюдается в большинстве модулей/классов; исключение - то,
   что осознанно и повторяемо отступает от нормы (а не случайная ошибка).
3. **Отличай исключение от нарушения.** Если отступление повторяется и у него есть явный
   триггер (тип класса, слой, аннотация, вид операции) - это узаконенное исключение,
   фиксируй его. Если отступление единичное и бессистемное - это, скорее, баг; в правила не
   заноси, в отчёте отметь как «возможное нарушение, не правило».
4. **Пиши на русском, короткий дефис `-`, не длинное тире.** ID правил (`CR-1`) - латиницей.
5. Не уверен - помечай `НЕЧЁТКО` и выноси вопрос пользователю, не выдавай догадку за правило.

## Шаг 1 - Определи корень, модули и роли

- Возьми путь проекта (если не дан - корень текущего проекта: `pom.xml`/`settings.gradle`/`.git`).
- Система сборки: Maven (`pom.xml`) или Gradle (`settings.gradle(.kts)`).
- Перечисли модули (Maven `<modules>`, Gradle `include`). Для монолита «модуль» один.
- Для каждого модуля определи **роль** по имени и содержимому (это гипотеза, уточнишь ниже):
  `*-api`/`*-spi` (контракты), `*-core`/`*-domain`/`*-model` (доменное ядро),
  `*-service`/`*-application` (логика), `*-web`/`*-rest`/`*-controller` (край/вход),
  `*-persistence`/`*-repository`/`*-dao` (хранилище), `*-common`/`*-util` (база),
  `*-config`/`*-starter` (сборка/конфиг), `*-client`/`*-integration` (внешние системы).

Запиши «Контекст» и список модулей с ролями в заметки. Подробности анализа - в
`references/analysis-guide.md` (прочитай его перед Шагом 2).

## Шаг 2 - Выведи единую архитектуру (иерархию и слои)

Цель - сформулировать, какой архитектуре следует КАЖДЫЙ модуль, и как модули соотносятся.
1. **Скелет модуля.** Открой 3-5 модулей и сравни структуру пакетов. Найди общий повторяемый
   скелет (например, у каждого модуля есть пакеты `api` / `domain` / `application` /
   `infrastructure`, или слои `controller` / `service` / `repository`). Это и есть «единая
   архитектура».
2. **Слои и направление зависимостей.** Определи, какие слои есть и куда разрешено смотреть
   (обычно край -> логика -> домен; хранилище -> домен; `common` доступен всем; `api`
   потребляют другие). Построй направление по реальным импортам/зависимостям модулей.
3. **Правила видимости.** Что публичное (`api`), что внутреннее (`impl`/`internal`), кто
   кого может импортировать.

Запиши выведенную архитектуру в заметки как основу для правил.

## Шаг 3 - Найди исключения и условия их применения

Это ядро задачи. Пройди по коду и найди места, где модуль/класс отступает от единой
архитектуры, и разберись, **законно это или нет и когда именно так можно**:
- отступления от слоёв (например, контроллер напрямую в репозиторий, минуя сервис);
- «обратные» зависимости (домен импортирует веб-тип);
- прямые обращения между модулями в обход `api`;
- разные способы делать одно и то же (например, чтение и запись организованы по-разному).

Для каждого повторяющегося отступления сформулируй **условие-триггер**: по какому признаку
понятно, что здесь применяется именно это исключение, а не общее правило, и чем оно
отличается от соседнего исключения. Пример формулировки: «read-only запросы допускается
выполнять напрямую через `*QueryService` в обход доменного сервиса; запись (команды) обязана
идти через доменный сервис - различие по типу операции (чтение/запись) и по суффиксу класса».

Единичные бессистемные отступления держи отдельно как «возможные нарушения», не как правила.

## Шаг 4 - Оформи правила по шаблону

Каждое выведенное правило запиши в заметки строго по шаблону (нумеруй `CR-1`, `CR-2`, …):

```markdown
### CR-1 · <короткое название правила понятным языком>
- **Область:** <какие модули / пакеты / слои это касается>
- **Правило:** <что должно соблюдаться - одна-две ясные фразы>
- **Почему:** <какая архитектурная идея за этим стоит>
- **Исключения:** <когда правило НЕ применяется и какое поведение вместо него; если
  исключений несколько - по какому признаку отличать одно от другого (триггер: тип операции,
  слой, суффикс класса, аннотация). Если исключений нет - «нет».>
- **Проверяемо тестом:** да/нет (архитектурные правила часто проверяются по импортам/структуре,
  а не юнит-тестом - тогда «нет, проверяется статически»)
- **Как ловить на ревью:** <конкретный признак: направление импорта, имя пакета, суффикс класса>
- **Источник:** выведено анализом архитектуры <ГГГГ-ММ-ДД>; примеры: <файл(ы)>
```

Держи правила краткими и проверяемыми. Не плоди дубли и не заноси общеизвестные банальности -
только то, что специфично для ЭТОГО проекта.

## Шаг 5 - Покажи и спроси разрешение (интерактивно)

Правила станут авторитетными для ревью, поэтому не пиши их молча.
1. Покажи пользователю короткую сводку выведенных правил (по одному заголовку `CR-n` +
   суть в одну строку) и отдельно список «возможных нарушений», которые ты НЕ заносишь.
2. Задай **интерактивный вопрос да/нет** (используй доступный инструмент вопроса; нет такого -
   обычным сообщением, дождись ответа): «Дописать эти N правил в custom-rules.md ревьюера?».
3. **Нет** -> не трогай `custom-rules.md`; сохрани черновик правил в файл рядом (в
   `project-data/architecture-rules-draft.md` в корне проекта) и покажи путь. Заверши.
4. **Да** -> переходи к Шагу 6.

## Шаг 6 - Допиши в custom-rules.md ревьюера (обогащение, без затирания)

Цель-файл: `custom-rules.md` скилла `pvatf-code-review`
(`.../pvatf-code-review/references/custom-rules.md`). Найди его: он лежит рядом с этим
скиллом в общем каталоге скиллов; если не нашёл - спроси у пользователя точный путь.

Правила именно **дописываются** (обогащение), старое не затирается:
1. Прочитай текущий `custom-rules.md`. Найди уже существующие `### CR-<n>` и продолжи
   нумерацию с максимального+1 (не переписывай существующие ID).
2. Если раздела для правил ещё нет - добавь в конец файла заголовок `## Правила (CR)` и
   пиши правила под ним. Пример-комментарий и пояснения в начале файла не трогай.
3. Не дублируй правило, которое по смыслу уже есть - вместо нового ID дополни существующее
   или пропусти (отметь в сводке, что пропустил как дубль).
4. После записи покажи пользователю: сколько правил добавил, какие ID, и путь к файлу.

## Если потерял нить (восстановление контекста)

Если забыл, где ты: (1) перечитай этот SKILL.md, (2) перечитай свой файл заметок,
(3) найди первый невыполненный пункт чек-листа и продолжи с него. Файл заметок - источник
истины о прогрессе.
