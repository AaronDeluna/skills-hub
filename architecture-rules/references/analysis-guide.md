# Гайд анализа архитектуры (как выводить иерархию, слои и исключения)

Прочитай перед Шагом 2. Здесь - как из реального кода вычленить единую архитектуру и её
законные исключения. Всё строится на **повторяемости**: норма - то, что соблюдается почти
везде; исключение - осознанное повторяемое отступление; нарушение - единичное отступление.

## 1. Роли модулей (уточни гипотезы из Шага 1)

Смотри не только на имя, но и на содержимое: какие пакеты, какие зависимости, есть ли
публичный контракт. Типичные роли и признаки:
- **api / spi / contract** - только интерфейсы, DTO, исключения; почти нет логики; на него
  зависят другие модули.
- **domain / model / core** - доменные сущности и правила; НЕ зависит от web/persistence.
- **service / application / usecase** - оркестрация логики; зависит от домена и портов.
- **web / rest / controller / api-app** - вход (HTTP, очередь); зависит от service.
- **persistence / repository / dao / adapter** - хранилище/адаптеры; реализует порты.
- **common / util / shared** - утилиты; на него можно всем, он - почти ни на кого.
- **config / starter / bootstrap** - сборка приложения, конфигурация.
- **client / integration** - выход к внешним системам.

## 2. Единая архитектура: общий скелет модуля

Открой 3-5 разных модулей и выпиши структуру пакетов каждого. Ищи **повторяющийся скелет**:
- Пример слоёной: `controller` -> `service` -> `repository` (+ `model`).
- Пример гексагональной/чистой: `api`(порт), `domain`, `application`, `infrastructure`(адаптер).
- Пример feature-модулей: каждый модуль = фича со своим `web`/`service`/`repo` внутри.

Если 4 из 5 модулей повторяют один скелет - это и есть «единая архитектура». Модуль, который
его не повторяет, - кандидат в исключение (или в нарушение). Запиши скелет явно, по пакетам.

## 3. Слои и направление зависимостей

Определи разрешённое направление «кто на кого смотрит». Обычная цель:
`web -> service -> domain`, `persistence -> domain`, `все -> common`, `потребители -> api`.
Как проверить по факту:
- Смотри импорты между пакетами/модулями: какой слой что импортирует.
- Норма - стрелки идут в одну сторону (внутрь, к домену). «Обратная» стрелка (домен
  импортирует web/persistence-тип) - сигнал исключения или нарушения.
- Полезно свериться с картой модулей (кто от кого зависит по сборке).

Сформулируй направление как правило: «Слой X может зависеть от Y и не может от Z».

## 4. Поиск исключений и их условий (ядро)

Пройди по коду и собери отступления от нормы. Для каждого реши: узаконенное исключение или
случайное нарушение - по **повторяемости и наличию триггера**.

Где искать отступления:
- **Пропуск слоя:** контроллер вызывает репозиторий напрямую, минуя сервис
  (`grep` импортов репозиториев в web-слое).
- **Обратные зависимости:** домен/core импортирует типы web/persistence/framework.
- **Обход api:** модуль импортирует внутренние (`impl`/`internal`) типы другого модуля,
  а не его `api`.
- **Два способа одного и того же:** чтение vs запись, синхронно vs асинхронно, кэш vs без -
  организованы по-разному.
- **Особые модули:** `config`, `starter`, тестовые фикстуры, legacy-модуль - к ним часто
  применяются другие правила.

Для каждого повторяющегося отступления опиши **триггер** - по какому признаку видно, что
здесь именно это исключение:
- по слою/модулю (например, «только в `*-batch`»),
- по типу операции («только read-only запросы»),
- по суффиксу/имени класса («классы `*QueryHandler`»),
- по аннотации/маркеру («помеченные `@Internal`»),
- по назначению («только в конфигурации приложения»).

И обязательно - **как отличить одно исключение от другого**, если их несколько
(«команды - через доменный сервис; запросы - напрямую через `*QueryService`; различие по
чтение/запись»).

Правило проверки «законно ли»: исключение встречается систематически, единообразно и его
триггер понятен -> это правило-исключение. Встречается один раз и вразнобой -> это «возможное
нарушение», не заноси в правила, вынеси отдельно.

## 5. Что НЕ заносить в правила

- Общеизвестные банальности, не специфичные для проекта («не глотать исключения») - это уже
  во встроенном чек-листе ревьюера.
- Единичные отступления без системы - это находки-нарушения, а не правила.
- Собственные вкусовые предпочтения - только то, что реально подтверждено кодом проекта.

## 6. Как формулировать признак «как ловить на ревью»

Правило полезно ревьюеру, только если понятно, как его поймать. Давай конкретный признак:
- направление импорта: «в пакете `..domain..` не должно быть импорта `..web..`/`..persistence..`»;
- имя пакета/суффикс: «репозитории вызываются только из `..service..`»;
- зависимость модуля: «модуль `*-domain` не зависит от `*-web` по сборке».
Так ревьюер (и человек) сможет проверить правило по grep/структуре, даже без запуска.
