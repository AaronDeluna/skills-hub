# Гайд анализа архитектуры проекта автотестов (как выводить устоявшиеся подходы)

Прочитай перед Шагом 2. «Архитектура» здесь - про то, как организованы тесты. Твоя задача -
**вывести уже сложившиеся в проекте подходы по повторяемости** и записать их, а не принести
готовые правила извне. Ничего не прописывай заранее: смотри, как реально сделано, и это
фиксируй.

Принцип один: норма - то, что соблюдается почти везде; узаконенное исключение - осознанное
повторяемое отступление с понятным триггером; единичное отступление - вероятная ошибка, не
правило.

## 1. Что вообще есть в проекте (определи по коду, не предполагай)

Пробегись по структуре и определи, из чего состоит проект. Возможные роли/слои тест-проекта
(это чек-лист «на что посмотреть», а не список того, что обязано быть):
- **Тесты** - классы с тест-методами (JUnit/TestNG), либо `.feature` + glue (Cucumber).
- **Шаги / степы** - слой сценарных шагов (`*Steps`, step-definitions), между тестом и
  страницами/клиентами.
- **Page Object / компоненты** - обёртки над UI (`*Page`, `*Screen`, `*Component`,
  Selenide/Selenium/Playwright).
- **API-клиенты** - обёртки над HTTP (`*Client`, `*Api`, RestAssured/HttpClient).
- **Модели / DTO** - запросы/ответы, доменные объекты теста.
- **Тест-данные** - билдеры/фабрики/фикстуры (`*Builder`, `*Factory`, `*Fixture`, data
  providers, ресурсы `*.json`).
- **Базовые классы / хуки** - `BaseTest`, `@BeforeEach/@AfterEach`, listeners, extensions.
- **Локаторы** - где живут селекторы (в page object, в отдельном файле, константы).
- **Ожидания/синхронизация, ассерты, утилиты** - helpers, soft-assert, waits.
- **Конфигурация/окружение** - профили, `config`, переменные среды, выбор стенда.
- **Организация запуска** - теги/группы/категории, suites, параллельность, ретраи.

Для каждой найденной роли запиши: как называется (суффикс/пакет), где лежит, примеры.

## 2. Единая архитектура: общий скелет и слои теста

Открой несколько тестов/пакетов и найди **повторяющийся способ организации**. Типичные оси,
по которым смотреть (какие реально применяются - выясни):
- **Слои обращения:** тест -> шаги -> (page object / api-client) -> драйвер/HTTP + модели.
  Определи по импортам, кто на кого смотрит и что откуда вызывается.
- **Разделение UI и API:** как оформлены UI-тесты и как API-тесты (это часто два разных
  подхода в одном проекте).
- **Где ассерты:** в тестах, в шагах или в page object - найди устоявшееся место.
- **Где локаторы:** внутри page object или вынесены.
- **Как готовятся данные:** билдер / фикстура / создание через API - что принято.
- **Организация по фичам/доменам:** тесты сгруппированы по функциональности, по экранам, по
  сервисам? Как названы пакеты.
- **Именование:** `*Test`, `*Steps`, `*Page`, `*Client`, `*Builder`, имена `.feature`.

Если 4 из 5 просмотренных мест повторяют один способ - это и есть устоявшийся подход. Запиши
скелет явно (по пакетам/суффиксам и направлению вызовов).

## 3. Поиск исключений и условий их применения (ядро)

Найди места, где сделано не как обычно, и реши для каждого: узаконенный подход-исключение
или случайность - по повторяемости и наличию триггера. Где искать (для тест-проекта):
- **Обход слоя:** тест напрямую дёргает page object/элементы, минуя шаги; или лезет в
  драйвер/`WebElement` вне page object.
- **UI vs API для подготовки:** предусловия и тест-данные создаются через API-клиент напрямую,
  а сам сценарий - через UI (когда именно так делают?).
- **Прямые обращения в обход обёрток:** работа с HTTP/селекторами напрямую вместо `*Client`/
  `*Page`.
- **Разные способы одного и того же:** несколько подходов к ожиданиям, к данным (билдер vs
  статическая фикстура vs создание по API), к ассертам (hard vs soft).
- **Особые наборы:** smoke vs regression, UI vs API, e2e vs компонентные - к ним часто
  применяются разные правила (теги, база, параллельность).

Для каждого повторяющегося отступления опиши **триггер** - по какому признаку понятно, что
здесь именно этот подход, и чем он отличается от соседнего:
- по типу теста (UI / API / e2e), по тегу/группе, по суффиксу класса (`*ApiTest` vs `*UiTest`),
- по назначению кода (подготовка данных vs проверка сценария),
- по слою (только в page object / только в шагах),
- по аннотации/маркеру.

Пример формы (НЕ бери как готовое правило - только как образец формулировки, у тебя будут
свои): «Прямой вызов API-клиента в обход шагов допускается ТОЛЬКО для подготовки предусловий
и тест-данных; проверки сценария идут через шаги. Триггер: код в `@BeforeEach`/setup или в
`*ApiTest` - подготовка; код в теле сценарного теста - через шаги».

Единичные бессистемные отступления держи отдельно как «возможные нарушения», в правила не
заноси.

## 4. Что НЕ заносить в правила

- Общие банальности не про этот проект («тесты должны быть независимыми») - без пользы.
- Единичные отступления без системы - это находки-нарушения, а не правила.
- Свои внешние представления о «правильной» тест-архитектуре - только то, что подтверждено
  кодом ЭТОГО проекта.

## 5. Признак «как ловить на ревью»

Правило полезно ревьюеру, только если понятно, как его поймать. Давай конкретный признак,
проверяемый по структуре/импортам/именам:
- «`WebElement`/`By`/драйвер используются только внутри пакета `..pages..`, не в тестах/шагах»;
- «в `*UiTest` нет прямых вызовов `*Client` в теле сценария (только в setup)»;
- «локаторы объявлены только в page object, а не в тестах»;
- «ассерты вызываются в шагах/тестах, а не внутри page object».
Так и ревьюер, и человек проверят правило по grep/структуре, даже без запуска.
