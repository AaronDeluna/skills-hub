# Формализатор задачи (Jira / SberTrack -> файл задачи со статусом)

Задача: взять тикет из трекера (или из текста, что дал пользователь), привести его к чёткому
формализованному виду, проверить, хватает ли данных для разработки, и записать во временный
файл по шаблону. Статус файла - ровно два значения: `ready` (готово к разработке) или
`not-ready` (не готово, нужны ответы). Этот файл потом берёт скилл `pvatf-dev-flow`.

## Работай по плану, шаг за шагом

1. Составь план из шагов ниже (Шаг 1 ... Шаг 5) в todo или первым блоком в заметках.
2. Иди по порядку, отмечай выполненное.
3. Сбился - перечитай этот SKILL.md и заметки, продолжи с первого невыполненного шага.

## Базовые правила

1. **Не выдумывай содержание задачи.** Бери только то, что реально есть в тикете или что дал
   пользователь. Чего не хватает - спрашивай, а не додумывай.
2. **Ничего не меняй в трекере** (не редактируй тикет, не пиши комментарии) без явной просьбы.
   Ты только читаешь задачу и пишешь свой файл.
3. **Статуса ровно два:** `ready` / `not-ready`. Промежуточных нет.
4. **Пиши на русском, короткий дефис `-`, не длинное тире.** ID задачи и статус - как есть.

## Шаг 1 - Получи задачу из источника

Определи источник и достань задачу. Тебе дают ключ/ID/ссылку (например, `PROJ-123`, ссылку
на Jira или SberTrack) либо текст задачи напрямую.

- **Jira.** Если доступен коннектор/MCP Atlassian - получи тикет по ключу (заголовок,
  описание, критерии приёмки, вложения-ссылки, комментарии). Если коннектор не авторизован -
  скажи пользователю, что нужно авторизовать Atlassian (в настройках коннекторов / `/mcp`),
  и предложи как fallback вставить текст задачи вручную.
- **SberTrack.** Публичного коннектора обычно нет. Получи задачу через внутренний доступ
  команды: API/CLI, который вы используете (если он задан в окружении/конфиге проекта), либо
  попроси пользователя вставить текст задачи. Не изобретай эндпоинты - используй то, что реально
  доступно; иначе fallback на ручной ввод.
- **Ручной ввод.** Пользователь вставил текст - работай с ним как с источником `manual`.

Запиши в заметки: источник, ID, сырьё (ключевые поля тикета).

## Шаг 2 - Формализуй по шаблону

Приведи задачу к формализованному виду (шаблон файла - в
`references/task-file-template.md`, прочитай его). Разложи по полям: цель, контекст, что
нужно сделать, критерии приёмки (Definition of Done), затронутые модули/области, входные и
выходные данные, ограничения. Пиши коротко и по делу, без воды; технические детали - как в
тикете.

## Шаг 3 - Проверь полноту (достаточно ли для разработки)

Реши, можно ли по этому начать разработку. Минимум, без которого задача `not-ready`:
- понятная **цель** (что и зачем);
- **что конкретно сделать** (поведение/результат), а не только «что-то не так»;
- **критерии приёмки** (как понять, что готово);
- **где** это делать - хотя бы область/модуль/компонент (если из задачи выводимо).

Чего не хватает - выпиши конкретными **вопросами** (не общими, а точечными: «в каком модуле»,
«какой ожидаемый результат при X», «какие граничные случаи»).

## Шаг 4 - Запроси недостающее у пользователя (если нужно)

Если после Шага 3 есть блокирующие пробелы:
1. Задай пользователю список конкретных вопросов (интерактивно, если есть инструмент вопроса;
   иначе обычным сообщением) и дождись ответов.
2. Дозаполни формализацию ответами.
3. Если пользователь недоступен/не ответил или пробелы остаются - оставь статус `not-ready` и
   перечисли открытые вопросы в файле; разработку по такому файлу начинать нельзя.

Если данных достаточно - вопросов не задавай.

## Шаг 5 - Запиши файл задачи

Запиши формализованную задачу в файл `project-data/tasks/<ID>.md` в корне проекта (создай
каталоги). Если ID неизвестен (ручной ввод) - придумай короткий slug и используй как ID.
Файл строго по шаблону из `references/task-file-template.md`:
- `status: ready` - если данных достаточно, открытых блокирующих вопросов нет;
- `status: not-ready` - если чего-то не хватает; тогда обязателен раздел «Открытые вопросы».

Существующий файл этой же задачи перезаписывай. В конце покажи пользователю: путь к файлу,
итоговый статус и (если `not-ready`) список открытых вопросов. Если статус `ready` - подскажи,
что дальше задачу можно отдать в `pvatf-dev-flow`.
