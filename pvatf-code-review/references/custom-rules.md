# Кастомные правила команды / фрейма

Правила код-ревью, специфичные для этого проекта: соглашения, устоявшаяся архитектура тестов,
требования фрейма, запреты и предпочтения. Ревьюер читает этот файл и учитывает правила
отсюда наравне со встроенными.

Файл делится на ДВА блока (см. заголовки ниже):
1. **Сгенерировано автоматически** - заполняет скилл `pvatf-arch-rules` (он выводит
   устоявшиеся подходы проекта). Этот блок скилл при перезапуске **перезаписывает целиком** -
   руками его не правь, правки потеряются.
2. **Добавлено человеком** - пишет команда руками. Скилл этот блок **никогда не трогает**.

Как ревьюер это применяет:
- **Оба блока пусты** (нет ни одного правила) -> ревьюер файл игнорирует, ничего не выдумывает.
- **Есть правила** -> применяй их при ревью (Шаг 3); проверяемые тестом доказывай так же, как
  встроенные (Шаг 4). В отчёте помечай источник: «кастомное правило (сгенерировано)» или
  «кастомное правило (человек)».
- Конфликт со встроенным правилом -> кастомное правило команды приоритетнее (это их проект).
- Конфликт между блоками -> **блок человека приоритетнее** сгенерированного.

Формат правила - шаблон `### CR-<n>` с полями Область / Правило / Почему / Исключения /
Проверяемо тестом / Как ловить на ревью / Источник. В блоке человека допустим и свободный
список с пометкой, проверяемо ли правило тестом.

Правила ниже - про **продуктовые** проекты, которые используют фрейм **PVATF**. Сам фрейм
лежит в пакете `ru.sber.qa` (и построен поверх `io.perfeccionista.framework`), поэтому
продуктовый проект **импортирует** `ru.sber.qa` - это и есть нормальное использование фрейма.
На сам фрейм эти правила не распространяются. Документация фрейма (все модули, как их
использовать и реализовывать) лежит в MCP-сервере `ai-pd1c-autotest-generation-remote`, инструмент
`mcp__ai-pd1c-autotest-generation-remote__get_pv_at_doc`. Когда для правила нужно свериться с
тем, какой модуль фрейма применять и как его правильно реализовать, - запроси документацию
через этот инструмент, а не додумывай.

### CR-1 · В продуктовом проекте нет собственного кода в пакете `ru.sber.qa`
- **Область:** боевой и тестовый код **продуктового** проекта (package-декларации классов).
- **Правило:** продуктовый проект не должен объявлять собственные классы в пакете фрейма -
  никаких `package ru.sber.qa...` в своих файлах. Импорт `import ru.sber.qa...` **разрешён и
  нормален** - это использование фрейма, а не нарушение. Ограничение - только на объявление
  своего кода в пакете `ru.sber.qa`.
- **Почему:** свой код в пакете фрейма встраивается в его namespace в обход нормального
  использования, ломает границы фрейма и мешает обновлениям.
- **Исключения:** сам фрейм PVATF (его код и живёт в `ru.sber.qa` - это легитимно). Правило
  применяется только к продуктовым проектам, не к фрейму.
- **Проверяемо тестом:** нет - это статическая проверка package-деклараций; доказывать тестом не
  нужно, лови поиском по коду.
- **Как ловить на ревью:** поиском по области ревью только по декларациям пакета:
  `^package ru\.sber\.qa`. Совпадение в продуктовом проекте - находка. Строки `import ru.sber.qa`
  не трогай - это норма.
- **Источник:** человек.

### CR-2 · `Service` реализуется через `io.perfeccionista.framework`
- **Область:** классы, которые реализуют интерфейс `Service` (`implements Service` в Java / `: Service` в Kotlin).
- **Правило:** класс, реализующий `Service`, должен использовать реализацию из пакета
  `io.perfeccionista.framework` (контракты/базовые сервисы фрейма), а не собственную или
  стороннюю реализацию `Service`.
- **Почему:** сервисы - точка входа фрейма; своя реализация в обход `io.perfeccionista.framework`
  ломает единый жизненный цикл и интеграцию с PVATF.
- **Исключения:** осознанное расширение фрейма, согласованное с командой (пометить в отчёте).
- **Проверяемо тестом:** частично - факт использования именно фреймового `Service` проверяется
  статически (импорты/иерархия); поведение при необходимости доказывается тестом на Шаге 4.
- **Как ловить на ревью:** для каждого класса, реализующего `Service`, проверь, что и сам `Service`,
  и его базовая реализация приходят из `io.perfeccionista.framework`, а не из собственной или
  сторонней реализации.
- **Источник:** человек.

### CR-3 · Используй модули фрейма, а не самопис
- **Область:** любые технологии/интеграции, для которых у фрейма есть готовый модуль (REST, БД,
  web/UI, очереди и т.д.).
- **Правило:** если в проекте есть реализация технологии, для которой фрейм даёт свой модуль, -
  использовать надо модуль фрейма, а не самописный клиент. Пример: для тестирования REST
  используется фреймовый `RestService`, а не «голый» HTTP-клиент. Так же и с другими модулями.
- **Почему:** модули фрейма дают единый подход, переиспользование и совместимость с остальной
  инфраструктурой PVATF; самопис - это разрозненные подходы и риск bypass.
- **Что делать ревьюеру:** какой именно модуль применять и как его правильно реализовать - смотри
  в документации фрейма через MCP `mcp__ai-pd1c-autotest-generation-remote__get_pv_at_doc` (там
  описаны все модули). Сверь найденную в проекте реализацию с рекомендованным модулем из
  документации.
- **Исключения:** технология, для которой у фрейма нет модуля (подтверди по документации через MCP).
- **Проверяемо тестом:** нет напрямую - это архитектурная проверка «используется ли фреймовый
  модуль»; лови на ревью.
- **Как ловить на ревью:** найди прямые вызовы клиентов и самописных обёрток (например, свой
  REST-клиент вместо `RestService`) и сверься с документацией фрейма (MCP), есть ли для этого
  штатный модуль.
- **Источник:** человек.

### CR-4 · Итоговая таблица-проверка использования фрейма (в конце отчёта)
- **Область:** финальный отчёт код-ревью (`CODE-REVIEW-REPORT.md`) для проекта, использующего PVATF.
- **Правило:** в самый конец отчёта, после всех разделов, добавь таблицу-проверку с метриками
  использования фрейма - ровно в таком виде (столбцы и нормы не меняй):

  ```markdown
  **Проверка:**

  | Критерий                       | Норма   | Комментарий                                        |
  |--------------------------------|---------|----------------------------------------------------|
  | % классов, использующих PVATF  | >= 80%  | Чем выше, тем меньше разрозненных подходов          |
  | % классов с `extends Service`  | 0%      | Если есть - разобрать, нужен ли этот модуль в PVATF |
  | % прямых вызовов клиентов      | 0%      | Если есть - подозрение на bypass                    |
  ```

- **Заполнение:** посчитай метрики по области ревью и под таблицей укажи по каждому критерию
  **фактическое значение** (в процентах) и вывод, соблюдена ли норма:
  - *% классов, использующих PVATF* - доля классов области, которые опираются на фрейм, то есть
    импортируют `ru.sber.qa` (импорт/наследование/сервисы фрейма). Норма `>= 80%`.
  - *% классов с `extends Service`* - доля классов, которые напрямую `extends Service`. Норма `0%`;
    если не ноль - в выводе разбери, нужен ли этот модуль в PVATF.
  - *% прямых вызовов клиентов* - доля мест с прямыми вызовами клиентов/самописных обёрток в обход
    модулей фрейма (см. CR-3). Норма `0%`; не ноль - подозрение на bypass.
- **Проверяемо тестом:** нет - это агрегированная метрика по коду, не тест.
- **Источник:** человек.
