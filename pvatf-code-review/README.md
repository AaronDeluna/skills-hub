# pvatf-code-review

Код-ревью JVM-проектов (Java/Kotlin) **на фактах**: находки не просто декларируются, а
подтверждаются реальным тестом. Тест написан на *правильное* поведение - значит его падение
доказывает баг, а прохождение снимает подозрение как псевдопроблему. Итог - один отчёт
`CODE-REVIEW-REPORT.md`, где сразу видно, что доказано, а что нет.

## Как запускать

Два режима:

### 1. С полным путём (ревью конкретного места)
Передай полный путь до файла, каталога или модуля - скилл ревьюит именно его.
- «Проверь `/Users/ivan/project/src/main/java/app/Pricing.java`»
- «Сделай ревью модуля `/Users/ivan/project/orders-service`»

### 2. Без пути (ревью изменений ветки)
Не указывай путь - скилл сам возьмёт **изменения текущей git-ветки** (что добавлено/поменяно)
и проверит их. По умолчанию смотрит последний коммит; если у ветки есть база (main/master),
может взять весь diff ветки.
- «Сделай код-ревью» (находясь в рабочей ветке)
- «Проверь, что я тут наделал»

Технически область ревью в этом режиме собирается так:
```
git diff --name-only HEAD~1 HEAD        # изменения последнего коммита
git diff --name-only main...HEAD        # или весь diff ветки от базы (main/master)
```
Ревьюятся боевые файлы (`.java`, `.kt` в `src/main`) из этого списка, с упором на
добавленные/изменённые строки.

## Что делает по шагам

1. Определяет область ревью (путь или diff ветки) и контекст (Maven/Gradle, тестовый корень,
   JUnit 5).
2. Проверяет зелёную базу: проект компилируется, тесты и checkstyle зелёные.
3. Читает код и собирает черновые замечания (кандидаты).
4. На каждое проверяемое замечание пишет точечный JUnit 5-тест в пакет `reviewproof` и
   прогоняет его: падение = баг подтверждён, прохождение = псевдопроблема.
5. Прибирается (регрессионные тесты на реальные баги можно оставить).
6. Обязательно проверяет, что проект компилируется и checkstyle зелёный (добавленные тесты
   не должны ломать статические проверки).
7. Пишет отчёт `CODE-REVIEW-REPORT.md`: ✅ подтверждено тестом · ❌ не подтвердилось ·
   ⚠️ мнение (тестом не проверяется) · ❓ не удалось проверить.
8. Если в области ревью есть Maven/Gradle-сборка (`pom.xml` / `build.gradle` / `gradle/`) -
   в конце спрашивает да/нет, запускать ли дополнительно ревью зависимостей
   (скилл `dependency-management-review`).

## Договорённости проекта

- Только **JUnit 5** (JUnit 4 не используется).
- В коде тестов **не используется `var`** - только явные типы.
- Имена тестов - латиницей; человекочитаемое описание через `@DisplayName`.
- Боевой код (`src/main`) скилл не меняет - только добавляет тестовые файлы.
