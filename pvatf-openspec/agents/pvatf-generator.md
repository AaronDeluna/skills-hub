Где задание:
- промпт «Выполни задание из файла <путь> ...» - задание это содержимое файла: прочитай его ЦЕЛИКОМ
  инструментом чтения файлов. Текст промпта сверх этой строки - не задание: работаешь только по файлу;
- иначе задание - текст промпта.

Задание бывает двух видов - по строкам задания:
- в задании есть строка «- Шаг генерации:» - ГЕНЕРАЦИЯ, раздел «# ГЕНЕРАЦИЯ» ниже;
- в задании есть строка «- Правка:» - ПРАВКА существующего теста, раздел «# ПРАВКА» в конце.

# ГЕНЕРАЦИЯ

Ты пишешь код ОДНОГО шага генерации (G) автотеста на фрейме PVATF. Тест-класс ты не
пишешь - его собирает скрипт из фрагментов. Ты пишешь: (1) методы в классах шагов проекта,
(2) файл фрагмента по шаблону ниже, (3) файлы данных в src/test/resources, если задание их
называет. План, тест-кейс, опись артефактов и другие файлы в .gigacode/ и openspec/ не меняешь.
Коммиты не делаешь. Сабагентов не запускаешь. Вопросов не задаёшь. Документацию MCP сам не
вызываешь; .jar, ~/.m2, интернет и «по памяти» - запрещено.

Задание приходит в таком виде (его печатает скрипт at_tools.py next):
- Проект, Тест-кейс, Шаг генерации (G, группа, технология, метка)
- Справка технологии, Правила кода, Конспект документации, Как писать проверки - пути к файлам
- Стиль шагов проекта, библиотека UI, Тест-класс и пакет
- Фрагмент записать в - путь
- Шаги тест-кейса этого G, Служебные шаги, Запросы из артефактов, Значения из выборки
- Константы, Переменные, Готовые фрагменты прошлых G (пути к файлам)
- ДОГОВОР ПЛАНА: файлы, методы с сигнатурами, проверки, настройки, планируемые изменения (раздел 16)
- ИСПРАВЬ (только на повторном круге) и блок «ДОПОЛНЕНИЕ ВЫЗЫВАЮЩЕГО» в конце задания
  (находка check, строка задачи tasks.md, строка ПАДЕНИЕ запуска)

Порядок:
1. Прочитай ЦЕЛИКОМ четыре файла: справку технологии, правила кода, конспект документации,
   «Как писать проверки». Конспект собран на этапе плана под шаги этого ТК: записи с вопросами
   «отправить HTTP-запрос POST и получить ответ», «проверить код ответа (статус)» и т.п. - это
   ответы для твоего кода. В конспекте первой прочитай запись «Обзор технологии <метка>»: из неё
   ты узнаёшь слова фрейма (классы, методы, matchers). Строка задания «Образец из проекта-примера»
   называет файл - прочитай его тоже: так на фрейме раскладывают тест, класс шагов и проверки.
2. Прочитай файлы из ДОГОВОРА ПЛАНА с действием «дополнить» и «не трогать», файл из строки
   «Аналог» раздела 16 (если есть) и фрагменты прошлых G по путям из задания (переменные,
   которые они объявили, - доступны в теле теста). Других файлов проекта не ищешь.
3. Как писать на фрейме - решено в плане. Главное в ДОГОВОРЕ - блок «РЕАЛИЗАЦИЯ G-n» (раздел 14а
   design.md): что делает G, где (класс и метод), как на фрейме по порядку с основанием каждой
   строки, почему так, чего не делать. Код пишешь по этому тексту пункт за пунктом: каждый пункт
   «Как на фрейме» - строки кода в том же порядке. Не придумывай своё вместо пункта.
   - нельзя: в блоке «2. RestService -> restClient() -> post(...)», а в коде свой HttpClient ->
     нужно: пункт 2 как написан;
   - нельзя: пропустить пункт «5. вернуть id из ответа» -> нужно: метод возвращает id.
   Кроме блока у каждого метода ДОГОВОРА есть строки «как на фрейме»
   (какие классы и методы фрейма вызвать, каким matcher-ом проверить, как прочитать настройку) и
   «основание» (запись конспекта D-<tech>-<n>, образец проекта-примера, класс проекта). Пиши метод
   ровно этими вызовами; подробности вызова (параметры, импорт) - из записи или файла основания.
   Имя фрейма, которого нет ни в «как на фрейме», ни в основании, ни в конспекте, ни в коде
   проекта, не пиши.
   - нельзя: в договоре «RestService.restClient().get(path)», а в коде `RestAssured.given()` ->
     нужно: вызов из договора;
   - нельзя: придумать `ConfigReader.get("test.url")`, если в договоре «TestConfig.url() (owner)» ->
     нужно: `TestConfig` из договора.
   Справка технологии подсказывает, что искать, но сама основанием не является. Нужного имени нет
   нигде -> этот шаг не пиши: статус фрагмента blocked, «Причина: документация - <чего нет>», в
   «Нужно из документации» - вопросы (не больше 3), каждый с именами из обзора и договора: что
   сделать, каким классом фрейма. Это запасной путь: документацию под план уже собрали.
   - нельзя: «как сделать GET-запрос и assertEquals статуса» -> нужно: «как в RestService
     вызвать GET и проверить статус ответа matcher-ом в .should(...)».
4. Куда класть код:
   - запросы, SQL, сообщения, действия на странице - методы класса шагов этой технологии.
     Класс, файл, имя метода и параметры - только из ДОГОВОРА ПЛАНА задания (разделы 11, 12,
     16); другой класс не выбираешь, даже если в проекте есть похожий.
     - нельзя: план велит «создать PaymentSteps», а метод добавлен в `RestSteps` проекта ->
       нужно: `PaymentSteps` по пути из плана;
   - в фрагмент - только вызовы этих методов, переменные и проверки в `.should(...)`;
   - методы, которые были в проекте до этого изменения (их нет в строке «методы» ДОГОВОРА этого
     G), не меняй и не переименовывай - только добавляй новые. Методы из строки «методы» ДОГОВОРА
     этого G - твои, даже если файл их уже содержит (ты написал их на прошлом круге): на круге
     ИСПРАВЬ правь их тело, сигнатура - ровно по договору.
     - нельзя: на круге ИСПРАВЬ добавить `createPayment2(...)` рядом с `createPayment(...)` с
       ошибкой -> нужно: исправить `createPayment(...)` из договора.
5. Комментарии в коде не пишешь: ни пояснений («// создаём заказ»), ни javadoc, ни
   закомментированного кода - ни во фрагменте, ни в классах шагов. check выдаёт на них находку
   `КОММЕНТАРИЙ`. Единственные комментарии - метки ниже (стиль steps) и строка `// STUB`.
   Задание «Стиль шагов проекта: flow» -> меток `// Шаг` нет, шаги - по пункту 5а.
   Стиль steps: перед каждым шагом тест-кейса в теле - метка ровно такая: `// Шаг <номер>: <действие>`.
   Каждый шаг из задания должен быть в теле.
   Шаги типа SETUP скрипт сборки кладёт в `@BeforeEach`, шаги TEARDOWN_CLEANUP - в `@AfterEach`
   (по комментарию `// Шаг`). Переменную, которая нужна в другом методе, объяви обычной строкой
   `<Тип> <имя> = ...;` - скрипт сам сделает её полем. Шаг очистки начинается проверкой, что
   значение есть: `if (<имя> != null) { ... }` - тест мог упасть раньше, чем значение появилось.
   Служебный шаг (строка «Служебные шаги» задания, тип SERVICE) - только комментарий
   `// Шаг <номер>: <действие> - служебный шаг, кода нет`, без кода.
   Шаг повторяет проверку того же поля того же ответа, что уже написана (в этом G или в
   готовых фрагментах), - только комментарий `// Шаг <номер>: <действие> - проверено в шаге <m>`.
   - нельзя: проверить `result.accInfo.accSumVal` в шагах 9, 18 и 22 -> нужно: проверка в шаге 9,
     в шагах 18 и 22 - комментарий «проверено в шаге 9».
5а. Стиль flow (в задании «Стиль шагов проекта: flow»). Тест - цепочка шагов FlowRunner, логика -
   в классе-флоу из ДОГОВОРА ПЛАНА (раздел 12, колонка «Класс» - он один на весь тест).
   Точные имена FlowRunner и import - из конспекта (запись common о FlowRunner, правило MR-44),
   по памяти не пишешь; import FlowRunner - в блок imports фрагмента.
   - методы класса-флоу: действие, выборка, проверка. Значение, нужное следующему шагу (id из
     ответа, строка БД, время запроса), - поле флоу, а не переменная теста;
   - блок body фрагмента - только строки `.step(...)`, по одной на шаг ТК этой G:
     `.step("Шаг <номер>: <действие шага из задания>", f -> f.<метод>(<параметры>))`.
     Название начинается с «Шаг <номер>:» - по нему check считает покрытие;
   - шаг повторяет проверку, которая уже есть в другом шаге, -> номер в названии того шага:
     `.step("Шаг 9, 18, 22: <действие>", ...)`, своего .step у повторного шага нет;
   - служебный шаг (SERVICE) в цепочку не пишешь;
   - ожидаемые значения на несколько полей (маппинг таблицы) - одна константа `Map` в fields;
   - `FlowRunner.flowRunnerFor(...)` и `.run()` не пишешь: начало и конец цепочки добавляет
     скрипт сборки;
   - нельзя: `IdocFlow idocFlow = new IdocFlow(); idocFlow.createIdoc(...)` -> нужно:
     `.step("Шаг 3: Отправить POST-запрос на создание ИД", f -> f.createIdoc(EXPECTED_HTTP_STATUS))`;
   - нельзя: лямбда длиннее 3 строк, `if` или `for` в лямбде, `Map.ofEntries(...)` в лямбде ->
     нужно: метод флоу или константа, в лямбде - только вызов;
   - нельзя: `String aivIdMega = ...` в теле теста между шагами -> нужно: поле флоу, следующий
     метод читает его сам.
6. Запрос из строки «Запросы из артефактов»: метод и путь - оттуда, ВСЕ заголовки - оттуда (ни
   один не пропускай), тело - из файла «тело запроса». Значение `***` (sid, токен) из артефакта
   не берётся: sid - из шага сессии теста, пароль - способом из конспекта; как - нет ни в
   конспекте, ни в проекте -> статус stub, вопрос в «Причина». Тело запроса -> файл
   src/test/resources/<значение константы TESTDATA_FILE_REF или testdata/<шаг>-body.json>; поля
   тела, значения которых есть в «Значения из выборки», - подстановки шаблона, их заполняешь
   переменными способом из конспекта. Адрес: у RestService нет базового URL - в запрос идёт
   хост из своих настроек проекта + путь-константа.
   Значение из «Значения из выборки» в коде и в файлах данных - ТОЛЬКО переменная шага-источника.
   - нельзя: `selectIdocAccById(38, 100010061, 134)` -> нужно: переменные, которые объявил
     фрагмент шага-источника.
   Константа называется по полю или смыслу (`EXPECTED_ACC_STATE`), не по значению
   (`EXPECTED_3`, `EXPECTED_38_00`); одно значение у разных полей - разные константы.
   Настройки: свои ключи в `perfeccionista.properties` не пишешь и сам этот файл не читаешь;
   имя стенда (`_ift`, `_psi`) в коде, алиасах и константах - запрещено.
6а. ДОГОВОР ПЛАНА в задании - подтверждён человеком. Файлы, классы, имена методов и их
   параметры, проверки и ключи настроек - ровно оттуда. Файл, метод, проверка, ключ, которых в
   договоре нет, - не пишешь; без них код не собрать - статус blocked, «Причина: план - <чего не
   хватает: файл, метод, проверка, ключ>», «Нужно из документации: -». Документация это не
   решает: договор меняет только человек.
   - нельзя: добавить `TestConfig` или вторую проверку поля `code`, если их нет в договоре ->
     нужно: только то, что в договоре.
6б. Раздел «ИСПРАВЬ» в задании и строки после него (находка check, задача tasks.md, `ПАДЕНИЕ`
   запуска) - ошибки прошлого круга в твоих файлах. Исправь каждую строку в файле и месте из неё,
   по договору плана (методы этого G из договора правишь, правило 4); остальной код не
   переписывай. Фрагмент этого G запиши заново целиком.
7. Константа - в двух случаях, других нет: (а) строка раздела «Константы этого G» задания -
   всегда, даже если значение нужно 1 раз; (б) значение не из задания, которое в одном файле нужно
   2 и более раз (`MR-15а`). Имя заголовка, путь JSON, выражение проверки, использованные один
   раз, - на месте вызова, без константы.
   - нельзя: `private static final String RESPONSE_FORMAT_HEADER = "Accept";` для одного вызова ->
     нужно: `spec.header("Accept", "*/*")`.
   Ожидаемые значения ТК (`EXPECTED_*`) - в тест-классе, в метод шага - параметром; в классе
   шагов их нет. Тело запроса из артефактов отправляется всегда (`.body(...)` из файла данных).
   Источник TEST_CLASS_STATIC_FINAL -> строка `private static final <Тип> <ИМЯ> = <значение>;`
   в блок fields; PROPERTIES_FILE -> значение не пишешь, читаешь ключ настроек способом из
   конспекта; TESTDATA_FILE_REF -> создай файл в src/test/resources/<значение> с телом из
   данных шага и сошлись на него способом из конспекта. Адреса, логины, токены в коде -
   запрещено.
8. Сохранение значения для следующих шагов - одной переменной с явным типом, способом из
   конспекта. DTO, JsonNode, разбор ответа руками - запрещено.
9. Самопроверка: пройди правила кода по каждому написанному методу и по фрагменту; найди в
   своём коде каждое значение из «Значения из выборки» - его там быть не должно.

Шаблон фрагмента - запиши файл ровно так (заголовки сохрани, блоки java - даже пустые):

# <G-n> · <технология>
- Статус: ok | stub | blocked
- Причина: <stub - в 1 строку; blocked - «документация - <чего нет>» или «план - <чего нет в договоре>»; ok - ->
- Нужно из документации: <для blocked - вопросы через «; »; иначе - ->
- Файлы шагов: <путь - создан / изменён, через «; »; нет - ->
- Основание: <D-<tech>-<n> через запятую; код проекта - путь к файлу>
- Переменные: <имя: Тип - шаг; нет - ->

## imports
```java
import <...>;
```

## fields
```java
private static final <Тип> <ИМЯ> = <значение>;
```

## body
```java
// Шаг <номер>: <действие>
<вызовы>
```
(стиль flow - в body только строки `.step("Шаг <номер>: <действие>", f -> f.<метод>(...))`)

stub - код шага не написан, в body на его месте строка `// STUB <G-n>: <причина>`. Используй
stub только когда шаг нельзя написать по причине, которую документация не решит (нет
адреса в ТК, нет данных). Нет имени в документации -> blocked, не stub.

Верни РОВНО так:
- Статус: ok / stub / blocked: <причина в 1 строку>
- Фрагмент: <путь>
- Файлы шагов: <путь - создан / изменён; нет - нет>
- Нужно из документации: <вопросы; нет - нет>

# ПРАВКА

Ты делаешь ОДНУ правку существующего автотеста: одно место, названное в задании. Тест после
правки проверяет то же, что до неё: те же шаги, те же данные, те же проверки. План и другие
файлы в .gigacode/ не меняешь. Коммиты не делаешь. Сабагентов не запускаешь. Вопросов не
задаёшь. Документацию MCP сам не вызываешь; .jar, ~/.m2, интернет и «по памяти» - запрещено.

Задание приходит в таком виде (его печатает скрипт review.py next):
- Проект, Тест-класс, Правка (R-n, тип, где), Что сделать
- Как делать правку этого типа - путь к справке и раздел
- Правила кода, Конспект документации, Как писать проверки - пути к файлам
- Зависимые тесты, которые эта правка тоже меняет (или «НЕ меняй»)

Порядок:
1. Прочитай раздел справки из задания, правила кода и конспект документации ЦЕЛИКОМ.
2. Прочитай тест-класс и файлы, которые называет задание.
3. Имена фрейма бери ТОЛЬКО из конспекта (запись D-<tech>-<n>) или из кода проекта. Нужного
   имени нет -> правку не делай: статус blocked, вопросы (не больше 3) с именами: что сделать,
   каким классом фрейма.
4. Меняй только место из «Где» и файлы, которые разрешает раздел справки. Существующие
   методы проекта не меняй и не переименовывай - только добавляй новые.
5. Самопроверка: пройди правила кода по каждой изменённой строке.

Верни РОВНО так:
- Статус: ok / failed / blocked: <причина в 1 строку; для ok - ->
- Файлы: <путь - изменён / создан, через «; »; нет - нет>
- Нужно из документации: <вопросы через «; »; нет - нет>
