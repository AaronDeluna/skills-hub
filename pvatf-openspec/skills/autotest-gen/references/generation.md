# Цикл генерации одного G и исправление находок

Часть скилла `autotest-gen`. Открывай, только когда SKILL.md направил сюда.

Скрипт: `python3 .gigacode/skills/autotest-gen/scripts/at_tools.py` (ниже - `at_tools.py`).

## Один G

1. Вывод `at_tools.py next <ключ>` после строки «ЗАДАНИЕ для агента pvatf-generator» -
   это задание. Передай его агенту `pvatf-generator` дословно, ничего не добавляя.
2. Ответ агента - строка `Статус:`:

| Статус | Что делаешь |
|--------|-------------|
| `ok` | `at_tools.py mark <ключ> <G-n> ok`, потом `at_tools.py compile <ключ> <G-n>` (SKILL.md, шаг 3), дальше `next` |
| `stub` | `at_tools.py mark <ключ> <G-n> stub`; причину из ответа - строкой в раздел 7 плана «Решения и блокеры»: `<G-n>: stub - <причина>`; compile этой G не нужен, дальше `next` |
| `blocked` | `at_tools.py mark <ключ> <G-n> blocked`. Вывод `СТОП: ... в плане не хватает` (агент написал «Причина: план - ...») -> вопрос человеку из строки СТОП, документацию не спрашиваешь, stub не ставишь. Иначе - раздел «Вопросы документации» ниже, потом `mark <ключ> <G-n> todo`, `next` - задание агенту снова |

3. Третий `blocked` с вопросами документации на тот же G (2 круга документации не помогли) -> `mark <ключ> <G-n> stub`,
   строка в раздел 7 плана `<G-n>: stub - нет в документации: <вопросы>`.

## Вопросы документации (статус blocked)

1. Вопросы - из строки «Нужно из документации» ответа агента, не больше 5.
2. По каждому сначала конспект:
   `python3 .gigacode/skills/autotest-gen/scripts/notes.py find <метка G> <2-4 слова>`.
   Нашлась запись `найден`, а агент её не увидел -> переходи к п.5.
3. Остальные - агенту `pvatf-docs` по шаблону `references/autotest-rules.md`, правило 3;
   метка и раздел - из таблицы того же правила.
4. Ответ агент пишет в файл сам, в конспект `openspec/pvatf/doc-notes/<метка>.md` его
   переносит `notes.py merge <метка> doc-notes` (порядок - `references/autotest-rules.md`,
   правило 2). Сам конспект не правишь.
5. `at_tools.py rules <ключ>` - обновляет `docs-now.md` для агента.

## Исправление находок check

Строка вывода `check` - одна находка. Порядок разбора - первая подходящая строка:

1. Строка начинается с `STUB` или `ЧЕЛОВЕК` -> не исправляешь, она уходит в итог человеку (код G
   stub и manual пишет человек).
2. Есть строка `НУЖНО: <G-n> - находок в классах шагов` -> находки в классах шагов этой G (файл из
   раздела 11 плана, не тест-класс; `ПРОВЕРКА НЕТ`, `ТЕЛО`, `ЗАГОЛОВОК`, `ПОКРЫТИЕ` по шагу) ты не
   правишь: check уже вписал их в задание G. Делай: `mark <ключ> <G-n> todo`, `next`, агент pvatf-generator, `mark ... ok`,
   compile. Находки из этой строки в таблице ниже не ищешь.
3. Остальные строки - тест-класс (в строке путь `test_file` из шапки плана) или файл, которого нет в
   плане. Их правишь по таблице ниже, только место из строки. Тест-класс правишь только через
   фрагмент `fragments/G-<n>.md` (блоки imports / fields / body) и `assemble`, сам файл теста не
   правишь.
  - нельзя: самому дописать метод в `PaymentSteps.java` по находке `МЕТОД НЕТ` -> нужно: строка
    НУЖНО этой G, агент дописывает метод по договору плана.
4. Строки нет в таблице ниже -> общее правило: находка `MR-<n> <тест-класс>:<строка>` - открой
   правило MR-<n> в `rules-now.md`, исправь строку во фрагменте G этого шага (комментарий `// Шаг`
   выше строки) так, как велит правило, потом `assemble`. Правило требует имени фрейма, которого
   нет в конспекте, - вопрос документации. Правка меняет договор плана (новый файл, метод,
   проверку) или правила MR-<n> нет - не правь: строка дословно в итог «Осталось человеку».

| Находка | Как исправить |
|---------|---------------|
| `MR-33` var | явный тип из объявления метода, который вернул значение |
| `MR-29` assert | matcher из конспекта (`docs-now.md`); matcher нет -> вопрос документации «каким matcher проверить <что>», ответа нет - строка оставляется и уходит в итог |
| `MR-4` полное имя | `import` в начало файла, в коде - простое имя |
| `MR-15` адрес или секрет | ключ настроек из конспекта вместо строки |
| `MR-14` sleep | ожидание фрейма из конспекта |
| `MR-42` метод в тест-классе | найди фрагмент G, где объявлен этот метод; `mark <ключ> <G> todo`, `next`, в конец задания допиши строку находки дословно - агент перенесёт метод в класс шагов из плана |
| `MR-21` TODO | доделай место по фрагменту или замени на `// STUB <G-n>: <причина>` и строку в раздел 7 плана |
| `ПОВТОР <файл>:<строка>` | второй раз проверено то же поле того же ответа: во фрагменте этого шага убери проверку, оставь комментарий `// Шаг <n>: <действие> - проверено в шаге <m>`, затем `assemble` |
| `ВНЕ ПЛАНА <файл>` | файла нет в разделе 11 плана, его создал агент: найди G, во фрагменте которой этот файл в строке «Файлы шагов»; `mark <ключ> <G> todo`, `next`, в конец задания допиши строку находки дословно - агент перенесёт код в файл из плана и удалит лишний. План сам не правишь; файл правда нужен - в итог «Осталось человеку»: правка плана |
| `МЕТОД НЕТ <файл>` | всегда класс шагов - строка НУЖНО этой G (агент) |
| `МЕТОД ВНЕ ПЛАНА <файл>` | в классе шагов - строка НУЖНО этой G (агент); в тест-классе - удали метод из фрагмента: вызовы - в body, код метода - задача агента (`mark <G> todo`, `next`, строка находки в конец задания) |
| `ПРОВЕРКА НЕТ шаг <n>` | всегда строка НУЖНО G шага <n> (агент): проверка - в методе шага по разделу 16 плана |
| `ПРОВЕРКА ВНЕ ПЛАНА` | поле проверяется в тест-классе - удали эту проверку из фрагмента; в классе шагов - G этого класса: `mark <G> todo`, `next`, строка находки в конец задания |
| `НАСТРОЙКА НЕТ <файл>` | ключа из раздела 14 нет в файле настроек: допиши в этот файл строку `<ключ>=<значение>` из строки раздела 14 плана, больше ничего в файле не меняй (`perfeccionista.properties` в разделе 14 не бывает) |
| `РАЗОВАЯ <файл>` | строковая константа используется один раз и это не данные ТК: впиши значение на месте вызова, константу удали (`MR-15а`) |
| `ОЖИДАЕМОЕ <файл>` | строка НУЖНО этой G (агент): константа - в тест-класс, в метод - параметром по разделу 12 плана |
| `ТЕЛО шаг <n>` | у запроса из описи есть тело, а в коде нет `.body(...)`: отправь тело из файла `testdata/<шаг>-body.json` способом из конспекта; нет способа в конспекте - вопрос pvatf-docs |
| `ИМЯ <файл>:<строка>` | константа названа по значению: переименуй по полю, которое проверяет шаг (`EXPECTED_ACC_STATE`), во фрагменте и во всех местах использования; одно значение у разных полей - разные константы |
| `СТЕНД <файл>:<строка>` | имя стенда (`_ift`, `_psi`) в строке кода: алиас и адрес - без стенда, стенд выбирается настройками (правило 14 `autotest-rules.md`) |
| `ЛИТЕРАЛ <файл>:<строка>` | значение из выборки записано числом или строкой: замени на переменную из находки (её объявил фрагмент шага-источника); в файле данных - подстановка шаблона |
| `ЗАГОЛОВОК шаг <n>` | заголовок запроса из описи артефактов не перенесён: строка НУЖНО G шага <n> (агент) |
| `НЕ ИСПОЛЬЗУЕТСЯ <файл>` | метод класса шагов из этой генерации нигде не вызывается: вызова нет в body фрагмента - допиши вызов во фрагмент шага из раздела 12; метода нет в разделе 12 - G этого класса: `mark <G> todo`, `next`, строка находки в конец задания (агент удалит метод) |
| `ПОКРЫТИЕ шаг <n>` | шага нет в теле: строка НУЖНО G шага <n> (агент заново, п. «Один G») |
| `КОМПИЛЯЦИЯ ...` | ошибка в классе шагов - строка НУЖНО этой G (агент); в тест-классе - правь через фрагмент `fragments/G-<n>.md` (блоки imports / fields / body) и `assemble`, сам файл теста не правишь |

После правок фрагментов - `at_tools.py assemble <ключ>`, потом `check`. Сам файл тест-класса не
правишь: assemble после ручной правки остановится строкой `ИЗМЕНЁН ВРУЧНУЮ`.
