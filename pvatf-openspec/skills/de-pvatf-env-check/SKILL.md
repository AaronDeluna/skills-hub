# Проверка и настройка окружения PVATF

Скилл запускает `de-pvatf-orchestrator`. Сам ты код тестов не пишешь и версию фрейма не меняешь (два исключения - `references/setup.md`, раздел 3:
новый проект без версии и `FRAME_VERSION_UNKNOWN`).
Режим приходит от оркестратора: `check` (только проверить), `setup` (проверить и
доставить недостающее), `setup <ключ ТК>` (то же и ещё окружение под этот тест-кейс перед
генерацией) или `init` (создать каркас нового проекта, потом `setup`). Сначала прочитай `references/autotest-rules.md` - общие правила окружения и генерации.

## Когда использовать / когда не использовать

| Просьба | Режим |
|---------|-------|
| «проверь окружение», «готов ли проект», перед генерацией автотестов | `check` |
| «настрой окружение», «подключи фрейм», «почини окружение по отчёту» | `setup` |
| ДЕЙСТВИЕ `env-setup <ключ>` от оркестратора: генерация автотеста, окружение под ТК не готово | `setup <ключ>` |
| «создай проект автотестов», «новый проект с нуля», в каталоге нет файла сборки | `init` |
| «обнови фрейм», «обнови окружение» | не этот скилл - `de-pvatf-env-update` |

## Предусловия

- Файлы работы - в каталоге изменения OpenSpec `openspec/changes/<имя>/` (`<имя>` - строка
  `ИЗМЕНЕНИЕ:` из `os_work.py next` оркестратора): артефакты `proposal.md`, `design.md`,
  `tasks.md` и рабочие файлы `outputs/`. Общее для проекта (конспект документации, `ENV.json`) -
  `openspec/pvatf/`. Пути в командах скриптов определяются сами - подставлять их не нужно.
- Запуск из корня проекта автотестов (там, где `pom.xml` / `build.gradle(.kts)` и `.gigacode/`);
  режим `init` - из пустого каталога будущего проекта.
- Python 3.8+ (команды `python3 ...`; на Windows, где нет `python3`, - `python ...` или `py -3 ...`).
- Maven или Gradle (или обёртка `mvnw` / `gradlew` в корне) - для проверки E6.
- Режим `setup`: агент `pvatf-docs` (из папки `agents/` набора); документация MCP - только через него.

**Скрипты лежат в `.gigacode/skills/de-pvatf-env-check/scripts/`.** Скрипта по этому пути нет -> найди
один раз инструментом поиска файлов: файл `env_check.py` в каталоге проекта и в `~/.gigacode` (работает и на Windows) -
и подставляй найденный путь.

## Шаги

### Режим check

1. Версии фрейма. Сначала проверь, нужен ли запрос:
   ```
   python3 .gigacode/skills/de-pvatf-env-check/scripts/env_check.py --notes-fresh openspec/pvatf/env/release-notes.md
   ```
   `RELEASE NOTES: СВЕЖИЕ` -> MCP не вызывай, файл не трогай, сразу команда проверки ниже.
   `НУЖЕН ЗАПРОС` -> вызови MCP-инструмент `get_pvat_release_notes` (таймаут 120 секунд; таймаут или
   ошибка -> повтори 1 раз) и запиши в `openspec/pvatf/env/release-notes.md` только строки-заголовки релизов - строки, где стоит номер версии
   (`## <версия>`, «Версия <версия> от <дата>»), дословно, по строке на релиз, не больше 30 строк.
   Описания изменений не переписывай: из файла скрипт берёт только номера версий. Нельзя:
   переписать ответ целиком. Нельзя: написать номер версии от себя - только строки из ответа.
   Снова ошибка -> файл не пиши. В команде ниже вместо `--release-notes <файл>` поставь
   `--offline` (и `--example <путь>`, если человек дал проект-пример): скрипт сам найдёт версию
   в скачанных исходниках фрейма (теги git), потом в проекте-примере, и напишет её в строку
   `САМАЯ НОВАЯ` с пометкой «без MCP». Сам версию не ищешь и не выбираешь.
   Запусти (таймаут команды - 600 секунд; компиляцию скрипт сам ограничивает 540 секундами):
   ```
   python3 .gigacode/skills/de-pvatf-env-check/scripts/env_check.py --release-notes openspec/pvatf/env/release-notes.md
   ```
   Скрипт сам выбирает команду компиляции (`mvn -q -DskipTests test-compile` или
   `gradle -q testClasses`, обёртка в приоритете), пишет `openspec/pvatf/env/ENV.json`
   и печатает сводку.
2. Покажи человеку сводку по шаблону из раздела «Контракт» - строки `СТАТУС`, `E1`-`E6` и
   все строки `ПРОБЛЕМА` дословно.
3. `СТАТУС: failed` -> предложи одной строкой: «Напишите: `/opsx-de-pvatf настрой окружение`».
   Ничего не исправляй сам.
4. Строка `ПРОБЛЕМА: info · FRAME_OUTDATED` -> фрейм отстаёт от самой новой версии. Статус она не
   меняет. В строке «Дальше» добавь: «`/opsx-de-pvatf обнови окружение` - обновить фрейм до <версия>».

### Режим init

1. Значения каркаса:
   ```
   python3 .gigacode/skills/de-pvatf-env-check/scripts/env_init.py defaults
   ```
   `ПРОЕКТ УЖЕ ЕСТЬ` -> каркас не нужен: выполни режим setup, закончи.
   groupId, artifactId, корень пакетов и стиль шагов названы в просьбе -> бери их. Иначе спроси
   одним сообщением (это разрешённый вопрос, ответа жди):
   «1) groupId, artifactId и корень пакетов через запятую? Пустой ответ - <значения из строки ПО УМОЛЧАНИЮ>.
   2) Как писать шаги тестов: `steps` - классы шагов предметной области, или `flow` - классы-флоу
   и FlowRunner? Выбор сохранится, все следующие тесты пойдут в том же стиле. Пустой ответ - `steps`».
2. Каркас (только Maven: проект-пример фрейма - Maven; Gradle просят -> скажи, что каркас
   создаётся только на Maven, и закончи):
   ```
   python3 .gigacode/skills/de-pvatf-env-check/scripts/env_init.py create --group <groupId> --artifact <artifactId> --package <корень пакетов> --style <steps | flow>
   ```
   Скрипт пишет `pom.xml` без зависимостей фрейма, каталоги `<корень>`, `<корень>/config`,
   `<корень>/steps`, `<корень>/tests` и `ENV-INIT.md` (корень, пакет тестов, стиль шагов).
   Раскладка пакетов - `references/autotest-rules.md`, правило 13. Имена
   фрейма он не пишет: их берёт режим setup из документации.
3. Выполни режим setup целиком, затем `references/setup.md`, раздел «Новый проект».


### Режим setup

1. Выполни режим check, шаг 1. `СТАТУС: ok` и ключа ТК нет -> скажи «окружение в порядке»,
   закончи. `СТАТУС: ok` и ключ ТК есть -> шаг 5.
2. Открой `references/setup.md` и пройди его по порядку: каждая строка `ПРОБЛЕМА` - одна
   правка по таблице, имена берутся только из ответа `pvatf-docs` или проекта-примера.
3. После всех правок снова запусти env_check.py (шаг 1 режима check).
4. Новых проблем стало больше или осталась та же `critical` -> верни правки
   (по списку из `ENV-SETUP.md`: изменённый файл - `git checkout -- <файл>`, созданный файл или каталог - `rm -r <путь>`, только для пути из `ENV-SETUP.md` внутри корня проекта), запиши причину, закончи.
   Проблем стало меньше, но `СТАТУС` не `ok` -> снова шаг 2 по оставшимся строкам `ПРОБЛЕМА`. Не больше 3 кругов «правка -> проверка»; после третьего круга правки не возвращай, оставшиеся проблемы запиши в `ENV-SETUP.md` строкой «не исправлено: 3 круга».
   Конец шагов 2-4: ключ ТК есть и `СТАТУС` не `failed` (остались только `warning`) -> шаг 5,
   предупреждения окружение под ТК не блокируют. `СТАТУС: failed` или ключа нет -> закончи.
5. Только с ключом ТК - окружение под тест-кейс (таймаут команды 600 секунд):
   ```
   python3 .gigacode/skills/de-pvatf-env-check/scripts/env_tc.py <ключ>
   ```
   `ОКРУЖЕНИЕ ТК: готово` -> закончи, в ответе строка «Окружение ТК: готово». Иначе открой
   `references/setup.md`, раздел 5 «Окружение под ТК», и пройди его: каждая строка `НУЖНО` -
   один вопрос `pvatf-docs` и одна правка. Ничего из `НУЖНО` человеку не перекладывай: модули,
   драйвер, классы настройки сервисов, регистрацию сервисов в `getServiceConfigurations()` класса
   конфигурации окружения и ключи настроек делаешь сам.
   После правок снова `env_tc.py <ключ>`. Не больше 3 кругов «правка -> проверка». Остались
   строки `НУЖНО`, на которые документация ответила «НЕТ В ДОКЕ» (например, версия драйвера),
   -> спроси человека одним сообщением списком (по строке на `НУЖНО`: что нужно и чего нет в документации), запиши их в `ENV-SETUP.md` и закончи.

## Контракт «вход -> выход»

Вход: режим (`check` / `setup` / `init`), необязательно - путь к проекту-примеру (драфту);
для `init` - groupId, artifactId, пакет.

Выход:
- `openspec/pvatf/env/ENV.json` - полный результат (пишет скрипт, руками не правится);
- режим setup - `openspec/pvatf/env/ENV-SETUP.md` по шаблону `references/setup.md`;
- режим init - ещё `pom.xml`, каталоги тестов, `openspec/pvatf/env/ENV-INIT.md`, базовый тест-класс;
- `openspec/pvatf/env/release-notes.md` - строки-заголовки релизов из ответа `get_pvat_release_notes` (не больше 30);
- режим setup с ключом - `openspec/changes/<имя>/outputs/ENV-TC.md` (пишет `env_tc.py`, руками не правится);
- ответ в чате строго по шаблону:

```
Окружение: <ok | warning | failed> (проверено <дата время из ENV.json>)
Проект: <строка ПРОЕКТ из вывода>
Версия фрейма: <строки ВЕРСИЯ через «; » или «не найдена»> · самая новая <строка САМАЯ НОВАЯ дословно, с пометкой «без MCP», если она есть; нет - «не найдена: <причина>»>
Проверки:
- E1..E6 · <название> · <статус> · <детали>
Проблемы: <по строке на ПРОБЛЕМА; нет - «нет»>
Сделано (только setup): <файл - что изменено; нет - «ничего»>
Окружение ТК (только setup с ключом): <готово | не готово: строки НУЖНО>
Дальше: <одна команда для человека>
```

Коды выхода env_check.py: 0 - ok или warning, 1 - failed, 2 - неверный запуск.

## Обработка ошибок

| Что случилось | Что делаешь |
|---------------|-------------|
| Скрипт скилла без компиляции и без MCP-вызова не закончил работу за 120 секунд | Прерви вызов, покажи вывод дословно, дальше не иди. Повторно не запускай |
| Код выхода 2 | Покажи вывод дословно, проверь, что запускаешь из корня проекта, запусти ещё раз. Снова 2 - остановись |
| `COMPILE_TIMEOUT` | Повтори ту же команду, не больше 2 раз (таймаут команды 600 секунд): Maven продолжит со скачанного. Снова таймаут - скажи человеку проверить доступ к репозиторию зависимостей; дальше не иди |
| `BUILD_TOOL_NOT_FOUND` | Скажи, какой команды нет. Сам ничего не устанавливай |
| `BUILD_FILE_MISSING` | Режим `init` -> это ожидаемо, иди по режиму init. Иначе скажи: «Нет pom.xml и build.gradle: запуск не из корня проекта или проекта ещё нет - для нового проекта напишите `/opsx-de-pvatf создай проект автотестов`». Правок не делай, закончи |
| `get_pvat_release_notes`: таймаут или ошибка после повтора | Запусти env_check.py с `--offline` вместо `--release-notes` (шаг 1). `FRAME_VERSION_NOT_FOUND` -> версия фрейма только от человека: `references/setup.md`, раздел 3 |
| env_init.py: `НЕВЕРНО` | Покажи строку дословно, спроси значения ещё раз одной строкой |
| `REPORT_NOT_WRITTEN` | Покажи строку `ПРОБЛЕМА` дословно, правок не делай, закончи |
| `pvatf-docs` вернул `MCP НЕДОСТУПЕН` или «НЕТ В ДОКЕ» | Эту проблему не исправляй, запиши в `ENV-SETUP.md` «не исправлено: нет в документации» |
| env_tc.py: `НЕ ЗАПИСАН: <файл>` | Окружение под ТК не подтверждено: генерация без `ENV-TC.md` не начнётся. Покажи строку дословно, закончи |
| env_tc.py: `НЕТ ПЛАНА` | Плана ТК нет: окружение под ТК не проверить. Покажи строку дословно, закончи |
| Скрипт упал с трассировкой | Покажи последние 20 строк вывода, ничего не исправляй вручную |

## Чек-лист проверки

- [ ] env_check.py запускался в этом чате, `ENV.json` свежий (дата в сводке - сегодня).
- [ ] В ответе есть все шесть строк E1-E6 и все строки `ПРОБЛЕМА`.
- [ ] Режим setup: каждое имя зависимости и класса в правках есть в ответе `pvatf-docs` или в проекте-примере.
- [ ] Режим setup: после правок проверка запускалась повторно, её статус - в ответе.
- [ ] Код тестов не менялся; версия фрейма не менялась (кроме нового проекта и `FRAME_VERSION_UNKNOWN` - тогда она равна строке `САМАЯ НОВАЯ`).
- [ ] Новый проект: версия фрейма в сборке равна строке `САМАЯ НОВАЯ` (из release notes), а не числу из документации или по памяти; строки `FRAME_VERSION_UNKNOWN` в последней проверке нет.
- [ ] Режим setup с ключом: `env_tc.py <ключ>` запускался последним, его итог - в ответе; правка по
      каждой строке `НУЖНО` сделана или записана в `ENV-SETUP.md` с причиной «НЕТ В ДОКЕ».
- [ ] `get_pvat_release_notes` вызывался в этом чате или `--notes-fresh` ответил `СВЕЖИЕ`; в строке «Версия фрейма» есть «самая новая».
- [ ] В `release-notes.md` только строки-заголовки релизов, не больше 30, описаний изменений нет.
- [ ] Режим init: env_init.py create вернул 0, затем выполнен режим setup и раздел «Новый проект» `references/setup.md`.
