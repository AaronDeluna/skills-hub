# План автотеста по тест-кейсу

Скилл запускает `de-pvatf-orchestrator`. Ты не пишешь код теста. Твоя работа: превратить тест-кейс в
проверенный план `openspec/changes/<имя>/design.md`, по которому `de-pvatf-autotest-gen` пишет
код. Почти всё делают скрипты; ты проверяешь только строки, которые скрипт пометил.
Сначала прочитай `references/autotest-rules.md` - общие правила окружения и генерации.

## Когда использовать / когда не использовать

| Просьба | Что делаешь |
|---------|-------------|
| «сгенерируй автотест по ТК <файл>», «разбери ТК», «напиши тест по логу / Allure» | шаги 1-8 |
| «проверь тест-кейс» (только оценка) | шаги 1-3, план не строишь |
| план уже `planned`, просят код | не этот скилл - `de-pvatf-autotest-gen` |

## Предусловия

- Файлы работы - в каталоге изменения OpenSpec `openspec/changes/<имя>/` (`<имя>` - строка
  `ИЗМЕНЕНИЕ:` из `os_work.py next` оркестратора): артефакты `proposal.md`, `design.md`,
  `tasks.md` и рабочие файлы `outputs/`. Общее для проекта (конспект документации, `ENV.json`) -
  `openspec/pvatf/`. Пути в командах скриптов определяются сами - подставлять их не нужно.
- Артефакт от человека - один из:
  - файл ТК из TMS: `.md`, `.xml`, `.json`;
  - ключ ТК в Zephyr (`CODE-T123`) - тогда нужен MCP-инструмент Jira `zephyr_get_testcase`;
  - Allure: файл `*-result.json` или каталог `allure-results/`;
  - лог прогона: `.log`, `.txt`;
  - код автотеста на любом фреймворке: `.java`, `.kt`.
- Окружение проверено: `openspec/pvatf/env/ENV.json` со статусом `ok` или `warning`
  (проверяет `de-pvatf-orchestrator` до запуска этого скилла).
- Агент `pvatf-artifacts` в `.gigacode/agents/` (разбор лога и Allure, шаг 1б).
- Python 3.8+ (команды `python3 ...`; на Windows, где нет `python3`, - `python ...` или `py -3 ...`).

**Скрипты лежат в `.gigacode/skills/de-pvatf-autotest-plan/scripts/`.** Скрипта по этому пути нет ->
найди один раз: инструментом поиска файлов: файл `tc_plan.py` в каталоге проекта и в `~/.gigacode` (работает и на Windows).

## Шаги

1. Оркестратор передал ключ, и `openspec/changes/<имя>/outputs/TC.md` уже есть -> этот шаг
   пропусти. Человек дал файл (ТК, лог, Allure, код теста) -> сразу команда `tc_convert.py` ниже с
   этим файлом; Zephyr и MCP не трогай.
   - нельзя: человек дал `tst.txt` (лог) -> искать `zephyr_get_testcase` и просить выгрузку ТК ->
     нужно: `tc_convert.py tst.txt --key <ключ>`.
   Передан только ключ ТК (`CODE-T123`), файла нет -> загрузи ТК из Zephyr:
   - вызови MCP-инструмент Jira `zephyr_get_testcase` с этим ключом (имя параметра - из
     описания инструмента), таймаут 120 секунд;
   - ответ инструмента запиши инструментом записи файлов, без правок и сокращений, в
     `openspec/changes/<имя>/outputs/zephyr.json` (ответ не JSON - в `zephyr.md`);
   - дальше `<файл ТК>` - этот файл, к команде ниже добавь `--key <ключ>`.

   Перевод в единый вид:
   ```
   python3 .gigacode/skills/de-pvatf-autotest-plan/scripts/tc_convert.py <файл ТК, лог, тест или каталог allure-results> [--key <ключ>] [--method <тест-метод>] [--name <имя теста>]
   ```
   Ключ изменения `NOTC-<n>` (оркестратор создал работу без ТК) -> спроси одной строкой «Имя тест-класса
   латиницей с окончанием Test (например PaymentLockTest)?» и запусти `tc_convert.py <файл> --key NOTC-<n>
   --class <имя>`.
   Строка `КЛЮЧА НЕТ:` -> спроси одной строкой: «Ключ ТК? Дайте ключ вида CODE-T123 или ответьте "ТК нет"».
   - ключ -> запусти снова с `--key <ключ>`;
   - «ТК нет» -> спроси одной строкой: «Имя тест-класса латиницей с окончанием Test (например PaymentLockTest)?» и
     запусти снова с `--no-tc --class <имя>`. Скрипт сам даёт служебный ключ `NOTC-<n>`; `@TmsLink` в тест не
     ставится.
   - нельзя: придумать ключ (`KARKAS-T0000`) или имя класса из ключа (`Notc1Test`), транслит (`OplataTest`) ->
     нужно: ключ и имя класса - только из ответа человека.
   Запомни ключ из строки `ТК:`. Дальше `<ключ>` - он. Строка `ТЕСТОВ НЕСКОЛЬКО:` -> покажи список и спроси одной строкой «Какой тест взять?», запусти снова с `--method <имя>` (код) или `--name <имя>` (Allure).
   Строка `ИСТОЧНИК: log` или `ИСТОЧНИК: code` - шаги восстановлены скриптом: покажи таблицу шагов из `TC.md` и спроси «Шаги восстановлены верно? Да / номер шага и как исправить». Исправь в `TC.md` только названные строки и иди дальше. В режиме OpenSpec этот вопрос даёт `os_work.py next` (ДЕЙСТВИЕ `подтверждение шагов`), «да» записывает `os_work.py steps-ok <имя изменения>`.
1б. Опись артефактов - запросы, заголовки, тела и SQL из лога и Allure (файл источника ТК берётся
   сам; добавь файлы и каталоги, которые человек дал сверх него):
   ```
   python3 .gigacode/skills/de-pvatf-autotest-plan/scripts/artifacts.py scan <ключ> [<файл или каталог> ...]
   ```
   Строка `РАЗБОР АГЕНТОМ: нужен` -> задание агенту:
   ```
   python3 .gigacode/skills/de-pvatf-autotest-plan/scripts/artifacts.py task <ключ>
   ```
   Вывод после строки «ЗАДАНИЕ для агента pvatf-artifacts» передай агенту `pvatf-artifacts`
   дословно (по имени; агента нет - обычный сабагент по правилу 7 `references/autotest-rules.md`).
   Сам разбор не делай. После ответа:
   ```
   python3 .gigacode/skills/de-pvatf-autotest-plan/scripts/artifacts.py merge <ключ>
   ```
   Строки `ОШИБКА` -> то же задание агенту ещё раз, к нему - строки `ОШИБКА`; не больше 2 кругов,
   потом покажи ошибки человеку и закончи. `РАЗБОР АГЕНТОМ: не нужен` -> дальше.
1в. Архитектура тестов. Строка `ПРОЕКТ: ... стиль шагов steps` или `flow` в выводе de-pvatf-env-check, или

   Сам не выбирай; пустой ответ - переспроси один раз, снова пусто - `steps`.
2. Проверка ТК:
   ```
   python3 .gigacode/skills/de-pvatf-autotest-plan/scripts/tc_check.py <ключ>
   ```
   Правила оценки и что значит каждая находка - `references/tc-rules.md`.
3. `СТАТУС: FAIL` -> покажи человеку все строки `НАХОДКА ... БЛОКИРУЕТ` и рекомендации по
   `references/tc-rules.md` (колонка «Как исправить ТК»), план не строй, закончи. Просили
   только оценку - покажи итог по шаблону и закончи. Находки TC-14 и TC-15 (тэги ТК) не блокируют:
   покажи их в строке «Тэги ТК» ответа с рекомендацией из `references/tc-rules.md` и иди дальше.
4. Черновик плана:

   ```
   python3 .gigacode/skills/de-pvatf-autotest-plan/scripts/tc_plan.py build <ключ>
   ```

   Строка `АРХИТЕКТУРА: не выбрана` -> шаг 1в. Строка `АРТЕФАКТЫ: разбор агентом не закончен` -> шаг 1б.

4б. Знакомство с технологиями ТК - до разделов 11-14 плана. Модель не знает слов фрейма, поэтому
   по каждой технологии скрипт даёт обзорный вопрос в документацию (один раз на проект), потом
   сбор документации под план - всё, что нужно шагам ТК (запросы, заголовки, тела, проверки, ожидания,
   передача значений), и образцы из проекта-примера `platform-v-at-maven-draft` (его скрипт ищет на

   ```
   python3 .gigacode/skills/de-pvatf-autotest-plan/scripts/intro.py todo <ключ>
   ```

   - `docs-task <метка>` -> вывод после строки «ЗАДАНИЕ для агента pvatf-docs» передай агенту
     `pvatf-docs` дословно; ответ `ЗАПИСАНО` -> `notes.py merge <метка> doc-notes` (правило 2
     `references/autotest-rules.md`);
   - `collect-task <ключ> <метка>` -> то же: вывод после строки «ЗАДАНИЕ для агента pvatf-docs» -
     агенту `pvatf-docs` дословно, потом `notes.py merge <метка> doc-notes`. Потребности (до 5 в
     задании) скрипт берёт из плана сам; уже найденное в конспекте он не выдаёт;
   - `examples-task <метка>` -> вывод после строки «ЗАДАНИЕ для агента pvatf-examples» передай агенту
     `pvatf-examples` дословно; его ответ целиком, без правок, запиши инструментом записи файлов в
     файл из строки `ПОСЛЕ ОТВЕТА`, потом `intro.py examples-check <метка>`. `ОШИБКА` -> строка
     `ДАЛЬШЕ` этого вывода.
   Потом снова `intro.py todo <ключ>`, пока не будет `ЗНАКОМСТВО: готово` (код 0). Строка
   `ДРАФТА НЕТ` -> передай человеку совет из неё одной строкой и иди дальше, ответа не жди.
   Человек написал «драфт установлен» -> `intro.py draft --again`; дал путь -> `intro.py draft

   Строка `ПРОЕКТ: <метка> - в проекте уже свои классы на фрейме (...)` - для этой технологии
   проект уже пишет на фрейме в своей архитектуре (классы шагов или флоу; классы настройки

   раскладку разделов 11-12 (классы шагов, методы, параметры) бери из этих классов проекта, а не

     драфта -> нужно: дополнить `PaymentSteps` или новый класс рядом, устроенный так же.
   - нельзя: задать агенту `pvatf-docs` свой вопрос «как сделать GET-запрос» -> нужно: задание из

   кандидатов и строку `ДАЛЬШЕ` с командой: выполни её (она пишет `package`, `test_file` и пути

     исправь строку раздела 11-14, из которой она взята: 15-16 пишет validate, руками их не правь.
   - нельзя: подтвердить план самому, пропустить вопрос -> нужно: `approve` только после «да» человека.

   - нельзя: человек согласился на правку («да, фильтр STATUS = 1») -> сразу `approve` -> нужно: после
     правки и validate - вопрос из строки `ПОДТВЕРЖДЕНИЕ`, `approve` только после ответа «да» на него.

## Контракт «вход -> выход»

Вход: путь к артефакту (файл ТК, Allure, лог, код автотеста) или ключ ТК в Zephyr; необязательно - ключ, тест-метод, имя теста.

Ключ без файла -> `zephyr.json` (или `zephyr.md`) - ответ `zephyr_get_testcase` без правок.

Выход в `openspec/changes/<имя>/outputs/`:
- `TC.md` - тест-кейс в едином виде (пишет tc_convert.py; sid, токены, пароли - `***`);
- `ARTIFACTS.md` - опись запросов и SQL из артефактов, связи шагов, служебные шаги, значения из
  выборки (пишет artifacts.py; `ARTIFACTS-REVIEW.md` - ответ агента pvatf-artifacts), тела - `artifacts/`;
- `TC-CHECK.md` - оценка ТК (пишет tc_check.py);
- общее для проекта, в `openspec/pvatf/` (шаг 4б, пишет intro.py и агенты; один раз на технологию):
