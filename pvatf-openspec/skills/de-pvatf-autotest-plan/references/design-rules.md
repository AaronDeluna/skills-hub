# Разделы 11-16 плана: что, куда и как

План (`design.md`) - договор. По нему пишется код, и `at_tools check` сверяет код с ним: файл,
метод или проверка не из плана - находка. Поэтому всё решается здесь, до кода, и человек это
подтверждает. Черновик строит `tc_plan.py build`. Клетки `ЗАПОЛНИТЬ` дописываешь ты по правилам
ниже. Остальные клетки не трогаешь. `validate` не пропускает план, пока в разделах 11-14 есть
`ЗАПОЛНИТЬ`.

Пакеты - правило 13 `autotest-rules.md`: тест - `<корень>.tests`, классы шагов - `<корень>.steps`,
данные - `<корень>.data`, конфигурация - `<корень>.config` (`.config.services` - настройки
сервисов). `<корень>` - пакет тестов из шапки без `.tests`.

## 11. Файлы

Одна строка - один файл, который появится или изменится. Действие:

| Действие | Когда |
|----------|-------|
| `создать` | файла нет, его пишет генерация |
| `дополнить` | класс проекта из раздела 6 подходит по технологии и предметной области - в него добавляются методы |
| `не трогать` | файл нужен тесту, но не меняется |
| `скрипт` | файл пишет скрипт набора (`perfeccionista.properties` - `env_props.py ensure`) |
| `de-pvatf-env-check` | файл настраивает de-pvatf-env-check (класс конфигурации окружения, регистрация сервисов) |

- Строка `<путь>/ЗАПОЛНИТЬ.java` -> имя нового класса шагов по предметной области шага,
  латиницей, без транслита: `JsonResponseFlow` (flow), `PaymentSteps` (steps).
  - нельзя: `Pvatf3783Steps`, `OplataSteps`, класс в `<корень>.tests.config` -> нужно:
    `src/test/java/ru/sber/qa/steps/JsonResponseFlow.java`.
- Строка «дополнить ... или ЗАПОЛНИТЬ» -> класс из раздела 6 подходит - удали «или ЗАПОЛНИТЬ...»;
  не подходит - замени путь на новый класс, действие `создать`.
- Файлов сверх таблицы не добавляй, если для них нет шага ТК. Конфигурация «на всякий случай»,
  второй класс настроек, свой интерфейс конфигурации - нельзя.

## 12. Методы шагов

Одна строка - один public-метод класса шагов. Класс - имя файла из раздела 11 без `.java`.

- Метод - имя Java с маленькой буквы, по действию: `postJsonResponse`, `selectAccount`.
- Шаги ТК - все шаги G, которые делает этот метод. Один метод может делать запрос и проверки
  его ответа (шаги 1, 2, 3).
- Параметры - через `;`: `<имя> <Тип> - откуда`. Откуда: `тест` (значение из тест-класса, в
  том числе ожидаемое значение ТК), `настройки <ключ>` (раздел 14), `шаг <n>` (переменная шага),
  `файл <путь>` (тело запроса из раздела 11). Параметров нет - `нет`.
  - нельзя: `host String` без источника, ожидаемое значение константой внутри класса шагов ->
    нужно: `host String - настройки test.sbermock.url; expectedCode BigDecimal - тест`.
- **Как на фрейме** - как метод сделает своё дело на фрейме: какие классы и методы фрейма он
  вызывает по порядку, как читает настройку, каким matcher-ом в `.should(...)` проверяет каждую
  проверку раздела 13 этого метода. Пиши по записям конспекта (обзор технологии и сбор под план,
  шаг 4б скилла), образцу `examples/<метка>.md` и классам проекта (строка `ПРОЕКТ` - только по
  ним). Генератор пишет код ровно этими вызовами - это и есть реализация.
  - нельзя: «отправить запрос и проверить ответ» (без имён), `RestAssured.given()` из памяти ->
    нужно: «`RestService` -> `restClient()` -> POST на `host` с телом из файла; статус -
    `HttpStatusMatcher` в `.should(...)`; поле `code` - `JsonMatchers.jsonPath(...)`».
- **Основание** - откуда взяты имена «Как на фрейме», через `;`: запись конспекта `D-rest-4`,
  образец `examples/rest.md вопрос 2`, класс проекта `PaymentSteps` или путь `.java`. `validate`
  ищет каждое имя фрейма из «Как на фрейме» в тексте основания и выдаёт ПРОБЛЕМА на имя, которого
  там нет. Имени нет ни в конспекте, ни в образце, ни в проекте -> не придумывай: задай вопрос
  документации (правило 2-3 `references/autotest-rules.md`), потом заполни.
  - нельзя: основание «документация» или «-» -> нужно: `D-rest-4; examples/rest.md вопрос 3`.

## 13. Проверки

Одна строка - одна проверка в коде. Черновик даёт строку на каждый шаг с ожидаемым результатом;
шаг проверяет 3 поля -> 3 строки с одним номером шага.

| Колонка | Что писать |
|---------|-----------|
| Объект | что проверяется: `ответ шага 1`, `строка выборки шага 4` |
| Поле | путь поля как в ответе: `code`, `result.locked`, `rqUid`; для кода HTTP - `status` |
| Как | одно из: `равно`, `не равно`, `содержит`, `ключ есть`, `ключа нет`, `не пусто`, `пусто`, `статус`, `больше`, `меньше`, `в диапазоне`, `по шаблону`, `проверено в шаге <n>` |
| Ожидаемое | константа раздела 4 (`EXPECTED_RESULT_CODE`), переменная раздела 5 или 10, значение в кавычках (`"*/*"`), `-` для «ключ есть / ключа нет / не пусто / пусто» |

- Одно поле одного объекта - одна строка. Шаг ТК проверяет то же поле ещё раз -> `Как` =
  `проверено в шаге <n>`, кода нет.
  - нельзя: `code` `равно` `EXPECTED_RESULT_CODE` и `code` `не равно` `"0"` -> нужно: одна строка
    `равно`, вторая - `проверено в шаге 1`.
- Ожидаемое значение ТК - константа раздела 4 в тест-классе, в метод шага приходит параметром.
- Время (дата создания, время вызова) - `в диапазоне`, ожидаемое - `<время запроса шага n> ± <допуск>`:
  допуск из ТК (`±1 минута`), в ТК его нет - 1 минута (`MR-53`).
  - нельзя: `DATE_CR` `содержит` `"yyyy-MM-dd HH:mm времени вызова шага 6"` -> нужно: `DATE_CR`
    `в диапазоне` `время вызова шага 6 ± 1 минута`.

## 14. Настройки

Одна строка - один ключ своего файла настроек (адрес, логин - то, что не пишется в код).

- Ключ - латиницей через точку: `test.sbermock.url`. Не `perfeccionista.*`, не `session.*`.
- Файл - файл из раздела 11 (`src/test/resources/test.properties`), не `perfeccionista.properties`.
- Кто читает - класс и способ из проекта или конспекта: `TestConfig (owner)`.
- Основание - откуда этот способ, как в разделе 12: `D-env-3`, `examples/rest.md вопрос 4`, класс
  проекта. `validate` проверяет имена из «Кто читает» по основанию так же.
- sid, токены, пароли - не в настройки: sid - из шага сессии теста.

## 14а. Реализация по G

Таблицы 11-14 говорят, ЧТО будет в коде. Раздел 14а - текст: что делает каждая G, как это
делается на фрейме и почему так. Это этап придумывания: всё решается здесь, генератор потом
только пишет код по этому тексту и своего не придумывает. Шаблон блока на каждую G пишет `build`
(старый план - `validate`), ты заполняешь все `ЗАПОЛНИТЬ`. Прочитай перед этим обзор технологии,
записи сбора под план (`notes.py find <метка> <слова>`), образцы `examples/<метка>.md` и классы
проекта из раздела 6.

```
### G-1 · шаги 1, 2, 3
- Что делает: создаёт платёж запросом POST и проверяет ответ (шаги 1-3 ТК)
- Где: дополнить PaymentSteps (класс проекта, REST этой области уже там), метод createPayment
- Как на фрейме:
  1. адрес сервиса - TestConfig.paymentUrl() (owner) [D-rest-7]
  2. RestService -> restClient() -> post(host) с телом из testdata/1-body.json [D-rest-4; examples/rest.md вопрос 2]
  3. статус ответа - HttpStatusMatcher в .should(...), ожидаемое - параметр expectedStatus [D-rest-5]
  4. поле code - JsonMatchers.jsonPath("code") в .should(...) [D-rest-6]
  5. вернуть id из ответа - переменная paymentId для шага 4 [D-rest-8]
- Почему так: PaymentSteps уже делает REST этой области - новый класс не нужен; адрес - из
  настроек (в коде адрес запрещён, MR-15); ожидаемые значения - константы теста, в метод приходят
  параметрами (раздел 12)
- Чего не делать: RestAssured напрямую, assertEquals, Thread.sleep, адрес строкой в коде
```

- Каждое поле - про эту G и этот ТК, без общих слов.
  - нельзя: «Что делает: выполняет шаги» -> нужно: «создаёт платёж запросом POST и проверяет ответ».
- «Где» - класс и метод из разделов 11-12 (`validate` проверяет, что класс G назван).
- «Как на фрейме» - пункты по порядку, как пойдут строки кода: настройка, вызов, проверки, что
  метод возвращает. Каждый пункт кончается `[основание]`: `D-<tech>-<n>`, `examples/<метка>.md
  вопрос <n>` или класс проекта. `validate` ищет каждое имя фрейма пункта в основании - имени нет
  -> ПРОБЛЕМА. Нет имени нигде - вопрос документации (правило 2-3 `references/autotest-rules.md`),
  не придумывай.
  - нельзя: «2. отправить запрос [документация]» -> нужно: «2. RestService -> restClient() ->
    post(host) [D-rest-4]».
- «Почему так» - решения: класс проекта или новый, откуда значения (тест, настройки, шаг), почему
  этот способ проверки. Строка `ПРОЕКТ` знакомства -> так, как в классах проекта.
- «Чего не делать» - что из правил набора здесь особенно легко нарушить (RestAssured напрямую,
  assert, sleep, адрес в коде, DTO ответа).
- Пункты 14а и колонка «Как на фрейме» раздела 12 - одно и то же решение: пиши их согласованно.
