# Настройка окружения (режим setup)

Часть скилла `env-check`. Открывай, только когда SKILL.md направил сюда.

Правило одно: что и как подключать - только из документации фрейма (агент `pvatf-docs`) или
из проекта-примера (агент `pvatf-examples`, если человек дал путь к драфту). Имена
зависимостей, классов, ключей по памяти не пишешь. Нельзя: «добавлю ru.sber.qa:allure2 с версией,
которую помню, так обычно». Нужно: «D-env-2: зависимость `<group:artifact>` из ответа pvatf-docs, версия -
`${<свойство версии фрейма из ENV.json>}`».

## 3. Правки

**Версия фрейма - из строки `САМАЯ НОВАЯ`, а если её нет - из ответа человека.** Число берёшь
из строки `САМАЯ НОВАЯ` сводки env_check.py. Её считает скрипт: по ответу MCP `get_pvat_release_notes`, а если MCP недоступен
(`--offline`) - по тегам скачанных исходников фрейма, потом по сборке проекта-примера (пометка
«без MCP» в строке). Сам версию не ищешь: из ответа `pvatf-docs`, из примеров документации,
из файлов проекта-примера, открытых вручную, и по памяти не берёшь - проект-пример читает скрипт.
- В сборке есть свойство версии фрейма (строка `ВЕРСИЯ`) -> зависимости фрейма ссылаются на него, число не меняешь
  (обновление - только `env-update`). Исключение - `FRAME_VERSION_UNKNOWN`: такой версии нет, значение -> `САМАЯ НОВАЯ`.
- Строк `ВЕРСИЯ` нет (новый проект, каркас `init`) -> заведи в `<properties>` свойство `pvat.version` со значением
  из строки `САМАЯ НОВАЯ`, все зависимости фрейма (и BOM фрейма, если он есть в ответе документации) - `${pvat.version}`.
- Строки `САМАЯ НОВАЯ` нет или там `-` (release notes не получены) -> зависимости фрейма не подключай, спроси человека одной строкой: «Какую версию фрейма PVATF подключить? release notes не получены: <ошибка>».
  Ответ - номер версии -> он и есть значение `pvat.version` (как строка `САМАЯ НОВАЯ`), запиши в `ENV-SETUP.md`
  «версия фрейма - от человека».

Нельзя: в `<pvat.version>` число из примера документации, из файла проекта-примера, открытого вручную, или по памяти.
Нужно: `<pvat.version><число из строки САМАЯ НОВАЯ></pvat.version>` - число переносишь из сводки
дословно, сам не придумываешь и не округляешь.

**Логирование - `LOGGING_MISSING`.** На фрейме логирование - простой логгер SLF4J: две
зависимости и один файл. Делаешь сам, без вопроса документации, ровно то, что в строке
`ПРОБЛЕМА` (чего нет - то и добавляешь, остальное не трогаешь):
- нет `slf4j-simple` / `slf4j-api` -> в `pom.xml` (в `<dependencies>`) ДОСЛОВНО
  ```xml
  <!-- Logger -->
  <dependency>
      <groupId>org.slf4j</groupId>
      <artifactId>slf4j-simple</artifactId>
      <version>${log.version}</version>
  </dependency>
  <dependency>
      <groupId>org.slf4j</groupId>
      <artifactId>slf4j-api</artifactId>
      <version>${log.version}</version>
  </dependency>
  ```
  и свойство `<log.version>2.0.16</log.version>` в `<properties>` (в проекте-примере или в
  конспекте `doc-notes/env.md` версия другая - бери оттуда). Gradle - те же две зависимости
  `org.slf4j:slf4j-simple` и `org.slf4j:slf4j-api` с одной переменной версии. Одна из двух уже
  есть - добавь вторую с той же версией.
- нет `simplelogger.properties` (в строке путь `<модуль>/src/test/resources/simplelogger.properties`) -> создай
  файл ровно по этому пути, в каждом модуле из строки
  ДОСЛОВНО, шесть строк:
  ```
  org.slf4j.simpleLogger.defaultLogLevel=INFO
  org.slf4j.simpleLogger.showShortLogName=true
  org.slf4j.simpleLogger.showDateTime=true
  org.slf4j.simpleLogger.dateTimeFormat=HH:mm:ss:SSS
  org.slf4j.simpleLogger.logFile=System.out

  #org.slf4j.simpleLogger.log.ru.sber.at=INFO
  ```
  (в проекте-примере файл выглядит иначе - бери оттуда).
Конфигурацию и зависимости другого логгера (`logback`, `log4j`) не добавляешь. Запросы и
ответы REST в консоль и в Allure пишет класс настройки REST (рецепт «Allure для REST» ниже) -
логгер и фильтры в код тестов не добавляешь.

**Allure для REST - `REST_ALLURE_MISSING` или строка `НУЖНО: allure-rest`.** Без этого класса
запросы и ответы REST не попадают ни в отчёт Allure, ни в консоль. Делаешь сам, ДОСЛОВНО (так в
проекте-примере фрейма):
```java
package <пакет>;

<импорты>

public class Allure2RestServiceConfiguration extends DefaultRestServiceConfiguration {

    @Override
    public RequestSpecification requestSpecification() {
        return super.requestSpecification()
                .filter(new AllureRestAssured())
                .filter(new RequestResponseConsoleLoggingFilter(Level.WARN));
    }
}
```
- `<пакет>`: новый проект - `<корень пакетов>.config.services`; существующий - пакет, где уже лежат
  другие `*ServiceConfiguration` проекта, их нет - подпакет `services` рядом с пакетом класса
  конфигурации окружения;
- `<импорты>`: `RequestSpecification` - `io.restassured.specification.RequestSpecification`,
  `AllureRestAssured` - `io.qameta.allure.restassured.AllureRestAssured`; пакеты
  `DefaultRestServiceConfiguration`, `RequestResponseConsoleLoggingFilter` и `Level` - из ответа
  `pvatf-docs` (вопрос - таблица раздела 1), по памяти не пишешь;
- регистрация: в `getServiceConfigurations()` у `RestService` класс настройки - этот:
  `.put(ConfiguredServiceHolder.of(RestService.class, new Allure2RestServiceConfiguration()))`.
  `RestService` уже зарегистрирован с другим классом -> меняешь только класс настройки в этой
  строке, остальное в строке (например `.setOrder(-10)`) не трогаешь;
- компиляция падает на `AllureRestAssured` -> в сборке нет `allure-rest-assured`: вопрос `pvatf-docs`
  «Как подключить allure-rest-assured к проекту на фрейме: groupId, artifactId, версия».

Нельзя: зарегистрировать `RestService` с `DefaultRestServiceConfiguration` и закончить - запросы не
видны в Allure. Нельзя: добавить `.filter(new AllureRestAssured())` в шаги или тесты. Нужно: один
класс `Allure2RestServiceConfiguration` по рецепту и регистрация `RestService` с ним.

По одной правке на проблему, только в файлах сборки и конфигурации. Исключение -
`TEST_ROOT_MISSING`: создай каталог `src/test/java` в модуле, где лежит файл сборки с
зависимостями фрейма (`mkdir -p <модуль>/src/test/java`), других правок по ней не делай:
- зависимость - в тот же `pom.xml` / `build.gradle(.kts)`, где уже стоят зависимости фрейма;
  версия зависимости фрейма - ссылка на свойство версии фрейма (строка `ВЕРСИЯ` из сводки), не число;
  зависимости логгера (`slf4j-*`) - `${log.version}` по рецепту «Логирование» выше;
- класс конфигурации - в `<корень пакетов>.config` (строка «Корень пакетов» в `ENV-INIT.md`, правило 13
  `autotest-rules.md`); `ENV-INIT.md` нет - базовый пакет тестов из строки `ПРОЕКТ`, подпакет `config`;
- `perfeccionista.properties` - в `src/test/resources/` модуля с тестами.

Ответ документации «НЕТ В ДОКЕ» или «найден частично» без нужного имени -> правку не делай.

### 5.2 Правки

| Что | Куда | Как |
|-----|------|-----|
| модуль, драйвер, allure-junit5 | файл сборки, где стоят зависимости фрейма | модуль фрейма - версия ссылкой на свойство версии фрейма (или без версии, если стоит BOM фрейма), правило версии - раздел 3; драйвер и allure-junit5 - версия из ответа. Версии нет в ответе -> спроси человека одной строкой версию драйвера |
| класс настройки сервиса | берёшь класс настройки из ответа как есть; свой класс создаёшь, только если ответ показывает свой класс-наследник, - в пакет, где лежит существующий `*EnvironmentConfiguration` (новый проект - `<корень пакетов>.config`) | имя и родитель - из ответа |
| регистрация | метод `getServiceConfigurations()` существующего `*EnvironmentConfiguration` - там, где он лежит, класс не переносишь (правило 13 `autotest-rules.md`); класса нет - создаёшь в `<корень пакетов>.config` | одна строка `.put(ConfiguredServiceHolder.of(<Сервис>.class, new <класс настройки>()))` на сервис, как в ответе; уже зарегистрированные сервисы не трогаешь |
| значения | `src/test/resources/perfeccionista.properties` | ключ из ответа, значение из строки `НУЖНО` дословно |

Нельзя: придумать регистрацию по памяти (`services()`, `.register(...)`, `ServicesConfiguration.builder()` -
такого API во фрейме нет) или оставить класс конфигурации без нового сервиса - строка `сервис` останется.
Нельзя: ключ `auth.url=http://localhost:8081;` - точка с запятой из ТК в значение не попадает (скрипт
печатает значение уже без неё). Нужно - дописать в цепочку `getServiceConfigurations()` строки по ответу:
```java
@Override
public @NotNull ServiceConfigurationManager getServiceConfigurations() {
    return super.getServiceConfigurations()      // начало цепочки - как уже стоит в классе, не меняешь
            // ... сервисы, которые уже были, - без изменений
            .put(ConfiguredServiceHolder.of(<сервис REST из ответа>.class, new <класс настройки REST из ответа>()))
            .put(ConfiguredServiceHolder.of(<сервис БД из ответа>.class, new <класс настройки БД из ответа>()));
}
```
Имена в угловых скобках - из ответа `pvatf-docs`, по памяти не пишешь. Ответ показывает другую форму
регистрации -> делаешь по ответу, пример выше не повторяешь. Значения - в `perfeccionista.properties`:
ключи из ответа `pvatf-docs`, значения из строк `НУЖНО`.

Каждая правка - строка в `ENV-SETUP.md` (шаблон раздела 4), в колонке «Проблема» - `НУЖНО <что> · <чего>`.
