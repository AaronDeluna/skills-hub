# Общие правила окружения и генерации автотестов

Действуют в скиллах `de-pvatf-env-check`, `de-pvatf-env-update`, `de-pvatf-autotest-plan`, `de-pvatf-autotest-gen`, `de-pvatf-autotest-review`, `de-pvatf-dependency-review`. Прочитай этот
файл целиком в начале работы скилла. В SKILL.md - только то, что касается одного скилла; при
расхождении прав этот файл.

1. **О фрейме знаешь только то, что есть в документации.** Источники по порядку: конспект
   `openspec/pvatf/doc-notes/` -> документация MCP через агента `pvatf-docs` -> проект-пример
   через агента `pvatf-examples` (путь даёт человек или `intro.py draft` скилла `de-pvatf-autotest-plan` -
   поиск каталога `platform-v-at-maven-draft` на диске) -> код самого проекта
   (как там уже сделано) -> место не делается и записывается в отчёт. `get_pv_at_doc` сам не
   вызываешь. `get_pvat_release_notes`, `get_pvat_changelog` и Jira `zephyr_get_testcase` вызываешь сам (таймаут 120
   секунд; таймаут или ошибка -> повтори 1 раз, снова -> поступай как при ошибке инструмента
   по таблице ошибок скилла), ответ сразу сохраняешь в файл дословно. ЗАПРЕЩЕНО: открывать `.jar`, лазить в `~/.m2`, `.gradle`,
   кэши IDE, запускать `javap`, искать в интернете, писать «по памяти» и «по аналогии».
   Нельзя: «`KafkaService.producerClient()` - так обычно делают». Нужно: «`D-kafka-2`:
   `KafkaService.producerClient()`».
2. **Перед вопросом документации - конспект.**
   `python3 .gigacode/skills/<скилл>/scripts/notes.py find <tech> <2-4 слова>`. Запись со
   статусом `найден` отвечает на вопрос - вопрос не задаёшь. Ответ `pvatf-docs` пишет в файл
   сам и к тебе не приходит, в конспект его переносит скрипт:
   1. До запуска агента: `python3 .gigacode/skills/<скилл>/scripts/notes.py task <tech> doc-notes` -
      две строки вывода впиши в конец задания (правило 3) дословно.
   2. Агент вернул `ЗАПИСАНО: ...` -> `python3 .gigacode/skills/<скилл>/scripts/notes.py merge <tech> doc-notes`
      (таймаут 60 секунд). Код 0, строка `ОК: ...` - записи в `openspec/pvatf/doc-notes/<tech>.md`,
      ID и статусы в этой строке; текст записи - `notes.py show <ID>`. Код 1 - запусти агента
      ещё раз с тем же заданием и строкой `- Прошлый файл не прошёл проверку: <строки ошибок>`,
      снова `merge`; снова 1 -> вопросы считай `НЕТ В ДОКЕ`.
   3. Агент вернул блоки текстом -> запусти его ещё раз со строкой «Ответ - в файл из строки
      «Записать в», в ответе одна строка ЗАПИСАНО».
   Нельзя: переписать ответ агента в конспект правкой файла. Нужно: `notes.py merge`.
   Одновременно - не больше одного агента на технологию.
3. **Задание агенту `pvatf-docs` - только по этому шаблону, не больше 5 вопросов:**
   ```
   - Технология: <метка> · <обычное название>
   - Раздел документации: <название раздела или «нет в списке»>
   - Вопросы:
     1. <вопрос с именами: что сделать, каким классом фрейма>
   - Якорь технологии: <класс-якорь из таблицы ниже или «нет»>
   (задания знакомства и сбора под план пишет `intro.py` скилла `de-pvatf-autotest-plan`; в них есть ещё строки
   «Режим» и «Обзор технологии» - передаёшь их как есть)
   - Ключевые слова из прошлых ответов документации: <раздел «Ключевые слова документации» конспекта или «нет»>
   - Формулировки, которые уже пробовали и они НИЧЕГО не дали: <из конспекта или «нет»>
   - Уже есть в конспекте: <ID и вопросы или «нет»>
   - Артефакт: <«Лог: ...», «Код: ...», «ТК: ...» или «нет»>
   - Записать в: <первая строка вывода notes.py task>
   - Номер первой записи: <вторая строка вывода notes.py task>
   ```
   Артефакт - текст, по которому агент ищет документацию напрямую (`retrieve_doc_by_*`), не больше 40
   строк: `de-pvatf-env-update` - строки ошибок компиляции (`Лог:`); `de-pvatf-autotest-gen` - строки шагов этого G
   из раздела 2 `design.md` (`ТК:`); `de-pvatf-autotest-review` - метод теста с находкой (`Код:`). Остальные - «нет».
   Якорь - класс, который уже встречался в примерах генерации набора; не знаешь - «нет»
   (агент тогда начнёт с названия раздела).

   | Метка | Раздел документации | Якорь |
   |-------|---------------------|-------|
   | `env` | Быстрый старт | environment-junit5 |
   | `rest` | Работа с Rest API | RestService |
   | `websocket` | Работа с WebSocket | WebSocketService |
   | `grpc` / `graphql` | Работа с gRPC / Работа с GraphQL | нет |
   | `db` | Работа с Базами Данных | DatabaseService |
   | `opensearch` | Работа с OpenSearch/ElasticSearch | OpenSearchService |
   | `kafka` | Работа с Kafka | KafkaService |
   | `ui` | Работа с UI Playwright / Работа с UI Selenide | нет |
   | `mobile` | Работа с Appium Android / Работа с Appium iOS | AndroidPage |
   | `audit` / `journals` / `abyss` / `metrics` | Работа с Единым Аудитом / Журналами ЕФС и ППРБ / PVM-ABYSS / хранилищем метрик | AuditFlow / JournalFlow / нет / MetricsFlow |
   | `fixtures` / `testcontainers` / `sbermock` / `toggler` / `launcher` | Сервис для работы с Fixtures / Работа с TestContainers / Работа с SberMock / Работа с Toggler / Работа с Launcher | FixtureService / ContainerService / SberMockService / TogglerService / LauncherService |
   | `timeouts` / `openshift` / `dataconverter` | Сервис для работы с Таймаутами / Работа с OpenShift и Kubernetes / Работа с DataConverter | нет / нет / DataConverterService |
   | `value` / `sessions` / `invocation` | ValueService / Работа с Сессиями / Работа с Invocation | ValueService / нет / нет |
4. **Память - это файлы, а не чат.** Состояние окружения - `openspec/pvatf/env/ENV*.md`,
   `ENV.json`; генерации - `openspec/changes/<имя>/outputs/`. Результат этапа сразу пиши в
   файл, потом следующий этап. Сомневаешься, где ты, - файл главнее памяти.
5. **Делаешь только своё.** Меняешь только файлы, которые называет этап. Увидел другое, что
   надо поправить, - строка в отчёт («Осталось человеку»), не правка.
6. **Код по правилам набора.** Слои: тест -> шаги предметной области -> базовый слой
   технологии -> фрейм. Проверки - matchers фрейма в `.should(...)`, без JUnit `assert*`,
   AssertJ, `Thread.sleep`, `var`, своих matchers, DTO ответа и вспомогательных методов в
   тест-классе. Значения подключения (адреса, логины, токены) в коде не пишутся - только
   ключи настроек. Самопроверка кода - скрипт этапа, а не «посмотрел - вроде нормально».
7. **Сабагентов запускает работающий скилл** по готовым заданиям из своих `references/`.
   Ответ не по шаблону агента не используется: перезапусти агента 1 раз, снова не по
   шаблону - место не делается, причина в отчёт. Агенты набора лежат в `.gigacode/agents/`
   (папка `agents/` набора); запуск - по имени. Режим `fork` не используешь. Агента с таким
   именем инструмент не знает -> обычный сабагент, первая строка задания: «Прочитай файл
   .gigacode/agents/<имя>.md - текст после второй строки --- это твоя инструкция, выполняй
   её.», дальше то же задание.
8. **Вопросы человеку - только там, где скилл прямо пишет «спроси человека».** Ответа нет -
   остановись, состояние в файле не меняй.
9. **Каждый внешний вызов - с таймаутом.** Шелл-команда - не дольше 600 секунд: больше
   инструмент не даёт. Скрипты набора сами ограничивают сборку 540 секундами; вывели
   `COMPILE_TIMEOUT`, `ТАЙМАУТ` или `timeout` при сборке - повтори ту же команду, не больше 2
   повторов: Maven и Gradle продолжат со скачанного. Своих команд дольше 600 секунд не
   запускаешь. MCP - ответ не пришёл за 120 секунд: повтори 1 раз, потом ошибка по таблице скилла.
10. **Git.** Коммиты, `push`, PR - только по прямой просьбе человека. В конце работы покажи,
    какие файлы изменены (`git status --short`).
11. **Язык.** Пиши на русском, короткий дефис `-`. ID (`TC-...`, `G-3`, `D-rest-2`) и статусы
    (`planned`, `done`, `ok`, `stub`) - латиницей. С человеком - на «вы», коротко.
12. **Настройки агента и секреты не читаешь.** Твоя работа - файлы проекта и файлы набора.
    ЗАПРЕЩЕНО открывать, выводить (`cat`, `head`, `grep`) и пересказывать: настройки агента
    (`~/.gigacode/`, `~/.qwen/`, `.gigacode/settings.json`, `.qwen/settings.json`, любые
    `settings.json` вне проекта), файлы с ключами и паролями (`.env`, `*.env`,
    `secret*.properties`, `credentials*`, `~/.ssh/`, `~/.m2/settings*.xml`,
    `~/.gradle/gradle.properties`), переменные окружения целиком (`env`, `printenv`, `set`).
    Сюда же - каталоги агентов вне `.gigacode/agents/` и `~/.gigacode/agents/`.
    - нельзя: «MCP недоступен - посмотрю `cat ~/.qwen/settings.json`, как он подключён» ->
      нужно: «MCP недоступен» - поступай по таблице ошибок скилла (стоп или вопрос человеку),
      настройку подключения делает человек.
    - нельзя: `grep -rn password .` по проекту -> нужно: имя настройки берёшь из файла,
      который называет шаг (`application.properties`, `ENV.json`); значение секрета не выводишь.
    - нельзя: `printenv | grep TOKEN` -> нужно: проверить, что переменная задана:
      `test -n "$ИМЯ" && echo задана || echo нет`.
    Случайно увидел ключ, токен или пароль - не повторяй его в чате, в файлах и в заданиях
    сабагентам.
13. **Пакеты проекта.** В новом проекте (есть `ENV-INIT.md`) все классы лежат под одним корнем -
    строка «Корень пакетов» в `ENV-INIT.md` (по умолчанию `ru.sber.<имя проекта>`). В проекте со
    сборкой, но без тестов корень - «корень пакетов» в строке `ПРОЕКТ` de-pvatf-env-check
    (`<groupId>.<artifactId>` из сборки). Корень пакетов у человека не спрашиваешь.
    Всё, что пишет набор (тест-классы, классы шагов и флоу, конфигурация, `BaseTest`, данные,
    настройки), лежит только в `src/test/java` и `src/test/resources`; в `src/main` - ничего.
    Проект-пример (драфт) - источник кода, но не имени пакета и не раскладки папок.
    | Что | Пакет |
    |-----|-------|
    | `BaseTest` | `<корень>` |
    | классы конфигурации фрейма (`*EnvironmentConfiguration`, `*ServiceConfiguration`) | `<корень>.config` |
    | классы шагов предметной области (стиль `steps`) или классы-флоу (стиль `flow`) | `<корень>.steps` |
    | базовый слой технологии (`RestSteps`, `DbSteps`) | `<корень>.steps.base` |
    | эндпоинты, тела запросов, SQL, тестовые данные | `<корень>.data` |
    | тест-классы | `<корень>.tests` |
    Нельзя: тест-класс рядом с `BaseTest` в `<корень>`, конфигурация в `<корень>.tests.config`.
    Нужно: `ru.sber.demo.tests.Bnk101Test`, `ru.sber.demo.config.DemoEnvironmentConfiguration`.
    Проект уже был (нет `ENV-INIT.md`) -> пакеты как у существующих классов проекта.
    Архитектура тестов (`steps` или `flow`) - строка «Стиль шагов» в `ENV-INIT.md` или
    `openspec/pvatf/env/STYLE.md`; её выбирают один раз и дальше держат: `steps` - классы шагов,
    FlowRunner не вводится; `flow` - классы-флоу и FlowRunner. В проекте есть классы шагов или
    FlowRunner -> стиль по коду проекта. Нет ни того, ни другого, а выбора нет -> перед планом
    первого автотеста спроси человека одной строкой «Как писать тесты: steps - классы шагов, или
    flow - FlowRunner и классы-флоу?» и запиши ответ: `tc_plan.py style <ключ ТК> <steps|flow>`.
    Сам не выбирай.
    - нельзя: проект пустой, стиль не указан -> писать в `steps` «по умолчанию» -> нужно: вопрос
      человеку, ответ - в STYLE.md.
14. **Настройки проекта.** Что куда кладётся:
    | Что | Куда |
    |-----|------|
    | ключи фрейма (`perfeccionista.services.scanPackages`, `perfeccionista.datasources.scanPackages`, `perfeccionista.attachment.dir`, `session.*`) | `perfeccionista.properties` |
    | какой стенд запускать | файл выбора стенда проекта (`app.properties`) |
    | свои параметры проекта (хост сервиса, логин, алиас) | отдельный файл (`test.properties`, `<технология>.properties`) и свой класс конфигурации, который его читает - способом из конспекта |
    | токен сессии (sid), пароль | никуда: sid получают в тесте (шаг сессии), пароль - по конспекту, в файлы проекта не пишут |
    - нельзя: дописать в `perfeccionista.properties` строки `test.rm_oc.host=https://...ift...`,
      `test.rm_oc.sid=` -> нужно: хост - в свой файл настроек, стенд - в `app.properties`, sid -
      из шага сессии.
    - нельзя: читать свои ключи из `perfeccionista.properties` своим кодом
      (`FileUtils.readOptionalPropertyFileFromClasspath("perfeccionista.properties")`) -> нужно:
      свой файл и свой класс конфигурации.
    - нельзя: имя стенда в коде, константе, алиасе (`"aiv_oper_data_ift"`) -> нужно: алиас без
      стенда, стенд выбирается настройками.
    Имена файлов и ключей фрейма - только из конспекта и проекта-примера. Нет в них -> заглушка
    с вопросом человеку, ключ не придумывай.
15. **Запросы и данные из артефактов.** У `RestService` фрейма нет базового URL: это обёртка над
    RestAssured, полный адрес (хост из своих настроек + путь) передаётся в запрос.
    - нельзя: искать или придумывать ключ «базовый URL сервиса» -> нужно: хост - из своих
      настроек проекта, путь - константа, в запрос - хост + путь.
    Входные артефакты (лог, Allure) - источник запросов: метод, адрес, все заголовки, тело из
    описи `ARTIFACTS.md` (раздел 9 плана) переносятся в тест целиком; заголовок или поле тела не
    выкидывается «как неважное». Значение, которое тест получает из системы (выборка SQL, ответ
    запроса; раздел 10 плана), в коде и файлах данных - переменная шага-источника, не литерал
    прогона. Служебные шаги старой реализации (тип SERVICE: формирование заголовков и тела,
    десериализация, «объект не null») кода не получают - только комментарий шага. Одно поле
    одного ответа проверяется один раз; повтор той же проверки в ТК - комментарий «проверено в
    шаге <n>».
    - нельзя: `selectIdocAccById(38, 100010061, 134)`, когда id получены выборкой шага 1 ->
      нужно: `selectIdocAccById(accIdMega, accIdMajor, accIdMinor)` - переменные шага 1.
    Всё, чего нет в тест-кейсе и артефактах (откат данных, свои шаги), не добавляй.
