# План автотеста по тест-кейсу

Скилл запускает `orchestrator`. Ты не пишешь код теста. Твоя работа: превратить тест-кейс в
проверенный план `openspec/changes/<имя>/design.md`, по которому `autotest-gen` пишет
код. Почти всё делают скрипты; ты проверяешь только строки, которые скрипт пометил.
Сначала прочитай `references/autotest-rules.md` - общие правила окружения и генерации.

## Когда использовать / когда не использовать

| Просьба | Что делаешь |
|---------|-------------|
| «сгенерируй автотест по ТК <файл>», «разбери ТК», «напиши тест по логу / Allure» | шаги 1-8 |
| «проверь тест-кейс» (только оценка) | шаги 1-3, план не строишь |
| план уже `planned`, просят код | не этот скилл - `autotest-gen` |

## Предусловия

- Файлы работы - в каталоге изменения OpenSpec `openspec/changes/<имя>/` (`<имя>` - строка
  `ИЗМЕНЕНИЕ:` из `os_work.py next` оркестратора): артефакты `proposal.md`, `design.md`,
  `tasks.md` и рабочие файлы `outputs/`. Общее для проекта (конспект документации, `ENV.json`) -
  `openspec/pvatf/`. Пути в командах скриптов определяются сами - подставлять их не нужно.
- Артефакт от человека - один из:
  - файл ТК из TMS: `.md`, `.xml`, `.json`;
  - ключ ТК в Zephyr (`CODE-T123`) - тогда нужен MCP-инструмент Jira `zephyr_get_testcase`;
  - Allure: файл `*-result.json` или каталог `allure-results/`;
  - лог прогона: `.log`, `.txt`;
  - код автотеста на любом фреймворке: `.java`, `.kt`.
- Окружение проверено: `openspec/pvatf/env/ENV.json` со статусом `ok` или `warning`
  (проверяет `orchestrator` до запуска этого скилла).
- Агент `pvatf-artifacts` в `.gigacode/agents/` (разбор лога и Allure, шаг 1б).
- Python 3.8+ (команды `python3 ...`; на Windows, где нет `python3`, - `python ...` или `py -3 ...`).

**Скрипты лежат в `.gigacode/skills/autotest-plan/scripts/`.** Скрипта по этому пути нет ->
найди один раз: инструментом поиска файлов: файл `tc_plan.py` в каталоге проекта и в `~/.gigacode` (работает и на Windows).

## Шаги

1. Оркестратор передал ключ, и `openspec/changes/<имя>/outputs/TC.md` уже есть -> этот шаг
   пропусти. Человек дал файл (ТК, лог, Allure, код теста) -> сразу команда `tc_convert.py` ниже с
   этим файлом; Zephyr и MCP не трогай.
   - нельзя: человек дал `tst.txt` (лог) -> искать `zephyr_get_testcase` и просить выгрузку ТК ->
     нужно: `tc_convert.py tst.txt --key <ключ>`.
   Передан только ключ ТК (`CODE-T123`), файла нет -> загрузи ТК из Zephyr:
   - вызови MCP-инструмент Jira `zephyr_get_testcase` с этим ключом (имя параметра - из
     описания инструмента), таймаут 120 секунд;
   - ответ инструмента запиши инструментом записи файлов, без правок и сокращений, в
     `openspec/changes/<имя>/outputs/zephyr.json` (ответ не JSON - в `zephyr.md`);
   - дальше `<файл ТК>` - этот файл, к команде ниже добавь `--key <ключ>`.

   Перевод в единый вид:
   ```
   python3 .gigacode/skills/autotest-plan/scripts/tc_convert.py <файл ТК, лог, тест или каталог allure-results> [--key <ключ>] [--method <тест-метод>] [--name <имя теста>]
   ```
   Ключ изменения `NOTC-<n>` (оркестратор создал работу без ТК) -> спроси одной строкой «Имя тест-класса
   латиницей с окончанием Test (например PaymentLockTest)?» и запусти `tc_convert.py <файл> --key NOTC-<n>
   --class <имя>`.
   Строка `КЛЮЧА НЕТ:` -> спроси одной строкой: «Ключ ТК? Дайте ключ вида CODE-T123 или ответьте "ТК нет"».
   - ключ -> запусти снова с `--key <ключ>`;
   - «ТК нет» -> спроси одной строкой: «Имя тест-класса латиницей с окончанием Test (например PaymentLockTest)?» и
     запусти снова с `--no-tc --class <имя>`. Скрипт сам даёт служебный ключ `NOTC-<n>`; `@TmsLink` в тест не
     ставится.
   - нельзя: придумать ключ (`KARKAS-T0000`) или имя класса из ключа (`Notc1Test`), транслит (`OplataTest`) ->
     нужно: ключ и имя класса - только из ответа человека.
   Запомни ключ из строки `ТК:`. Дальше `<ключ>` - он. Строка `ТЕСТОВ НЕСКОЛЬКО:` -> покажи список и спроси одной строкой «Какой тест взять?», запусти снова с `--method <имя>` (код) или `--name <имя>` (Allure).
   Строка `ИСТОЧНИК: log` или `ИСТОЧНИК: code` - шаги восстановлены скриптом: покажи таблицу шагов из `TC.md` и спроси «Шаги восстановлены верно? Да / номер шага и как исправить». Исправь в `TC.md` только названные строки и иди дальше.
1б. Опись артефактов - запросы, заголовки, тела и SQL из лога и Allure (файл источника ТК берётся
   сам; добавь файлы и каталоги, которые человек дал сверх него):
   ```
   python3 .gigacode/skills/autotest-plan/scripts/artifacts.py scan <ключ> [<файл или каталог> ...]
   ```
   Строка `РАЗБОР АГЕНТОМ: нужен` -> задание агенту:
   ```
   python3 .gigacode/skills/autotest-plan/scripts/artifacts.py task <ключ>
   ```
   Вывод после строки «ЗАДАНИЕ для агента pvatf-artifacts» передай агенту `pvatf-artifacts`
   дословно (по имени; агента нет - обычный сабагент по правилу 7 `references/autotest-rules.md`).
   Сам разбор не делай. После ответа:
   ```
   python3 .gigacode/skills/autotest-plan/scripts/artifacts.py merge <ключ>
   ```
   Строки `ОШИБКА` -> то же задание агенту ещё раз, к нему - строки `ОШИБКА`; не больше 2 кругов,
   потом покажи ошибки человеку и закончи. `РАЗБОР АГЕНТОМ: не нужен` -> дальше.
1в. Архитектура тестов. Строка `ПРОЕКТ: ... стиль шагов steps` или `flow` в выводе env-check, или
   файл `openspec/pvatf/env/STYLE.md` есть -> дальше. Иначе спроси человека одной строкой (это
   разрешённый вопрос, ответа жди): «Как писать тесты: steps - классы шагов предметной области,
   или flow - FlowRunner и классы-флоу?». Ответ запиши:
   ```
   python3 .gigacode/skills/autotest-plan/scripts/tc_plan.py style <ключ> <steps|flow>
   ```
   Сам не выбирай; пустой ответ - переспроси один раз, снова пусто - `steps`.
2. Проверка ТК:
   ```
   python3 .gigacode/skills/autotest-plan/scripts/tc_check.py <ключ>
   ```
   Правила оценки и что значит каждая находка - `references/tc-rules.md`.
3. `СТАТУС: FAIL` -> покажи человеку все строки `НАХОДКА ... БЛОКИРУЕТ` и рекомендации по
   `references/tc-rules.md` (колонка «Как исправить ТК»), план не строй, закончи. Просили
   только оценку - покажи итог по шаблону и закончи. Находки TC-14 и TC-15 (тэги ТК) не блокируют:
   покажи их в строке «Тэги ТК» ответа с рекомендацией из `references/tc-rules.md` и иди дальше.
4. Черновик плана:
   ```
   python3 .gigacode/skills/autotest-plan/scripts/tc_plan.py build <ключ>
   ```
   Строка `АРХИТЕКТУРА: не выбрана` -> шаг 1в. Строка `АРТЕФАКТЫ: разбор агентом не закончен` -> шаг 1б.
   Строка `ОКРУЖЕНИЕ: нет в сборке: ...` - в проекте нет модуля фрейма под технологию ТК (раздел 8
   плана). В этом скилле не подключай и человека не проси: перед генерацией оркестратор сам
   запустит `env-check` (ДЕЙСТВИЕ `env-setup <ключ>`), тот подключит модули, драйвер, сервисы и
   подключения по документации. В ответе - строка «Окружение под ТК» по шаблону.
5. Строка `ПРОВЕРИТЬ:` называет шаги с уверенностью LOW или UNKNOWN. Открой
   `references/classify.md` и исправь в `design.md` только эти строки раздела 2 (тип, группа,
   технология, метка, G) и, если шаг сменил группу, - строку G в разделе 3. Причину пиши в
   колонку «Основание»: `выбрано по <маркер>`. Остальные строки не трогай.
6. Шапка плана: `package` равен `-` (нет ENV.json или пакета) -> руками шапку не правь, запусти
   `python3 .gigacode/skills/autotest-plan/scripts/tc_plan.py package <ключ>` - он печатает
   кандидатов и строку `ДАЛЬШЕ` с командой: выполни её (она пишет `package`, `test_file` и пути
   раздела 11). `КАНДИДАТОВ НЕТ` -> спроси человека пакет одной строкой, ответ - в ту же команду.
   - нельзя: `build --force` ради пакета, правка `test_file` руками -> нужно: `tc_plan.py package`.
   Константы с источником
   `UNKNOWN` - выбери источник по `references/classify.md`, раздел «Константы».
7. Проверка плана:
   ```
   python3 .gigacode/skills/autotest-plan/scripts/tc_plan.py validate <ключ>
   ```
   Каждую строку `ПРОБЛЕМА` исправь в `design.md` и запусти снова. Строки про разделы 11-14
   (файлы, методы шагов, проверки, настройки) и клетки `ЗАПОЛНИТЬ` - заполни по
   `references/design-rules.md`, прочитай его целиком перед первой правкой. После 3 запусков с
   проблемами - покажи их человеку и закончи.
8. Подтверждение плана. Строка `ПОДТВЕРЖДЕНИЕ: нужно` -> покажи человеку разделы 11-16
   `design.md` как есть (11-14 - таблицы, 15 - привязка шагов ТК к коду, 16 - планируемые изменения
   по файлам) и спроси одной строкой «План верен? да / номер строки и как
   исправить». Это обязательная остановка, даже если человек просил «без остановок»: код пишется
   только по подтверждённому плану.
   - «да» -> `python3 .gigacode/skills/autotest-plan/scripts/tc_plan.py approve <ключ>`, потом итог по шаблону;
   - правки -> исправь названные строки, снова шаг 7 и этот шаг. Правка в разделе 15 или 16 ->
     исправь строку раздела 11-14, из которой она взята: 15-16 пишет validate, руками их не правь.
   - нельзя: подтвердить план самому, пропустить вопрос -> нужно: `approve` только после «да» человека.

## Контракт «вход -> выход»

Вход: путь к артефакту (файл ТК, Allure, лог, код автотеста) или ключ ТК в Zephyr; необязательно - ключ, тест-метод, имя теста.

Ключ без файла -> `zephyr.json` (или `zephyr.md`) - ответ `zephyr_get_testcase` без правок.

Выход в `openspec/changes/<имя>/outputs/`:
- `TC.md` - тест-кейс в едином виде (пишет tc_convert.py; sid, токены, пароли - `***`);
- `ARTIFACTS.md` - опись запросов и SQL из артефактов, связи шагов, служебные шаги, значения из
  выборки (пишет artifacts.py; `ARTIFACTS-REVIEW.md` - ответ агента pvatf-artifacts), тела - `artifacts/`;
- `TC-CHECK.md` - оценка ТК (пишет tc_check.py);
- `design.md` - план, `plan_status: planned`, `approved: yes` после «да» человека (пишет tc_plan.py, ты правишь
  только строки из шагов 5-7); разделы 11-14 - файлы, методы шагов, проверки, настройки: по ним пишется
  код, `at_tools check` сверяет код с ними; разделы 15-16 - привязка шагов ТК к коду и планируемые
  изменения ([ADDED] / [MODIFIED], сигнатуры, параметры, проверки, аналог), пишет validate;
  раздел 9 - запросы из артефактов по шагам, раздел 10 - значения из выборки (в тесте - переменные);
  раздел 8 «Окружение под ТК» - технологии ТК (EXPLICIT - названа в шаге или импорте, IMPLIED - следует
  из смысла шага, RECOMMENDED - базовая обвязка) и есть ли их модуль в сборке.

Ответ в чате строго по шаблону:
```
Тест-кейс: <ключ> · <название> · шагов <n>
Источник: <tms | allure | log | code> · артефакты: <запросов n, SQL n, связано шагов n | нет>
Архитектура: <steps | flow> (<ответ человека | код проекта>)
Проверка ТК: <PASS | WARNING | FAIL> · средняя оценка <n> · блокирующих находок <n>
Тэги ТК: <находки TC-14, TC-15 и что добавить; нет - «в порядке»>
План: <planned | не сошёлся> · шагов генерации <n> · технологии: <группы через запятую> · констант <n>
Тест-класс: <test_file из шапки>
Окружение под ТК: <нет в сборке: метки из строки ОКРУЖЕНИЕ - настроит env-check перед генерацией, без участия человека; иначе «в порядке»>
Исправлено вручную: <шаг - что - основание; нет - «нет»>
Дальше: «Напишите: /orchestrator продолжи генерацию <ключ>»
```

## Обработка ошибок

| Что случилось | Что делаешь |
|---------------|-------------|
| Скрипт скилла без компиляции и без MCP-вызова не закончил работу за 120 секунд | Прерви вызов, покажи вывод дословно, дальше не иди. Повторно не запускай |
| tc_convert.py: `ФОРМАТ НЕ РАСПОЗНАН` / `ШАГОВ НЕТ` | Покажи строку дословно, попроси ТК в формате `references/tc-rules.md`, раздел «Формат ТК». Дальше не иди |
| tc_convert.py по логу или коду: `ШАГОВ НЕТ` | Покажи человеку строки `ИСКАЛ` и `ПОХОЖЕ НА ЗАПРОС` дословно и спроси одной строкой: «Лог в другом формате. Дать Allure-результат этого теста или собрать ТК в markdown по этим строкам?». Ответ «собери» -> напиши `tc-<ключ>.md` по формату `references/tc-rules.md` только из строк лога (значения sid и токенов - `***`), покажи человеку, после «да» - `tc_convert.py tc-<ключ>.md` |
| artifacts.py merge: `ОШИБКА` после 2 кругов | Покажи строки `ОШИБКА` человеку и закончи |
| tc_convert.py: `ФАЙЛ НЕ ЧИТАЕТСЯ` | Покажи строку дословно, попроси путь к файлу ТК от корня проекта. Дальше не иди |
| Инструмента `zephyr_get_testcase` нет среди инструментов | Скажи: «Jira MCP не подключён: нет инструмента zephyr_get_testcase. Подключите Jira MCP или дайте путь к файлу ТК (md, xml или json)» и закончи |
| `zephyr_get_testcase`: таймаут 120 секунд или ошибка | Повтори 1 раз. Снова -> покажи ошибку дословно, попроси путь к файлу ТК (md, xml или json) и закончи |
| `zephyr_get_testcase`: ТК не найден или ответ пустой | Покажи ответ дословно, попроси проверить ключ или дать путь к файлу ТК и закончи. Файл `zephyr.*` не пиши |
| tc_plan.py build: `ПЛАН УЖЕ ЕСТЬ` | План уже утверждён - не перестраивай. Человек прямо просит перестроить -> `--force` |
| Код выхода 2 у любого скрипта | Покажи вывод, проверь, что запускаешь из корня проекта, запусти снова. Снова 2 - остановись |
| Шаг нельзя отнести ни к одной группе по `classify.md` | Группа `other`, технология `ValueService`, в «Решения и блокеры» - строка `шаг <n>: группа не определена, проверить человеку` |

- [ ] `РАЗБОР АГЕНТОМ: нужен` -> агент pvatf-artifacts отработал, `artifacts.py merge` вернул 0.

- [ ] При FAIL план не строился.
- [ ] Источник log или code -> шаги показаны человеку и подтверждены до tc_check.py.

- [ ] В `design.md` вручную изменены только строки из `ПРОВЕРИТЬ`, шапка, константы `UNKNOWN` и клетки `ЗАПОЛНИТЬ` разделов 11-14.
- [ ] Последний `tc_plan.py validate` вывел `ИТОГ: план сошёлся`.
- [ ] Разделы 11-16 показаны человеку, `tc_plan.py approve` - только после его «да».
- [ ] Ответ в чате - по шаблону.
