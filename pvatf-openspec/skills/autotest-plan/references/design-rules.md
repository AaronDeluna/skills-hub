# Разделы 11-16 плана: что, куда и как

План (`design.md`) - договор. По нему пишется код, и `at_tools check` сверяет код с ним: файл,
метод или проверка не из плана - находка. Поэтому всё решается здесь, до кода, и человек это
подтверждает. Черновик строит `tc_plan.py build`. Клетки `ЗАПОЛНИТЬ` дописываешь ты по правилам
ниже. Остальные клетки не трогаешь. `validate` не пропускает план, пока в разделах 11-14 есть
`ЗАПОЛНИТЬ`.

Пакеты - правило 13 `autotest-rules.md`: тест - `<корень>.tests`, классы шагов - `<корень>.steps`,
данные - `<корень>.data`, конфигурация - `<корень>.config` (`.config.services` - настройки
сервисов). `<корень>` - пакет тестов из шапки без `.tests`.

## 11. Файлы

Одна строка - один файл, который появится или изменится. Действие:

| Действие | Когда |
|----------|-------|
| `создать` | файла нет, его пишет генерация |
| `дополнить` | класс проекта из раздела 6 подходит по технологии и предметной области - в него добавляются методы |
| `не трогать` | файл нужен тесту, но не меняется |
| `скрипт` | файл пишет скрипт набора (`perfeccionista.properties` - `env_props.py ensure`) |
| `env-check` | файл настраивает env-check (класс конфигурации окружения, регистрация сервисов) |

- Строка `<путь>/ЗАПОЛНИТЬ.java` -> имя нового класса шагов по предметной области шага,
  латиницей, без транслита: `JsonResponseFlow` (flow), `PaymentSteps` (steps).
  - нельзя: `Pvatf3783Steps`, `OplataSteps`, класс в `<корень>.tests.config` -> нужно:
    `src/test/java/ru/sber/qa/steps/JsonResponseFlow.java`.
- Строка «дополнить ... или ЗАПОЛНИТЬ» -> класс из раздела 6 подходит - удали «или ЗАПОЛНИТЬ...»;
  не подходит - замени путь на новый класс, действие `создать`.
- Файлов сверх таблицы не добавляй, если для них нет шага ТК. Конфигурация «на всякий случай»,
  второй класс настроек, свой интерфейс конфигурации - нельзя.

## 12. Методы шагов

Одна строка - один public-метод класса шагов. Класс - имя файла из раздела 11 без `.java`.

- Метод - имя Java с маленькой буквы, по действию: `postJsonResponse`, `selectAccount`.
- Шаги ТК - все шаги G, которые делает этот метод. Один метод может делать запрос и проверки
  его ответа (шаги 1, 2, 3).
- Параметры - через `;`: `<имя> <Тип> - откуда`. Откуда: `тест` (значение из тест-класса, в
  том числе ожидаемое значение ТК), `настройки <ключ>` (раздел 14), `шаг <n>` (переменная шага),
  `файл <путь>` (тело запроса из раздела 11). Параметров нет - `нет`.
  - нельзя: `host String` без источника, ожидаемое значение константой внутри класса шагов ->
    нужно: `host String - настройки test.sbermock.url; expectedCode BigDecimal - тест`.

## 13. Проверки

Одна строка - одна проверка в коде. Черновик даёт строку на каждый шаг с ожидаемым результатом;
шаг проверяет 3 поля -> 3 строки с одним номером шага.

| Колонка | Что писать |
|---------|-----------|
| Объект | что проверяется: `ответ шага 1`, `строка выборки шага 4` |
| Поле | путь поля как в ответе: `code`, `result.locked`, `rqUid`; для кода HTTP - `status` |
| Как | одно из: `равно`, `не равно`, `содержит`, `ключ есть`, `ключа нет`, `не пусто`, `пусто`, `статус`, `больше`, `меньше`, `по шаблону`, `проверено в шаге <n>` |
| Ожидаемое | константа раздела 4 (`EXPECTED_RESULT_CODE`), переменная раздела 5 или 10, значение в кавычках (`"*/*"`), `-` для «ключ есть / ключа нет / не пусто / пусто» |

- Одно поле одного объекта - одна строка. Шаг ТК проверяет то же поле ещё раз -> `Как` =
  `проверено в шаге <n>`, кода нет.
  - нельзя: `code` `равно` `EXPECTED_RESULT_CODE` и `code` `не равно` `"0"` -> нужно: одна строка
    `равно`, вторая - `проверено в шаге 1`.
- Ожидаемое значение ТК - константа раздела 4 в тест-классе, в метод шага приходит параметром.

## 14. Настройки

Одна строка - один ключ своего файла настроек (адрес, логин - то, что не пишется в код).

- Ключ - латиницей через точку: `test.sbermock.url`. Не `perfeccionista.*`, не `session.*`.
- Файл - файл из раздела 11 (`src/test/resources/test.properties`), не `perfeccionista.properties`.
- Кто читает - класс и способ из проекта или конспекта: `TestConfig (owner)`.
- sid, токены, пароли - не в настройки: sid - из шага сессии теста.

## 15-16. Привязка и планируемые изменения

Пишет `validate`, когда план сошёлся. Ты их не пишешь и не правишь.

- 15 «Привязка шагов ТК к коду» - строка на шаг ТК: G, `Класс.метод(Тип имя, ...)`, запрос, проверки.
- 16 «Планируемые изменения» - блок на файл: `[ADDED]` (создать) или `[MODIFIED]` (дополнить), путь,
  пакет, методы с сигнатурой, источник каждого параметра, проверки метода, аналог из проекта, G;
  для тест-класса - базовый класс, `@TmsLink`, константы, порядок вызовов; в конце порядок G.
- Видишь в 15-16 ошибку -> исправь строку 11-14, из которой она взята, и снова `validate`.
  - нельзя: поправить сигнатуру прямо в разделе 16 -> нужно: исправить «Параметры» в разделе 12.
- Сигнатура без параметров при параметрах в шаге (`list()`, а шаг шлёт запрос на адрес из
  настроек) -> в разделе 12 не хватает параметра: допиши `host String - настройки <ключ>`.
