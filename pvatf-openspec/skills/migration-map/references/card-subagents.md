# Сабагенты Этапа 5: разбор технологии, составитель карточки, проверяющий карточки

Часть скилла `migration-map`. Открывай на Этапе 5, когда строишь карточку юнита `tech`.

Зачем: к Этапу 5 твой контекст забит инвентаризацией, конспектом и матрицей. Карточку,
написанную «по памяти» из такого контекста, легко написать с пропусками. Поэтому карточка
строится из ФАЙЛОВ, а не из памяти, и каждый кусок делает сабагент с чистым контекстом:

```
5.1 разбор технологии   -> inventory/analysis-<tech>.md   (скрипт analyze.py)
5.2 заготовка + составитель -> units/M-<nnn>.md           (скрипт card.py new, потом сабагент заполняет)
5.3 card.py           -> механические находки            (скрипт)
5.4 проверяющий         -> смысловые находки               (сабагент сверяет карточку с разбором)
5.5 исправление         -> составитель правит по находкам   (не больше 2 кругов)
```

Технологии идут по одной, в порядке паспорта. Для каждой - весь цикл 5.1-5.5, потом
следующая. 5.1 и 5.3 - скрипты, 5.2 (составитель) и 5.4 (проверяющий) - ОБЯЗАТЕЛЬНО через
своего сабагента. Только
если вызов сабагента вернул ошибку (не «долго» и не «проще самому») -> покажи ошибку в чате, запиши в журнал карты `сабагент не запустился: <ошибка>` - делаешь этот шаг сам, по тем же промптам и шаблонам.

## 5.1 Разбор технологии - скриптом

Разбор - это факты о коде, на которых стоит вся карточка: кто обращается к технологии, как,
какие действия делает, сколько в нём проверок какого вида. Всё это считает скрипт: он сам
читает файлы проекта и пишет `inventory/analysis-<tech>.md` по шаблону. Файлы проекта для
разбора ты не открываешь и сабагента разбора не запускаешь.

Что подставить:
- `--old` - старая библиотека технологии: пакеты из строк `G` карты (`io\.restassured`);
- `--core` - классы старого ядра технологии: имена из строк `L` карты, через `|`;
- `--frame` - обращения к сервису фрейма в обход шагов (имена из конспекта
  `doc-notes/<tech>.md`, как фрейм получает клиент технологии); нет - не передавай;
- `--steps` - классы шагов этой технологии из архитектурного плана (их не считать потребителями);
- `--other` - импорты других технологий `migrate` из паспорта: `метка=regex;метка=regex`;
- в конце - каталоги исходников из паспорта.

Команда (таймаут 120 секунд):
```
python3 .gigacode/skills/migration-map/scripts/analyze.py <tech> --old "<regex>" --core "<Класс|Класс>" --frame "<regex>" --steps "<Класс|Класс>" --other "<метка=regex;...>" <каталоги>
```
Пример для `db`:
```
python3 .gigacode/skills/migration-map/scripts/analyze.py db --old "java\.sql|org\.postgresql" --core "DbConnectionPool|BaseDao|PaymentDao" --steps "DbSteps" --other "rest=io\.restassured;kafka=org\.apache\.kafka" src/test/java
```
- `ОК: ... · потребителей <n> ...` -> разбор записан, дальше 5.2. Файл разбора целиком в
  чат не читаешь: составитель и проверяющий читают его сами.
- `НИЧЕГО: ...` (код 1) -> `--old` / `--core` не совпали с кодом: сверь их со строками `G` и `L`
  и запусти снова. Второй раз `НИЧЕГО` -> запись в журнал карты, технология без юнита `tech`,
  вопрос во «Входящие».
- В разделе «Не удалось» есть классы старого ядра, которых не нашлось -> проверь имя в строке
  `L` (`find . -name "<Класс>.java"`), исправь `--core`, запусти снова.

Потребитель с другой технологией `migrate`, которая идёт позже по порядку (колонка «Другие
технологии»), -> файл откладывается (Этап 5, «Файлы на несколько технологий»): в разборе
остаётся, в карточку составитель его не возьмёт.

## 5.2 Сабагент «составитель карточки»

Пишет ОДИН файл - карточку юнита `tech` - строго по шаблону и только из переданных
файлов. Это единственный сабагент карты, которому можно писать файл. Код проекта он не
трогает.

**Сначала заготовка - скриптом** (таймаут 60 секунд):
```
python3 .gigacode/skills/migration-map/scripts/card.py new M-<nnn> <tech> --depends <M-nnn,M-nnn> --core-mode <new|in-place>
```
Скрипт пишет `units/M-<nnn>.md`: шапку, `covers` (строки `G` и `L` технологии), «Данные
подключения» из `CONNECTIONS.md`, команды поиска и таблицу потребителей из разбора, подшаг
`S-01`. `ОК: заготовка ...` -> запускай составителя: он заполняет оставшиеся `<...>` и пишет
подшаги. `ОШИБКА: ...` -> сделай то, что в ней сказано (нет разбора - 5.1; нет таблицы
«Перенос в фрейм» - Этап 3 для этой технологии), и запусти снова.

Что подставить:
- номер юнита, `depends_on`, `core_mode`, стиль шагов, `scope` - из карты;
- пути к файлам-источникам (он читает их сам).

**Промпт (копируй дословно, подставь `<...>`):**
```
Ты пишешь карточку юнита миграции одной технологии на фрейм PVATF. Меняешь ОДИН файл:
<абсолютный путь>/openspec/changes/<имя>/outputs/units/M-<nnn>.md. В нём уже лежит заготовка:
шапка, «Данные подключения», команды поиска, таблица потребителей, подшаг S-01 - их не
переписывай, только заполни в них поля `<...>`. Больше ничего не создавай и
не меняй, код проекта не трогай, сборку не запускай. Всё, что пишешь, бери только из
файлов ниже - по памяти ничего не добавляй. Имена классов и методов фрейма - только из
конспекта.

Шаблон карточки и правила «Как писать подшаг» (прочитай целиком и выполни каждое):
<путь к скиллу>/references/tech-unit-template.md

Источники (прочитай):
- разбор технологии: <путь>/openspec/changes/<имя>/outputs/inventory/analysis-<tech>.md
- целевая картина: блок `T-<tech>` в <путь>/openspec/changes/<имя>/design.md (раздел 2), строки `G` и `L` с технологией <tech>
- архитектурный план: строки технологии <tech> и разделы 1-2 в <путь>/openspec/changes/<имя>/outputs/ARCHITECTURE.md
- конспект: <путь>/openspec/pvatf/migration/doc-notes/<tech>.md и doc-notes/common.md
- подключения: раздел <tech> в <путь>/openspec/changes/<имя>/outputs/CONNECTIONS.md
- отложенные в другую технологию файлы: <список; нет - "-">

Параметры юнита: id M-<nnn>; depends_on [<...>]; core_mode <new|in-place>; стиль шагов <steps|flow>; scope <full|core>.

Как строить:
1. Таблица «Потребители» карточки - из «Потребители» разбора, кроме отложенных файлов.
2. Подшаги по порядку видов из шаблона. `core`: первым - базовый слой технологии, если он
   есть в плане; методы классов шагов - действия из колонки «Действия» разбора, ни одного
   лишнего. `usage`: снизу вверх по колонке «Уровень», тесты последними; лимит - 3 файла и
   600 строк; каждый потребитель - ровно в одном `usage`.
3. В каждом `usage` - таблица «Критерии по файлам»: «Было» - числа из разбора по этому
   файлу (ассертов, разборов в объект, обращений к старому, DTO), «Должно стать» - с
   именами классов шагов и записями `D-<tech>-n` для каждого вида проверок файла.
4. `cleanup` - каждая строка `L` технологии; `review` - все файлы `core` и `usage`.
5. «Правила подшага» - строго по `references/substep-rules.md`: строка вида подшага плюс добавки, других номеров нет.

Верни ТОЛЬКО:
- Файл: <путь> - записан / не записан: <причина>
- Подшагов: <n> (разбор 1, env <n>, core <n>, usage <n>, cleanup <n>, review <n>)
- Полей `<...>` из шаблона осталось: <n; все заполнены - 0>
- Потребителей в разборе: <n>, в подшагах usage: <n>, отложено: <n>
- Чего не хватило в источниках: <что и где; нет - "нет">
```

Сабагент не умеет писать файлы -> добавь в конец промпта «Файл не пиши, верни текст
карточки целиком», и сохрани ответ в файл сам, слово в слово, ничего не меняя.

## 5.3 Механическая проверка - скрипт

```
python3 .gigacode/skills/migration-map/scripts/card.py M-<nnn>
```

Скрипт проверяет: незаполненные поля шаблона `<...>`, файлы «нет в проекте» (кроме тех,
что создаёт юнит выше или подшаг выше), поля каждого подшага, пустые слова, лимиты файлов, «Правила подшага»,
команду `MR-48` в чекпоинтах `usage`, покрытие потребителей (каждый ровно в одном
`usage`), «Критерии по файлам» в каждом `usage`, строки `L` технологии, ссылки
`D-<tech>-n` на существующие записи конспекта, «создал - подключи», число строк файлов.
`находок 0` -> к 5.4. Есть находки -> копишь их для 5.5.

## 5.4 Сабагент «проверяющий карточки»

Сверяет смысл: то, что скрипт не видит.

**Промпт (копируй дословно, подставь `<...>`):**
```
Ты проверяешь карточку юнита миграции на фрейм PVATF. Только читаешь и находишь
нарушения: ничего не меняй. Свои правила не придумывай, вкусовые замечания не пиши.

Карточка: <путь>/openspec/changes/<имя>/outputs/units/M-<nnn>.md
Разбор технологии: <путь>/openspec/changes/<имя>/outputs/inventory/analysis-<tech>.md
Шаблон и правила «Как писать подшаг»: <путь к скиллу>/references/tech-unit-template.md
Конспект: <путь>/openspec/pvatf/migration/doc-notes/<tech>.md

Проверь по пунктам:
К1. Каждое действие из колонки «Действия» разбора есть методом в подшагах `core`; в `core`
    нет методов, которых нет в разборе.
К2. В «Критериях по файлам» каждого `usage` числа «Было» совпадают с разбором по этому файлу.
К3. Для каждого вида проверок файла из разбора в «Должно стать» названа запись `D-<tech>-n`,
    и в конспекте эта запись про такой вид проверки.
К4. «Что сделать» каждого подшага - действия с именами файлов, классов, методов; по ним
    можно работать, ничего не додумывая.
К5. «Итоговый результат» - по строке на каждый файл подшага, проверяемый факт.
К6. «Чекпоинт» проверяет именно «Итоговый результат» этого подшага.
К7. `usage` идут снизу вверх по уровням из разбора, тесты последними.
К8. DTO ответа из разбора удаляются: метод возвращает валидируемый объект, вызывающие
    переходят на `.should(...)`.
К9. Нет шагов, которые правят или повторяют старое ядро («перевести RestHelper на PVATF»),
    делегатов, фасадов, вложенных классов, вспомогательных методов в тест-классах.

Верни РОВНО так:

## Находки
| Пункт | Подшаг | Что не так (1 строка) | Как исправить (1 строка) |
|-------|--------|-----------------------|--------------------------|
| К<n> | S-<nn> | <...> | <...> |

## Без находок
- <пункты без находок через запятую>
```

## 5.5 Исправление

1. Собери находки скрипта (5.3) и проверяющего (5.4) в один список.
2. Находок нет -> карточка принята, дальше - строка в разделе 4 карты (Этап 5, «Для
   каждого юнита»).
3. Находки есть -> запусти составителя ещё раз: тот же промпт плюс в конце «Карточка уже
   есть. Исправь в ней ТОЛЬКО эти находки, остальное не трогай:» и список. Потом снова 5.3
   и 5.4.
4. Больше двух кругов исправления не бывает. После второго круга находки остались ->
   исправь их сам (обычно это 1-2 строки), запусти 5.3 ещё раз и запиши в журнал карты:
   `M-<nnn>: карточка дописана вручную, находки: <коротко>`.
